# 同组织连续付款：前台耗时定位

2026-10-12，本机 Windows / AMD Ryzen AI 9 HX 370 / Go 1.27.1。

## 结论

当前测试的主要成本是成员提交状态和收款钱包保存收款的持久化路径。来源证书缓存确实减少了校验工作，但只省下全路径中的一小段，尚未形成稳定的整笔付款 p50 改善。

## 测量口径

- 六种配置，各 100 笔依赖前一笔输出的连续付款，三轮轮换配置顺序，共 1,800 笔，全部成功。
- 各配置使用完全相同的预生成、预签名交易。四个成员使用独立临时 bbolt 数据库和真实 localhost HTTP。
- 计时起点为 CollectDirect 调用前，终点为 ReceiveDirect 验证证书并保存收款后。构造/签署交易、后台 INSTALL、公开执行不在此区间。
- 每笔计时结束后完成四成员 INSTALL，再开始下一笔，保证缓存确实热起来。此测试不包含后台 INSTALL 与下一笔前台同时竞争的情况。
- 成员分段取实际第三张被网关选中的票所对应的成员；不把四个并行成员的耗时相加。
- NoSync 只用于新建临时实验库作成本对照，没有修改生产设置，不能视为保持崩溃恢复保证的优化。
- 原始数据：`profiles-monotonic.json`；统计程序：`analyze.py`；结果：`summary.json`。`profiles.json` 是早期试测，不用于本报告。
- Windows 时间源有明显计时量化。短阶段使用多次测量的平均值，以及独立 100 次循环的摊销耗时核对，不解释短阶段 p50=0 为没有成本。

## 主要时间花在哪里

下表为全持久化基线 300 笔的平均值；总计平均 7.950 ms，p50 7.203 ms，p95 9.891 ms。

| 环节 | 平均耗时 |
|---|---:|
| 第三票成员数据库 Update | 3.563 ms |
| 收款钱包数据库 Update | 1.535 ms |
| 成员来源证书处理（含摘要/映射建立） | 0.422 ms |
| 成员解码、交易/承诺、输出检查 | 0.757 ms |
| 其余：钱包验收、网关验票、HTTP/调度等 | 约 1.673 ms |

两处数据库 Update 合计约 5.10 ms，占总平均耗时约 64%。成员 Update 中，等待进入回调约 0.031 ms，业务回调约 0.397 ms，回调结束至提交返回约 3.135 ms。钱包的回调后阶段约 1.473 ms。当前顺序负载下，数据库提交返回是大头，进入业务回调前的等待不是主要成本。

“回调后阶段”包含应用变更、bbolt 提交、写入与同步，以及这段时间内的调度。没有单独测量 FlushFileBuffers 系统调用，不能把整段都称为 fsync 时间。HTTP/调度等剩余成本也不能称为纯网络 RTT。

最慢的 5%（15 笔）平均 20.30 ms，其中第三票成员 Update 13.85 ms、钱包 Update 1.66 ms。最大离群点为 154.57 ms，其中 150.41 ms 位于成员回调后的提交段。慢请求也指向该阶段；这仍不能确定设备或操作系统内部停顿原因。

## 少验签为什么没有明显变快

缓存组的来源证书处理平均约 0.05 ms，基线约 0.42 ms。这一小段确实变快了，差值约 0.37 ms，只相当于基线全路径的约 5%。独立循环测得一份完整来源证书的验证约 0.23–0.31 ms，也支持这个数量级。

先前热缓存实验中，每 100 笔、四成员有 396 次缓存命中：第 2–100 笔的来源证书已通过上笔 INSTALL 入缓存。400 次未命中来自各新证书首次安装。缓存没有失效；它节约的工作不在最大的耗时段。

四个成员并行验证，节省不能再乘以四作为付款延迟收益。数据库和调度的波动足以遮住这几个百分点的潜在收益。缓存组本轮合并 p50 7.594 ms，三轮分别为 8.219、7.569、6.910 ms；基线三轮为 7.052、7.297、7.350 ms。不能把这组结果解释为缓存必然变慢，也不能宣称稳定加速。

## 存储对照

| 配置 | 300 笔合并 p50 | 合并 p95 |
|---|---:|---:|
| 成员与钱包正常持久化 | 7.203 ms | 9.891 ms |
| 仅成员 NoSync | 6.531 ms | 8.521 ms |
| 仅钱包 NoSync | 6.428 ms | 8.501 ms |
| 成员和钱包均 NoSync | 4.529 ms | 6.216 ms |
| 正常持久化，关闭请求 trace | 7.137 ms | 9.542 ms |

这些对照支持“持久化路径是主要成本”的定位，但不能把 NoSync 的差值当成可直接交付的性能收益。两端同时变化存在交互，不要求两种单独对照的收益相加等于联合对照。基线一轮存在长尾，平均值高于通常的单笔水平，因此报告同时保留 p50、p95 和各轮原始数据。

## 下一步优先级

1. 优先检查成员提交的数据量、写放大、提交组织，以及收款钱包的保存路径，保持成员持久化完成后才返回签票的约束。
2. 按实际目标分别衡量“拿到可验证证书”与“收款已持久化”；不能通过偷偷更换计时终点声称优化成功。
3. 并发付款可研究批量提交；严格依赖前一笔的单条付款链不应凭空等待凑批，可能反而更慢。
4. 验签缓存可减少 CPU 工作；是否提高并发吞吐量要另测。本次测试不足以给出吞吐量结论。
5. 来源优先排序改变后台执行，本轮没有运行公开执行，不能用它解释此处前台延迟。

## 本轮代码影响

只增加可选诊断：两个 requesttrace 阶段标记、测试数据库工厂、独立 profiling 测试与统计脚本。未修改验签规则、持久化默认值、签票条件或付款协议。

验证：1,800 笔诊断付款成功；sameorglab、member、transport、gateway、protocol、wallet 六个包的测试通过。

## 与侧边栏 GPT 的讨论

已向用户指定的 GPT 对话发送方法、分段数据及存储对照，并要求复核并行耗时归因。GPT 认可：缓存确实减少校验工作，两处数据库提交是当前本机顺序付款主要成本，底层具体耗时仍不能直接等同于 fsync。

保留的提醒：热缓存来自计时区间外的 INSTALL，应区分前台收益和完整后台工作量；各组 p50 不能直接相加；并发批量提交不应直接套到单条依赖链。

纠正的泛化：GPT 提到的 WAL 不适用于这里的 bbolt；钱包落盘是当前测试终点，不能据此推导“协议上必须等待钱包落盘才能构造下一笔”。
