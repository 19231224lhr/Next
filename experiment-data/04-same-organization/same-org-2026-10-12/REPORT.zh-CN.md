# 同组织转账优化：Windows 本地受控对照

## 结论

三项原型均已实现并做对照，但没有证据支持全部默认开启。保留上一轮请求内验签去重；本轮跨请求缓存与编号传输保持关闭，来源优先排序保留为实验候选。

- A 在已预热条件下也没有稳定降低整笔付款耗时。它省掉一处前台重复验签，但存在序列化、缓存维护及后台预热成本。
- B 在已预热时减少认证请求体数据量 32.30%；未预热时先请求编号再补传完整证书，数据量增加 67.04%，请求次数从 400 增至 796。
- C 在本批队列回放中把缺失来源事件从 41 次降至 0，临时资金缺口峰值从 2,800 CAL 降至 0。CAL 容量峰值与释放轨迹没有改善。
- ABC 没有展示稳定的整体付款提速；不将局部计算节省称为系统加速。

## 对照结果

每组 100 笔连续付款、独立重复三次；表中延迟是三次运行各自单笔 p50 的中位数。请求数据是 100 笔付款发往四名成员的请求体总字节，不包含 HTTP 头、响应、INSTALL 或区块传播。

| 方案 | 已预热：单笔 p50 | 未预热：单笔 p50 | 已预热请求体字节 | 未预热请求体字节 |
|---|---:|---:|---:|---:|
| 基线 | 7.776 ms | 7.657 ms | 1,119,404 | 1,119,404 |
| A：复用证书验证 | 8.069 ms | 7.922 ms | 1,119,404 | 1,119,404 |
| B：只传证书编号 | 8.301 ms | 8.583 ms | 757,856 | 1,869,824 |
| C：后台来源优先 | 7.860 ms | 7.845 ms | 1,119,404 | 1,119,404 |
| A+B+C | 7.936 ms | 8.629 ms | 757,856 | 1,869,824 |

三次完整运行和逐笔延迟保存在 `results.json`，汇总在 `summary.json`。没有做统计显著性检验。C 不改前台路径，其前台耗时差异主要体现运行波动，不应归因于后台排序。

## 测量到底包含什么

- Windows/amd64，AMD Ryzen AI 9 HX 370，Go 1.27.1。
- 四个真实成员对象通过独立 localhost HTTP 服务接收请求；真实 Collector 收集三签；两个不同用户在同一组织内轮流付款。
- 成员与钱包使用正常持久化 store，没有打开不等待同步或内存钱包选项。付款计时包含认证请求、三签收集、收款钱包证书验证和保存；不包含构造签名请求、发送钱包保存、后台 INSTALL 或公共执行。
- 每笔传递 100 CAL，连续 100 笔；五组使用完全相同的已签名交易序列，三轮轮换方案运行顺序。
- 基线包含上一轮已经完成的“单次请求内去掉重复验签”，但没有跨请求复用或编号传输。
- warm：每笔付款后等待四个成员完成正常后台 INSTALL，再发下一笔。这是明确的已预热条件，不是假定真实连续发送必然命中。
- cold：先连续认证，最后统一 INSTALL，测真实的缓存未命中及自动补传。这里的缓存统计在整个阶段结束后读取；cold 的 CacheHits 包含后续 INSTALL 对已缓存来源的复用，不能解释为前台命中。
- `InstallMS` 单独记录预热工作的墙钟时间。缓存预热会增加一次完整证书验证，不能只看前台而忽略后台成本。
- 这不是四台远程机器的完整共识网络实验。没有模拟 WAN 带宽、丢包或远端延迟。

## C：额度回收的单独判读

认证完同一批 100 笔付款后，先按证书 fact 排序作为既有 outbox 键序的受控串行回放；C 对同一队列做来源优先排序。实际 Relay 有并发和分页，不能把这次串行回放的差值直接视为线上 Relay 加速。

回放使用真实委员会状态转换，再生成测试委员会签名的区块证明，由正式验证和成员跟随代码应用；未运行真实 CometBFT 共识网络。每处理一笔就跟随一次，观察条件一致。

| 指标 | 基线 | 来源优先 |
|---|---:|---:|
| CAL 成员预留峰值 | 10,000 | 10,000 |
| 每执行一步后的 CAL 预留均值 | 4,950 | 4,950 |
| 最终 CAL 预留 | 0 | 0 |
| 缺失来源事件 | 41 | 0 |
| 临时资金缺口峰值 | 2,800 | 0 |
| 最终临时资金缺口 | 0 | 0 |
| 最终 FUEL 已用/未返还额度 | 9,400 | 9,400 |

当前成员在确认自身签发付款公开执行后，就按已有规则释放 CAL。此次所有付款先认证再执行，因此峰值由批量积压决定；不能据此排除实时并发提交场景下的不同结果。来源顺序在本轮减少的是中间缺口与费用预留等待，没有降低每张证书的担保要求，也没有减少最终费用消耗。

## 实现位置与默认状态

- `internal/member/direct_cache.go`：同配置、按完整证书内容寻址的缓存；最多 4096 个条目，另有 32 MiB 原始字节上限；本实验设置 256 条。淘汰与重启均安全退化为未命中。
- `protocol/direct_reference.go`、`internal/transport/direct.go`：编号请求携带完整原始交易与签名，引用包含完整证书及签名的摘要。仅在明确缓存未命中或旧节点不支持时补传，不对认证失败盲目重试。
- `internal/gateway/direct_order.go`：有界待执行批次的来源优先排序；缺少来源不会阻塞独立提交。当前用于实验回放，尚未替换生产 Relay 的并发调度。
- 成员 `DirectCacheEntries=0`、客户端 `PreferDirectReferences=false` 为默认；未更改论文、担保上限、三签门槛、输入锁或公开执行语义。
- 测试入口：`internal/sameorglab/experiment_test.go`。
