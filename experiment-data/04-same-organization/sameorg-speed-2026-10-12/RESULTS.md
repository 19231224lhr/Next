# 本轮转账速度优化：实现与结果

2026-10-12，本地 Windows 11、Go 1.27.1，工作目录 `.e8-worktree`，分支 `fix/partial-approval-reclamation`。本轮是在已有证书直达收款人与内部资金池实现上继续优化。旧版基准取自本轮开工前完整代码快照 `.scratch/speed-baseline-20261012`，包含此前未提交的功能，因此不能用 Git HEAD 代替该基准。

## 已落实的改动

1. **慢收款人不再拖住整批投递。** 原先四条消息一起发送，必须等整批结束才处理下一批。现在任一位置空闲就继续发送，同时限制同一收款人只占一个位置。失败任务有退避和轮转，避免占满通道或挡住同一钱包的后续有效消息。
2. **组内资金池少做无用工作。** 正常付款先申请签票，不再预先向四个成员查询历史凭证；只有失败或慢请求才恢复查询。成员已经持久保存并验证过的完全相同父凭证可直接复用，修改过或陌生的凭证仍完整验证。
3. **将两件独立的保存工作并行。** 收款钱包核验、保存收据的同时，成员保存完整付款凭证。钱包收据和至少两个不同成员的保存都成功后，才允许续付或退出。钱包重启会重新确认成员副本。没有新增每笔付款的就绪标记落盘；获得足够确认后及时取消剩余慢请求。
4. **增加可选的收款端收票路径。** 付款人的签名请求可以直接交给收款端，由收款端收集原有的三名成员签票，保存完整付款材料和公开提交队列，再保存钱包收据。原来的网关直接投递路径仍可使用。该路由优化也可能用于跨组，不能全部算作同组特有收益。

## 组内资金池的实测

最终数据：`comparison-20261012-234431/summary.json`。每种方案运行 5 轮，每轮连续 200 笔，轮间交替执行顺序；每次使用新的同步 Bolt 存储。表中取五轮各自 p50、p95 的中位数。计时到收款钱包保存收据及两个成员保存完整凭证完成，三名用户轮流付款。退出和后续普通付款也在每轮验证通过。

| 方案 | 单笔 p50 | 单笔 p95 |
|---|---:|---:|
| 本轮之前的资金池实现 | 7.6076 ms | 10.6060 ms |
| 只减少恢复查询和重复验证 | 7.5764 ms | 10.5290 ms |
| 最终实现，保留串行保存作对照 | 7.7368 ms | 10.8842 ms |
| 最终实现，并行保存 | **6.7334 ms** | **9.6511 ms** |

最终版相对旧版：p50 降低 **11.49%**，p95 降低 **9.00%**。同一最终实现中，并行相对串行的 p50 降低 **12.97%**。少查询、少验签单独测只有约 0.41% 差异，不能据此声称稳定提速；本轮主要可见收益来自重叠保存的等待。

这些是本机四个真实成员 HTTP 服务及同步持久化的实验结果。实验驱动使用测试密钥生成公开执行证明，没有部署真实验证者共识网络；此处也没有测量 Pool 相对普通 Direct 的优势。五轮保留全部结果，其中第一轮最终版 p50 略慢于旧版，不将汇总改善说成每轮都更快。`comparison-20261012-234134` 为修复剩余 RPC 取消前的初测，不能替代最终数据。

## 收款端直接收票的实测

最终数据：`recipient-verified-raw.txt`、`recipient-verified-raw.summary.json`。3 轮，每种场景每个方案 50 笔；采用实际网关 HTTP 付款处理器、持久投递队列和收款处理器作为旧路径。每条收款记录校验对应本次计时的交易 ID。下表仍为各轮 p50 的中位数。

| 条件 | 现有网关直接投递 | 收款端直接收票 | 解释 |
|---|---:|---:|---|
| 本地，没有额外交付延迟 | 11.9759 ms | 11.9600 ms | 基本没有稳定提速 |
| 网关到收款钱包这一段额外等待 20 ms | 34.4194 ms | 11.3522 ms | 耗时降低约 **67.02%** |

第二行是人为设置的交付等待，不是真实广域网测试，也不是所有链路都增加了 20 ms。它说明：把收票位置移到收款端，能够避开原路径的额外交付等待。不能据此宣传所有转账都快 67%。本机各轮波动较大，全部原始样本均保留。

两种方案的共同终点是收款钱包持久接受，并在本地保留完整付款材料。原路径先持久保存投递材料，公开提交队列在后台保存；收款端先同步保存公开提交材料，再保存钱包收据。因此这是实际实现比较，并非隔离单次 RPC 或完全相同 fsync 顺序的微基准。两臂用新的实验实例，资金、用户和工作负载相同，具体父凭证签票集合可能不同。

## 队列阻塞与正确性

故意让一个收款钱包一直不响应，同时给其他钱包投递：旧版在 1 秒测试截止前只完成 2 条正常消息；新版约 **3.95 ms 完成其他 7 条**，被阻塞的钱包仍未恢复。这证明批次阻塞得到消除，不是一般单笔转账延迟的百分比测试。同一钱包并行数限制为 1，未宣称其高并发吞吐量提高。

验证包括：整仓测试、命令编译、六个修改涉及包的 race 检查；错误签名、混合内容签票、重复签票、错误收款人、保存失败、旧收据覆盖、同交易不同完整凭证、重启确认和取消剩余请求。收款端还验证了真实关闭/重开存储后，新 relay 不靠内存通知即可提交原有完整交易。

最终代码审查见 `final-review.md`，无未解决的实质问题。侧边栏 GPT 的建议已用于检查恢复与结果解释；代码与测试是结论依据。

## 使用与复现

- 资金池继续通过 `EnableInternalPools` 显式启用；`poolctl -receive` 已接入保存与副本确认，发送命令重启后也会确认父收据。普通资金池收款调用 `wallet.CompletePool`；证书收集接口 `CollectPoolCertificate` 本身不代表收款完成。
- 收款端路径通过 gateway 的 `-collect-at-recipient` 开关启用，配置本地 `RecipientKey` 文件，可选 `RecipientOwner` 必须与密钥匹配。沿用现有组织、网络和成员配置，钱包存入 `recipient-wallet.db`。`POST /v3/recipient/collect` 接收签名付款请求。
- 同一收款钱包的 `POST /v3/recipient/prepare` 保存已由持有人签名的续付请求；204 只表示本地预约成功，调用方仍需将相同请求交给下一收款端或常规网关。此轮没有增加钱包 UI 或自动路由发现。
- `python compare_pool.py --ablation` 运行四种资金池二进制；最终二进制通过 `go build -o docs/experiments/sameorg-speed-2026-10-12/pool-lab-after.exe ./cmd/pool-lab` 生成。旧版和 fastpath 二进制已保留，散列见 `manifest.json`。
- 设置 `UTXO_RECIPIENT_EXPERIMENT=1` 后运行 `go test ./cmd/gateway -run '^TestRecipientCollectionExperiment$' -count=1 -v`；`summarize_recipient.py` 汇总日志。
