## Earlier findings (resolved by re-review)

1. **P1 — The offered rate is gated by public closure.** `run_next.py:179-184` starts `bench-v4` with `--concurrency 1` and its default `--max-pending 0`. In `cmd/payctl/direct_dispatch.go:19-41`, that mode keeps a worker until the entire task returns; `cmd/payctl/direct_bench.go:232-297` waits for wallet finality and member observations after the fast receipt. Thus a requested `--rate 2` does not imply two sends per second. The retained final sync smoke's native summary records 2 transactions over 2.466 s at target 1/s, which illustrates the accounting but is too small to quantify the cap. Before the offered-load sweep, use a bounded positive `--max-pending` (which releases the send permit at the fast receipt), and report actual send times, dispatch lag, and realized rate. Alternatively label these runs as closure-coupled serial workloads.

2. **P1 — Receipt samples are conditional on later closure.** `run_next.py:26-51` rejects a chain if the native report has any `Error`, and independent runs unless every sample has `Outcome=COMPLETE`. In native `runChain`, observer errors become `report.Error` after `ReceiveDirect` and `ReadyUnixNS`; in `benchDirect`, `Outcome=COMPLETE` is assigned only after public wallet finality and four member observations. The recorded `FastMS` itself ends at receiver certificate verification and `ReceiveDirect`, but a later closure failure or timeout discards an otherwise valid receipt sample. Keep separate receipt and closure statuses, or explicitly disclose this selection rule and apply the same rule to FastPay.

3. **P2 — Terminating the Python adapter can leave the nine servers running.** `run_next.py:170-188` joins the `lab-run` supervisor in a `finally` block for ordinary exceptions, but it installs no SIGTERM handler. A coordinator sending SIGTERM to the Python PID exits Python immediately, bypassing `stop_lab`; `lab-run` and its children may survive. Also, `stop_lab:90-101` escalates by killing only the supervisor if it hangs, which can orphan children. Handle termination so normal SIGTERM enters the cleanup path, and verify child PIDs have exited before declaring a run closed. Prefer a dedicated process group for bounded escalation.

4. **P2 — Memory-mode description is broader than the implemented switches.** `run_next.py:17-23` sets member, gateway, committee application, and Comet experiment flags. `cmd/committee/database.go` uses in-memory Comet DBs for `blockstore`, `state`, and `evidence`; this does not establish that every Comet store is in memory. The report's phrase “Comet stores” should name those specific DBs and retain any remaining disk writes in the resource accounting.

5. **P3 — The JSON parser's conservation checks are incomplete.** `chain_result` checks later input IDs, certificate input kind, and equality of successive output amounts. If both amounts are absent, equality passes; it also does not check the first output's 100 CAL or receipt timestamps' ordering. Native `runChain` constructs the 100-CAL transfer from the prior wallet coin, so this is a report-validation gap rather than evidence of a protocol bug. If aggregation relies on the JSON as its integrity gate, assert every hop's amount, asset, nonzero output ID, and sent/ready ordering.
