# 测量口径与运行记录

## 版本、环境与计时

本轮冻结两套源码和二进制。No C3 与 C3 v1 使用同一份修改前源码，分别关闭费用机制或开启旧费用规则；C3 v2 使用本轮终稿实现。它们不是原论文 4.599 s 实验的历史二进制。Git 起点之外仍有未提交的源码，因此以源文件清单和二进制 SHA-256 共同标识版本。

测试机器为 AMD Ryzen AI 9 HX 370，Ubuntu 24.04/WSL2，所有被比较服务和客户端都继承 CPU 0–3 的亲和性。这是四个逻辑 CPU，按客体拓扑对应两核四线程，不写成四个独立物理核心。每个 Go 进程 GOMAXPROCS=1。FastPay 官方运行时和单 worker 调优运行时分开报告。所有正式负载依次运行。

服务使用内存存储。Next 钱包使用 ext4 上的 NoSync 存储，FastPay 客户端钱包使用内存；两者并非同一持久化后端。比较针对当前本机原型的收款可用终点。Next 的公开执行及成员闭合另外统计。FastPay 形成证书本身只需一次往返，本轮 receiver-confirmed 测量包含客户端收款确认/同步，不解释成协议必须多轮才能出证书。

性能链每跳转移 100 CAL。C3 v2 基础服务费配置为 0 CAL，FUEL 预留、认证承诺、固定报酬和费用状态转换仍执行。非零 CAL 收费由三种顺序实验（每笔 2 CAL）验证。零报价结果不涵盖所有非零 CAL 经营账户更新开销。独立单笔实验沿用冻结的 bench-v4 构造器，也使用零报价。

链时间从第一笔请求发出到最后一笔通过收款钱包验证；不含第一笔准备，包含后续请求准备及客户端衔接间隔。准备阶段之和因此使用第 2 至末笔。单笔延迟与整体链完成时间分别报告，不能从单笔 P50 直接推出整链加速。

## 运行异常如何处理

1. `pilot-source-first`：真实来源/后继已执行，最后用于推进纪元的实验 ClockTick 被错误套入付款提交封装而遭拒。修正实验工具的原始命令提交方式后重做 pilot；该失败保留，不计入正式费用统计。生产传输协议未为此放宽校验。
2. `formal-switches/005-r2-final-switches`：原适配器以 Unix 时间检查收据先后，在 WSL 墙钟回跳约 1.017 s 时误报第 298 笔失败。原生报告实际记录了 1000 笔有效收据和完整后台闭合。已有 Go `time.Sub` 单调持续时间与偏移一致。修正适配器后，对全部相关链统一采用单调时间和身份/依赖/本金/闭合校验；原始非零退出状态、错误文件和数据保持原样。原运行继续计入原有配置组，没有选择性重跑。余下预定运行位于 `formal-switches-remaining`。
3. 冻结源码测试初次打包遗漏测试 PEM 和嵌套模块边界文件，导致测试失败。补齐测试资产与模块标记后，全套 `go test -tags=comet_v3 ./... -count=1` 通过；两次打包失败日志和最终日志均保留。补入的文件没有改变本次四个已冻结可执行程序的源码或哈希。
4. 混合负载也出现同类墙钟回跳。统一用同一客户端的计划起点和原生单调耗时重建窗口：发送相对时间为 `ScheduledNS − FormalNS + Monotonic.ScheduleLagNS`，再分别加 `FastNS`、`PublicNS`、`MemberNS` 得到完成位置。窗口采用左闭右开区间，排空时间从窗口末端计算。六项混合负载分析器测试及三项链分析器测试通过；原始报告不修改，所有运行重新计算，不沿用旧分析器的窗口计数。

## 费用与拥堵统计

每张凭证的直接输出费用只统计一次。多个池快照包含同一套全网奖励账户，不能重复累加。累计 Spent、PoolReflow 与已经分配的 Credit 是事件计数或归属记录，不能再当作额外存量加入守恒式。

费用实验的来源输入为 100 CAL，签名输出为 98 CAL，服务费为 2 CAL；后继的签名输出为 96 CAL，服务费仍为 2 CAL。收款完整是指到账等于签名约定输出，不是忽略服务费宣称收到原始输入 100 CAL。

拥堵实验使用真实 32 KiB 公共区块上限，包含 60 笔普通/优先付款及 4 笔来源补交。保留比例比较 0.01% 与 25%，0.01% 不能称为“关闭”。观测等待从同一客户端首次提交起到验证区块可见为止，含共识和观察延迟。客户端未观察完成的积压不是节点实际内存池长度。

资源监控每 0.5 s 采样父进程及子树，包含启动与准备，可能漏掉很短命的进程；RSS 是瞬时和，网络计数是宿主 loopback 总量。因此资源表是整次运行的观测，不能冒充单次协议函数成本或隔离后的精确网络字节数。RTT 代理另有每条链路的字节、分块及实际保留时间统计。

有限额度/暂停矩阵通过 `run_capacity.py` 在原生负载及排空结束后、服务关闭前读取费用池，不改变计时终点。成员 `/debug/budget` 在普通性能服务中未启用，返回的 404 如实记录；本轮未为取快照改变该服务配置。成员闭合仍以原生客户端的验证区块观察为准。最终公共池的 Free/Held/Spent 可独立核对，包含预热的费用，不能只除以正式窗口付款数计算单价。

有限额度与暂停矩阵也经过 0 ms 代理，各条件与本组 control 比较。代理仍有转发和任务调度开销，0 ms 不等于无代理；不把这组时延直接并入主混合负载。RTT 曲线应连同自己的 0 ms 控制组解释。

## 与侧边栏 GPT 的核对

已讨论终稿费用顺序、正常报酬与超时归责、共识提案排序的适用范围，以及零报价性能配置和单调计时修正。GPT 同意按现有实验计划继续，并建议统一重分析全部运行、区分零报价与实际 CAL 收费的成本。没有根据讨论改变成功终点、删掉不利运行或跳过安全检查。
