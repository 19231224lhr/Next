## Findings

### Resolved P1 (original finding): Full-mempool selection can exceed Comet's encoded block byte limit

Location: `internal/committee/c3_scheduler.go:66`, integrated by `cmd/committee/main.go:215-216`; `internal/committee/app.go:156-160` repeats the same raw-byte accounting.

The new callback reaps the entire mempool and selects up to `MaxTxBytes` using `len(raw)`. CometBFT v0.38.26 `types/tx.go:107-114` validates the returned list using `ComputeProtoSizeForTxs`, including each transaction's protobuf field tag and length prefix. Thus a candidate set whose raw lengths fit but encoded lengths exceed the limit is selected and returned; `state/execution.go` rejects it after PrepareProposal. The consensus caller treats proposal creation errors as fatal. A concrete boundary is any single valid transaction with `MaxTxBytes == len(raw)`, or many valid transactions whose raw total is just below the limit but whose framing exceeds the remaining space. This is especially relevant to the requested congestion experiment.

The baseline App also counted raw bytes, but Comet's initial framing-aware limited reap prevented this production trigger. The new unlimited reap removes that protection, so this is introduced by this integration. Use Comet's encoded transaction size in both selection/quotas and the final App bound. Add a boundary test that passes the result through `types.Txs.Validate`; the existing scheduler test explicitly budgets `len(sourceRaw)` and therefore accepts exactly this invalid boundary.

### Resolved P1 (original finding): An epoch credit followed by a FUEL top-up can permanently block member replay

Location: `internal/committee/direct.go:93` versus `:146`, `internal/member/blocks.go:261`, and `internal/rules/reserve.go:96`.

`BeginC3Epoch` increases the public FUEL grant amount immediately. Members learn cumulative credits only from successful payment or clock-tick result data. The reserve-increase execution path returns before adding those credits. Concrete sequence: public and member grant are 1000; an epoch credits 9, making the public grant 1009; before a credit-bearing payment/tick, submit an authorized successful FUEL reserve increase with Previous=1009 and Amount=10. The member sees the top-up with its grant still 1000, so ApplyReserveIncrease rejects `g.Amount != c.Previous`. Block following cannot advance past this block; a later credit-bearing transaction, including one later in the same block, does not cure the earlier failing ordered update.

Publish/apply authenticated cumulative credits before every command whose public grant may include them, or carry a block-level credit transition that members process before transactions. A test should cover epoch settlement with no payment/tick, top-up as the first subsequent relevant command, duplicate block delivery, and restart. `TestFinalC3MemberCreditOnlyAddsObservedDelta` calls the credit helper twice and does not cover this integration sequence. This interaction is new with final C3 epoch grant increments; the preexisting reserve helper's strict Previous check was correct for its former input stream.

## Positive checks and evidence boundaries

The examined fee state machine retains exec/priority and repay after compensation, pays each output resolution once, and derives unused release from immutable masks. Final register/open/close fees are prohibited by policy; normal order changes therefore do not create reflow. CAL revenue mutations share the same discarded-on-error overlay as consumption and execution, and the settled-fact fast path prevents a second charge. Final plan fields are bound into the versioned commitment; v1 encoding appends no new fields.

Issuer/pool policy validation and QC checks bind the configured issuer. Actual payment includer is selected from the block proposer address, and `cmd/internal/config/config.go:56-68` compares configured reward identities and weights to trusted validators. Shared rewards use largest remainder; timeout reflow instead floors each recipient and carries the original payer's dust, as the design requires. Epoch weights are accrued before the block's mutations, and the final tests exercise the last-block top-up boundary. Member release restores only escrow Released, not spent rewards/reflow. Remote proposal validation does not reject based on an unseen remote queue; the full local reap is finite and Comet's proposal creation does not retain a mempool lock across PrepareProposal in the inspected dependency.

At initial review the final tests were substantive rather than solely helper mirrors: multioutput alternate-quorum attachment, failed CAL accounting rollback, order/timeout paths, three-member hidden approval limits, concurrent hidden approvals, and ledger/member restart were covered. The two missing integration checks identified then have now been added and reviewed in the follow-up above. These checks still do not by themselves establish all F1-F6 claims: helper-level epoch allocations are not a real-service multi-epoch F6 experiment. I did not inspect completed final experiment outputs or run service/performance jobs. Do not present this review or the focused test logs as a formal proof or completed experimental validation.
