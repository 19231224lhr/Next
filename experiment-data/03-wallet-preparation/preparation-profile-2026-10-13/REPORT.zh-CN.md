# Next 连续付款的请求准备成本排查

2026-10-13。本轮调查的是下一笔付款在发送前为什么花时间。主要发现是：保存请求包含多项检查和等待；同一请求在保存与发送前各编码一次，两次都会验证付款签名；实验客户端还为每笔付款启动高频上链观察，增加了 CPU 和分配开销。没有证据把全部差额归给数据库或密码学承诺。

## 1. 实测范围

沿用上一轮 `run_next.py`：同一台 Windows/WSL2 主机，所有 Next 进程共同限制在逻辑 CPU 0–3，`GOMAXPROCS=4`；4 个组织成员、4 个真实 Comet 委员会服务、1 个网关，另有客户端和实验监督进程。成员、网关、委员会应用状态使用原有实验内存模式，钱包使用 ext4 上的 NoSync Bolt。正常区块验证、钱包跟随和成员闭合持续运行。

仍测普通 Direct 路径，未开启短来源引用或精简批准，也未测 Pool。每条链只有第一个钱包预先持有 100 CAL，后续付款消费实际收到的上一笔输出。

共完成 16 条 100 笔链，1,600 次真实收款全部通过，所有公开执行与成员闭合记录完成，均只提交一次。包括五条分段计时链、三组成对的观察机制对照、三条完整客户端 CPU 采样链和两条仅覆盖前台转账阶段的 CPU 采样链。另对真实链中的已签名请求做六类组件微测，各重复三次。

本轮数据用于解释 Next 的内部成本；上一轮 Next/FastPay 原始对照数据保持原样。新的分段数据不能当作对历史那五轮额外 72–102 ms 的逐笔追溯，也不能与旧 FastPay 时间拼成新的对比结论。

## 2. 时间花在哪里

只统计第 2–100 笔的准备过程，因为第一笔准备在整链计时开始之前。下表为五条诊断链的平均累计时间，不是各阶段中位数的相加。

| 互不重叠的阶段 | 每条链后 99 笔平均累计 | 占准备总时间 |
| --- | ---: | ---: |
| 保存请求，包括编码、校验、排队和提交后返回 | 50.1 ms | 41.6% |
| 生成交易及资金引用的密码学承诺 | 26.8 ms | 22.2% |
| 发送前再次编码请求 | 15.1 ms | 12.6% |
| 计算付款签名 | 12.4 ms | 10.3% |
| 读取上一笔到账记录 | 7.4 ms | 6.1% |
| 组装输入、输出、授权引用和交易体 | 6.4 ms | 5.3% |
| 记录交易编号等结果字段 | 2.3 ms | 1.9% |

准备总时间平均 120.6 ms；尚未分配到上述阶段的计时和记录间隔平均约 0.075 ms。各轮准备累计为 98.0、136.4、149.0、106.1 和 113.3 ms。

为拆开保存请求，进一步包裹原来的钱包 Store 接口，只增加时间戳，仍调用相同的 Group/Bolt 更新。三条轮询对照链的保存时间平均为 47.0 ms，内部构成为：

| 保存请求内部阶段 | 后 99 笔平均累计 |
| --- | ---: |
| 进入更新前的编码及检查 | 13.6 ms |
| 更新排队，直到本次回调开始 | 10.9 ms |
| 钱包描述符、资金状态和消费锁检查 | 8.9 ms |
| 回调结束后的提交与调用方恢复 | 13.6 ms |

“提交与调用方恢复”包含 backing transaction 的其余工作、提交和 goroutine 恢复，不能解释为纯磁盘 I/O。保存请求还会重新解析该输入的完整到账记录。因此不能把 47.0 ms 都称为写数据库的成本。

## 3. 请求编码为什么也明显耗时

实际调用链是：

`SaveDirectRequest → DirectRequest.MarshalBinary → FastTx.MarshalBinary → VerifyAuth → VerifyOwner`

保存完成后，`runChain` 为 HTTP 发送再次调用 `request.MarshalBinary()`，上述付款签名验证又做一次。

地址描述符验证已有精确缓存。在持续使用三个钱包的场景里，重复调用地址检查通常命中缓存；它不是这里的主要验签成本。交易编号也重复计算，但成本较小。

使用同一条真实链第二笔保存下来的请求，在没有服务器和链观察并发的条件下，三次组件微测的中位耗时为：

| 组件 | 每次耗时 |
| --- | ---: |
| `NewFastTx`，生成交易及承诺 | 60.9 µs |
| `SignOwner`，使用已计算的交易编号签名 | 13.3 µs |
| 完整 `DirectRequest.MarshalBinary` | 45.7 µs |
| 单独 `FastTx.VerifyAuth` | 36.5 µs |
| 命中地址缓存后的钱包描述符检查及绑定查询 | 1.21 µs |
| `FastTx.ID` | 2.99 µs |

组件 CPU 采样中，`DirectRequest.MarshalBinary` 路径采到的 3.76 秒里，`crypto/ed25519.Verify` 累计约 2.96 秒；约 79% 花在付款签名验证。这里的“编码”主要成本确实包括验签，不能只理解为字节拷贝。

`NewFastTx` 的 3.55 秒采样中，承诺生成占约 3.34 秒，主要工作为 RSA 群元素检查和模幂。它有实际成本，但单独执行约 61 微秒，不能独自解释并行实验中一笔准备接近毫秒的墙钟耗时。这些微测不能直接相加重建真实链延迟；它们没有真实链的排队、后台工作和新状态解析。

## 4. 高频实验观察会干扰前台

`observeChainHop` 为每笔付款启动一个观察 goroutine，每 5 ms 调用 `DirectFinal`。`DirectFinal` 每次读取并 JSON 解析整份 `DirectCoin`，其中包括证书等字段。百笔链逐渐形成很多同时观察的任务，即使钱包还没有提交新区块，它们仍重复解析相同记录。

在专门只覆盖准备第一笔到取得末笔收据这一段的 CPU 采样里，客户端共采到 380 ms CPU，观察路径占 220 ms，约 58%，主要是到账记录的 JSON 解析。这是该次客户端 CPU 采样的占比，不是全部服务的 CPU 占比，也不是整链墙钟时间的 58%。完整客户端采样还覆盖等待公开执行的后段，观察路径占约 60%–72%；不能把后段采样全归到前台延迟。

对照版本使用钱包的真实区块提交通知唤醒观察者。观察者先订阅通知，再查询状态，避免查询与订阅之间漏掉提交；只有正常 follower 验证区块并成功提交钱包状态后才发通知。每笔付款仍检查真实钱包状态，随后仍等待成员闭合。

三组成对实验仅改变这一观察方式，交替安排运行顺序：

| 轮次 | 轮询检查次数 → 通知版本检查次数 | 准备累计：轮询 → 通知 | 整链收据时间：轮询 → 通知 |
| --- | ---: | ---: | ---: |
| 0 | 34,196 → 251 | 88.7 → 82.5 ms（缩短 7.0%） | 570.7 → 630.7 ms（增加 10.5%） |
| 1 | 22,528 → 228 | 119.7 → 87.2 ms（缩短 27.1%） | 721.2 → 574.2 ms（缩短 20.4%） |
| 2 | 23,222 → 205 | 115.1 → 96.5 ms（缩短 16.1%） | 762.6 → 664.8 ms（缩短 12.8%） |

三轮准备过程均缩短，配对降幅中位为 16.1%。整链两轮更快、一轮更慢，不能宣称有稳定的固定百分比提升。仅覆盖前台的通知版本 CPU 采样为 160 ms，未采到观察路径；这表明这层观察开销很小，不表示它实际为零。

## 5. 后续优化顺序

1. **复用保存时产生并验证过的请求字节。** 钱包方法可以在原来的原子保存成功后，返回这次实际保存的字节，发送方直接使用；无需接受调用方传入的“已验证”字节，也无需删掉验证或提前发送。这样可消除发送前的第二次完整编码与付款验签。尚未实现此接口，本轮未给它报性能提升百分比。
2. **用提交通知取代高频实验观察。** 本轮已实现并用真实链验证，作为 opt-in 诊断对照保留。它改善实验客户端的资源使用，不构成新的支付协议创新，也不属于同组织独有的收益。
3. **把重复编号计算作为小修。** 独立计算约 3 微秒，优先级低于上述两项。密码学承诺应继续保留，不能为了少几十微秒改变修复机制的安全含义。

本轮没有改变服务器、证书规则、担保容量或默认付款行为。已新增客户端诊断和可复现对照开关，原论文和原对比数据没有更新。

## 6. 复现与材料

- `run_profiles.sh`：五条细分计时链和一次完整客户端 CPU 采样。
- `run_observer_ab.sh`：三组交替顺序的轮询/通知对照和两次完整客户端 CPU 采样。
- `run_foreground_profiles.sh`：两种观察方式各一次仅覆盖前台阶段的 CPU 采样。
- `run_components.sh`：真实请求的六类组件微测，各三次。
- `analyze.py`：校验逐笔链接、先收款再准备、100 CAL 输出、真实证书输入、收款和闭合记录、阶段分解及整链时间关系，生成 `analysis.json`。
- `results/`：所有原始 native JSON、适配器结果、CPU profile 和微测输出。
- `source-snapshot/`、`tracked-source.patch`、`manifest.json`：最终诊断源码、工作区差异和材料哈希。先前几轮使用同一诊断代码的较早版本，清单中说明了逐次增加的计数器和 CPU 采样范围。

诊断开关：`UTXO_CHAIN_BUILD_PROFILE=1` 启用阶段计时；`UTXO_CHAIN_COMMIT_NOTIFICATIONS=1` 选择通知观察；`UTXO_CHAIN_CPU_PROFILE=/absolute/path` 保存 CPU 采样；配合 `UTXO_CHAIN_CPU_FOREGROUND_ONLY=1` 可在末笔收据取得后停止采样。所有环境开关由实验脚本局部设置。

最终 `go test -count=1 -tags=comet_v3 ./cmd/payctl` 通过，Linux 客户端与组件微测二进制构建成功，`analyze.py` 校验 16 条链通过。后台实验进程已退出。
