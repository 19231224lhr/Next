第二轮复核意见

本轮核对范围：clarification-source.txt（proposal_batch 及其测试、ApproveDirectBytes、partial_reclaim、source_recovery、direct_deadline、repair.go、engine.go、compensation_runtime、audit_capital.py、运行脚本）、experiment-source-manifest.json（309 项）和 clarification-verification.txt（构建比较、新的测试日志）。

范围说明：我仍然只阅读源码和日志，没有构建或运行任何东西；网络实验也没有重跑。下面的结论都基于这些材料。

一、逐项事实复核
1. WAL 批处理与 autofile：撤回安全疑问

proposal_batch.go 的行为与作者描述一致：

批处理的触发条件很窄。 只在 RoundStepPropose 步骤下启用，且首条消息必须是本地消息（PeerID == ""），高度和轮次都必须匹配当前状态。队列中只收集已经就绪的本地 BlockPart；remaining 计数保证批次不会越过最早可能完成区块的位置。
先落盘、后处理。 批内消息先逐条 wal.Write，再 FlushAndSync；任一步失败即 panic。全部成功后才逐条执行 handleMsg。
投票不进入批处理。 投票走 handleSingleInternal，即 WriteSync 后接 fail.Fail()，与上游一致。
边界消息的顺序正确。 预取到的边界消息在批次处理完之后才单独写入，因此排在批次可能产生的 newStep 之后。
新增测试覆盖了关键故障。 写失败、Sync 失败、写入前缀后重放、Sync 后重放、提案后重放等场景都已通过。

结论：原 M6 中"内部消息 WAL fsync 可能被绕过"的疑问撤回。 剩下的只是论证完整性问题（见第三部分 B5），不是反例。

2. 截止期与 ClockTick：问题已回答

AnchorDirectDeadlines 在高度 H+1 的命令执行之前运行，用 H+1 携带的 H 的中位提交时间加上 TimeoutSeconds 来设定截止期。这样，H 之前的空闲时间不会缩短在 H 中开启的义务，设计合理。

decisionStep 发现公开时间落后于截止期时，会提交 ClockTick 推进区块时间；本地墙钟只用来调度提交时机。

结论：原 M7-3 撤回。 只需在正文写明这一机制，并给出当前构建使用的 timeout 值（次要）。

3. 储备账户映射：问题已回答

各环节的账户是同一个：

成员审批时检查 t.Certifier == cfg.Org；
CAL 准入键的账户取自 t.Certifier；
公开验证要求 summary.Issuer == cfg.Org；
NewEngine 按 AccountKey(g.Key.Account, CAL) 汇总各授权的支撑额度，并禁止受保护账户充当注资来源。

由此，补偿扣款的账户 AccountKey(Issuer, CAL) 与授权的支撑账户一致，Theorem 1 依赖的映射成立。撤回。

4. 审批、失效回收与来源重提交：与引理一致
ApproveDirectBytes 在一次 db.Update 中原子完成：Intent 检查、输入与费用输入锁、费用校验、slice 扣减和审批记录写入。这与 Lemma 2 和 Lemma 8 的前提一致。
reclaimPartial 的守卫与 Lemma 3 逐条对应：同一配置、不同 TxID、共享同一输入实例、无已观察执行、无 INSTALL 或 outbox、无 Pending、Paid、Recovered 或费用效果。
recoverExposedSources 与 Lemma 4 一致：只有原签名者才能重建，先校验事实再写 outbox，并且不新增任何扣减。

结论："关键代码未提供"一项撤回。

5. 清单、二进制指纹与资本审计：问题已解决
experiment-source-manifest.json 确有 309 项。比较结果显示，P/R 与 chain 构建的 source、comet_go 和实际运行二进制的差异列表均为空。
audit_capital.py 确认 source_sha256 是每轮 final-resources.json 的哈希，不是源码哈希。
新测试日志带有 -tags comet_v3 -count=1，八个包全部通过，退出码为 0。

原 M9 第 2–5 点撤回。 唯一保留的是 S3-A 中 14.15 倍比值的构建归属需要标注（次要）。

6. C3"混合体"：不构成反例，撤回反例式表述

我核对了实际的安装与读取路径：

Execute 要求 c.Next == digest(body)，并要求重建的 block hash 和 part-set header 都等于已保存的原始 BlockID。
PrepareMaterialization 只取已提交 Task 或 Revision 中的 Body，并再次校验摘要。
Install 的回调要求安装后的区块体与 Task Body 逐字节相等。
Canonical 读取的是应用状态中已提交的 Revision Body，而不是 BlockStore 中物理安装的版本。

因此，逐 part 混合得到的区块体虽然能满足 CH 关系和 BlockID，却通不过任何一道实际守卫，不能被安装或作为规范修订读出。

首轮 M4 第 2 点中"削弱 C3 与 Reparo 的区别"这一论据撤回。"等 BlockID 不等于授权"本来就是 §IV-H Reader scope 所定义的接口语义。剩下的只是用途与表述问题（见 B3）。

7. 历史存储依赖与无 CH 构建：属于已声明的范围

作者已明确把这两点划在范围之外：保留原始历史的诚实副本是前提，裁剪后经 state sync 加入的副本不在支持范围内，也没有测过无 CH 构建。

我核对到，Canonical 在没有修订时会回退到 bs.LoadOriginalBlock，ExecuteDecision 正是通过这条路径读取原始区块。这是模型前提，不是反例。

"无 CH 构建"和"state-sync 支持"的要求撤回，归为扩展。 只保留"前提应在相关引理中显式写出"的表述要求（见 B4）。

二、M1 的定性

它不推翻任何已陈述的定理：

Theorem 1：攻击使 Q_g 达到 B_g、储备降到 0，但始终满足 Q_g ≤ B_g 且 Gap ≤ A。轮换签名者测试中 Q_g = B_g 恰好说明这个界是紧的，而不是被突破。
Theorem 2：被滞留的输入仍计入 U，守恒成立。
Theorem 3：其假设（每笔支付恰好成功一次）本身就排除了 Intent 失败者。
Theorem 4 与 Lemma 5：照原文陈述成立，且 Lemma 5 已经描述了该机制。

所以 M1 不是模型内反例，而属于下面第二类"主张与用途不足"。具体有三层：

攻击的本金成本没有被点明。 正文承认储备会损失、容量会滞留，但没有说出攻击者的可用本金前后不变。被滞留的输入在价值上恰好等于储备损失，攻击者付出的只有 FUEL。这一事实决定了签发方实际承担的风险，应在正文中写成显式命题，而不是分散在 Lemma 5、§V-F 和 S3 三处。
对第三方的影响没有写明。 只要 CAL 认证容量耗尽，所有路由到该组织的输出都无法再被花费，即使输入全是最终输出，持有这些输出的诚实第三方也会被冻结，直到外部注资；而注资后攻击可以重复。§III-E 的"Stoppage"段只写了"新认证可能停止"，没有写出"既有最终资金被冻结"这一后果。
标题和摘要与实际定位不符。 "Direct Guarantees"和"funded obligation that protects the executed successor"会让读者以为签发方或接收者受到了保护。实际上补偿维护的是供应完整性（式 (8) 中的 D）；子交易输出在执行时就已是最终输出，不依赖储备。

是否必须做协议缓解？ 我的判断是：在作者不承诺开放服务长期抗耗尽的前提下，协议缓解不是接受的必要条件，但重新界定主张是必要的。如果作者愿意做缓解，最小必要目标建议定为：

同一 Subject 的 Intent 等价提交（两个 owner 签名、同一 (Subject, Nonce)、不同 TxID，可公开验证）造成的签发方净 CAL 损失，以该 Subject 被没收的价值为上界，且该部分容量滞留可以释放。

这一目标不涉及费用当保险，也不需要全局准入或 Subject 保证金。

一个可能的实现方向：失败交易 T2 的输入已经被签发方成员锁定，其总值等于 T2 的输出总值，因此足以覆盖其所有输出可能引起的补偿。可以定义一条"没收执行"命令，以等价提交证据加上 T2 的 QC 为凭据，按 T2 的输入规则执行，但把输出统一结算到签发方储备，即按 Repaired 和 Recovered 处理。T2 自身的缺失输入会照常对其直接签发方开立义务，因此不需要新的记账类型。这需要在协议规则中事先声明"签署等价 Intent 即授权没收"。

三、更新后的问题分类
A. 模型内反例

本轮补充后，我没有发现能够通过实际守卫、并推翻任一已陈述引理或定理的反例。 首轮中可能被理解为正确性质疑的几项（WAL、截止期、储备账户映射、C3 混合体）均已撤回。

B. 论文主张与用途不足（应在当前范围内修订）
B1. M1 的显式化。 内容见第二部分第 1–3 层。这是本轮最重要的一项。
B2. 补偿保护对象的表述。 应说明补偿维护的是供应完整性，而不是接收者；与 B1 一并修改。
B3. C3 的用途陈述。
应明确：完整 BlockID 相等只是必要条件，原始体、更早的修订和逐 part 混合体同样满足；授权只来自已执行前缀中的精确 Revision 和 Task。
Table IV 中 B 唯一独有的一行，应给出具体使用者或场景（例如审计方必须拿到修订后正文的哪种流程），或者把 C3 定位为次要贡献。
每个修复区块 0.28–2.19 MiB 的额外开销，应与这一收益放在一起陈述。
B4. 历史存储前提要写进引理。 Lemma 12 和 §III-A 应明确：补偿决定的执行通过 Canonical 读取原始区块；在当前实现中，C2 位于 comet_v3 构建内；"无适配依赖"不等于"无历史存储依赖"。作者已同意这一区分，只需落实到正文。

关于读取历史区块的目的：决定所核对的身份、事实和金额，义务记录本身已经保存，因此读取历史区块的独特作用看起来主要是检查 funding 槽位能否等宽替换。若理解有误请指正。

B5. 共识修改的书面论证。 补充材料目前没有逐项列出 overlay 的全部修改。应包括：身份比较、Propose 步骤下凭当前轮 polka 直接 precommit 的新转移、proposal batch 的 WAL 顺序、autofile 的 Sync 跳过、ABCI 响应的批量 WriteSync。每项应对照 Tendermint [22] 的规则说明所保持的不变式（lock 与 POL 条件、"本节点签名的消息先落盘再生效"）。新的 ProposalBatch 测试可以作为佐证引用。
B6. Theorem 3 的定位。 建议降为命题，或明确说明它刻画的是"诚实完成情形下的顺序无关性"。
B7. 次要修正。 S3-A 标注构建 721800c；正文写明截止期与 ClockTick 机制及 timeout 取值；补全作者单位；补全 Table I 的符号；降低正文密度（首轮 M10 维持，但它不是决定性问题）。
C. 超出现有主张的扩展（不作为接受条件）

以下各项都属于扩展，不作为接受条件：

超出上述最小目标的协议缓解，例如 Subject 保证金或全局准入；
多机或广域网部署、FastPay 或 Sui 基线、当前构建上的吞吐测量。正文主张的对比对象本来就是"逐跳等待"，并没有过度声称；
无 CH 构建、对 state sync 和历史裁剪的支持、一般化到 n = 3f+1、重配置与规则升级；
TLA+ 模型检查、激励分析。
四、维持大修时最关键的 3 项及验收条件
第 1 项：M1 显式化与主张重新界定（B1 + B2）

必须满足以下全部条件：

(a) 增加一个命题，含形式陈述和证明草图：在现有模型下，一个本金中性的对手只需付出 FUEL，就可以使任一授权的储备净损失达到 B_g，并使认证容量耗尽。以 S4-B(b) 的轨迹作为紧性实例，同时给出攻击者每轮所需的临时资本、FUEL 成本，以及每轮的储备损失和滞留价值。
(b) 在 §III-E 中写明：既有最终资金在注资前会被冻结，受影响的是持有这些输出的第三方。
(c) 摘要、引言和 §III-E 改写对"guarantee"的表述，说明补偿保护的是供应完整性，并写明适用的部署前提（例如 Subject 可问责或存在协议外追索），不再把开放部署作为默认设定。
(d) 用一段文字说明是否采用第二部分的最小缓解目标；如果不采用，说明理由。

满足 (a)–(c) 即可视为该项通过；实现第二部分的最小缓解是加分项，不是必需。

第 2 项：C3 的用途定位与历史存储前提（B3 + B4）

验收条件：

正文对 C3 的保证给出精确陈述：在本地已验证前缀 H 上，导出的修订正文等于已提交 Task 的 Body，且与完整 BlockID 一致；BlockID 只是必要条件。
给出 C3 相对于索引 M 的独有价值，并配一个具体使用场景；否则把 C3 降为次要贡献。
Lemma 12 和 §III-A 写明决定执行对原始区块存储的依赖，以及当前实现中 C2 与 CH 构建的关系。
第 3 项：共识修改的书面论证（B5）

验收条件：

补充材料中新增一节，逐项列出 overlay.py 对 CometBFT 的全部语义修改（不含纯计时埋点），每项给出不变式和对照 [22] 的论证。
其中，新的 precommit 转移须论证安全性（lock 与 POL 规则得到保持）以及每轮每节点至多一次 precommit；WAL 相关修改须论证"本节点签名的消息先持久化再生效"仍然成立。
引用已有和新增的测试作为实现层面的佐证。不要求机械化证明。
五、小结

补充材料解决了首轮列出的全部"缺失材料"类问题，也没有发现模型内反例。剩余问题都集中在主张与实际保证之间的对应关系上，其中 M1 的显式化最为关键。

我维持大修的建议。但修订的性质已经从"需要补证据、需要回应潜在正确性问题"，转变为"在当前范围内修正主张、补充论证"。若上述 3 项满足验收条件，我预计可以接受。
