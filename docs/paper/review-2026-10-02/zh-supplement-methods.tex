\section{归档构建的实验方法}
\label{sec:supp-methods}

\noindent\textbf{版本谱系与部署。}
结果保留各自原始版本标识（表~\ref{tab:supp-builds}）。\emph{续花与记账基线}以提交 \texttt{d99ec92} 为准，实现分层续花和记账转换；其赔付与历史表示一并提交。制品记录了每个二进制文件的 SHA-256 指纹和每次运行的配置。九服务的续花、赔付与偿还、存储和短时吞吐各系列使用该版本。最初的十四服务配对运行使用相同的单义务规则，其时批处理结果标签尚未与直接结果标签分开，跨类型编解码回归测试覆盖了这一分离。基线的存储、内存续花和短时吞吐对照中的成员以 GOGC=200 和 GOMAXPROCS=16 运行；该覆盖设置不用于委员会、网关或钱包进程。

\emph{decision-first 版本}（记账域 \texttt{DIRECT\_ACCOUNTING\_V5\_DECISION\_FIRST}）实现基于公共证书的补交、赔付决定，以及独立的历史表示命令。它源自分支基点 \texttt{0e7bae5}，后者是 \texttt{d99ec92} 的仅含文档变更的后代。九次功能运行使用初始实现快照，其源码包 SHA-256 以 \texttt{2c91b0251024322c} 开头。该系列后期快照的包 SHA-256 以 \texttt{449b4d4072c99588} 开头，它在读取任何历史区块之前就拒绝位置与已提交状态不匹配的决定，并把每轮到期决定的有界扫描从 8 项提高到 32 项；普通支付路径不变。六次普通路径运行、完整测试套件和竞态测试使用该系列后期快照。经审计的提交 \texttt{f185f73} 另外要求附在支付上的证书与其证书输入一一对应，它不改变所测负载中被接受的支付。基线版本与 decision-first 版本的数值分开报告。

归档的运行范围运行记录基点 \texttt{e3870e1} 与实现 \texttt{a083ff6}。原始续花记录 \texttt{f0c0a274}，资本记录基点 \texttt{8e1fb40} 与实现 \texttt{5807546}，组织路径记录基点 \texttt{bb65af69} 与已验证源码 \texttt{13be856}。归档的批处理集成使用 \texttt{f82f8cd}，结构性历史表示计数则在基线代码上重复测得。源交易失败检查点 \texttt{c1ebf2d} 使用已被取代的迟到源交易规则，不支持当前的论断。

Mac 试验共用一台 M4 Max 主机，16 个 CPU 核心、64\,GiB 内存，结构性微基准测试运行于 Windows amd64。基线版本的内存链和短时吞吐试验使用内存中的服务状态和 NoSync 钱包。赔付与偿还试验使用落盘的委员会应用状态和 BlockStore，成员和网关在内存中。存储对照只改变成员提交，在 bbolt NoSync 与同步事务之间切换。每次运行都从全新的创世状态开始。另有六次十四服务的落盘链运行，使用基线记账规则和用户自付 FUEL。其中三次快速 100 跳运行耗时 668.960--688.080\,ms，跳间确认运行耗时 114.496--118.742\,s。它们属于与正文九服务结果不同的存储与部署配置。

\noindent\textbf{Decision-first 功能运行。}
九次运行使用十四服务配置，450 个初始输出，落盘的委员会，成员为默认的 NoSync 模式，flush 与 gossip 设置为 10\,ms，显式授权的组织代付 FUEL；签名及所有金额与消费检查保持开启。普通支付压力钱包使用 NoSync 钱包选项，两跳故障演示使用默认钱包模式。每次运行中，一个注入的故障使原发布者在完整 QC 形成之后无法提交或 INSTALL 父支付，所以原签署者持有其批准而不持有 QC。子支付花费该父支付的 TXCer。在补交处理中，驱动程序从不提交原支付。对照处理通过实验开关关闭自动补交步骤。持有经 INSTALL 存入的完整材料的成员所做的普通备用提交仍保持启用；INSTALL 本身负责在组织内复制该材料。暂停处理同样关闭补交，并且在标记文件存在期间，使全部四名委员会成员的输入适配与分片适配 HTTP 端点返回暂停状态；共识、决定和支付处理并未暂停。

计时从子支付第一次 HTTP 发送开始。快速接收在钱包验证证书并记录输出时结束。公共事件通过轮询跟随者的状态端点来观察，所以包含轮询延迟，两次公共观察之差不是从确切提交时刻起算的协议延迟。赔付时间包含配置的 30-s 义务期、委员会 tick 推进的公共时间，以及后台调度。在暂停处理中，脚本在赔付之后提交迟到的源交易，并等待全部四名委员会成员的状态端点都显示义务已偿还、且历史表示既未提交也未物化。它保存这四项观察，移除标记，然后等待历史表示在全部四名成员处提交并物化。状态端点的稳定性标志比较头部哈希、数据哈希和交易身份。完整区块身份与分片集合头由物化步骤和真实共识的集成测试检查，所以不把该标志单独当作完整身份的证明。偿还以及适配的恢复没有各自的时间戳。这些测量不包含与周期性扫描、投票收集，或暂停适配下的早期耦合版本的比较。

每种处理有三轮，每次功能运行都通过四项检查：四个委员会成员的状态哈希相同、缺口为零、支付已关闭、outbox 已排空。补交与对照两种处理还各自带有三次各 300 笔普通支付的运行。逐次运行的数值见表~\ref{tab:supp-functional}。

\noindent\textbf{Decision-first 普通路径运行。}
六次运行比较位于分支基点的版本与最终的 decision-first 快照，顺序为 AB、BA、AB。每次以 100 笔/秒发送 300 笔支付，并发快速请求 64 个，未完成请求至多 256 个，使用 NoSync 压力钱包。总耗时包含全部 300 笔支付的公共确认和成员跟随；它既不是单笔支付的时间，也不是最大吞吐。每次运行的发送时段约为 2.990\,s。正文中的汇总数值是各次运行统计量的中位数，而不是对全部支付合并计算的分位数。普通的最终输出不携带输入证书，所以这些运行没有测量输入尚未成为最终输入的支付所保留的存储。逐次运行的数值见表~\ref{tab:supp-cost}。

\noindent\textbf{回归测试覆盖。}
赔付决定在尚未到期、网络/槽位/金额不匹配、备付金不足，或与已记录的决定冲突时被拒绝。重复的决定没有经济效果，包括偿还之后，此时它不返回任何变更、效果或费用输出；源交易先到与决定先到两种顺序都已覆盖。补交针对跨组织和多层源交易、重复暴露，以及已被观察到或已排队的支付（这些支付不会被重建）做了测试。普通验证拒绝不匹配的材料，补交前后原始批准、支付字节和 CAL 额度保持不变。历史表示要求决定已成功，在源交易偿还之后仍然可以进行，并且不会第二次恢复成员进度或 Worker 切片。在身份与重放方面，真实的门限适配保持完整共识身份、后继交易的区块体和预先签名的后继交易引用。对原始历史的重放在每个高度重现应用状态，对同一已决定集合逐项和不同分组的历史表示得到相同的最终区块体和分片 opening，输入数为 1、2、4 和 8，跨越两个真实分片。完整测试套件和静态检查在该系列后期快照上于 Windows 和 macOS 通过，竞态检测器在 macOS 上通过成员、历史表示和委员会运行时各包，完整套件和静态检查在经审计的提交上再次通过。

\noindent\textbf{计时与汇总。}
认证接收延迟一般从钱包第一次实际发出 HTTP 请求起，到收款方验证并完成本地原子记录止。资本与源交易失败的驱动程序包含少量发送前的构造，所以其比较仅限于同一驱动程序族内。本地 NoSync 事务完成并不是同步持久化的回执。公共与成员完成时间戳记录的是对经认证执行的观察，而不是委员会的内部提交。发送方的单调时钟测量跨站点 ACK 延迟，包括返回路径，收款方可以在前一个发送方收到该 ACK 之前就发起其后继交易。目标提供速率、实际发送速率和含排空的完成速率分别保留。图注区分交易分位数与跨运行的统计量，单次运行内的样本变异不是对跨运行不确定性的估计。

\noindent\textbf{交付门控运行。}
在归档的交付门控版本上，有门控的变体等待三名成员 INSTALL 完整材料，或等待经认证的公共执行成功，以先发生者为准，且不收集第二个签名法定人数。在每秒 200 笔、持续 30\,s 的条件下，每种模式三次配对运行各发送并完成 6,000 笔支付。运行级接收 P50 的中位数在立即投递时为 1.300\,ms，有门控时为 2.167\,ms。另外的 100 跳试验把中位链耗时从 287.983 降到 200.356\,ms（图~\ref{fig:delivery-gate}）。

三对十四服务运行，顺序依次为正常/扣留、扣留/正常、正常/扣留，使用基线版本的初始构建（批处理结果标签分离之前），委员会与成员数据库落盘，成员和钱包为 NoSync。每次以 100 笔/秒发送 4,000 笔支付，历时 40\,s。与之并行，另有四个两跳演示，其源交易或被正常送达（正常运行），或被扣留、在 30\,s 后被赔付并随后偿还（扣留运行）。全部六次运行中，4,000 笔支付全部完成。各所有者角色最终持有的 CAL（30,000 和 830,000）以及两个备付金余额（$10^{12}$）在六次运行中一致，扣留运行记录了 400\,CAL 赔付和 400\,CAL 偿还，所以最终分配与延迟中性一致。正常/扣留运行的接收 P50 分别为 1.070/1.127、1.089/1.108 和 1.083/1.097\,ms，P95 为 26.84/59.23、29.49/58.44 和 27.41/55.15\,ms；所有运行的完成速率为 97.2--97.8 笔/秒。接收 P50 比配对的正常运行高 1.3--5.3\%，P95 为其 1.98--2.21 倍。因此，并发赔付在该配置下影响接收的尾部，而这些配对不能区分造成这一影响的具体环节。

六次各 1,000 笔支付、速率 100 笔/秒的运行，使用九服务配置（委员会落盘，钱包为 NoSync），仅在成员存储上不同。NoSync 成员时，接收 P50 为 1.002--1.035\,ms，P95 为 33.97--40.62\,ms，含排空的完成速率为 93.11--93.93 笔/秒。成员提交为同步时，P50 为 43.19--51.85\,ms，P95 为 80.98--96.56\,ms，完成速率为 90.99--92.72 笔/秒。全部支付完成。由于钱包仍为 NoSync，这一对照单独隔离出同步成员提交的代价。

\noindent\textbf{历史表示微基准测试与批处理集成。}
这些结构性测量使用早期的耦合历史表示命令，它同时还承载经济步骤。在 Windows amd64、Go~1.27.1 上的微基准测试，把 $k\in\{1,2,4,8\}$ 个缺失输入放在同一个历史区块的同一个分片中。五次重复中，单条命令需要 $k$ 条命令和 $k$ 次分片适配，而一个批处理只需各一次，输入适配仍为 $k$ 次。在 $k=8$ 时，编码命令总字节数从 127,336 降到 2,752（图~\ref{fig:repair-cost}）。分散对照把批处理与紧凑编码区分开：八个独立的目标区块仍需要八条命令和八次分片适配，而字节数从 30,008 降到 5,440。在 $k=1$ 时，两种格式都执行一次分片适配，编码大小分别为 3,751 和 680 字节。因此，紧凑字段解释了字节数下降的一部分，共享的区块表示则解释了适配次数的减少。这些是编码后的命令大小，不是网络流量总量或密码学计算总量。它们也不包含 decision-first 版本中每个已决定输出所携带的那条 88 字节的决定命令。

一次归档的、十四服务落盘的批处理集成运行（\texttt{f82f8cd}）把四个实际缺失的源交易合并为一个 1,568 字节的批处理，其 BatchID 在全部委员会副本上一致。迟到父交易的处理之后，随后以 100 笔/秒提供的 1,000 笔支付全部完成。接收 P50/P95 为 1.048/26.531\,ms，总完成时间为 11.120\,s，含观察与关停。缺口和 outbox 都已排空，委员会状态哈希一致。该批处理携带经济步骤，且早于决定与历史表示的分离。

\noindent\textbf{外部出资的授权控制器。}
资本实验每 200\,ms 采样一次成员可用额度。令 $\rho$ 为声明的每秒 CAL 授权需求，其中把每个工作负载单元里的父请求和子请求都计入，令 $u$ 为认证尚未完成的不同请求数。控制器设定
\begin{align*}
 b &= 200+100u,\\
 H_{\mathrm{low}} &= \rho\,(0.8\,\mathrm{s})+b,\\
 H_{\mathrm{target}} &= 1.25H_{\mathrm{low}}.
\end{align*}
其中水位线和突发余量以 CAL 计。当观察到的最低成员可用额度 $A_{\min}$ 低于 $H_{\mathrm{low}}$ 时，建议的授权额度增量为
\[
 \Delta B=100\left\lceil
 \frac{1.5(H_{\mathrm{target}}-A_{\min})}{100}
 \right\rceil,
\]
并受已配置的授权上限和可用的外部资金限制。同一时刻至多有一次增量在途。其公共命令原子地扣减外部来源，并记入备付金和授权额度，跟随的成员加上由此产生的份额之差，而不清除已有批准。该实验预先提供 $\rho$，而不是估计未知的生产需求。控制器的决定是对实际有资金支撑的转账的请求，而不是创造支撑资本的机制。

\noindent\textbf{资本负载记账。}
每个条件各有一次 300-s 运行，每个成员一个 Worker，用户 FUEL 充足。从 3,600 CAL 起步，恒定、速率阶跃和父交易延迟三个条件在外部转入 10,800、18,000 和 19,700 CAL 之后，分别结束于 14,400、21,600 和 23,300 CAL（表~\ref{tab:eval-capital}）。每个条件都完成 6,000 个两跳单元，即 12,000 笔支付，花费 1,128,000 用户 FUEL。相应的固定高值对照全部完成，而固定低值条件只关闭了 6,000 个单元中的 46 个，有 5,826 个未启动，并记录了 64 笔部分批准的支付。这些类别的单位不同，不合并为一个支付计数。逐次运行表保留了完整的七条件比较，但并不意味着每个条件重复三次。该系列在较早的版本上运行，其中没有发生赔付。

\noindent\textbf{身份、资源使用与保留的历史。}
多身份配置使用共享的客户端，所以 2,048 个钱包身份并不对应 2,048 个独立的操作系统进程。把独立输入与十跳支付相比，三次运行的中位数为：每笔支付 12.67 对 15.24 core-ms，每笔支付 59.32 对 71.83\,KiB 的 HTTP 负载。内存报告把节点总 RSS 和保留的历史，与活跃义务、待处理工作和 outbox 分开，所以不断增长的历史占用不会被报告为不断增长的支付积压。逐次运行的资源汇总及其归档源位置包含在制品索引中。

\noindent\textbf{针对特定端点的 Lightning 参照。}
归档部署使用 LND v0.21.3-beta 和 regtest 中的 Bitcoin Core 31.1，采用同步的 LND 持久化及其 50-ms 通道提交设置。三次全新部署中，每次有两个节点和一条直连通道。经过 20 次预热转账之后，每次运行发出 100 笔串行、交替的 10,000-satoshi 支付，使用预先准备的 invoice，并以接收方 \texttt{SETTLED} 作为完成事件；所报告的 P50/P95 为 282.12/320.17\,ms。另有一次 Next 运行，以 100 笔/秒发送 300 笔支付，持续 3\,s，使用内存中的服务状态和 NoSync 钱包存储。收款方认证接收的 P50/P95 为 0.9625/1.2075\,ms。工作负载并发度、持久性和完成语义各不相同，所以这些记录是部署参照，而不是归一化的加速比。

\subsection{归档的运行范围系列}
归档的运行范围系列是对续花结果的补充。一个活跃的组织使用赞助的费用、复用的地址和独立的最终输入。五次各 150,000 笔支付的运行全部完成（图~\ref{fig:operating}）。在 2,000 笔/秒的目标下，两次运行的完成速率为 1,948.66--1,950.45 笔/秒（含排空），接收 P50 为 2.521--2.566\,ms。把目标提高到 2,200 时，完成速率为 2,103.63--2,106.29 笔/秒。在 2,400 时，实际达到的速率为 2,174.68，P50/P95 升至 7.174/89.38\,ms，4,096 项的待处理准入上限被触发 1,635 次。运行曲线把达到的完成速率与其对应的队列压力配对给出。
