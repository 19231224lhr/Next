\section{实现与评估}
\label{sec:evaluation}

Next 的评估把收款方侧的续花与有资金支持的关闭及保持身份的修复联系起来。我们先考察相互依赖的付款，然后依次考察来源故障、修复成本、组织边界和运行容量。这些测量检验第~\ref{sec:protocol} 节的机制在第~\ref{sec:model} 节模型下的表现；第~\ref{sec:security} 节则在所述模型下确立它们的安全性质。

\noindent\textbf{实现与测量。}
Go 实现使用原子的状态 overlay、独立的区块跟随者，以及经修改以强制执行完整区块身份和经授权的历史安装的 CometBFT v0.38.26。门限 RSA 适配使用 CIRCL v1.6.5，并采用可信离线 dealer 初始化。网络实验运行在一台 Mac Studio 上，配置为 M4 Max、16 个 CPU 核、64\,GiB 内存、macOS~26.6.2 和 Go~1.27.1。四个委员会进程，加上每个组织的四名成员和一个网关，共得到九个或十四个服务进程。延迟/容量试验主要使用内存的成员与委员会后端，以及采用 NoSync 的 bbolt 钱包；签名与原子状态更新保持启用。来源修复与批集成试验使用磁盘支持的委员会应用状态和 BlockStore。每次运行都从全新创世开始。当前的续花和回款试验使用最终的用户 FUEL。存储、配对背景和短时吞吐对照使用经授权的组织 FUEL 代付。归档的续花、运行区间和批集成系列使用经授权的费用代付。补充材料记录每个系列的构建与设置；批集成单独于较早的结构性测量进行报告。

已认证收款的延迟通常从钱包实际发出第一个 HTTP 请求开始，到收款方验证并原子地本地记录之后结束。资金/来源故障驱动包含少量发送前的构造，并在各自的系列内比较。公共完成与成员完成是观察端点，而不是内部提交时间戳。完成吞吐包含最终的后台排空。跨站点 ACK 计时使用发送方的单调时钟，并包含返回路径。

\subsection{无需逐跳结算的持续花费}
\label{sec:eval-continuation}

一条 100 跳的付款链到达最后一个已认证收款的中位时间为 158.846\,ms，而当相继的各跳等待公共确认时为 65.204\,s。三个钱包轮流转移 100 CAL，每笔付款都由其前驱的输出在线构造，并用各自的最终 FUEL 支付费用。每种模式重复三次，在九服务内存配置上共产生六次运行和 600 笔付款。两种模式都在最后一个已认证收款处结束；等待基线则在各跳\emph{之间}插入公共确认等待。委员会的提交、flush 和 gossip 设置分别为 250、10 和 10\,ms。在这些设置下，等待基线中的公共执行及其观察每跳耗时约 0.65\,s；认证续花移除了这一跳间等待。

图~\ref{fig:continuation} 给出六次整链耗时。快速运行耗时 158.492--159.905\,ms。全部 297 个快速模式的后继请求都消费前一个已认证的输出，并在其已认证收款之后、但在观察到其公共完成之前发出。一个单输入、单输出的 TXCer 为 779 字节；请求在第一跳为 1,979 字节，之后为 2,766 字节。对这一固定的交易形态，直接证据的大小在全部 100 跳中保持不变。这些观察表明，在线的相依花费不会在收款方的关键路径上插入公共确认等待。

\subsection{有资金支持的关闭与来源回款}
\label{sec:eval-liabilities}

\noindent\textbf{来源回款矩阵。}
九次运行使用种子 23、37 和 59，被扣留父交易的比例为 0\%、1\% 和 5\%。每次运行以每秒 20 个两跳单元的速率提供负载，持续 60\,s（1,200 个单元，2,400 笔付款），对应固定的 60,000-CAL 备付金，用户支付 FUEL，且没有增额。九服务部署使用磁盘支持的委员会应用状态和 BlockStore、内存的成员与网关，以及 NoSync 钱包。被扣留的父交易在其赔付已提交并已在全部四个副本上安装之后才被释放，因此每个被扣留的来源在 30\,s 的公共时间截止之后被赔付，并在其后执行。

全部 21,600 笔付款都已关闭。216 次赔付（每次 1\% 运行 12 次，每次 5\% 运行 60 次）之后都有回款。每次运行结束时，没有任何义务为 Open 或 Repaired，缺口为零，净 Spent 与 Reserved 为零，备付金恢复到 60,000\,CAL（表~\ref{tab:eval-audit}）。图~\ref{fig:reserve-recovery} 给出三次 5\% 运行的轨迹。采样到的最低备付金在 1\% 时为 59,800--59,900\,CAL，在 5\% 时为 59,600\,CAL；它反映的是驱动器的释放调度，而不是备付金规模的结果。正常子付款的运行级收款 P50 为 1.185--1.251\,ms，被扣留的父交易及其子付款分别为 1.171--1.207 和 1.176--1.190\,ms。截止时间之后，委员会提交被观察到的时间中位数为 1.003--1.254\,s，在全部四个副本上完成安装的时间为 1.257--1.761\,s（P95 最高 2.015\,s），其中包含 250-ms 的观察轮询。每笔正常付款花费 94 FUEL，每次修复增加 5；奖励、销毁和退款之和等于费用上限，Held 为零。

另外两个十四服务的控制实验区分了永久损失与延迟回款。当父交易始终不到达时，孙付款保留其 100 CAL，而负责的发行者的备付金保持低 100 CAL。当跨组织链以孙付款先到达时，中间来源关闭其自身的直接义务；根发行者被赔付的 100 CAL 在根之后执行时得到回款。两种情形中四个委员会的状态都一致。缺席父交易自身的费用与工作量预留可能保持未决。

\noindent\textbf{配对终态检验与干扰。}
三对十四服务运行按正常/修复、修复/正常、正常/修复的顺序，使用最初的来源回款构建，即批结果标签分离之前的构建，委员会与成员数据库在磁盘上，成员与钱包为 NoSync，每次以每秒 100 笔、持续 40\,s 发送 4,000 笔付款。与此同时，另有四个两跳演示，其来源要么被正常送达（正常运行），要么被扣留、在 30\,s 后被赔付并随后回款（修复运行）。六次运行中的 4,000 笔付款全部完成。各所有者角色最终持有的 CAL（30,000 与 830,000）以及两个备付金余额（$10^{12}$）在六次运行中完全一致，且修复运行记录了 400\,CAL 的赔付和 400\,CAL 的回收。正常与修复运行的收款 P50 分别为 1.070/1.127、1.089/1.108 和 1.083/1.097\,ms，P95 分别为 26.84/59.23、29.49/58.44 和 27.41/55.15\,ms；各次运行的完成速率为 97.2--97.8 笔/秒。最终分配与定理~\ref{thm:security-neutrality} 一致。收款 P50 比配对的正常值高 1.3--5.3\%，P95 为其 1.98--2.21 倍。因此在此配置下，并发的修复会影响收款的尾部；这些配对运行并不能分离出造成这一点的具体阶段。

\noindent\textbf{存储对照。}
在九服务配置（委员会在磁盘上，钱包为 NoSync）上，六次各 1,000 笔、每秒 100 笔的运行，仅成员存储不同。成员为 NoSync 时，收款 P50 为 1.002--1.035\,ms，P95 为 33.97--40.62\,ms，含排空完成 93.11--93.93 笔/秒。成员采用同步提交时，P50 为 43.19--51.85\,ms，P95 为 80.98--96.56\,ms，完成 90.99--92.72 笔/秒。全部付款均完成。这隔离出同步成员提交的代价；钱包仍为 NoSync，因此这是在第~\ref{sec:model} 节执行模型下的成员提交对照。

\subsection{在保持后继付款的同时共享修复工作}
\label{sec:eval-repair}

同块批处理共享表示工作，而不合并被赔付义务的身份。在 Windows amd64 与 Go~1.27.1 上的结构性微基准，把 $k\in\{1,2,4,8\}$ 个缺失输入放入同一个历史区块的同一个分片。在五次重复中，单项修复需要 $k$ 条命令和 $k$ 次分片适配，而一个批只用各一次；输入适配仍为 $k$ 次。在 $k=8$ 时，编码后的命令总字节从 127,336 降到 2,752（图~\ref{fig:repair-cost}）。

分散对照把批处理与紧凑编码区分开来。八个独立的目标区块仍需要八条命令和八次分片适配，而字节数从 30,008 降到 5,440。在 $k=1$ 时，两种格式都执行一次分片适配，编码分别为 3,751 与 680 字节。因此，紧凑字段解释了字节减少的一部分，而共享的区块表示解释了分片适配次数的减少。这些是编码后的命令大小，不是总网络流量或总密码学工作量。

跨层回归执行检查后继付款的保持与经济一致性。对于一笔使用 40/60 输入的付款及其已执行的后继付款，来源修复保持原始授权、输出身份和完整区块身份。在固定的前状态、时间和条目顺序下的比较，给出与逐项赔付相同的经济投影。重放同一原始公共历史会重现每个高度的应用哈希。这些回归还涉及跨分片故障、原子的批拒绝、重复命令和交错目标的安装。

一次归档的十四服务、磁盘支持的批集成运行，把四个实际缺失的来源合并为一个 1,568 字节的批，其 BatchID 在全部委员会副本上一致。处理完迟到父交易之后，以每秒 100 笔提供的后续 1,000 笔付款全部完成。收款 P50/P95 为 1.048/26.531\,ms；总完成时间为 11.120\,s，含观察与关闭。缺口与发件箱排空，委员会状态哈希一致。结构性测量隔离出表示成本；这次集成运行则检验修复以及部署服务之间后续付款的处理。

\subsection{跨注册组织的续花}
\label{sec:eval-network}

跨组织续花沿用同一条证书路径，其延迟反映所注入的通信距离。在补充材料标明的归档构建上，双组织套件在 24 次运行中完成 342,000 笔付款。两个钱包进程各持有 32 个身份，分布在 64 条通道上；每个组织提供每秒 50 笔付款。延迟比较使用十跳的同组织/跨组织负载，注入的 HTTP RTT 为 0、20 和 100\,ms，每个条件重复三次。每个代理方向增加一半的 RTT；组织内部的认证和委员会 P2P 不注入延迟。

对于共同的前 120-s 队列，三次运行级跨组 ACK P50 的中位数分别为 1.632、21.658 和 101.967\,ms；同组的值在 1.615--1.744\,ms 之间（图~\ref{fig:network}）。ACK 包含返回路径，但收款方可以在接受之后即发起其后继付款，而无需等待该 ACK 到达前一个发送方。在 100-ms 跨组 RTT 下，三次 300-s 运行各完成 30,000 笔付款；待决峰值为 106--110，并且在排空时没有持续的尾部增长。该实验在一台物理主机内隔离出 HTTP 路径延迟。

\noindent\textbf{当前构建的独立输入吞吐。}
三次各 30,000 笔付款的运行，在九服务内存配置、NoSync 钱包以及经授权的组织 FUEL 代付下，以每秒 2,000 笔为目标。成员进程使用 200\% 的 Go GC 目标和 16 个运行时处理器。全部付款完成，四个委员会状态一致。含排空的完成速率为 1,750.27、1,820.91 和 1,887.31 笔/秒，历时 15.9--17.1\,s，收款 P50 为 2.646、2.842 和 2.824\,ms，P95 为 47.9、49.1 和 48.0\,ms。驱动器记录到 6,551--7,570 笔付款必须等待一个快速收款准入名额，且 P95 的派发滞后为 179--229\,ms，因此提供负载并非均匀地维持在每秒 2,000 笔。这些是短时的完成测量；补充材料另行标明 150,000 笔付款系列的构建与时长。


在归档构建上，冗余的认证与已安装的证据，使服务在所规定的故障下得以维持。在每秒 200 笔的九次运行中，一名成员被延迟或暂停 30\,s，完成 216,000 笔付款。带有一份完整已安装副本的网关丢失对照显示，备用提交发生在 INSTALL 之后 2.503--2.508\,s；进展需要一份幸存的完整副本。冲突对照既不产生相互冲突的双重 QC，也不产生重复的本金/费用效果，而部分批准仍是容量成本。

补充材料保留冻结构建的映射和完整的逐次运行记录，包括多身份的 CPU/HTTP 成本，以及与积压分开的历史内存增长。其 2,048 个身份共用客户端，而不是代表 2,048 个进程。它还记录了一个单独配置的 LND 部署参考，其完成端点和持久化设置各不相同。
