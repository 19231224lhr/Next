\section{实现与评估}
\label{sec:evaluation}

我们评估依赖支付的延迟、备付金的关闭与偿还、证据驱动的源交易解决，以及历史表示的开销。随后，组织路径实验和负载实验刻画快速路径的运行条件。

\noindent\textbf{实现与版本。}
Go 实现使用原子状态 overlay、独立的区块跟随者，以及经过修改的 CometBFT v0.38.26，后者被用来强制执行完整区块身份和经授权的历史安装。门限 RSA 适配使用 CIRCL v1.6.5，由可信的离线分发者初始化。实验在一台 Mac Studio（M4 Max，16 个 CPU 核心，64\,GiB 内存，macOS~26.6.2，Go~1.27.1）上运行。四个委员会进程，加上每个组织的四个成员和一个网关，使这台主机上共有九个或十四个服务进程，且每次运行都从全新的创世状态开始。

结果来自三类版本，其标识见补充材料。\emph{基线版本}（提交 \texttt{d99ec92}）实现分层续花以及第~\ref{sec:protocol-execution} 节的记账；其赔付与历史表示一并提交。\emph{decision-first 版本}实现第~\ref{sec:protocol-resubmission} 节和第~\ref{sec:protocol-decision} 节的补交与独立的赔付决定。\emph{归档版本}提供交付门控、组织路径、运行范围、资本和批处理集成各系列，并在使用处加以标注。在一个版本上测得的数值，不用于另一个版本。

\noindent\textbf{测量约定。}
认证接收延迟从钱包第一次发出 HTTP 请求开始，到收款方验证并完成原子的本地记录之后结束。公共完成时间和成员完成时间是客户端对经认证执行的观察，包含轮询，不是内部提交时间戳；完成吞吐量包含最终的后台排空。延迟与容量试验主要使用内存中的成员与委员会后端，以及采用 NoSync 的 bbolt 钱包，同时启用签名和原子状态更新；恢复试验和 decision-first 试验使用落盘的委员会。续花试验与恢复试验使用最终的用户 FUEL，而存储、配对后台和短时吞吐的对照使用经授权的组织代付 FUEL。

\subsection{无需逐跳结算的连续花费}
\label{sec:eval-continuation}

我们把认证续花与在各跳之间等待公共执行进行比较。在基线版本上，100 跳链到达最后一次认证接收的中位耗时为 158.846\,ms，而每一跳都等待公共确认时为 65.204\,s。三个钱包轮流转账 100 CAL，每笔支付都由其前一笔的输出在线构造，并用自己的最终 FUEL 支付费用。每种模式重复三次，在九服务的内存配置上共得到六次运行、600 笔支付。两种模式都以最后一次认证接收为终点，等待模式则在各跳\emph{之间}增加一次公共确认。在委员会 commit、flush 和 gossip 设置分别为 250、10 和 10\,ms 时，公共执行及其观察每跳耗时约 0.65\,s。认证续花消除了收款方路径上的这段等待。

图~\ref{fig:continuation} 给出六次整链耗时。快速运行耗时 158.492--159.905\,ms。快速模式下全部 297 个后继请求，都消费其前一笔已认证的输出，并在该输出的认证接收之后、其公共完成被观察到之前发出。一个单输入、单输出的 TXCer 为 779 字节，请求在第一跳为 1,979 字节，之后为 2,766 字节。对于这种交易形态，直接证据的大小在全部 100 跳中保持不变，因为每个请求携带的是其直接输入的证书，而不是祖先链。

为检验这一优势是否依赖于内存中的成员存储，我们在九服务的落盘配置上，使用 NoSync 钱包和用户自付 FUEL，做了三组配对的 100 跳试验。这些试验仅在成员存储上不同（NoSync 或同步；顺序为 N/S、S/N、N/S），每组之后各跟一条同步的等待链。中位耗时分别是：NoSync 续花 681.127\,ms，同步续花 4.471\,s，同步等待 65.013\,s。因此在成员提交为同步时，认证续花仍比等待快 14.5 倍。全部 900 笔支付完成，且各委员会状态一致。

在归档的交付门控版本上，认证之后有一个投递门控，它等待三名成员 INSTALL 完整材料，或等待经认证的公共执行成功。该门控不收集第二个签名法定人数；改为立即交付会缩短续花。在每秒 200 笔支付、持续 30\,s 的条件下，每种模式三次配对运行各完成 6,000 笔支付，运行级接收 P50 的中位数从有门控时的 2.167\,ms 降到 1.300\,ms（下降 40.0\%）。另外的 100 跳试验从 287.983 降到 200.356\,ms（下降 30.43\%）。授权不变，补充材料列出了配对运行。

\subsection{有资金支撑的关闭与偿还}
\label{sec:eval-liabilities}

本实验检验赔付是否保持后继支付不变，以及每次赔付是否在其源交易随后执行时恰好偿还一次。

\noindent\textbf{赔付与偿还矩阵（基线版本）。}
九次运行使用随机种子 23、37 和 59，被扣留父交易的比例分别为 0\%、1\% 和 5\%。每次运行按每秒 20 个两跳单元的速率提供负载，持续 60\,s（1,200 个单元，2,400 笔支付），对应一份固定的 60,000-CAL 备付金，使用用户自付 FUEL 且不充值。九服务部署使用落盘的委员会应用状态和 BlockStore，成员和网关在内存中，钱包为 NoSync。驱动程序只有在每个被扣留父交易的赔付已在全部四个副本上提交并完成安装之后，才释放该父交易，所以每个被扣留的源交易都在 30-s 公共时间期限之后被赔付，并在其后执行。

全部 21,600 笔支付都完成关闭。216 次赔付（1\% 的每次运行 12 次，5\% 的每次运行 60 次）各自之后都有偿还。每次运行结束时，没有义务处于 Open 或 Repaired，缺口为零，净 Spent 和 Reserved 为零，备付金回到 60,000\,CAL（表~\ref{tab:eval-audit}）。所采样到的最低备付金在 1\% 时为 59,800--59,900\,CAL，在 5\% 时为 59,600\,CAL。它反映的是驱动程序的释放节奏，不是备付金规模的结果，补充材料绘出了三次 5\% 运行的轨迹。正常子支付的运行级接收 P50 为 1.185--1.251\,ms。从期限起算，委员会提交（在该版本中它承载历史表示）的观察时间中位数为 1.003--1.254\,s，全部四个副本上完成修订区块体物理安装的时间中位数为 1.257--1.761\,s（P95 最高 2.015\,s）；两者都包含 250-ms 的观察轮询。每笔正常支付花费 94 FUEL，每次赔付增加 5，奖励、销毁与退款之和等于费用上限，Held 为零。

账本层面的回归测试直接覆盖到达顺序：四跳链的全部 24 种到达顺序，在有到期赔付与无到期赔付两种情形下，各取三种签发组织序列，共得到 144 条轨迹；另有 48 条拆分--合并轨迹，在两种赔付模式下，改变一个 40/60 拆分、两条分支及其合并的全部到达顺序。192 条轨迹中的每一步都保持独立计算的资产投影守恒。每条轨迹结束时，各签发组织的备付金恢复，Spent 与 Reserved 为零，$\mathsf{Paid}=\mathsf{Rec}$，已消费的输入仍保持已消费。

两个十四服务的对照实验区分永久损失与延迟偿还。父交易始终不到达时，孙支付保留其 100 CAL，而负责的签发组织的备付金仍然低 100 CAL。当跨组织链以孙支付最先到达的顺序到达时，中间源交易关闭其自己的直接义务，根签发组织被赔付的 100 CAL 在根交易其后执行时得到偿还。两种情况下四个委员会状态一致，缺席的父交易自身的费用和工作预留可能保持未清偿。

三组配对的十四服务运行使用基线版本的初始构建（在批处理结果标签分离之前），每次 4,000 笔支付、速率 100 笔/秒，其正常运行与扣留源交易运行最终的所有者持有和备付金余额完全一致，与定理~\ref{thm:security-neutrality} 一致。并发赔付使接收 P95 升高为 1.98--2.21 倍，这些配对不能区分造成这一升高的具体环节。

一个使用 NoSync 钱包的存储对照把成员提交单独隔离出来：NoSync 成员时接收 P50 为 1.0\,ms，同步提交时为 43--52\,ms。

早期版本的资本系列（每个条件一次运行、没有赔付）表明，10,800--19,700\,CAL 的外部新增，足以维持从 3,600-CAL 起步、各含 6,000 个两跳单元的 300-s 运行，而固定 3,600-CAL 的对照只关闭了 6,000 个单元中的 46 个。

\subsection{补交、决定与历史表示}
\label{sec:eval-repair}

我们检验原签署者能否送达被扣留的源交易，适配不可用时赔付与偿还能否继续进行，以及这些机制在普通支付路径上的代价。

\noindent\textbf{设置。}
decision-first 版本运行于十四服务配置，使用全新的创世状态，每轮 450 个初始输出，落盘的委员会，成员为默认的 NoSync 模式，flush/gossip 设置为 10\,ms。用户支付 FUEL，所有签名、金额和消费检查均保持开启。九次功能运行使用初始实现快照，下文的普通路径运行使用最终快照（见补充材料）。一轮功能运行先认证一笔父支付，在完整 QC 形成之后阻止其原发布者提交或 INSTALL 它，再让一笔子支付花费该父支付的 TXCer。原签署者持有其批准，但不持有完整 QC。共运行三种处理，每种三轮：\emph{补交}（按设计运行的版本）、\emph{对照}（关闭自动补交）和\emph{暂停}（关闭补交，并由一个标记使全部四名委员会成员的适配端点暂停，而共识、决定和普通支付继续）。计时从子支付的钱包 HTTP 发送开始。快速接收在钱包验证并本地记录时结束，公共事件是带轮询的客户端观察。这些两跳演示使用默认钱包模式，因此其接收时间不能与下文 NoSync 压力运行的接收时间相比较。

\noindent\textbf{基于公共证书的补交。}
在全部三轮中，子支付的快速接收耗时为 13.91--13.94\,ms。子支付所在的区块在 1.414、1.990 和 1.440\,s 被观察到，被扣留的源交易随后在 2.014、2.565 和 2.039\,s 完成公共执行，比子支付晚 575--600\,ms，且驱动程序没有提交原支付（图~\ref{fig:c3-resolution}a）。每次审计都显示有一个义务被履行（Fulfilled）、没有赔付，且签发组织的备付金未被动用。收款方在约 14\,ms 之后即可继续，而约 2\,s 是后台源交易被观察到的完成时间。这些时间间隔是轮询粒度下的客户端观察，不是协议延迟的上界，两次公共事件之间的 575--600\,ms 也未进一步分解。

\noindent\textbf{无需适配的赔付。}
关闭补交之后，源交易始终缺席，义务在每一轮中都越过其 30-s 期限。其后的决定在义务仍处于 Open 时执行。适配可用时，赔付在 35.839、35.888 和 35.864\,s 被观察到。驱动程序随后提交迟到的源交易，签发组织的 100\,CAL 得到偿还。这 35.8\,s 包含 30-s 的义务期、公共时钟的推进、后台调度和轮询，不是密码学计算的时间。历史表示在赔付之后 1.13--1.16\,s 完成物化（36.994、37.021 和 37.019\,s）。

全部四个适配服务暂停时，赔付在 35.837、35.814 和 35.891\,s 被观察到（图~\ref{fig:c3-resolution}b）。驱动程序同样提交迟到的源交易，脚本仅在全部四个委员会状态都显示义务已偿还、且历史表示既未提交也未物化之后，才解除暂停。随后历史表示完成提交与物化，观察时间为 42.748、42.736 和 42.798\,s，其中包含暂停所持续的时间。

对照实验单独隔离出补交这一步，暂停则单独隔离出对适配的依赖。所观察到的先后顺序表明，在 decision-first 版本中，经济关闭与偿还的进行独立于适配。

在全部六个对照与暂停轮次中，签发组织支付 100\,CAL 并得到 100\,CAL 的偿还，没有新增用户输出，备付金得以恢复。暂停之后的历史表示既不再扣减，也不再记入。24 项委员会观察（六轮、四名成员）确认历史表示已提交并物化、区块体已改变、身份检查成立；完整区块身份由物化检查和共识集成测试验证（见补充材料）。全部九次功能运行都通过审计（四个委员会成员的状态哈希相同、缺口为零、支付已关闭、outbox 已排空），补交与对照两种处理还各自带有三次各 300 笔普通支付的运行，全部完成。

\noindent\textbf{普通路径的开销。}
六次运行比较位于分支基点（提交 \texttt{0e7bae5}）的版本与最终的 decision-first 快照，顺序为 AB、BA、AB。每次以 100 笔/秒发送 300 笔支付，并发快速请求 64 个，未完成请求 256 个。取各次运行统计量的中位数，接收 P50 在改动前为 1.096\,ms、改动后为 1.071\,ms，接收 P95 为 27.441 和 30.530\,ms，区块观察 P50 为 1,101 和 1,104\,ms，包含全部公共确认与成员跟随的完成时间为 3.815 和 3.845\,s。各次运行的范围相互重叠：P50 为 1.052--1.112 对 1.045--1.073\,ms，P95 为 17.951--39.945 对 22.084--33.744\,ms，完成时间为 3.805--3.871 对 3.791--4.000\,s，全部 1,800 笔支付均完成。这些是短时输入负载下的普通路径测量。它们既不能证明零开销，也不能给出吞吐上限；而且普通的最终输出不携带输入证书，所以这些运行没有检验大量待决支付所保留证书的存储。

\noindent\textbf{历史表示的批处理。}
我们在基线代码线上对历史表示命令做了结构性微基准测试（Windows amd64，Go~1.27.1），把 $k\in\{1,2,4,8\}$ 个缺失输入放在同一个历史区块的同一个分片中。五次重复中，单条命令需要 $k$ 条命令和 $k$ 次分片适配，而一个批处理只需各一次，输入适配仍为 $k$ 次。在 $k=8$ 时，编码命令总字节数从 127,336 降到 2,752。这些计数来自早期的耦合命令，它同时还承载经济步骤。decision-first 版本为每个已决定的输出增加一条 88 字节的决定命令，上述计数并不包含它，所以它们并不给出当前协议的命令流量总量。另一个分散对照把八个输入放在八个独立的目标区块中，仍需要八条命令和八次分片适配，而字节数从 30,008 降到 5,440，所以紧凑字段解释了一部分下降，共享的区块表示则解释了适配次数的减少。这些是编码后的命令大小，不是网络流量或密码学计算量；补充材料有对应的图和一次归档的批处理集成运行。

一项使用真实门限 RSA 的回归测试，对由 1、2、4 和 8 个输入组成、跨越两个真实分片的一组已决定输入，分别从原始区块出发：作为一个批处理应用；按顺序逐条应用；以及按逆序、以一个、两个和三个为一组应用。每种方式最终得到相同的最终区块体和分片 opening，而命令历史和修订号不同。这是对收敛性质的有限检查，不是网络测量。

\subsection{跨注册组织的续花}
\label{sec:eval-network}

为测量通信距离的影响，我们在补充材料所记录的一个归档版本上运行了双组织套件：两个钱包进程各持 32 个身份，经 64 个 lane 发送，每个组织提供 50 笔/秒，24 次运行共完成 342,000 笔支付。延迟比较使用十跳的同组织与跨组织负载，注入的 HTTP RTT 为 0、20 和 100\,ms，每个条件重复三次。每个代理方向增加一半的 RTT，组织内部认证和委员会 P2P 不注入延迟。

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{network.pdf}
  \caption{ACK 延迟（ms）与注入的跨站点 HTTP RTT（ms）的关系。每个点是前 120-s 样本组的三个运行级 P50 的中位数；误差条跨越这些 P50 的最小值与最大值。总提供速率为 100 笔/秒。委员会 P2P 未加延迟。}
  \label{fig:network}
\end{figure}

对共同的前 120-s 样本组，三个运行级跨组 ACK P50 的中位数依次为 1.632、21.658 和 101.967\,ms，同组数值范围为 1.615--1.744\,ms（图~\ref{fig:network}）。跨组 ACK P50 随注入 RTT 变化，测得的超出部分为 1.6--2.0\,ms。ACK 包含返回路径，但收款方可以在接受之后即刻发起其后继交易，无需等待该 ACK 到达前一个发送方。在 100-ms 跨组 RTT 下，三次 300-s 运行各完成 30,000 笔支付；待处理峰值为 106--110，并能排空，没有持续的尾部增长。该实验在一台物理主机内隔离出 HTTP 路径延迟。

\subsection{运行容量与服务可用性}
\label{sec:eval-operating}

\noindent\textbf{独立输入吞吐（基线版本）。}
三次各 30,000 笔支付的运行以 2,000 笔/秒为目标，使用九服务的内存配置、NoSync 钱包和经授权的组织代付 FUEL。成员进程使用 200\% 的 Go GC 目标和 16 个运行时处理器。全部支付完成，四个委员会状态一致。含排空的完成速率为 1,750.27、1,820.91 和 1,887.31 笔/秒，历时 15.9--17.1\,s，接收 P50 为 2.646、2.842 和 2.824\,ms，P95 为 47.9、49.1 和 48.0\,ms。驱动程序记录到有 6,551--7,570 笔支付需要等待快速接收准入名额，P95 派发滞后为 179--229\,ms，所以提供的负载并不是均匀的 2,000 笔/秒。这些是基线版本上的短时完成测量，没有在 decision-first 版本上重新测量；该版本在普通支付上的开销由上文的六次运行对比检验。补充材料说明了 150,000 笔支付系列所用的版本和时长。

在归档版本上，冗余认证与已 INSTALL 的证据在所述故障下维持服务。九次每秒 200 笔的运行完成 216,000 笔支付，其间有一个成员被延迟或暂停 30\,s。网关丢失对照中，一名成员持有经 INSTALL 复制的完整材料，备用提交在 INSTALL 之后 2.503--2.508\,s 出现。冲突对照既没有出现相互冲突的双 QC，也没有重复的本金或费用效果，而部分批准仍然是一种额度代价。

补充材料第~S2 节的多身份测量报告每笔支付的 CPU 和 HTTP 负载开销；2,048 个身份共享客户端。历史内存增长与积压分别报告。该节还给出 LND regtest 参照，其完成事件、持久化设置和负载并发度与 Next 的测量不同。
