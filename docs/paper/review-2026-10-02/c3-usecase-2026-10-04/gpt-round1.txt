\noindent\textbf{Consumer, motivation, and alternatives.}
Consider a prospective local archival inspector operated by a guarantor
on an honest replica that has executed prefix $H$. A case record
contains the original coordinates $(h,j,k)$ and complete BlockID. The
operator revisits that record after compensation to inspect the
historical reserve debit and current repayment state, keeping the case
linked to the original block. This scenario is proposed, not an observed
customer requirement.

Original history plus a decision index already answers this question.
An ordinary materialized funding view can expose the same reserve debit
and status, carry the original BlockID as a source pointer, and retain
the original body for verification. Both alternatives preserve original
references and permit auditing without successor re-signing or
re-execution. A source pointer, however, does not by itself make a
projection's bytes a block body compatible with the original commitments.
A view caching C3's authorized bytes inherits C3 rather than avoiding it.

For a revision-aware inspector that also consumes block-shaped
representations, C3 offers an additional operation. Within one read
transaction on $V_H$, it selects the authorized body, checks its exact
committed Task, reconstructs the part-set header using the supplied
openings, compares both components of the original BlockID, and decodes
\texttt{ReserveFunding} from that same body. The body being inspected,
rather than merely an associated original, satisfies the original
commitments. This property is optional: an inspector accepting a separate
annotated view does not need it.

Authorization still comes from successfully executed decisions and
representation commands in $V_H$, not from BlockID equality or a
chameleon-hash equation. Prefix, revision, and Task distinguish
representations sharing one BlockID. The permanent decision and
obligation remain necessary; repayment changes the economic state
without erasing the historical advance. Revised bodies are not
re-executed as original payments.

The existing \texttt{TestHistoricalExportConsumer} illustrates this
local operation. It does not establish deployed demand, compatibility
with unmodified clients, or lower integration effort than ordinary
materialization. The evaluation therefore separates representation
compatibility, authorization from executed state, and measured costs.

\noindent\textbf{Functional completion criterion.}
A minimal comparison should supply A, M, and B to the same local
inspection routine at a fixed prefix and repeat after repayment.
The economic answers should agree on coordinates, transaction identity,
amount, reserve debit, decision, and obligation state.
The routine should separately report whether the reserve reference
occurs in the body checked against the original complete BlockID,
and whether that representation is authorized in the selected prefix.
These checks must use actual bytes, openings, and executed records,
not strategy-name predicates. A source pointer must not be relabeled
as proof that a derived body satisfies the original commitments.
Any alternative satisfying the same checks must be accepted.
The observed results should determine the final comparison;
neither failure of M nor superiority of B is presumed.
This check establishes neither deployed demand nor a performance result.

复用同一 fixture、同一读事务。 A 使用已有原块＋索引路径；M 从 A 的决定和义务记录构造测试内物化元组，保留原坐标和 BlockID 指针，不借用 B 的修订正文；B 使用现有 Canonical／Task 路径。
