# 快速支付安全论证：论文调研与建议路线

快速支付论文需要回答“用户为什么可以在最终结算前放心接受并继续付款”。对本项目，合适的下一步是给出明确模型、核心安全性质及协议级数学论证；不必一开始就把整个 Go 项目交给定理证明器验证。现有实验提供实现与性能证据，不能代替对所有允许执行次序的安全推理。

研究重点保持为低延迟、可连续续花、无需用户逐对建立支付通道。本文只整理相关工作和待论证事项，**没有完成本系统的安全证明，没有新增模型或修改协议**。

调研日期：2026-09-25。选取七项直接相关的支付研究，以及一项变色龙哈希区块链基础工作；重点阅读安全定义、证明章节和限制。主体为 2023–2025 年工作，保留 FastPay、Snappy 两项 2020 年直接先例及 2017 年密码学基础。这是围绕本项目的定向调研，不是整个领域的穷尽综述。预印本与正式发表状态分别标注。

## 论文采用的论证方式

### 数学论证与机器验证

“有形式化安全论证”和“生产代码经过机器验证”不是同一件事。协议级数学证明先定义攻击者、状态和合法操作，再说明安全性质对允许的执行成立。有限模型检查用工具枚举给定范围中的状态和消息次序；它可以发现很隐蔽的反例，但没有反例不代表任意规模均安全。机器辅助证明则让验证器检查形式化模型或指定程序的证明义务，结论仍受模型与假设限制。

与我们最接近的快速支付论文，常见路线是协议模型与数学证明，而不是整套生产实现的机器验证。FastPay 将偿付能力、兑换和可用性分开；Snappy 直接讨论商户能否拿到承诺金额。二者都把资金与故障条件放进论证，说明“签名是真的”不足以单独支持完整支付安全。[Baudet 等，FastPay](https://arxiv.org/pdf/2003.11506)；[Mavroudis 等，Snappy](https://www.ndss-symposium.org/wp-content/uploads/2020/02/24049-paper.pdf)。

| 论文与版本 | 安全论证及阅读位置 | 对本项目的参考价值 |
| --- | --- | --- |
| **FastPay，AFT 2020** | 第 3 节模型、第 5 节与附录 A；偿付能力定理、兑换与可用性命题及数学证明 | 把凭证权利、真实资金和进度条件分开 |
| **Snappy，NDSS 2020** | 第 V 节、定理 1；在兼容付款状态及足额抵押等条件下论证商户取得全额 | 担保支付应说明正常与追偿路径都如何保障收款人 |
| **Zef，WPES 2023**，另有 2022 预印本 | 第 4–5 节，尤其 “Safety of the protocol”；法定集合、spent 集合及可花价值不增加的推理 | 可以采用状态不变量组织论证；交易里的 NIZK 不等于整个协议已被机器证明 |
| **Sui Lutris，CCS 2024** | 第 5 节 Security Proofs；包括 Client-Perceived Safety 和 No Conflicts | 必须明确用户拿到哪一种证书后获得什么保证，不能混同交易证书与效果证书 |

上表各项原文：[FastPay](https://arxiv.org/pdf/2003.11506)、[Snappy](https://www.ndss-symposium.org/wp-content/uploads/2020/02/24049-paper.pdf)、[Zef](https://sonnino.com/papers/zef.pdf)、[Sui Lutris](https://sonnino.com/papers/sui-lutris.pdf)、[Stingray](https://arxiv.org/html/2501.06531v1)、[Why3 Lightning](https://arxiv.org/html/2503.07200v1)、[TLA+ Lightning](https://arxiv.org/html/2505.15568v1)。Zef 发表信息见[作者机构记录](https://discovery.ucl.ac.uk/id/eprint/10198601/)；它是 WPES 论文，不应写成 CCS 主会论文。

这些研究也提示了“安全”的范围差异：有的重点保护资金，有的进一步保证无冲突和条件活性。因此不能只比较“有没有形式化证明”，还要比较证明对象、攻击者和终态。2025 年 TLA+ Lightning 版本替代其 2023 年预印本，不应当作两份独立证据；Why3 工作也不能被表述为 LND 或 Core Lightning 已整体得到机器验证。

### 与便捷支付定位的关系

“无需付款双方预建通道”是相对通道类方案的便利性优势，但不是我们相对所有快速支付项目独有的特性。FastPay、Zef 也不以逐对通道建立和路径流动性作为每次付款的前提。我们更合适的候选贡献，是将快速可续花的输出权利、直接发行组织担保和后台责任处置结合，并展示用户不必等待前置交易结算的实际效果。[FastPay](https://arxiv.org/pdf/2003.11506)；[Zef](https://sonnino.com/papers/zef.pdf)。

这一定位仍需要承认组织备付、用户费用与初始可信组织信息等前提。“即插即用”宜解释为避免用户管理双边通道及路由流动性，而不是零资金、零配置，或不修改现有公链即可部署。速度优势应限定在已有对照的环境和到账口径；本文没有得出“比所有同类方案都快”的结论。

### 历史修订的额外责任

变色龙哈希提供受控修改后保持承诺值的密码学机制，不自动保证修改的业务合法性。基础论文专门讨论授权编辑、密钥管理和公开碰撞后的安全问题；不能随便选一个支持制造碰撞的哈希就认为系统安全。[Ateniese 等，EuroS&P 2017](https://eprint.iacr.org/2016/757)，重点第 3–4 节；[作者机构全文](https://iris.uniroma1.it/retrieve/e3835319-b7b7-15e8-e053-a505fe0a3de9/Venturi_redactable_2017.pdf)。

对本项目的推论是：需要分别说明“谁可以批准修订”“只能修改哪里”“赔付确实扣除了哪个账户的资金”“原输出权利为什么不变”。还要核对所选密码学实例、门限密钥和分片承诺满足所引用的假设。保持 BlockID 不变本身，不等于任意新内容都获得原 Commit 的授权；不能把修订后协议的全部安全性直接归结为原版 CometBFT 已有结论。

## 本系统的最小论证范围

### 以用户权利为中心

建议把总目标表述为：在明确的故障、资金和信息可得条件下，诚实收款钱包按规则接受输出与 TXCer 后，其支付权利不会被冲突交易、前置交易缺失或合法赔付修订剥夺；满足进度条件时，该权利可以继续支付并得到结算处理。

这是**待建立的目标**，不是本次已经证明的定理。合法消费后原输出退出可花状态属于正常转账，不属于权利被剥夺；协议明确的费用也应从本金损失中区分。

| 待论证事项 | 通俗问题 | 必须覆盖的边界 |
| --- | --- | --- |
| 凭证与授权绑定 | 这张凭证真的是给这个人、这笔金额的吗？ | 交易身份、输出索引、金额、资产、所有者、消费组织、网络与规则配置；篡改与重放 |
| 唯一消费 | 同一笔钱能否同时付给两个人？ | 组织内冲突、跨组织路由、最终 UTXO 与未最终凭证消费路径之间的衔接；若纳入散户路径也必须覆盖 |
| 预算覆盖与核销 | 所有已经承诺的责任有钱覆盖吗？同一额度会不会被退两次？ | 成员重叠权限、Worker 分配、局部签票、累计核销、实际支出残余；外部充值不得算作内部循环回收 |
| 直接责任与资金闭合 | 前置永不到达，赔付究竟补了什么？ | 责任唯一、正常到账与超时赔付竞态、重复投递、迟到来源、真实扣款、后继不回滚且不重复增值 |
| 受限修订一致性 | 换了输入后，各节点为什么还认同同一结果？ | 不可变输出与用户授权、修订审批、普通内容摘要、版本与输入槽绑定、分片和重放的一致性 |
| 条件活性 | 什么条件下已经收到的付款最终能完成？ | 完整证据可得、实际诚实补投者、网络最终送达、委员会进度、充足费用与签署资源；不能由“不双花”直接推出“不堵塞” |

只证明第一轮三票不会对同一输入产生冲突证书，无法覆盖整张表。另一方面，论证这些性质并不要求交易再多跑一轮，也不要求委员会恢复逐笔通知工作。它们主要是对已有规则的研究与整理。

### 假设与证明的分界

可以明确采用成熟密码学原语的安全假设，以及委员会在故障阈值内对命令顺序达成一致的抽象接口。固定四成员、三票门槛时，组织与委员会的故障边界要分别写清楚。引用底层结论必须检查我们使用它的方式，特别是历史修订是否改变了其承诺绑定条件。

不能把自己需要论证的性质写成假设，例如“所有 TXCer 必定有资金”“不同组织自然不会双花”“赔付不改变任何账务”。这些正是协议需要建立的保证。真实外部注资可以作为环境输入，但不能假定无限补钱后再声称有限备付永远安全或自动循环。

当前设计允许赔付后合法父交易迟到，原输出所有者仍可取得迟到来源，组织已经发生的赔付损失不恢复。因此不能将待证明性质简单写成“正常来源与赔付绝不同时出现”。应分别核对同一义务不重复赔付、迟到交易真实消耗父输入、输出实例身份不混淆、后继不重复加款，以及全局价值核算。允许有明确出资人的价值转移，不等于允许无资金依据的增发；现有策略是否满足上述性质，仍待正式论证。

实验内存模式可以对应“不丢失诚实成员状态”的模型，不必扩展为产品级崩溃恢复。若成员遗忘已签记录后还用原密钥继续签票，就可能超出该模型；论文应明确排除这种恢复方式，而不是用低延迟实验替它背书。网络延迟与消息乱序下的安全，与最终需要网络恢复才能继续推进的活性，也要分别说明。

### 已有实验带来的约束

[E3](../experiments/liability-repair-2026-09-23/README.md) 已覆盖前置缺失、赔付后迟到、真实历史输入修订和一些重放夹具，为直接责任与修订论证提供例子；它明确未证明一般拜占庭安全及轻客户端最新修订验证。不能因为四个节点在实验中结果一致，就认定任意恶意行为下也一致。

[E4](../experiments/fault-conflict-2026-09-23/README.md) 记录了 79 条局部批准残留，并在 B1 中观察到网关暂停十秒内没有自主公共完成。这不等于凭证无效，也不等于永久不能结算；它说明“不会双花”“不会丢钱”和“当前一定有人继续投递”是不同性质。因此暂时不宜承诺任意冲突下永久可用，或一轮交付后即使所有完整证据持有者离线也必定自动结算。

## 建议的后续路线

已将上述原文发现及项目边界提交给[侧边栏 GPT](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)讨论两轮。其首轮评审支持以接收权利、唯一消费、资金安全、受限修订四项安全性质及一项条件活性组织论文。我进一步要求区分安全与最终完成，并修正其对赔付后迟到来源的过强表述；第二轮回复接受这两项修正，并确认全局资金一致性仍属于待证明事项。此处将六项证明义务作为四项安全性质与条件活性的展开，讨论本身不构成学术证明或同行评审。

数学论证、有限模型检查和机器证明也不是简单的强弱排名；一般性的手工定理可能覆盖比有限机器检查更广的执行范围，关键是具体模型、假设和可检查性。

最小可行路线是先固定论文中的协议版本和支付完成定义，整理组织签发、直接输入消费、义务终结、赔付修订、额度回收这几个状态转移，再围绕上表组织数学论证。主文解释关键性质和假设，详细论证可放附录。是否能形成完整证明，须以实际推导为准；不能预先承诺只用三票交集就能全部证明。

如果继续使用工具，优先考虑小范围 TLA+/TLC 模型检查并发次序：冲突申请、重复核销、来源到账与赔付同块、INSTALL 晚到和公共终态交错。它适合发现状态机反例；密码学安全另用原语假设及论证处理。初版不必验证整个 Go 程序，也不必一口气引入 Lean、Coq、Why3 等多套工具。

最终论文应把三类证据明确分工：实验回答实现效果及所测故障表现，数学论证回答模型内安全为什么成立，有限模型检查辅助寻找复杂交错中的遗漏。对本项目，最值得投入的是让“收到即可继续付款”有完整的权利与资金解释，而不是再增加扩容实验。
