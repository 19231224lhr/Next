## 1. 结论与优先级

当前核心快速路径具备论证认证绑定、防双花、直接责任唯一关闭和受限修订的基础；本轮没有证实这些路径上的冲突有效 QC 或重复赔付反例。但发现了**补资账户角色重叠时，当前代码实际接受的管理转移会破坏资金守恒或备付覆盖**。因此不能声称“所有通过初始化检查的配置均安全”。

| 结论 | 证据等级 | 后续动作 |
| --- | --- | --- |
| 三票交叠、签票前原子占用支持同实例唯一消费 | 源码支持的条件论证 | 固定身份、路由和不回滚假设后形式化 |
| 未公开 QC 也受成员预算约束 | 动态覆盖证明草图 | 验证批准、累计释放、赔付和补资的归纳关系 |
| 补资账户与备付账户重叠可破坏经济不变量 | **本地真实执行已复现，尚未修复** | 优先补齐账户角色隔离与管理转移检查 |
| 部分批准、未消费 Promise 可以长期占用额度 | 已确认的活性限制 | 不宣称任意请求都最终释放或永不阻塞 |
| 赔付后合法迟到会保留组织损失，并产生实例 1 | 源码及既有测试支持 | 区分账务守恒与抗战略延迟能力 |
| 门限适配与历史重放需要独立安全论证 | 实现与测试支持，密码学证明未完成 | 单独证明允许改写范围及原始执行语义 |

## 2. 分析模型

研究对象是当前启用 DirectPolicy 的 wire 4 网络。允许恶意付款人、恶意网关、重复／乱序／延迟消息，以及每组织最多一名拜占庭成员；委员会独立满足固定验证者集合的 BFT 故障上限。

安全前提包括：可信配置、正确密钥与不可伪造签名；诚实成员不丢失或回滚已批准状态；同一输入实例具有唯一消费路由；委员会执行确定且提交结果可信；整数与规范编码检查成立；密码学承诺满足所需性质。配置中的“补资账户与备付账户角色隔离”目前**不是已完整实现的校验**，见第 4 节。

内存与默认成员 NoSync 模式仅提供运行期间的原子状态，不提供掉电耐久保证。一个丢失签署记录后继续用同一身份批准的节点，不能继续按本模型的诚实成员计数。此限制与实验从全新创世启动的用途一致，不需要为本轮分析新增复杂恢复系统。

活性另外需要最终可达的网络、足够诚实响应者、公共交易可被调度、跟块推进和可用额度。安全不依赖固定消息延迟上界，有限时间完成则不能脱离这些条件。

## 3. 核心安全性质与论证草图

### 3.1 认证绑定与唯一消费

TXCer 签名绑定 Summary，Summary 绑定交易身份、全部输出摘要／金额、配置及授权向量。钱包必须验证输出正文和对应索引。有效组织签名不能授权另一所有者、另一金额或另一网络的输出。

对同一 `SpendKey=(OutputID, Instance)`，两个三票集合至少相交两人；在四成员至多一恶意的条件下，至少一名交叠成员诚实。`ApproveDirectBytes` 在本地原子事务中检查 Candidate／Consumed 并占用输入与资源，事务成功后才签票。该诚实成员不能再签冲突事实，因而两个冲突消费不能同时取得有效三票。

这个论证依赖固定消费路由和不遗忘状态，不能只写“三票天然防双花”。未最终输入与最终输入使用同一实例消费键；跨组织改变的是新输出路由，既有输入仍由其指定组织裁决。

公共执行另在同一转移中检查唯一消费、登记缺口、产生输出及费用变化；失败不会留下半笔修改。`CheckTx` 接收或 HTTP 202 不作为消费成立或额度释放的证据。

源码：[成员批准](../../internal/member/direct.go)、[交易及证书验证](../../protocol/v3.go)、[公共执行](../../internal/rules/direct.go)。

### 3.2 动态 CAL 覆盖：把未公开 QC 包含在内

以下是每个 Grant 的证明草图，**不是仅靠公共 Reserved 检查推出的结论**。

令当前授权为 `B`，每成员总份额为 `s(B)=floor(2B/3)`。对成员 m 的每项原子成功批准 a，定义实际未恢复占用 `r(m,a)=cap(a)−applied(m,a)`。包含尚未签出、仅有局部票及已经形成 QC 的批准，按事实去重。成员所有 Worker 合计应保持：

`L(m)=Σ r(m,a) ≤ s(B)`。

令 C 为该 Grant 下已形成的有效 QC 集合，包括未公开和仅由用户持有的 QC。对 c 定义：

`w(c)=cap(c)`，若 c 自己的交易尚未 Settled；否则 `w(c)=Paid(c)`。

未成立交易仍保留全部本地占用；成立后恢复 `cap−Paid`，实际损失保留。连续认证跟块使滞后成员至多多占用而不提前恢复，因此每个诚实签署者应满足 `r(m,c)≥w(c)`。

取固定三名诚实成员 H；即使四人都诚实，也可任取三人。每个三票 QC 至少包含 H 中两人，故：

```text
2 × Σ(c∈C) w(c)
  ≤ Σ(m∈H) Σ(c∈C 且 m 签过 c) r(m,c)
  ≤ Σ(m∈H) L(m)
  ≤ 3 × floor(2B/3)
  ≤ 2B
```

因此 `Σ w(c)≤B`。未公开 QC 不会逃出这个计数；局部批准只增加右侧占用、降低可用容量，不能强行纳入“至少两名诚实签署者”的左侧。历史已经完全履行且无损失的 QC 权重为零，不能对全部历史批准永久累计原 cap。

成立前已经赔付的部分包含在 cap 中，成立后只保留 Paid，不能再重复加一次损失。部分未消费 Promise 的潜在责任也由未成立证书的全 cap 覆盖。增量补资后，成员仅按新旧 `s(B)` 差值补充；滞后成员使用更小份额。

还须形式化证明三个连接条件：①每项签票都有原子成功的占用；②累计恢复单调且只属于同一批准；③自身 Settled 后不会再发生该证书的新赔付。第三点的代码理由是：自身交易成立会创建全部输出，后继消费走最终来源分支；已赔输出的旧实例 0 保持已消费，迟到实例 1 不能凭旧证书消费。

**该引理首先约束授权风险，不自动保证真实账户有钱。** 多 Grant 还需按实际账户汇总初始备付，排除重复资金分配及从已承诺备付中抽走资金。当前补资反例正是这层连接条件的缺口。

源码：[份额函数](../../protocol/amount.go)、[批准占用](../../internal/member/direct.go)、[累计恢复](../../internal/member/blocks.go)、[增量补资](../../internal/rules/reserve.go)。

### 3.3 责任、赔付与迟到来源

缺失输入对应唯一 DirectObligation；只有 Open 且到期的义务可以赔付。新块原子完成实际扣款、责任关闭、费用推进、修订授权和待办，重复提交不能再扣一次。父交易先到与赔付先到由公共顺序决定。

赔付补的是已经执行的子交易输入缺口，**赔付瞬间不新增子收款余额**。随后合法父交易必须消费自己的输入，才能创建独立实例 1；旧实例 0 不复活，也不返还组织已支出本金。

在封闭 CAL 系统中，候选不变量为：

`最终未消费 CAL + 真实 CAL 账户余额 − Open 缺口 = 初始 CAL`。

例如初始用户最终币 100、组织账户 100：

| 事件 | 未消费最终币 | 组织账户 | Open 缺口 | 左式总量 |
| --- | ---: | ---: | ---: | ---: |
| 初始 | 100 | 100 | 0 | 200 |
| 父未到、子先执行 | 200 | 100 | 100 | 200 |
| 组织赔付 | 200 | 0 | 0 | 200 |
| 父迟到：消费原 100、生成实例 1 的 100 | 200 | 0 | 0 | 200 |

此例说明实例 1 有真实来源，不表示所有者不会获益或组织不会亏损。策略性拖延可能让组织承担损失；当前没有证明抗延迟套利、盈利或激励相容。该性质不能由账务恒等式替代。

FUEL 分开核对 `Maximum=Held+Rewards+Burned+Refunded`，不把 CAL 赔付或已花手续费当作可循环恢复的钱。

源码：[直接责任与赔付](../../internal/rules/direct.go)、[费用](../../internal/rules/accounting.go)、[赔付及重放测试](../../internal/redaction/payment_test.go)。

### 3.4 受限历史修订

必须区分三个约束：稳定 TxID 的业务身份；公共 `RepairInput` 的经济授权；物理 BlockStore 的允许表示。Comet 封装固定部分还包含所有者签名、Admission、QC 和输入证书，不能与不包含签名字节的 FastTx.ID 混为一谈。

`nextBody` 以公共状态重新定位 Open／到期义务、位置和版本，只允许指定 Funding 引用及 opening 变化，并逐字节比较其余内容。`Execute` 检查适配后的分片承诺和稳定块身份，再与赔付一起提交。门限贡献用于构造 opening；上链验证的是最终结果，不是重新验证三份 share。已提交待办才允许物化，物化不再扣钱。

三份贡献至少包含两名诚实成员，不要求这三份全诚实；恶意者拒绝配合时的活性需要能取得三名诚实成员的可用贡献。底层 RSA／门限适配安全、重复公开适配后的安全性及可信初始化仍需独立论证，不能从单元测试通过推出。

原始执行版本用于已检查的重放、blocksync 和共识追块路径。普通 `VerifyBlock` 认证固定交易数据和执行结果，不等于独立轻客户端已经完整验证最新修订分片、版本及其授权。不能仅凭“块哈希不变”接受任意新正文。

源码：[修复验证](../../internal/redaction/repair.go)、[Comet 承诺](../../third_party/cometbft/types/redaction.go)、[同步适配](../../third_party/cometbft/overlay.py)、[跟块验证](../../finality/block.go)。

## 4. 已复现缺陷：补资来源与备付角色重叠

`EvaluateReserveIncrease` 从 `ReserveFundingAccount(Network, Subject)` 读取来源，从 `Grant.Key.Account` 读取目标，分别计算并写回。签名、Grant 身份、版本和余额检查存在，但没有完整排除来源与受保护备付账户的重叠。

本轮使用真实 `NewEngine` 初始化、签名的 ReserveIncrease 以及 `Engine.ExecuteAt`，没有手工修改初始化后的账本。结果如下：

| 配置 | 初始化／命令 | 总 CAL 前→后 | 具体结果 |
| --- | --- | --- | --- |
| 独立外部补资账户，对照组 | 接受／接受 | 2000→2000 | 来源 1000→900，目标 1000→1100 |
| 来源等于目标 | 接受／接受 | **1000→1100** | 同键先写 900、后写 1100；后写覆盖前写，增加 100 无来源资金 |
| 来源是另一组织已全额授权的备付账户 | 接受／接受 | 2000→2000 | 来源备付 1000→900，原 Grant 仍 1000；目标 Grant 增至 1100，总授权 2100 超过总资金 2000 |

这是**有配置前提的管理转移校验缺陷**。不意味着普通外部用户能重选已有组织 ID，也没有证据表明现有实验使用了这种配置；但这些配置确实通过当前初始化，因此不能仅把它们称为“代码已经禁止的非法输入”。

只检查 `source != destination` 能解决第二行，不能解决第三行。最小修复方向是：初始化明确补资账户与所有备付账户的角色隔离，补资执行也拒绝违反该隔离的来源；若将来允许同账户多用途，则必须核算未承诺的可支配余额。当前不需要为此引入完整资金治理框架。

**状态：已复现，未修复。** 本轮任务是分析，未静默改变业务规则。冻结一般资金安全命题前，应修复并补充拒绝用例。若先在受限模型中排除重叠，必须显式列为额外前提，不能声称该前提已由实现全面保证。

复现材料：[独立诊断源文件](security-analysis-2026-09-26/reproduce.go.txt)、[执行结果](security-analysis-2026-09-26/result.json)。将源文件复制为仓库内 `.run/security-review/cases/main.go`，执行 `go run -tags=comet_v3 ./.run/security-review/cases`。程序仅使用本地内存状态和临时生成的 RSA 密钥，不连接运行节点；输出用于描述反例，退出成功不代表系统安全。

## 5. 明确保留的活性与经济边界

| 场景 | 当前结果 | 不能推出的结论 |
| --- | --- | --- |
| 合法请求只取得一两票后不再推进 | 本地输入和预算保留，没有自动安全取消 | 任意请求最终释放；有限额度下可无限抗恶意占用 |
| 缺失父证书仅部分输出被消费 | 实际义务可结束，其余 Promise 仍占覆盖 | Open 缺口为零就等于全部额度空闲 |
| 一个 Worker 热、其他 Worker 有闲额 | 当前没有自动迁移 | 全组织有钱就一定能立即签发 |
| 网关在完整材料复制前失联 | 父原交易未必能由其他节点重建 | 无人保存完整父材料也必然正常提交父交易 |
| 钱包只有输出正文及完整 TXCer | 仍可构造子交易并走直接担保路径 | 不能据“无法重建父交易”断言无法续花；但新付款还需费用、额度、路由成员和公共推进 |
| 网络或组织传播过慢触发赔付 | 组织真实损失保留，合法迟到按实例 1 处理 | 超时代表已经证明作恶；组织损失必可追回；机制必然抗套利 |

恶意者可以用多笔合法输入制造局部批准残留，这属于服务可用性问题；不能以随意超时清锁换取表面活性。诚实请求在资源足够、无永久冲突、消息最终送达时的活性，可以作为单独的有条件命题。

## 6. 本轮排除的过强反例

1. **“子交易 Settled 就释放父证书额度”不成立。** `applyPayment` 按当前事实查自己的 Approval；父交易不成立时不会释放父批准。自身成立后不会再首次产生其缺失实例的赔付。
2. **“旧 KeySpend 与 DirectSpendKey 并存就已能跨路径双花”没有当前入口证据。** Direct 引擎的 `ExecuteAt` 不把普通付款转到旧结算规则；旧慢速逻辑还要求委员会路由。未来若同时开放两套入口，仍须重新分析，不能把代码共存当作攻击已可达。
3. **“父完整交易不可得则 TXCer 失去用途”不成立。** 当前后继验证有意只需直接输出证据。父正常传播与子担保兑现是不同的活性路径。

这些意见在与 GPT 交叉核对时被修正，未作为漏洞写入结论。GPT 的认可也不是证明证据，最终以可核实源码、轨迹和明确假设为准。

## 7. 下一步证明顺序与本轮验证

建议按以下依赖次序推进，不先重做更多 TPS 实验：

1. 处理第 4 节缺陷，固定账户角色、Grant 归属及合法初始状态集合。
2. 建模批准、签票、发布、公共执行、跟块、赔付、物化、补资；以事实和实例区分身份。
3. 先证明唯一消费与授权绑定，再证明动态预算引理及其与真实账户的连接。
4. 逐转移证明 CAL／FUEL 记账、义务至多一次、实例 0／1 关系。
5. 分开证明受限修订与原始重放等价；最后在公平调度、预算和证据条件下分析活性。

本轮重新执行 `go test -count=1 -tags=comet_v3 ./protocol ./internal/rules ./internal/member ./internal/committee ./internal/redaction ./finality ./crypto/chameleon`，7 个包全部通过。现有测试覆盖重复／迟到、部分赔付、同块父／修复顺序、篡改、物化和重放等指定轨迹；它们没有覆盖第 4 节账户角色反例，所以“现有测试全过”和“发现新缺陷”并不矛盾。

目前可以支持的是**明确条件下的安全论证路线和局部性质**，不能写成已经证明任意配置安全、无条件持续可用，或激励相容。
