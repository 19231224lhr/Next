# E7：跨组织付款与网络延迟敏感性

> 实施更新（2026-09-24）：预检发现 200 TPS 在 100 ms 注入下超过现有网关主投递路径的并发容量；该轮保留为未通过的过载预检。正式矩阵统一采用 **100 TPS**，其他并发、协议、节点和时长不变，计划机会因此为 **342,000**。D100 的 30 秒复测实发 3,000 笔，全部接收、上链、成员完成且审计通过，没有配额阻塞；D0 同口径复测后冻结。以下 200 TPS 内容是原候选，不能引用为已完成正式实验速率。GPT 复核认可统一工作点调整，要求保留负结果并单列两组织实发量。

状态：实施方案，尚未启动实验。已结合 [GPT 评审会话](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90) 返回的意见收敛；基于 `re` / `20be6cb` 的 wire 4 实现与 E8 单调计时修正。目标速率及并发配置需经过预跑冻结，正式矩阵与计量口径按本文执行。

**目标：** 在相同资源下比较同组织与跨组织的真实付款，并测量指定网络延迟对快速确认、连续续花和后台收尾的影响。

**实现方式：** 复用现有 Go 钱包、组织、委员会和 Python 实验脚本；增加双钱包进程的收款入口与标准 HTTP 延迟代理。采用分阶段实施与验证，不修改支付协议，不引入新的消息中间件。

## 1. 研究问题与范围

1. 在总硬件、组织数量和输入速率相同的条件下，同组织与跨组织付款的延迟及处理成本差多少？
2. 真正消费上一跳输出的跨组织连续续花，能否完成付款、公共结算和成员额度收尾？
3. 跨站通信变慢时，快速确认、实际吞吐及后台待办如何变化？

本实验研究双组织互操作和网络敏感性，不证明增加组织就能线性扩容，也不改变签名、消费路由、预算或赔付协议。实验成功指结果可核验，不要求必须达到某个 TPS。

## 2. 固定配置

- Mac Studio M4 Max，两个组织各 1 网关、4 成员，共享 4 委员：始终运行 14 个服务，组织内部仍取 3/4 认证。
- 两个钱包执行进程分别服务组织 A、B，候选共 64 个独立钱包身份，各 32 个；同组织对照也保持两个组织和两个钱包进程活跃，约各承担一半签发。代理与观察器开销单列。
- 用户自付已最终 FUEL，CAL、费用输入和工作权限充足；动态补资、串行取证、人工父交易延迟关闭。固定金额、输入输出结构、存储模式、总创世资金及输入池规模。
- 复用 E8 真实接收、指定输出续花、单调时间和审计逻辑；不能直接使用其固定 `Organizations[0]` 的负载入口。新增实验路由和收款接口，不修改节点付款规则。
- 正式轮重新创世、重启进程，预热独立记录。工作点、活动链数、名额上限在预跑后一次冻结；不能按组调整并发以掩盖差异。
- 初始候选为 64 条活动 lane（两侧各 32）、每站点 128 个快速任务名额、全局 2048 个未完成任务名额；这些都是驱动限制，不是协议参数。独立输入组也采用相同并发上限。若预跑需要调整，全部组统一冻结新值并保留原因。
- 正式组使用同样的 10 秒低负载预热、最长 60 秒预热排空，再进入测量窗口；预热未排空视为准备失败并记录，不能悄悄带入某一组。所有正式配置的创世输入池按最长 300 秒配置预备，所有权分配和总量保持匹配，多余输入不消费。

## 3. 最小对照矩阵

### 第一层：同机双组织

| 配置 | 付款范围 | CAL 输入 |
| --- | --- | --- |
| A | 同组织，两个组织各自付款 | 独立最终 UTXO |
| B | 跨组织，双向均衡 | 独立最终 UTXO |
| C | 同组织，两个组织各自续花 | 多条独立 10 跳链 |
| D | 跨组织，A/B 逐跳交替 | 多条独立 10 跳链 |

候选为**总计 200 TPS、每轮 120 秒、每点三轮**。先做短预跑核实资源余量及驱动供给；如共同工作点需要降低，统一调整并公开预跑，不能只降低某一组。相同种子配对、轮换顺序。A/B 比较普通付款的组织差异，C/D 比较真实续花的组织差异，避免把依赖与跨组织两项成本混成一项。

### 第二层：网络延迟敏感性

只对 C/D 增加目标 HTTP 往返延迟 20、100 ms；零注入组复用第一层，但必须经过同样的代理及收款入口。每点三轮、120 秒。D 的最高延迟组直接延长到 300 秒，作为代表性持续观察，不再另跑整套五分钟矩阵。

统一主对照取每轮前 120 秒的首次发送付款队列，并跟踪这些付款的最终结果；D/100 ms 另列完整 300 秒及后续窗口。不能把 120 秒与 300 秒全轮分位数直接当作等长对照。候选 200 TPS 下，24 轮计划发送机会共 684,000 个（不含预热），不把这个计划数提前称为成功数。

以上共 24 轮：第一层 12 轮，新增网络条件 12 轮。所有网络档使用同一个冻结目标速率；发不满本身就是结果，不无限补发落后的发送机会。结束后最多观察 60 秒，未完成明确保留。

## 4. 网络拓扑及注入边界

逻辑站点 A 放组织 A 和其钱包，B 放组织 B 和其钱包，C 放四委员。同站点不注入延迟，跨站点请求方向和响应方向各注入目标 RTT 的一半。0 ms 表示零注入，不是实际通信零耗时。

首版优先复用标准 HTTP 反向代理增加请求/响应延迟，不为实验新造 TCP 仿真框架。代理按来源站点与目标站点识别，公开逐条链路清单；接入收款交付、公共提交、跟块及状态查询。INSTALL 通常发生在组织内部，本拓扑不应误加跨站延迟。组织成员之间同站点，委员会 P2P 同站点，均没有额外延迟。

这是**HTTP 消息延迟模拟**，不是完整 WAN：不模拟 TCP 拥塞、带宽限制、丢包、重传和广域网共识。首发建连与连接复用分别记录；真实负载前后通过相同代理测量 RTT 的 P50/P95，并采样代理排队时间。每请求只注入一次；所有业务与控制路径计数核对，防止绕过代理、重复注入或代理串行化成为瓶颈。

20/100 ms 表示额外注入的往返预算，真实观测 RTT 包含本机基础开销及排队。代理只在请求转发前与响应交付前各延迟一次，不按读取分片重复 sleep。保留取消、超时和连接复用；0 ms 组同样经过代理。开始前固定路由覆盖表：付款钱包→所属网关、网关→所属成员、INSTALL、公共提交、钱包/成员跟块及查询、钱包→收款入口，逐项写清站点、是否注入和实际调用计数。

解释时拆开两层：零注入 C/D 比较同机组织路径；增加延迟后的 C/D 差异同时包含跨站收款交付，不能全部归因于跨组织验签。委员会仍是本地集群，不能称为委员会跨地域部署实验。单独注入组织内部成员链路可作为后续扩展，不混入本轮。

## 5. 真实收款与计时

保持现有组织交付路径：付款钱包提交交易并取得新 TXCer，再通过明确的收款接口把输出和 TXCer 发给收款进程。接收方独立验证绑定和签名、完成原子接收，才返回带付款事实标识的 ACK。所有组使用同一流程；公共确认不能冒充快速证书接收。

主指标为**付款首发 → 收款接收确认返回发送端**，在发送端同一个单调时钟内计量。这包括 ACK 回程，应称“收款确认往返时间”，不可与 E8 进程内快速到账值直接当作同口径比较。另列发送端取得 TXCer 耗时、收款交付 RPC 耗时、收款进程内验签及接收耗时；它们不靠跨机墙钟相减。

续花由收款进程完成接收后入本地有界就绪队列，消费指定上一跳输出；不等 ACK 回到上一付款人，更不等公共确认。每站点独立限速为总目标的一半，控制器提前发下场景及预算，不逐笔发同步调度命令。各链根两侧均衡，未就绪、限速和队列满导致的机会未使用分别计数。付款事实及 `(lane, hop)` 防止重投收款引发重复下一跳。

“立即触发”是接收完成后即可进入就绪队列，实际发送仍受既定速率与并发限制。同组织也通过相同收款接口并完成接收，不能直接操作另一个钱包对象绕过路径。当前指定输出已最终则使用普通输入，尚未最终才携带其 TXCer；不得为了提高未确认比例保留过期凭证。截止时停止新付款，保留未发链后缀与已发前缀；已有付款的幂等补交、收款确认和后台观察可以继续，不能据迟到接收启动截止后的新一跳。

10 跳整链时间由起始进程记录首发与最终接收完成通知的本地单调时间差，明确含最终通知回程；相同通知拓扑用于所有组。不累加每跳 ACK 时间冒充整链时间。跨进程 Unix 时间仅用于定位关联，不能据其直接宣称严格父提交前比例。未最终 TXCer 输入、委员会实际缺失输入责任分别统计。

## 6. 冷启动与真实跨机补充

冷/热验证做小型独立对照，不混入主矩阵：明确清空的是描述符/证书验证缓存还是 HTTP 连接，启动后先就绪再测，连接预热与业务缓存预热分离。每次冷样本用新进程，随后测热样本，重复至少十次。现有组织公钥和成员信息由实验配置预置；这只能叫“预置信任下首次验证”，不能写成已实现动态节点发现或首次交换信任。

首轮只选零延迟跨组织代表路径，冻结同一对身份；先预建连接但不发送该身份的业务，记录首次付款和随后使用独立输入的热付款。实际哪些缓存未命中以计数为准，不清除公钥信任或业务状态，不为得到“全冷”结论反复清空在线状态。若无法排除启动背景工作，只报告冷启动首笔与预热后付款，不归因为纯缓存收益。

若 Mac 与 Linux 服务器可用，补做真实跨机收款代表点；先记录配置、连接方式、实际 RTT 和资源余量。服务节点留在 Mac，收款钱包在远端。它验证真实收款链路，不代表组织成员或委员会已分散到多机，更不代表新增硬件的扩展性。该项独立报告，不假定设备现在可用，不阻塞同机主矩阵。

## 7. 指标与审计

- 每轮列计划机会、实际首次发送、重试、快速接收确认、公共成功、成员完成、未发和未决。报告各阶段 P50/P95/P99，分窗实际吞吐、每组织待办与最老年龄。
- 把快速收到证书、账本观察及原签署成员额度解除分开。签署组织可能逐跳改变，但每张已存在 TXCer 的责任不随转手迁移；按输入所引用的直接发行组织核对责任记录。
- 四委员状态一致；CAL/FUEL、手续费及退款守恒，组织代付为零；输入唯一消费，链尾与截止前真实前缀一致；签署成员原占用、解除额度、未成证残留及各组织 outbox 分别核对。
- 无需每笔让所有八成员都存在签署记录：签署权限审计针对实际占用成员；各进程跟块进度与全局待办仍独立检查。
- 同步采样服务 CPU、RSS、代理及钱包开销。借鉴 E8，缩小创世池并保持各组一致，不把历史增长与活动积压混淆；不为降低数字而删除应保留状态。

## 9. GPT 评审采纳及最终边界

GPT 支持保留“同/跨组织 × 独立/续花”四组、采用 20/100 ms 两档、以收款接收事件触发续花，并明确 ACK 主指标含回程。我采纳这些建议；“中央驱动负责全局速率”具体落实为预分配各站点额度，而非每跳在线取令牌，避免人为串入控制通信。

两个措辞进一步收紧：独立组测得的是当前付款路由、认证与交付的综合差异，不自动是“纯跨组织验签成本”；ACK 指标是发送端观察到收款已接收的确认时间，不是收款人首次可用瞬间。增加延迟会同时改变用户交付与后台跟块节奏，因此结果应按阶段和责任状态解释。

本轮能够支持的是所测双组织拓扑下的跨组织互操作、因果续花与 HTTP 延迟敏感性。不承担多组织水平扩容、WAN 共识、真实丢包拥塞、无限期运行或动态信任发现的结论。真实跨机补充只有完成后才写进结果；本文件仍是计划，不是已完成报告。
