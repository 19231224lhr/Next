## 1. 研究主张与证明范围

本系统要保障的是：**诚实钱包接受与确切输出绑定的 TXCer 后，可以据此构造后继付款；前置交易尚未成立时，公共账本以直接发行组织的有界担保支持当前付款，而不是等待祖先全部到齐。**

“可以构造后继付款”与“后继必在某个时间内成功”分开。前者依赖凭证和授权；后者还依赖消费组织、预算、费用、证据投递及委员会进度。TXCer 不是公共终局证明，也不保证原交易无条件最终到达。

本文只覆盖固定配置下启用 DirectPolicy 的 wire 4 快速路径、公共直接执行、用户自付或既有授权代付、补资和受限赔付修订。不把旧版慢速入口、动态组织注册、任意跨路由输入混合交易、状态丢失后的重启和任意第三方轻客户端纳入定理。

采用四层证据标签：

| 标签 | 本文含义 |
| --- | --- |
| 条件推导 | 在本文列出的抽象转移和假设下给出数学推理；不等于全仓库证明 |
| 实现对应 | 核查具体函数如何实现某个前提；仍缺全程序精化证明 |
| 测试／实验支持 | 已执行特定输入、故障或时序，观察到预期结果 |
| 未完成义务 | 目前不能由上述证据推出的性质，保留为独立问题 |

下文用“定理”指**抽象模型内的条件命题**，并逐项列出实现连接条件。不能删除这些条件后在摘要中写成“整个系统已形式化验证”。

## 2. 系统与攻击者模型

### 2.1 参与方和故障界

每个组织有四名固定成员，三名不同成员的匹配签名构成 QC。对每个纳入保障的组织，整个执行期间至多一名成员拜占庭；存在固定的至少三名诚实成员。委员会是独立的四节点 BFT 集合，在所用等权配置中至多一名拜占庭；更一般应按投票权阈值表述。

攻击者可以控制付款人、网关或中继，提交冲突、篡改及重复消息，控制消息顺序并任意延迟。允许不同组织中的恶意成员串通，但每个相关组织仍须满足自己的故障上限。这里不证明移动腐化、不受限密钥泄露或一个组织完全失守后的偿付保证。

网关不拥有资金裁决权。成员原子批准是输入锁和本地额度的裁决点，委员会提交是公共经济状态的裁决点。HTTP 接收、内存队列入队和后台副本回执不是公共终态。

### 2.2 明确采用的外部假设

| 编号 | 假设 | 作用 |
| --- | --- | --- |
| A1 | 网络、规则、创世、组织及委员会公钥可信；每个消费路由对应唯一固定的授权配置 | 防止同一输入绕到两个不相交裁决集合；不假定组织身份可自动发现 |
| A2 | 所有者／成员签名不可伪造，普通摘要抗碰撞，规范编码无歧义 | 将字节认证连接到唯一业务事实 |
| A3 | 诚实成员批准状态原子更新，签票前完成更新，不回滚、不遗忘、不私自取消 | 支撑法定集合交叠及预算推导 |
| A4 | 公共层对被接受命令给出一致、确定、原子的顺序；跟块只应用经认证的连续成功结果 | 支撑终态、赔付、费用和累计释放 |
| A5 | 金额为有界非负整数，所有加减、编码长度及转换遵守检查，不发生溢出 | 抽象算术与实现算术对应 |
| A6 | 受限变色龙承诺与门限适配在采用的初始化及重复公开适配模型下满足所需安全性质 | 这是待独立论证的密码学依赖，不由“三份 share”或测试替代 |

A4 对受限 Comet 适配而言是**待精化的接口假设**。原版 BFT 结果不能自动覆盖修改后的交易／分片承诺和历史表示；第 8 节单列这条证明义务。

实验内存状态和 NoSync 仅符合运行期间原子性的前提。丢失签署记录后仍使用原密钥签票的节点不能继续计作 A3 下的诚实成员。全新创世实验不构成掉电恢复验证。

### 2.3 合法初始状态

所有输入实例和账户键唯一；初始批准、消费、责任、费用进度和修订记录为空。CAL 和 FUEL 账户按资产分离，Grant 固定归属及版本，不重复创建或任意缩减。

对真实 CAL 备付账户 x，初始余额必须满足：

$$\sum_{g:\,backing(g)=x} B_g(0)\le A_x(0).$$

同一账户支持多个 Grant 时必须求和。代码在 `NewEngine` 中进行该聚合校验。实际参与 wire 4 取证的 CAL Grant 账户须等于发行组织账户；这一点由 `PrepareDirectVector` 与 Grant 身份核对共同约束，不能仅由任意创世字段推断。

补资源账户不属于 `ProtectedCAL`（所有组织 CAL 账户与所有 CAL Grant 账户的并集）。当前启动及执行代码均检查这一隔离。补资可以使用共享外部来源，但每次都实际扣款；模型没有“凭公式增发备付”的操作。

## 3. 身份、状态与可见事件

### 3.1 身份不能混用

| 符号 | 对应对象 |
| --- | --- |
| t | 稳定 FastTx.ID，绑定 Body、Claims 与输入承诺 |
| c | Fact，即输出摘要的域分离哈希；QC、批准、覆盖及幂等按它关联 |
| o | OutputID，绑定网络、t 和输出索引 |
| k=(o,i) | SpendKey，i 为实例号；普通实例 0，特定合法迟到输出为实例 1 |
| g | 固定身份、归属、版本及资源类型的 Grant |
| h,v | 公共高度与该历史表示的修订版本 |

TXCer 绑定全部输出摘要、金额、配置及资源向量；钱包还验证具体输出正文与索引。FastTx.ID 稳定并不表示全部报文字节相同。公共封装的固定内容还包括所有者授权、组织授权及直接输入证书；只有允许的 Funding/opening 经授权可变。

### 3.2 最小状态向量

令全局状态为 $S=(L,E,K,W,V)$：

| 状态 | 必须保留的内容 |
| --- | --- |
| L：成员 | 输入 Candidate/Consumed、Intent、Approval 原始扣占、Worker Available/Reserved、累计 Applied、Paid 与跟块游标 |
| E：材料与网络 | 已发票、完整 QC／提交材料在哪些参与方可得、INSTALL 与待投递消息 |
| K：公共经济状态 | 创建和消费实例、真实账户、Grant Amount/Reserved/Spent、Payment、Coverage、Promise、DirectObligation、费用托管及修订授权 |
| W：钱包 | 已接受正文／TXCer、最终创建事实、实例及本地已消费标记 |
| V：历史表示 | 原始执行材料、规范授权版本、物理版本、修订待办及承诺 |

`Coverage.Remaining` 是整张证书尚未解除的承诺，`OpenGap` 是已实际执行但来源缺失的金额。未被消费的 Promise 可能有前者而无后者。模型不能把两者合成一个“待结算余额”。

### 3.3 原子转移

| 转移 | 前置条件与效果 | 不产生的效果 |
| --- | --- | --- |
| Approve(m,T) | 检查授权、路由、证据、输入锁和各维度预算；原子记录输入占用与原批准后才允许签票 | 不改变公共余额，不因尚未成证而自动解锁 |
| Certify / Receive | 三票相符；接收方验证输出绑定并本地接收 | 不等于上链，不新造公共资产 |
| Install / Submit | 验证完整材料，保存／传播；INSTALL 约束本地输入消费 | 不替代原批准，不凭回执释放额度 |
| Execute(T) | 原子消费输入及费用、必要时登记整证书覆盖和直接缺口、产生输出、处理来源到达 | 不等候完整祖先历史，不异步补记已生效输出的缺口 |
| Anchor | 按公共高度及区块时间一次确定截止 | 本机时间不授权赔付，重试不重置截止 |
| Repair(o) | Open 且到期，授权修订合法；原子扣备付、关闭缺口、处理费用、保存修订待办 | 不给子收款人再增加一次余额 |
| Follow | 认证连续公共成功结果，原子应用本地变化并推进游标 | 不给没批准过的成员返额度 |
| Materialize | 按已提交授权及版本写历史表示 | 不重复执行付款或赔款 |
| TopUp(g,a) | 合法外部来源余额足够；同事务源减 a、备付加 a、Grant 加 a及防重 | 不清锁、不重置历史损失、不挪用其他备付 |

SourceArrive 与 LateParent 是 Execute 的输出创建分支，不是另一个可以直接造币的接口。失败转移不合入公共／本地 Overlay；重试幂等为无经济变化的转移。

## 4. 认证与唯一消费

### 引理 1：输出认证绑定

在 A1–A3 下，诚实钱包接受的输出必须与已认证摘要的对应索引一致；在普通哈希及签名假设下，攻击者不能将凭证改用于另一金额、所有者、网络、路由或交易身份。

**论证。** QC 验证固定配置中不同成员对同一 Fact 的签名。Fact 绑定规范输出摘要；`VerifyOutput` 再核对实际正文及索引。三票至少两票来自诚实成员，这些成员按规则验证当前交易和直接证据。不匹配正文改变摘要或导致正文核对失败；更换签名事实需要伪造签名或破坏摘要假设。这里不把普通哈希抗碰撞误用于允许适配的变色龙 Funding 承诺。

**实现对应：** [协议及证书](../../protocol/v3.go)、[QC 验证](../../protocol/certificate.go)、[钱包接收](../../internal/wallet/direct.go)。精确规范编码与密码学原语为独立依赖。

### 定理 2：同实例不存在两份冲突有效消费 QC

对同一合法 SpendKey，若两项不同消费事实都取得三票，则两个签署集合至少交叠两名成员，其中至少一名诚实。唯一消费路由使两集合属于同一授权组织。A3 要求该成员先在原子事务中占用输入，随后才能签票；它不能在第一次占用后为另一事实签票，矛盾。

补充边界：

- 同一 Fact 的不同签名子集或重复交付不是两次消费。
- 未最终证书输入与最终输入都以同一 `(OutputID, Instance)` 检查消费，不能因父后来上链而清锁。
- 后继输出可以指定不同组织，但旧输入路由不随提交网关改变。
- 公共 Execute 独立检查 Consumed 并在同事务写入，公共顺序下同实例至多成功一次。
- 实例 1 是协议允许、另有真实来源的迟到输出，不是清除实例 0 的消费标记。

**实现对应：** [ApproveDirectBytes](../../internal/member/direct.go)、[EvaluateDirectPaymentAt](../../internal/rules/direct.go)。定理限于已核查的 wire 4 路径，不能覆盖另行开放的兼容消费入口。

## 5. 从签署预算到真实赔付能力

### 5.1 本地残余与公开状态分开

固定一个 CAL Grant g。$B_g(t)$ 为累计授权，$s(B)=\lfloor2B/3\rfloor$。成员本地观测的授权 $B_{m,g}\le B_g$，因为配置固定、授权只通过已提交补资单调增加。

对成员 m 的原子成功批准 a，令 $r_{m,a}=cap_a-applied_{m,a}$，包含尚未返回签名和仅局部签票的批准。所有 Worker 合计：

$$L_{m,g}=\sum_a r_{m,a}\le s(B_{m,g})\le s(B_g).$$

初始 Available 总和为 s，批准等量从 Available 移至 Reserved；累计恢复只移回差额；补资仅增加新旧 s 之差。故此不等式可按三个转移归纳，且不依赖 Worker 负载均匀。

### 5.2 QC 风险权重及保守跟块

令 $C_g$ 是截至当前已有三份有效签名的不同 Fact 集合，包括未公开、用户私有及尚未被收集器组装的可成证事实。它是证明中的集合，不要求委员会可枚举它。

令 $p_c$ 是**该证书自己发行的输出已产生的累计实际赔款**，不是该证书交易所用父输入的赔款。定义：

$$w_c=\begin{cases}cap_c,&\text{该证书自己的交易尚未 Settled},\\p_c,&\text{自己的交易已 Settled}.\end{cases}$$

证明连接条件为：对 c 的任一诚实签署者，$r_{m,c}\ge w_c$。

1. 自身未 Settled：恢复目标为零，r=cap，已赔金额也已包含在 cap 内。
2. 自身已 Settled 而成员尚未跟到：r 仍为 cap，不会低估 p。
3. 成员跟到自身 Settled：连续前缀先处理此前赔付，恢复 cap−p，留下 r=p。
4. 自身 Settled 后不能再首次赔付其输出：正常输出实例 0 已创建；此前已用的实例 0 保持 Consumed；已赔输出保留旧消费并创建实例 1。后续缺失分支不能为它们再建 Open 义务。

第 4 项是连接公共与本地状态的关键，不可仅凭 target 单调检查替代。现有代码和测试支持这些分支，仍需完整状态机精化检查。

### 定理 3：有效认证风险不超过单 Grant 授权

在上述连接条件成立时，选定三名诚实成员 H。每个三票证书至少由 H 中两人签署。因此：

$$2\sum_{c\in C_g}w_c
\le\sum_{m\in H}\sum_{c\in C_g:m\text{签署}c}r_{m,c}
\le\sum_{m\in H}L_{m,g}
\le3\lfloor2B_g/3\rfloor\le2B_g.$$

从而 $Q_g=\sum_c w_c\le B_g$。局部批准没有三票，不进入左侧；它们仍占右侧容量，可能损害活性。不能对全部历史 cap 永久求和，也不能把 Paid 在 w 之外再算一次风险。

### 定理 4：剩余潜在责任有真实备付覆盖

令 $S_g=Usage_g.Spent=\sum_{c\in C_g}p_c$，并定义保守剩余责任：

$$E_g=\sum_{c\in C_g}(w_c-p_c)=Q_g-S_g\le B_g-S_g.$$

E 包含未公开证书和未使用输出的保守责任，不是 OpenGap，也不声称是最小所需备付。已登记 Coverage 的 Remaining 总和不超过 E：未成立证书的 Remaining 至多 cap−p，已成立证书的 Remaining 为零。

对账户 x 定义备付不变量：

$$\sum_{g:backing(g)=x}(B_g-S_g)\le A_x.$$

**归纳。** 创世按账户聚合检查建立初始式；正常付款和正常解除不减少 CAL 备付；补资同时增加目标 B 和余额；赔付同时增加对应 S、减少同账户余额；隔离规则禁止以该备付作为其他补资的来源。重复及拒绝命令均无变化。因此，在枚举转移没有其他备付扣款的范围内，此式保持。

合并得到：

$$\boxed{\sum_{g:backing(g)=x}E_g\le\sum_{g:backing(g)=x}(B_g-S_g)\le A_x.}$$

这涵盖未公开 QC、已支出残余、多个 Grant 共享账户和动态补资。已注册 Reserved 只是 E 的部分；尚未登记的有效证书首次登记后也应满足公共授权上界。代码仍执行自己的实时 Reserved+Spent 检查。

**结论限度。** 它证明的是模型内的 CAL 容量覆盖，不是存在钱就自动取得三份签票或自动赔付。实际推进还依赖 FUEL、工作权限、材料、调度和修订能力。若添加备付提现、Grant 缩减／迁移或新资金入口，必须新增归纳分支。

**实现对应：** [份额算术](../../protocol/amount.go)、[成员占用](../../internal/member/direct.go)、[累计恢复](../../internal/member/blocks.go)、[公共覆盖及赔付](../../internal/rules/direct.go)、[补资](../../internal/rules/reserve.go)、[创世聚合与账户隔离](../../internal/committee/engine.go)。

## 6. 直接责任与 CAL 记账

### 定理 5：每项直接义务至多关闭／赔付一次

义务按 OutputID 唯一索引，只有缺失的实例 0 实际被消费时建立。状态只能从 Open 进入 Fulfilled 或 Repaired。来源和赔付在同一公共顺序上竞争：先到来源使后续赔付不再可执行；先赔付则后来来源走迟到分支，不重新扣款或打开旧义务。所有判断与消费、扣款、缺口变化原子提交。

义务唯一关闭不意味着“原交易成立”和“赔付”两事件绝不同时出现：合法父可在赔付后到达。它消费自己的真实输入，创建独立实例 1；组织损失保留，子收款余额不因修复再增一次。

### 定理 6：含缺口的封闭 CAL 记账保持一致

定义 U 为公共已最终且未消费的 CAL 实例金额（按 SpendKey 去重），A 为所有真实 CAL 账户余额，包括外部补资源，D 为所有 Open 实际缺口金额。初始总 CAL 为 $C_0$，候选不变量：

$$U+A-D=C_0.$$

**Execute 的一般情况。** 设当前交易消耗已最终输入总额 F、以证书补足缺失输入总额 M，全部输出金额 O=F+M。设这些输出中，已被子交易消费且本次正常关闭 Open 义务的总额为 H。这些实例不会重新变成可用币；其他输出（含合法迟到实例 1）加入可用最终输出。所以：

$$\Delta U=(O-H)-F=M-H,\quad\Delta D=M-H,\quad\Delta A=0.$$

这同时涵盖先父后子、先子后父、同块顺序、多个输入／输出及跨组织直接缺口；不需要递归找整条链的根。

**Repair。** 对金额 a，$\Delta A=-a,\Delta D=-a,\Delta U=0$。赔付补足先前已生效输出的来源。

**TopUp。** 来源与目标不同且同事务真实转资，全部账户之和不变。Approve、Receive、Install、Follow 和 Materialize 不改变公共 U/A/D。拒绝和重复转移不改变它们。

由初始式与逐转移归纳，在这个封闭 CAL 模型中不变量保持。TXCer、Grant、Coverage 和成员权限不作为资产再加一次。若纳入铸造、销毁、跨链流入等操作，必须显式扩展边界项。

**不等于经济无损。** U+A 在存在缺口时可以高于初始值，D 正是待覆盖负债。守恒需与定理 4 一起使用，不能用负债项掩盖无备付承诺。赔付后迟到也可能让原所有者受益；当前不论证抗战略延迟、损失追偿、盈利或激励相容。

## 7. FUEL、收费与权限恢复

每笔交易费用上限 M 分解为：

$$M=Held+Rewards+Burned+Refunded.$$

用户自付时，最终 FUEL 输入在 Execute 消费，超额部分找零，M 进入托管；组织代付时从授权 FUEL 账户扣 M。Register、Settle 和 Close 有阶段防重；每项修复费用随唯一义务关闭收取，不能把多输入修复费用写成“整笔最多收一次”。

输入为证书的数量 n 已用于预留最多 n 项修复费用。正常来源到达不收赔付费用，全部直接义务终结后执行 Close，余额退回原费用来源。退款与找零使用确定身份及保留索引，不能被触发关闭的其他交易领取。

局部等式不足以单独证明全局没有重复记账。全局应核对：

$$U_F+A_F+\sum Held+RewardAccounts+BurnCounter=F_0.$$

其中奖励账户与普通 FUEL 账户按实际不同存储角色分别计量；已退款金额已经进入 U_F 或 A_F，不能再加累计 Refunded。支付历史中的累计 Rewards/Burned 仅用于对应校验，不重复加入真实奖励／销毁计数。

每个收费阶段将 Held 的减少等量转为奖励、销毁或退款；幂等重复没有新增转移。此为封闭费用模型的条件推导；全部费用输出、别名隔离及实际键映射仍属于实现精化义务。

成员只有原 Approval 才可应用释放。CAL 按自身 Settled 的 cap−Paid 恢复，工作权限等费用 Closed 才恢复，代付费用只恢复未实际支出部分。累计 Applied 仅增加，重复 Follow 不再增加 Available。这个性质既不要求私有核销通知，也不允许任意清除未完成批准。

**实现对应：** [费用状态机](../../internal/rules/accounting.go)、[公共费用与输出处理](../../internal/rules/direct.go)、[用户 FUEL](../../internal/rules/direct_fee.go)、[成员跟块](../../internal/member/blocks.go)。

## 8. 受限修订与重放：三个不同命题

### 8.1 经济授权及不可变内容

`RepairInput` 必须定位已提交的 Open 到期义务、输入槽、基础版本及前一规范正文。`nextBody` 从规范旧交易只替换指定 Funding，要求所得完整编码与命令正文逐字节一致，同时验证新资金引用和 opening。其他 Body、Claims、输出、所有者授权及组织／输入认证保持不变。

因此，在经济状态机与承诺假设下，**被接受的修复不改变既有付款的所有者和输出权利**。块哈希相等本身不足以推出这项结论，精确允许范围和公共授权不可省略。

### 8.2 物化不重复执行经济效果

修复在新块先提交经济效果和待办，再将相应历史表示写入 BlockStore。物化只处理已授权版本，不再扣款；落后或重复物化不改变经济状态。原始执行材料保留，重放按原始付款及后续修复事件顺序进行，不能将最新修订正文当成最初交易直接重放。

同块多个输入修复、相邻版本、重复物化和追块要分别对应规范版本与物理版本。现有测试验证若干序列；这尚不是所有同步路径的精化证明。

### 8.3 尚未完成的密码学及共识连接

- 所用 RSA 门限适配在可信初始化、腐化阈值、重复公开 opening 情况下的安全归约；测试覆盖重复适配不等于证明密钥不会泄露。
- 固定业务内容、可适配资金输入、稳定交易／分片承诺与 BFT 已签对象之间的组合关系。
- 原始重放、blocksync、共识追块与修订物化的等价性；不能仅引用未修改 CometBFT 的证明。
- 独立轻客户端验证“最新修订正文＋授权历史”的完整接口。普通 `VerifyBlock` 验证公开执行结果，不代表验证了这一额外对象。

**实现对应：** [修复构造与执行](../../internal/redaction/repair.go)、[Comet 承诺](../../third_party/cometbft/types/redaction.go)、[物理修订](../../third_party/cometbft/store/redaction.go)、[同步适配](../../third_party/cometbft/overlay.py)、[普通跟块验证](../../finality/block.go)。

## 9. 用户权利与条件活性

### 9.1 可组合的用户安全结论

在认证、唯一消费、预算覆盖和公共状态机假设成立时，诚实接收者持有的合法未消费实例不能被没有其授权的另一消费取得；后继交易若以该实例进入公共执行，来源缺失会对应有界直接责任；合法赔付修订保持后继输出和授权不变。

这是“提前取得可继续支付的、有责任支持的权利”，不把快速接收直接称为公共终局。用户自己已合法签发冲突候选的情况，也不能套入“当前没有冲突占用”的后续活性前提。

### 9.2 三类推进分别论证

| 目标 | 额外需要的进度条件 |
| --- | --- |
| 一次新付款形成 QC | 三名诚实响应者、合法且无永久冲突的输入、所选 Worker 各维额度足够、费用可用、请求得到公平处理 |
| 当前完整交易正常公开执行 | 完整提交材料仍可得，至少一个持续投递者，委员会最终同步和公平纳入，公共准入及其他资源条件持续满足 |
| 缺失输入最终关闭 | 来源合法到达，或锚定／共识时间推进到期且有可用修复构造者、足够诚实门限贡献、费用和公平执行；观察还需跟块推进 |

公平性必须针对持续可执行的操作；不能在预算被其他请求长期耗尽时仅以“网络最终送达”推断活性。无限网络延迟下不承诺完成时限，超过期限也不自动构成作恶证明。

钱包只有 Output+TXCer 仍可构造后继付款，不需要完整祖先材料；但原父交易走正常公开路径需要其完整提交材料。两条路径不要混为一谈。

### 9.3 明确保留的限制

局部批准可能长期保留输入和额度；未被使用的 Promise 不自动到期释放；Worker 不自动调配；完整证据尚未扩散时网关故障可能阻断原交易自主提交；内存历史仍会增长。这些限制不否定已给出的唯一消费条件推导，但排除了“任意恶意输入下永不堵塞”“无限期稳定运行”等主张。

## 12. 论文可采用的表述

> 我们将快速接收、公共执行和责任终结建模为不同事件。在固定授权路由、诚实成员状态不回滚及公共顺序一致等条件下，法定集合交叠排除同实例的冲突认证；成员残余预算限制包括未公开证书在内的承诺，并通过真实备付、已支出残余和隔离补资连接到剩余资金覆盖。直接义务按唯一输出关闭，赔付为已生效后继输出补足来源，而不重复增加收款余额。受限修订保留交易核心和输出授权；其密码学实例及共识适配仍是独立证明义务。E1–E8 检验这些机制的实现轨迹、性能及已知边界，不替代全程序安全证明。

术语与论证分工参考 [FastPay](https://arxiv.org/abs/2003.11506) 的预付资金支付模型和 [Stingray](https://arxiv.org/abs/2501.06531) 的拜占庭有界计数器研究。它们不能直接证明本系统的动态释放、直接缺口或历史修订；详细相关工作见[既有文献调研](fast-payment-security-proof-survey-2026-09-25.md)。
