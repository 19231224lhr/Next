# Next 与 Lightning/LND 的同机支付性能对比方案

状态：已与侧边栏 GPT 评审的实施建议，尚未部署或执行。本实验独立于 E5；不复用 E5 的代理结果作为外部系统基线。

## 1. 比较目标

比较同一台 Mac、相同发送计划下，两套实现的付款完成延迟、持续成功付款率和运行成本。回答“收款观察多快、收到之后继续付有多快、持续输入时是否积压”，不预设 Next 必须优于 Lightning。

结果必须标注具体 LND 版本、通道拓扑、存储配置和负载。单通道上限不代表整个 Lightning Network 的上限；Next 单组织与 LND 也不具有相同的信任或故障模型。

## 2. 部署选择

| 选择 | 用途与取舍 |
| --- | --- |
| Mac 原生 Bitcoin Core regtest + LND | 推荐；与 Next 同为原生进程，不引入单侧虚拟机开销 |
| 两套系统全部迁入同一 Linux VM | 原生部署受阻时的备选；需重新测 Next，不能拼接旧的 Mac 数字 |
| 公共 Lightning 网络 | 可作后续现实环境验证；路由、资金与网络不可控，不用于首轮公平基线 |

硬件沿用 Mac Studio M4 Max、16 核、64 GB。2026-09-24 检查 SSH 可用、数据卷约 213 GiB 可用；当前命令路径未找到 bitcoind、lnd 或 docker，不据此断言机器任何位置都未安装。

建议隔离目录 `/Users/richz/lab/man/utxo-ln-compare`，内分版本化二进制、每轮配置、节点数据和结果。单独实验分支，不修改现有主实验的默认存储方式。

固定 LND 官方发布版本及 SHA-256，候选为当前核对到的 `v0.21.3-beta`；Beta 是该官方版本名称。Bitcoin Core 的具体兼容发布版本在部署预检时冻结，同样保存下载来源、校验值、完整配置和编译信息。不能用持续变化的 master 作为正式基线。

部署步骤：

1. 启动独立 Bitcoin Core regtest，仅监听本机；建立实验钱包，生成成熟测试币。
2. 启动各有独立数据目录、P2P/RPC 端口的 LND 节点。保留正常验签、通道状态持久提交、TLS 与 macaroon 认证。
3. 节点连接、充值、开通道、挖出所需确认；检查通道 active、图信息可路由、双向余额和协商参数。
4. 预建正式发票、建立常驻 RPC 连接及接收订阅，完成独立预热并排空。
5. 启动计时。开通道和充值不计入稳态付款延迟，另记初始化耗时与锁定资金。正常 Lightning 付款不等待每笔 Bitcoin 出块，不人为加入这一等待。

所有资金均为 regtest 测试币，不需购买 BTC，不连接主网。两套系统轮流运行，不能同时争抢机器后称为同环境；顺序交错、重复三轮。记录负载器与服务进程的资源开销，Next 后台委员会、INSTALL、跟块始终开启。

## 3. 两种拓扑

**主比较：LND 两节点一条直连通道，Next 一个担保组织内两个钱包。** LND 直连是必须保留的简单基线，不为制造优势而只选长路由。Next 使用完整的四成员、网关、四委员和钱包，报告其总资源成本，不硬凑两边节点数。

**补充：LND Alice → Router → Bob，两条通道、一个中继。** 单独列路由付款结果，不与直连混成一个“闪电网络速度”。首轮不扩展大量随机图、多实现、多跳数组合。

首选 LND 是为方便 Go/gRPC 接入和原生部署；只代表这个具体实现。Core Lightning 可在首轮结论稳定后作为第二实现验证，不能通过只选较慢实现来概括协议性能。

## 4. 存储条件必须分组

当前 Next 是应用/块存储内存、实验钱包 NoSync。代码还显示：`cmd/member/main.go` 在关闭成员内存模式后使用 `OpenNoSync`，因此仅取消环境变量并不能得到同步写盘版本；实验钱包也需明确切换。

| 组别 | Next | LND | 可以说明什么 |
| --- | --- | --- | --- |
| 当前实现探索组 | 保留现有实验模式 | 官方正常存储 | 两种已声明配置的运行表现；不能把全部差异归因于协议 |
| 同步提交对照组 | 安全关键成员状态、钱包、组织及委员会相关状态使用明确同步提交配置 | 官方正常存储 | 减少关闭写盘带来的偏差；仍不宣称安全、故障恢复保证完全等价 |

论文的性能主结论优先依据第二组。若现有 Next 同步路径无法用小改动准确恢复，先完成第一组并明确其限制，不伪称完成公平耐久性对照。只增加实验存储选择与核验，不借机开发完整恢复系统。

不关闭 LND 的通道安全提交来获得主结果；RAM 磁盘只可作为后续 I/O 敏感性分析，不能称为与 Next 内存事务相同。

## 5. 测量口径

由同一常驻 Go 测量进程使用单调时钟记录事件，避免拿只有秒级精度的 invoice `settle_date` 计算毫秒延迟。每笔只计一个逻辑支付；重试次数另列。

| 时点 | Next | LND |
| --- | --- | --- |
| 计划发送 | 开环调度计划时刻 | 同左 |
| 实际发送 | 钱包首次调用发送接口 | 首次调用 `SendPaymentV2` |
| 收款观察 | 验证 TXCer 并完成对应模式下的钱包事务 READY | `SubscribeInvoices` 观察该 payment hash 的 `SETTLED` |
| 付款方成功观察 | 按实际可用接口单列，不人为增加 ACK | 付款流 `SUCCEEDED` |
| 后台完成 | 公共成功、成员收尾分别记录 | 双方付款状态及 HTLC 收尾核验，不强行等待通道关闭上链 |

LND 的 `SETTLED` 暂命名为“收款结算事件观察”，不是未经验证的“即时可续花”。部署阶段核对固定版本的事件与通道状态顺序，再用后继付款实验验证。`ACCEPTED`、HTTP 成功或首次看到 preimage 不能充当正式完成。

发票提前生成，对应 Next 的预备输入、收款信息和必要离线构造；两边都不把收款请求生成算进“从钱包发送开始”的计时。所有在线验证与网络协议正常执行。正式负载用常驻 gRPC/HTTP 连接及事件流，不循环启动 lncli、不逐笔轮询余额。

## 6. 最小实验矩阵

### 单笔与连续付款

- 单笔：预热后并发 1，逐笔完成并排空后再发；每轮 100 笔、三轮，给 P50/P95，保留首次冷启动样本但不混入预热数据。
- 连续付款：先做 Alice、Bob 同通道往返的 100 次因果接续，Next 同样两个钱包往返。上一笔达到指定收款事件后立即尝试下一笔，下一笔不能在前一笔之前预先发送。
- LND 每一步的后继付款方，在前次到账之前可发送余额都应不足一笔金额；保留金与必要费用之外配置一份可循环本金，核对后继确实依赖前次新增可用余额。不能只检查初始接收方一次。Next 两钱包之间只有一份循环本金，明确消费上一笔输出、用户费用另有充足最终 FUEL。
- 若无法证明余额依赖，结果只能称“收到后触发的串行支付”，不能声称同一笔钱的真实续花。记录事件到下一次发出、下一次完成、失败及重试；不插入隐藏 sleep。
- 可发送能力需扣除通道储备、承诺费用及未决 HTLC，不能只看 `local_balance`。若收到结算事件后仍需等状态变为可发送，这段时间计入整链时间。循环本金与双方另行锁定的储备、担保资金分别列出。
- 同通道回付不证明任意第三方可续花。Lightning 从另一通道支付还依赖该通道的出向流动性；三钱包环形实验不能直接照搬 Next 的 UTXO 链条语义。

### 持续吞吐

探索输入率 5、20、50、100、200、500、1000 TPS；达到过载后停止盲目上调，全部稳定则继续更高档。每档先短测定位拐点，不把所有档位都跑很久。

正式选择一个双方低负载档、一个双方共同稳定档、各自拐点附近档，每档 180 秒、三次独立重复。共用同一份方向、金额和到达时间计划，记录每秒曲线，停止发送后另设有界排空期。

主吞吐负载用预先平衡的双向独立付款计划，两个方向各占一半；相同计划用于 Next。该场景用于避免单向抽干通道，不代表真实支付方向总是平衡。单向容量耗尽另列，不混入计算吞吐上限。

TPS 按双向合计的唯一支付计数。共同稳定档由正式重复的实际发送、成功完成和队列曲线确认，不能仅凭预扫命名；各自边界档不用于同负载的延迟排名。

报告计划率、实际发送率、接收成功率、付款方成功率、P50/P95/P99、失败/未知/未发送、发送滞后、在途数量、最老年龄、排空时间和资源。Next 额外展示后台公共成功与成员债务，不能只数 TXCer。

客户端设置有限并发和最大未完成数量；预跑验证增加客户端容量不会显著改变稳定点。若客户端满或实际发送追不上，明确标为供给受限，不将其自动解释为服务端极限，也不删除未发样本。停止发送时仍未发的请求保持未发，不延长输入期补齐后改称原 TPS 成功。

稳定档要求实际发送接近计划、成功率达到预先冻结标准、待办数量与最老年龄无持续上升、结束后正常排空且账务核对通过。三分钟只能证明这段时间内的稳定，不证明任意时长。

## 7. 资金与参数预检

固定小额支付，候选 10,000 sat；最终金额以固定版本的通道保留金、承诺费用、dust 与 HTLC 限额预检为准。CAL 不与 BTC 建立人为汇率；两边比较固定复杂度支付，分别报告本金及手续费。

每个方向的可用通道余额，应覆盖峰值在途支付金额、方向失衡、费用与安全余量。余额充足仍可能碰到最大在途 HTLC 数或金额上限，必须区分原因。公开通道容量、双方初始余额、channel type、协商 HTLC 上限、fee policy、路由与客户端并发。

不在计时内隐式开通道、自动补币或免费再平衡；需要重置时结束该轮、重新预热。Next 的担保权限及用户 FUEL 在主吞吐实验中充足且记录，不把 E2 的资金阻塞混进来。持续吞吐的双向充分余额与续花的一份本金是不同初态，分别新建实验，不混用。

首轮固定单路径、单分片付款，记录 `max_parts`，不用模拟 HTLC 或 bypass 签名。有 Router 时显式设置足够的支付费用上限，避免默认零费用上限使合法收费路由失败。LND 先测官方默认，再仅在独立预跑中有限调整官方支持的提交批量/周期；选定配置后冻结并做正式重复。默认与调优结果均保留，不能逐轮择优。根据真实瓶颈决定是否调参，不预设一定更小的 batch 或周期更快。

参数按锁定 tag 核对：通道的 `channel-commit-interval`、`channel-commit-batch-size` 与图数据库的 `db.batch-commit-interval` 不混为一谈。运行日志记录实际 Store 类型和同步选项，实验结束时的审计导出不算运行期间的耐久提交。

## 8. 实施顺序与产物

1. 部署并冻结二进制/配置；先跑通一笔直连收款与一笔反向付款。
2. 核对完成事件、余额和同步提交模式；完成观测器不会遗漏早到事件的测试。
3. 单笔与因果接续；确认压测工具本身没有外部排队或周期查询瓶颈。
4. 双向直连阶梯短测；冻结正式负载和验收条件，跑正式重复。
5. 加一中继的补充对照；只有确实必要才扩展到更多通道或 Linux 多机。
6. 审计每笔支付 hash、付款/收款金额、手续费、余额变化、残留 HTLC，以及 Next 公共记录与成员收尾。保留超时后的最终状态，避免将未知简单算失败后重复付钱。

产物：一键部署/停止和复现脚本、统一负载器、逐笔时间 CSV、每秒队列及资源曲线、配置/版本/二进制指纹、三重复汇总图、中文报告。报告结论限定具体实现与环境，解释安全保证、资金结构和后台工作差异。
