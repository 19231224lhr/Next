# 成员签发并发名额占满：取证与同步策略对照

2026-09-21；目标是解释完整系统500 TPS时成员429，不改变支付协议或共识。

## 结论

本机实验中，成员请求主要在等待共享数据库写者和事务提交返回，期间一直占用128个前台名额。同步提交策略是显著影响因素；后台观察上限造成的集中补发，以及三票完成后被取消但仍在处理的请求，会放大瞬时拥堵。验签计算不是这轮的主要占位来源。

所有改动均为测试构建overlay，生产源文件、并发参数与共识参数未改。只在NoSync对照轮关闭成员库的强制同步，随后回到原同步版本验证；测试节点均已停止。NoSync未被正式采用。

## 环境和测试边界

- 同一台Mac Studio M4 Max，14进程；4委员、2组织各4成员和1网关。独立最终UTXO，org0向org1收款钱包付款。
- 与上一轮相同180000个创世输出；每轮新目录，不复用运行数据库或共识签署状态。成员GOMAXPROCS=16/GOGC=200。
- 5000笔，目标500TPS。快速并发256、总未完成上限2048、每成员前台128/后台32。
- Comet三库实验MemDB；钱包、网关、委员会应用数据库保持同步bbolt。仅B轮的成员bbolt使用NoSync=true。
- 请求准备在计时外，计时从付款钱包HTTP发送开始。原派发器的补赶逻辑原样保留。
- 成员诊断记录留内存，限流快照每成员最多8份，首份附一次goroutine堆栈；各请求记阶段，Group批次记起止和业务回调来源。三轮探针相同，有诊断开销。

## 限流现场

A轮成员0首次429时128个活跃请求：

| 位置 | 数量 |
|---|---:|
| 业务回调结束，仍等待Update返回 | 63 |
| 已请求Update，业务回调尚未开始 | 62 |
| 正在进入/解码 | 3 |
| 上述请求中上下文已取消 | 47 |

取消状态在handler仍活跃、名额未释放时读取；A轮5000笔全成功，没有基准全局错误取消，因此这47个不受全局取消污染。未采集精确取消时刻和Group实际入队时刻，不能把它们全部归类为可安全提前丢弃的工作。

现场写者批次为63项ApproveDirect＋1项InstallDirect，无跟块回调：总100.235ms，业务回调4.046ms，其后到base.Update返回96.173ms。堆栈为`FD.Fsync → File.Sync → bbolt.fdatasync → Tx.writeMeta → Tx.Commit → DB.Update → Bolt.Update → Group.run`，goroutine标为runnable。

这证明现场处于同步提交路径，但96ms还包含键值应用、页整理、写入、同步和调度，不能叫作一次fsync耗时，也不能仅凭堆栈认定SSD硬件慢。其它批次跟块callback最长约65～75ms，也占共享写者；不能说所有等待都来自跟块。

四成员19967个已受理请求，累计占位时间约97.92%落在“Update调用到回调开始”与“回调结束到Update返回”两个区间。此数是并发请求累计时长占比，不是CPU占比、物理写者利用率或可全部消除的开销。

## 压测器的补赶突发

A轮6.00/6.25/6.50秒时，AwaitingFast=0，AwaitingBackground=2048，计划未发送分别62/187/312笔。后台观察批量完成、总名额释放后，原派发器集中追赶：最密10ms发81笔，100ms发257笔，250ms发487笔。成员0首次429发生于约7.0145秒。

这不是始终平滑的500TPS。补发会放大成员瞬时压力，但不能单独解释全部存储等待。NoSync也改善后台跟块速度，降低触碰2048的机会，因而A/B结果包含存储与负载反馈的联合变化；不能把所有收益线性换算为fsync耗时。

## 与GPT的讨论和建议

已在“评审两版支付系统”中分享代码、现场、补发时间线，并讨论归因边界。共同确认：先解决输入节拍的测量问题，再评估成员同步策略；第四票取消是放大因素，未证明是唯一根因；不能因ctx取消撤销已受理事务或提前返还预算。

建议下一步分开做：

1. 压测器增加不累计欠额的发送节拍/很小的突发限额，仍保留原计划时间、全部请求、实际发送速率、发送滞后和后台队列指标。发不满500就明确报告，不能重设时间掩盖积压。
2. 按用户每次重启实验、不要求恢复的用途，将成员NoSync做成显式实验选项，保留正常运行中的原子更新、隔离、顺序裁决和所有业务检查，并与默认同步模式分开记录。在相同平滑负载下复测，再决定采用。NoSync仍写数据页，并非内存数据库，也不再提供原先“可靠落盘后签票”的崩溃保证。
3. 取消前置只作为后续小减负：未受理前可响应取消；入队成功后的事务仍按原流程完成。不要为了释放HTTP名额而把无界事务留在后台。

本次足以定位优先方向，无需先扩大128、删除验签或重写共识。独立机器上的存储争用可能不同，不能把同机数字当部署环境的确定上限。
