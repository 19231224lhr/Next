## 网关向成员分发：这次精确量了什么

原先这个粗区间是“网关 handler 进入 → 成员 handler 进入”，其中还混入了网关授权检查、序列化、HTTP 建连、操作系统及成员运行时调度。

新增标准库 `httptrace` 时间点：分发协程启动、序列化完成、取连接、建连、取得连接、请求写完、首字节返回；同时记录**实际被收进证书的三个成员**。下表每笔选择“网关收下第三份有效票”的对应成员，共 100 条关键路径，不再用最晚签名者猜测获选集合。

| 可相加的关键分发路径 | 均值 / ms |
|---|---:|
| 网关解码与付款授权检查 | 1.958 |
| 准备扇出、安排本成员请求 | 0.085 |
| 已安排 → 分发 goroutine 开始 | 0.299 |
| 客户端进入、序列化与 HTTP 请求准备 | 1.605 |
| 获取连接（包括需要时的建连） | 2.831 |
| 取得连接 → 请求写完 | 0.195 |
| **请求写完 → 成员 handler 进入** | **23.656** |
| **网关 handler → 成员 handler，全程** | **30.630** |

全程 P50 **33.91 ms**、P95 **55.61 ms**。约 **77.2% 的累计分发时间**落在“请求已写出，但成员 handler 尚未开始”这段。这里 WroteRequest 代表 HTTP 客户端完成写入，不代表服务端已读到，更不能把后面的全部差值叫网络传输延迟。

连接不是主要解释：首 64 笔的关键请求获取连接均值 4.39 ms，后 36 笔仅 0.06 ms，但后者取得连接到 handler 仍平均 27.46 ms。在全部 300 份获选响应中，202 份使用新连接、98 份复用；复用连接的“写完 → handler”仍平均 14.02 ms。两个统计集合不同，不能互换。

代码核对结果：

- `Collector.CollectDirect` 本来就是四路 goroutine 并行，取得三份有效票后返回，没有等第四份的同步屏障。
- `MemberHandler` 前台配额是非阻塞准入，满了返回 429，不在这里排一个隐藏队列。本轮无失败。
- 共用 HTTP Transport 每目标最大连接 128、最大空闲连接 64。本轮主要延迟在**已经取得连接并写完之后**，没有证据支持优先扩连接池。
- 分发之后，关键成员的数据库排队均值 21.81 ms、回调本身 0.107 ms、回调结束至持久返回 26.71 ms。这些属于后续认证阶段，不混入上表分发，也不能把末项直接等同一次 fsync。

完整样本：[300 条获选成员路径](selected-members.csv)、[100 条第三票路径](quorum-completing-member.csv)、[汇总](dispatch-summary.json)。

## 额外运行时诊断：发现 GC 与调度等待

为判断成员 handler 为什么迟迟没开始，另建一个独立创世网络补测 100 笔，同时收集网关和四成员的 Go runtime trace。该轮全部成功且审计通过，耗时 **2.113 秒**，快速到账 P50 **168.94 ms**。它增加了运行时采样负担，**不与上述正式轮合并、不用于宣称性能升降**。结束后恢复正式轮的高度 7 网络，其交易数仍为 100。

通过记录相同的 Unix 纳秒时间，将每个 handler 对应到 runtime trace 的 goroutine，按“请求写完 → handler 进入”的实际区间裁剪状态。第三票关键路径共 100 条：

| 该区间内的互斥状态 | 墙钟均值 / ms |
|---|---:|
| GC 协调等待（栈含 `gcMarkDone` / `gcAssistAlloc`） | **9.235** |
| GC 标记协助等待 | **5.077** |
| Runnable：可运行但尚未得到运行机会 | **5.260** |
| 网络等待状态 | 3.028 |
| 连接 goroutine 尚未创建 | 2.275 |
| Running / Syscall / 其他合计 | 0.032 |
| **总计** | **24.906** |

在这轮诊断中，明确的 GC 等待合计 **14.31 ms，占 57.5%**；Runnable 另占 21.1%。GC 停止世界与区间平均重叠 12.32 ms，但它与上述状态有重叠，**不能再相加**。Running 也不等于实际消耗的 CPU 时间。

具体例子：交易索引 63、成员 0，写完到 handler 为 **49.28 ms**。其中 **45.00 ms** 的等待栈为：

```text
net/http.(*conn).serve
  → net.(*TCPAddr).String
  → runtime.slicebytetostring / mallocgc
  → runtime.gcAssistAlloc
  → runtime.gcMarkDone
```

这已经发生在 UTXO 业务处理之前，**不是应用数据库锁，也不是网关顺序发四次请求**。它证明至少一类慢请求被成员的 GC 协调拖住。14 个独立 Go 进程共享 16 核，每个成员在 trace 中报告 GOMAXPROCS=16；多进程争用是值得验证的候选原因，但本轮未做 CPU 隔离对照，不能据此认定是唯一根因。

运行时跟踪自身会分配内存、记录栈并扰动调度；因此 57.5% 只描述这轮诊断，不能机械套到正式轮。下一步若继续，应先做**关闭 runtime trace 的受控对照**，分别验证每进程 CPU 并行度与 GC/分配压力的影响；保留所有验签和同步写入，不直接重写网络层，也不关闭 GC。当前仅定位，没有应用这些调优。

运行时汇总：[runtime-summary.json](runtime100/runtime-summary.json)；逐条归因：[runtime-attribution.csv](runtime100/runtime-attribution.csv)；原始二进制 trace 位于 `runtime100/reports/runtime/`。展开的文本视图可重建，已排除 Git。

新增埋点测试覆盖真实 HTTP 新连接/复用连接、诊断关闭不记录事件、并行扇出头部容量，以及仅已有 localhost debug 路由内的 runtime trace。相关 race 测试、全项目 `go test ./...` 和 `go vet ./...` 均通过。业务与共识参数不变，数据来源和二进制哈希保存在 `metadata.json`、`runtime100/metadata.json`。

正式结果证明此次新创世的 100 笔闭环正常，不等于持续吞吐上限。当前前台定位已从模糊的“分发慢”缩小到**HTTP 写出之后的成员接收、GC 和调度等待**，其余数据库与后台阶段独立保留测量。
