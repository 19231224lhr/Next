# 100 笔 UTXO 后台分阶段诊断

日期：2026-09-19。基线：`bbdd4a2c036fc6bdb9a0384d33e41a024c6c23e1`，加本目录 `instrumentation.patch` 的诊断修改。

## 结论

**本轮最大的等待在担保组织投递到委员会之前。** 网关完成快速证书组装后，到委员会首次收到交易，中位数 **1,877.79 ms**，P95 **3,890.21 ms**。委员会收到后的单笔检查与执行通常只需约 **1.4 ms**。因此，下一步应优先检查组织侧持久化与投递调度，而不是先削减委员会验签。

这次只补测量，没有优化业务路径。实际发送恰好 100 笔，无预热付款，100 笔成功。四个委员会各有 100 笔已完成记录，状态哈希相同，缺口为 0；停节点后的审计显示所有组织成员和网关投递队列为 0。

## 实验与时间口径

- Mac Studio M4 Max，所有进程在同一台 Mac；两组织各四成员、两个网关、四委员会。使用独立创世目录 `.run/trace100-v4`，不复用旧交易。
- 总计 100 笔、最多 64 笔未完成；每笔消费独立的已最终 UTXO，跨组织收款。工作线程等当前交易完成钱包观察与成员状态检查后，才发送下一笔。它是有限的闭环负载，不是恒定到达率或最大 TPS 测试。
- 每笔从付款钱包调用 HTTP 发送前开始计时，预构造、签名和保存请求不计入该笔延迟。剩余 36 笔在压测程序中的发送前排队另列 `send_offset_ms`，不混入交易延迟。
- `UTXO_EXPERIMENT_FLUSH=10ms`、`UTXO_EXPERIMENT_GOSSIP=10ms`；保留全部验签、同步持久化、后台 INSTALL、跟块更新。开启 `UTXO_SETTLEMENT_TRACE=1` 和 `bench-v4 -trace`。
- 埋点写入有界内存，不写共识状态。后台原始记录在付款实验结束后再获取；原有压测程序的成员状态查询仍保留。全部节点记录未达到 4,096 条上限，四委员会各完整关联 100 笔。
- 单进程时间差为本机测量；跨进程时间戳也来自同一 Mac。不能直接推广为跨地域网络结果。开启埋点的本轮不能直接用于宣称相对无埋点旧实验的性能提升。

当前块 H 的结果承诺放在 H+1 的认证头中，因此读取 H 需要下一高度材料。这与委员会主动向钱包发送逐笔证明不同。表中的 277.50 ms 包含下一高度推进、轮询和读取；**不要求等 H+1 的应用 Commit 返回**，相应头部可能更早可读。

成员侧补充：org0-member0 跟块的存储排队中位数约 0.007 ms，整块本地状态应用约 2.24 ms，应用结束到 Update 返回约 28.19 ms（16 个成功跟块样本）。本轮证据不支持把主要秒级等待归因于成员逐笔核销验签。

## 排队在哪里

| 相对实验开始 | 已发送 | 快速到账 | 委员会已收到 | committee0 已提交 |
|---|---:|---:|---:|---:|
| 0.25 s | 64 | 64 | **3** | 0 |
| 1.00 s | 67 | 64 | **3** | 3 |
| 2.00 s | 68 | 68 | 24 | 11 |
| 3.00 s | 83 | 83 | 47 | 27 |
| 4.00 s | 100 | 100 | 67 | 55 |
| 5.25 s | 100 | 100 | 100 | 83 |
| 5.75 s | 100 | 100 | 100 | 100 |

最直接的证据是 0.25 s 时：64 笔已快速到账，但其中 61 笔尚未送达委员会。约 0.18 s，网关首批 3 笔投递调用已经返回；下一组任务却直到约 1.157 s 才进入，间隔约 977 ms。这个时间差发生在组织投递循环推进中。

对应代码路径：

1. `cmd/gateway/main.go` 给网关传入原始 Bolt 存储；证书持久化没有使用成员侧已有的 Group 批量提交。`internal/store/bolt.go` 用一把写锁串行执行同步事务。
2. `internal/gateway/relay.go` 每次扫描最多 16 条，分成每组 4 条；每组必须全部返回，下一组才开始。外层还有 100 ms 定时扫描。它不是持续释放空位的工作池。
3. `internal/gateway/direct.go` 在网关端先等待 INSTALL 目标成员结束，再投递。投递返回后，还要在同一个网关数据库中保存下次重试时间，整个任务到此才返回。
4. 记录按交易事实键扫描，不按钱包发送时间；扫描游标后方的新记录要等待下一轮。因此单笔等待取决于所在扫描位置，未必按发送顺序递增。

**已测定的是组织投递队列的秒级等待和上述串接路径；写锁排队、磁盘同步与调度各自占那 977 ms 的多少，尚未独立埋点，不能把它全部称为 fsync。** 现有记录足以确定下一步优先区域。

## 是否越晚发送越慢

按实际 HTTP 发送时间排序，每 20 笔一组，取各组中位数：

| 发送顺序 | 快速到账 ms | 凭证响应 → 委员会接收 ms | 发送 → 真实提交 ms |
|---|---:|---:|---:|
| 1–20 | 224.53 | 1,889.87 | 2,698.74 |
| 21–40 | 223.93 | 2,648.53 | 3,489.25 |
| 41–60 | 221.36 | 1,966.80 | 2,930.39 |
| 61–80 | 165.29 | 2,165.11 | 2,818.88 |
| 81–100 | 126.98 | 1,504.45 | 2,062.95 |

本轮有明显排队，但**没有呈现发送序号越大延迟必然越大的单调趋势**。前 64 笔近乎同时发送，后 36 笔受闭环并发限制分批进入；负载停止后队列排空。是否在持续固定输入速率下无界积压，需要后续持续负载测量，不能由这 100 笔直接断言。

## 测量边界与下一步

`follow_committed` 是跟块存储 `Update` **返回后**采集的时间，并非磁盘硬件完成时间。另一个 goroutine 的只读查询可能已经看到新状态，而跟块 goroutine 尚未返回或记录时间。本轮部分 `wallet_observe_lag_ms` 为负，最小约 -38.26 ms；保留原始数值，不裁成 0，且不把该差值当作纯轮询延迟。同样，`wallet_update_flush_ms` 包含存储提交、返回和调度，不能全部归因于磁盘。

下一步建议只改组织侧最明显的串接点，分别验证：复用已有 Group 合并网关写入；让付款提交不依赖完成所有后台 INSTALL；减少投递循环中不必要的整组等待。先逐项小改、保留持久化与重试语义，关闭埋点做同负载成对复测，再讨论提高并发。此次尚未实施这些优化。

验证：相关包测试、存储/中继/传输/成员/跟块的 race 测试，以及 `go test -tags=comet_v3 ./...` 均通过；真实 100 笔闭环与停机审计通过。
