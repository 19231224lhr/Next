## 问题与判断

最近一轮 100 笔／64 闭环并发全部成功，埋点轮总闭环 2.619 s，无埋点参照轮 2.538 s。“接纳→提案准备”P50 301.13 ms，“提案准备完→开始执行”P50 309.04 ms，不是协议固定要求的两次 300 ms 等待。

前一段主要与前一高度尚未提交的区间重合；后一段包含提案传播、检查、两阶段投票及持久化。重合不是完整因果归因；多数高度的 100 ms TimeoutCommit 期限已经在处理过程中消耗，不能假定降低参数再省 100 ms。

当前 direct 公共付款绕过旧版验证缓存。同一份材料在 CheckTx、PrepareProposal、ProcessProposal、FinalizeBlock 检查及 ExecuteAt 中反复解析、验证。63 笔业务块实测：

| 工作 | 整块耗时 |
| --- | ---: |
| PrepareProposal | 39.811 ms |
| ProcessProposal | 39.375 ms |
| Finalize 内检查累计 | 39.222 ms |
| Execute 累计，包含又一次验证 | 49.554 ms |
| 应用 Commit | 67.832 ms |

这些数字不能直接相加作为端到端可节省时间。100 笔仅落入 4 个业务块，表中不是 100 个独立区块样本。

## 第一步：复用本节点已完成的静态验证

最小改动集中在 `internal/committee/precheck.go`、`engine.go`、`direct.go`，以及 `internal/rules/direct.go` 的只读 TxID getter。调用方和共识流程保持原样。

- 包住 `verifyV3`：命中返回已验证对象，未命中走完整原验证，成功后缓存。
- 每个 Engine 私有缓存；配置已在 NewEngine 内深拷贝，运行中固定，无须额外上下文摘要或 TTL。配置切换需新 Engine／清空缓存。
- 键使用 `protocol.Digest("VERIFIED_DIRECT_SUBMISSION_BYTES", raw)`，覆盖完整公共报文，包括 OwnerAuth、Funding/opening、组织认证及输入凭证。不能用 TxID、Fact 或变色龙交易哈希。
- 缓存已冻结的只读验证对象；不保留调用者原始缓冲。调用期间 raw 必须只读，现有调用不需要为每次命中额外复制报文。
- 把现有约 50 行 FIFO 容器提取为内部 `verificationCache[T]`，旧／新验证对象分别实例化。每份保留 2048 条／8 MiB 编码字节预算；两份合计上限 16 MiB 编码字节，不是 Go 堆内存精确上限。超大单项照常验证但不缓存，也不挤掉已有项。
- 查找／插入持短锁，验签在锁外；首版允许并发冷 miss 重复验证，不增加 singleflight 或新的调度层。保留现有 put 的锁内同键检查，重复插入不能重复追加 FIFO 或增加字节计数。
- 当前账本上的消费状态、余额、grant、责任及赔付终态仍由 EvaluateDirectPaymentAt 每次检查。ClockTick 和 RepairInput 不进入本缓存。
- ExecuteAt 用已验证对象的值类型 TxID getter 记录 PaymentLocation，省去末尾再次解码；不暴露内部交易指针。

组织三票认证、所有者签名校验、担保责任规则和同步持久化全部保留。冷启动与缓存驱逐只影响速度，不能影响裁决。

## 验证与测量

1. 记录完整验证次数、命中／驱逐／超大项数及编码字节占用；按阶段保留时间。不能只看命中率。
2. 容器先测并发同键插入、FIFO 驱逐、条数／字节边界和超大项绕过。业务重点测试：同 ID 下 OwnerAuth、Funding/opening 或认证材料变化必须重新验证；暖缓存后账本消费／授权变化仍正确拒绝；相同交易重复提交仍幂等；冷热、驱逐、重启结果一致；并发 race 和对象只读性，以及调用结束后改变原始缓冲不能改变缓存对象。
3. 复用既有子先父后、部分赔付、历史修复及重放测试，核对费用、结果和状态根。
4. 固定 63 笔有效块以相同父状态、命令顺序和高度／时间做禁用、冷、热对照；热组只预热验证，不提前执行交易。再以相同 100 笔／64 并发、新创世和原配置做 A→B→A（A 禁用缓存，B 启用缓存）。缓存开关对照两边都用同一 getter；原提交另作完整补丁对照。
5. 同时报告块大小／轮次、真实全验次数、Prepare／Process／Finalize／Commit、逐笔到账／上链和整批排空。四委员状态、费用、outbox 排空仍须一致。

## 第二步：依据新测量拆解持久化

先细分应用 Commit 的编码／准备、等待与实际数据库提交；63 笔块 67.8 ms、其他业务块约 21 ms，不能全归为 fsync。

之后在同一轮测量提案／投票的 WAL 与 FilePV，再检查 BlockStore 和 EndHeight WAL。只有证明属于同一持久化边界内的重复工作才考虑合并；当前不删 sync、不改双签保护、不同时调整超时。

## 可确认与待验证

已确认存在可复用的重复解析与静态验签路径。缓存命中可以省下这些重复工作，同时维持现有执行裁决。

尚不能确认两个约 300 ms 区间会缩短多少、总闭环改善多少，或持续 TPS 上限。必须以实现后的对照实验判断；缩短前块处理有望减少下一块等待，但不是消除所有等待。
