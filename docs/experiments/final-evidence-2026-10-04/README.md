### 等待分解

下表为三个运行的 P50 的中位数，逐跳差值后统计。阶段分位数不可相加。委员会时间采用实际取数端 committee0；这与提前续花判据使用四副本最早提交是两个口径。

| 区间 | fast | wait |
|---|---:|---:|
| committee0 应用提交→完整 BlockData 返回 | 395.096 ms | 285.884 ms |
| 完整取数→VerifyBlock 成功后的 PrepareBlock 入口 | 0.114 ms | 0.0835 ms |
| 上述入口→本地事务成功后的回调 | 0.940 ms | 0.128 ms |
| 提交后回调→驱动观察 | 2.669 ms | 3.099 ms |
| 接收→下一跳实际发送 | 0.269 ms | 585.442 ms |

`transport.CommitteeClient.Block(h)` 先请求 `/commit?height=h+1`，再取 h 的 block/results。RPC 对最新高度使用 LoadSeenCommit，对较早高度使用 LoadBlockCommit；该接口不要求客户端另外等待 h+2。`finality.VerifyBlock` 检查 h+1 的签名头和对 h 及其结果的承诺。应用提交到取数仍包含下一高度证据形成、副本/跟随、轮询和网络等，**不是最早可得时间，也不是纯查询开销**。最后失败记录不能界定全局证据可得区间。

时间来自同一主机 UnixNS 跨进程关联；链总时长沿用客户端单调时钟。成功获取到 PrepareBlock 入口是验证阶段，非纯密码验签计时；本地提交后回调也包含调度且 NoSync 钱包不等耐久落盘。原始带符号差值保留，fast 的公共观察→下一构建为负表示已经续花，不列成顺序等待。插桩计时属于本轮配置，不声称开销为零。见 [逐跳 CSV](results/follow-timing.csv)、[分析](results/follow-timing-summary.json)。

### 评审追加：轮换签署者的备付损失边界

新增 `TestRotatingQuorumsReachFundedLossBound` 使用实际成员批准、公共执行及赔付入口。一个拜占庭成员绕过自身额度签名，三个诚实成员按 (0,1)、(0,2)、(1,2) 轮换，每轮认证一个 100 CAL 的永久 Intent 失败来源，再由合法子交易消费并赔付。备付 300→200→100→0，诚实成员累计预留依次为 (100,100,0)、(200,100,100)、(200,200,200)。第四笔在全部诚实成员处被额度检查拒绝；重复赔付无新增扣款，CAL/FUEL 守恒。

这是确定性回归，证明全局资金覆盖上界可达到，修正“固定三个签署者两轮后停止”不能代表最大损失的误读；不测量攻击盈利、攻击成本或部署韧性。原输入仍受签名锁定，不能把组织损失直接当作攻击者自由收益。[实际执行日志](rotating-quorum-regression.log) 保留完整三轮状态。

## 发送名额复算与最终版本身份

[analyze_dispatch.py](analyze_dispatch.py) 从既有时间戳复算 [dispatch-analysis.json](results-mixed/dispatch-analysis.json)。驱动先取得快速名额，再进入串行发送限速器，到钱包到账后释放。因此第 3 轮全部名额占用时间的 **63.31% 在 HTTP 发送前**；这段 P95 589.422 ms，与限速等待 P95 589.418 ms 对应。917 次快速上限检查点上，已取名额未发送和已发送待到账任务的中位数分别为 59 和 5，不能据此把 64 个名额都理解为正在执行的慢成员请求。

这是对计数口径的细分；保留总未完成回压，不推断 CPU、存储、跟块中的根因。释放时刻使用紧邻 fastDone 前的 FastUnixNS 近似。

[构建一致性检查](../../paper/review-2026-10-02/fourth-revision-2026-10-04/build-identity-check.json) 核实309项清单=305项构建源码（含测试）+两个驱动+go.mod/go.sum；链、P、R 实际节点与客户端一致。最终八包回归见 [final-targeted-regression.log](final-targeted-regression.log)。本轮网络实验共 **23,654 笔**（600+21,048+2,006），均闭合；轮换回归单列，不混入网络性能统计。
