# 最新批量提交版的逐阶段耗时

数据来自 `trace-b`：100 笔独立最终 UTXO、64 闭环并发、跨组织、完整埋点，代码为 `824f059` 的网关实现。不是空闲状态下单笔测试，也不是无埋点的 3.92/4.15 秒两轮。没有为本次分解重新发交易。

每笔从付款钱包发送 HTTP 前计时。100 笔全部可关联各阶段；快速到账中位数 184.67 ms，发送到 committee0 本地提交 1679.72 ms，发送到钱包观察并验证上链 1958.65 ms。整个 100 笔实验至全部完成观察为 3.781 秒。

前台与后台并行，网关与成员均可能中继；网关排队和 INSTALL 是网关路径，实际首次收到的提交可能来自成员。不能把所有表行当作同一串行关键路径，也不能把各行中位数相加得到端到端中位数。共享区块阶段按本轮 100 笔付款加权，不是独立区块样本。

下一高度认证头用于钱包验证此前区块及执行结果；301 ms 包括它的形成、可获取及钱包轮询，并不意味着本笔交易又等待 301 ms 才真正上链。组织成员自行跟块也并行发生，从 committee0 提交到四个签发成员都记录跟块完成，中位数 384.92 ms。

`transactions.csv` 中的 `wallet_observe_lag_ms`、`member_observe_lag_ms` 是观察时间相对于异步完成埋点的有符号偏移。状态可能在完成埋点写入前已经可见，因此可为负，不能解释成负的物理处理时间。

## 优化优先级

1. **先检查投递调度。** 44 个处理组的运行中位数 78.11 ms；有提交的组，从本组最后一次 Submit 返回到组结束，仍有中位数 29.61 ms。累计投递排队时间的 96.40% 与先前处理组运行重叠。说明组占用依然限制推进，但不能把这部分全部归因于写锁或 INSTALL。下一步应分别测组内 INSTALL、状态提交，以及一个任务结束后是否必须等待同组其他任务。
2. **随后检查 INSTALL 的实际工作。** 本轮每笔约 55 ms；现有数值包含远程成员处理和持久化，尚不能认定其中哪些验证冗余。先分解，再决定缓存、合并或调度调整，不能直接删除证据保存。
3. **最后单独评估共识等待与跟块观察。** 270/295/301 ms 值得关注，但分别属于选入提案、共识推进和钱包获取认证头；对延迟和持续吞吐的影响不同。逐笔最终检查和业务执行都不足 1 ms，本轮不应优先删减这些检查。

快速路径的 141 ms、48 ms 也应继续跟踪；前者包括成员请求、验证、预算占用及同步持久化，后者包括钱包验签和保存，现有数据不足以把它们称为纯验签开销。
