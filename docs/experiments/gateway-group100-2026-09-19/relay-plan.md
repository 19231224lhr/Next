# 公共投递等待：定位与最小改造方案

日期：2026-09-19。原评审基线为 `8b39df1`。网关调度的第一项改造已实现，见 [第一步结果](../gateway-relay100-2026-09-19/README.md)；成员延迟备用的实现与验证见 [第二步记录](../gateway-relay-fallback-2026-09-19/README.md)。纯重试时间内存化尚未实施。本文保留原方案及边界，不更改支付协议与委员会结算规则。

已与用户指定的侧边栏 [GPT 完成两轮评审](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)。最终顺序：动作解耦与到期前置 → 成员有限延迟备用 → 纯重试时间内存化。滚动并发是配套，不能将组屏障认定为全部或主要可消除损耗；技术结论以代码和实测为依据。

## 结论与证据

733.02 ms 是这次 100 笔、并发 64 实验中，网关 outbox 保存完成到首次进入 relay 处理的中位等待，不是委员会执行一笔付款的耗时。当前组织中继把证据复制、公共提交、重试状态写盘串成一项工作，再以四笔为一组等齐。这种调度耦合没有业务必要，是当前应优先移除的限制。

| 实测或代码事实 | 含义 |
| --- | --- |
| 每 100 ms 扫描、每批最多 16 项、四项一组等齐 | 新任务没有保存后立即唤醒；慢任务延迟下一组 |
| 公共 Submit 在 INSTALL 扇出全部返回之后 | 成员复制的延迟直接占用公共投递通道 |
| INSTALL 扇出中位 54.83 ms | 是前一批任务服务时间的一部分，不应再全算成本笔 733 ms 的独立分项 |
| 成员 INSTALL 写事务前中位 0.64～0.86 ms，写事务阶段 36.56～40.60 ms | 主要等待在存储路径，删除验签不是解决方向；写事务阶段包含排队与持久化 |
| 100 笔触发 498 次 Submit：网关 100、成员 100/100/100/98 | 五个发送者存在实际重复工作；不代表执行了 498 次或验签放大五倍 |
| 总计 1,140 次 relay 处理及更新请求 | 尚未到期的任务也先解码、验签，再判断是否提交；无变化更新不等于物理写盘 |
| 组内已分配任务空槽比例 9.35% | 只把四笔等齐换成滚动并发，未必有很大收益；96.4% 等待与前组重叠不等于 96.4% 都可删除 |

后四项可运行 `python analyze_relay_work.py` 重算，输出 [relay-work.json](relay-work.json)。包含未满四项的组时，按全部四槽计算空槽比例为 14.57%。这些是现有日志分析，不是新的性能实验。

## 第一项改造：保存后分开推进

```text
完整付款材料持久保存至同一 outbox
    ├─ 提醒公共投递：有空位就向委员会提交
    └─ 提醒 INSTALL：独立向成员复制完整材料

已验证成功区块 → 钱包更新状态、成员核销、删除对应 outbox
```

只在当前 wire4 网关中继实现，不先动旧版路径、成员备用策略或共识参数。复用现有 outbox、Group、HTTP 客户端，不增加消息中间件。

- **滚动补位**：公共投递和 INSTALL 使用独立、固定上限的执行槽。一个完成就补一个，不再等待同组其他任务。公共并发保持 4；当前 INSTALL 也限 4 个目标 RPC，避免“4 个任务各自扇出 4 路”的隐性放大。
- **保存后唤醒**：持久成功后发送非阻塞提示；提示只是加速，原始任务仍在数据库。启动扫描、定时补扫继续保留。新增提示与旧任务游标公平推进，队列满可丢提示，不能丢持久任务。
- **先检查资格**：先分别判断 Submit、INSTALL 是否到期、是否已有同类任务排队或在途，再解码验签和更新。Submit 未到期不能阻止仍需执行的 INSTALL。不让未到期任务占用执行槽睡眠。一次调度可以复用同份已验证且不可变的材料。
- **独立去重**：公共任务按 `(FactID, Submit)`，复制任务按 `(FactID, Install, 目标成员)` 覆盖排队及执行中状态；完成回报不能丢。ACK、唤醒、执行槽属于临时调度信息。

公共完成不以 HTTP 202 为准，仍以已验证成功区块为准；INSTALL 仍持续复制，不能因首次接收成功就永久停止补投。公共块先到时，现有成员可以依据实际批准记录核销，不要求先存在 INSTALL 记录。

首补丁保留当前持久重试时间和正间隔。重试更新必须在事务里重读最新 outbox，记录不存在就结束，只改重试字段，不能回写扫描时的整份旧记录。迟到 INSTALL、迟到保存继续在事务里检查 Observed，避免重新创建已完成任务。临时 ACK 的迟到回报也不能无限保留已完成任务。关闭时先停止接纳与调度，再等在途任务退出，最后关闭 Group。

## 后续独立减负

1. **成员延迟备用**：网关先投递，成员保留有限延迟后的独立补投能力；期限从首次持久安装开始，按成员编号适当错开，随原安装事务保存。重复 INSTALL、202 或重启不能重新开始宽限期。不新增选主或独占投递权。先量化重复请求下降与网关失联后的接管时间。
2. **纯调度时间是否还需写盘**：wire4 的 `NextSubmitUnixNS` 仅控制重试节奏，不负责资金安全或终态；固定交易封装可重发。可考虑后续改成内存节流，保留任务创建和公共完成删除的持久事务，重启允许提前幂等重发。先看第一项改造后重试写盘还占多少，不能为了省一次写盘引入复杂缓存或无界定时任务。旧版路径语义不随之改变。

内存节流若实施，复用调度器和一个有界 `(Fact, Action) → inFlight/nextDue` 表、共用 ticker。未到期或在途条目不能被淘汰后立即重发；表满时新任务留在持久 outbox 等待公平补扫。必须测量调度表满等待，容量过小会变成新的限速器。成员首次备用期限与后续可丢失的重试节奏分开处理。

## 验证方式

先验证慢/失败的一个 INSTALL 目标不会阻挡公共提交，通知丢失和队列满可由补扫接续，持续新流量下旧任务不饥饿，已完成任务不被迟到写入复活，重启与正常退出不遗失持久任务。

性能采用相同环境的原版→修改版→原版 100 笔对照，保留验签和同步持久化；埋点定位后再关闭埋点复测。关注：

- 保存完成→首次实际 Submit、委员会实际接收；不能只把 relay_enter 标记提前。
- INSTALL 和 Submit 各自的排队、执行、最老任务年龄，以及重复/失败请求数。
- 物理写事务数、写盘时间、前台到账 P95、最终上链与全部后台完成时间。
- 再做持续负载，比较已保存、已提交、已上链、已完成任务的速率，确认没有把队列移到 INSTALL、数据库或委员会。

这项改造能删除无必要的前置等待，但不能保证任何输入速率下都不排队。只有后台完成速度长期覆盖输入速度、队列年龄不持续上涨，才支持“持续运行无积压”的结论。
