# 网关批量提交：100 笔对照实验

2026-09-19。基线代码 `1922996`。本目录 `gateway.patch` 是唯一生产代码改动：在 `cmd/gateway/main.go` 中将 Bolt 包装成已有的 `store.Group(256, 64)`，Collector、Relay、BlockFollower 共用它，底层数据库由 Group 关闭。没有新增数据库、凑批定时器、后台框架或协议规则。

## 结论

**批量提交减少了网关真实持久事务和排队，100 笔后台闭环明显加快。** 关闭埋点的三轮原版平均 5.859 秒，两轮修改版平均 4.034 秒，本样本平均缩短约 31%。这不是持续最大 TPS 测试，也不证明后续负载不会积压。

前台并非每轮都变快。无埋点修改版的快速到账中位数为 212、175 ms，原版为 173、157、173 ms；修改版 P95 为 251、229 ms，原版为 200、183、190 ms。补测没有复现首次中位数差距，但 P95 仍偏高，**不能宣称前台延迟完全没有回退**。本补丁直接优化的是后台存储；高并发共享机器上的资源竞争和前台尾延迟仍需下一轮测量。

## 实验条件与时间口径

- Mac Studio M4 Max，4 委员、2 组织各 4 成员、2 网关，共 14 个本机进程。旧版独立实验服务保持原状，未为本实验停止；不属于完全隔离的性能环境。
- 每轮独立创世目录，128 个初始 UTXO/用户，实际发送 100 笔，64 闭环并发，跨组织收款，输入均为已最终 UTXO。各轮随机生成密钥与交易身份，配置一致，不是同一条链重复消费。
- 保留所有验签、同步落盘、INSTALL、4 个投递任务一组、100 ms 扫描、2 秒补投规则、10/10 ms 传播参数。仅替换网关二进制；`binary-sha256.txt` 验证另三个程序两组完全相同。
- 顺序为诊断 A1→B→A2，再无埋点 A1→B→A2；因 B 快速到账较慢，追加无埋点 B2→A3。每轮节点就绪后等待 3 秒，不做预热付款。创世密钥生成和节点启动不计入付款用时。
- **单笔起点**：付款钱包调用 HTTP 发送之前；**快速到账终点**：钱包验证并保存 TXCer 返回；**上链观察终点**：钱包自行获取并验证区块、更新本地状态；**闭环总用时**：首笔发送到最后一笔完成钱包观察及四个签发成员状态检查。发送前压测排队不计入单笔延迟。
- 各表中位数使用两个中间值平均；原始程序 Summary 的 p50 取较低中间值，两者可能略有差别。不同阶段的中位数不能直接相加。

## 有埋点：验证减负机制

| 指标 | 原版 A1 | 修改版 B | 原版 A2 |
|---|---:|---:|---:|
| 100 笔闭环总用时 | 5.932 s | **3.781 s** | 5.626 s |
| 网关保存中位耗时 | 275.53 ms | **58.79 ms** | 322.25 ms |
| 保存后到首次投递处理，中位数 | 1564.14 ms | **733.02 ms** | 1398.05 ms |
| 网关逻辑 Update 数 | 250 | 271 | 265 |
| 网关有实际变化的持久事务数 | 216 | **74** | 215 |
| 网关累计 bbolt 写入与同步时间 | 4.209 s | **1.632 s** | 3.972 s |
| 单笔发送→committee0 本地 Commit，中位数 | 2902.14 ms | **1679.72 ms** | 2601.15 ms |
| 快速到账中位数 | 188.55 ms | 184.67 ms | 174.90 ms |

修改版 271 个逻辑更新进入 124 次底层 Update，其中 74 次真正改变数据并提交；其余跳过无变化提交。批次大小分别为：1×86、2×13、3×15、4×6、7×1、14×2、55×1。**逻辑调用没有减少，但许多调用共享一次持久提交**，符合优化目的。

分析按一个物理事务关联多个业务回调，写入同步时间只计一次。`WriteTime` 包括页写入与同步，不能当作一次 fsync，也不能乘以该批交易数。保存请求到回调开始的等待包含进入事务前的排队；没有把低 Bolt 写锁时间单独当成优化成功依据。

## 验证与实现边界

八轮共 800 笔全部成功。每轮停节点后审计：四委员会均 100 笔已关闭、状态哈希一致、缺口为 0、无逐笔私有证明记录；成员及网关 outbox 均为 0，CAL/FUEL 总量与费用记账校验通过。代码与实验只采用普通已最终 UTXO 输入，未在本轮重跑所有异常赔付场景。

测试命令：

```sh
go test -race ./internal/store ./internal/gateway ./cmd/gateway
go test -tags=comet_v3 ./...
```

均通过。补充验证包括：成功/拒绝/成功同批隔离、提交前不返回、整批存储失败、故障后继续阻断写入、有界队列满时正常关闭；真实网关保存/跟块/重试的三种先后顺序及关闭重开后不恢复已完成 outbox；HTTP 响应可在 Group 持久化阻塞时先被客户端完整读取。使用既有关闭顺序：HTTP 正常 Shutdown 等待仍在 handler 内执行的保存，Relay/Follower 退出后关闭 Group。

这轮不改投递调度。修改后首次投递仍有约 0.73 秒中位等待；下一步可独立定位整组等待、INSTALL 与成员/委员会并发工作的剩余成本，同时观察快速到账 P95。不能把所有处理组占用都归因于数据库，也不能预先承诺增大并发就能解决。
