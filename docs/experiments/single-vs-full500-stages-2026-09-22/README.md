# 单笔与 500 TPS 目标负载的阶段比较

2026-09-22，Mac Studio M4 Max，14 个本机进程；本轮仅测试，没有修改业务代码。

## 结论

单笔快速到账 **12.89 ms**；500 TPS 目标负载下，快速到账 **P50 80.02 ms / P95 703.16 ms**。高负载下成员验证本身仍很短；明显增加的是成员状态更新等待，以及进入网关之前、成员回包和钱包保存等环节的等待。

9 万笔实际发送历时 **195.560 秒**，实际发送 **460.21 TPS**；成功完成 **89,957** 笔，**43** 笔失败。全部任务结束 **197.036 秒**，成功闭环平均 **456.55 TPS**。这轮不支持“稳定达到 500 TPS”的结论。

## 方法与范围

- 两轮均从新实验目录和同一创世配置开始，最终 UTXO 独立输入、跨组织收款；先 1 笔，再 90,000 笔，计划速率 500 TPS、计划发送窗口 180 秒。
- 实际发送时刻是钱包 HTTP 调用前。快速到账终点是收款钱包验证并保存 TXCer 完成；发送前排队不混入快速到账时间。
- 快速到账并发 256，总在途任务上限 2048；受反压影响，实际发送时间超过计划 180 秒。准备交易及请求预保存不计入运行时间。
- 全部记录端到端阶段；内部埋点每 100 笔一次。高负载取得 **900/900** 份完整抽样，包含 2700 份被采用的成员票，900 条最后一票路径；单笔完整记录。样本最大事件数 103，未触及 128 条事件上限。
- 两轮业务二进制相同；成员 bbolt NoSync，网关/钱包/委员会应用状态仍正常提交，Comet 区块/状态等实验内存后端；mempool 10000、TimeoutCommit 500 ms、flush/gossip 10 ms。
- 保留验签、输入消费与额度约束；无全局 settlement/runtime trace，仅请求头触发的内部埋点。抽样快速到账 P50/P95 为 81.49/698.88 ms，未抽样为 80.00/703.16 ms，说明抽样结果与整轮相近，但不是独立的埋点开销对照实验。
- 测试覆盖层仅扩展交易数量、同步 Group 预保存请求、独立输入失败后继续记录（不重试）、1% 埋点；overlay 和二进制哈希已保存。

## 成员内部：决定凑齐三票的最后一票路径

每笔选取最后被网关采用的成员票，分析该成员的真实事件。成员间是并行的，下面不能乘以四。各行是独立分位数，不能把 P50 或 P95 相加得到总延迟。

| 阶段 | 单笔（ms） | 500 TPS 目标轮 P50（ms） | P95（ms） |
|---|---:|---:|---:|
| 分发协程等待启动 | 0.012 | 0.074 | 2.199 |
| 分发启动 → 成员处理入口 | 0.332 | 0.802 | 32.874 |
| 成员接收正文并解码 | 0.155 | 0.133 | 0.467 |
| 成员业务验证 | 0.442 | 0.446 | 1.973 |
| 提交状态更新 → 更新回调开始 | 0.006 | 0.409 | 234.266 |
| 本笔状态更新回调执行 | 0.163 | 0.064 | 0.166 |

| 成员处理入口 → 响应准备好（合计） | 0.850 | 3.617 | 400.780 |

## 判断与下一步定位

1. **验证计算不是本轮主要增长点。**最后一票成员验证中位数 0.442 → 0.446 ms；本笔状态回调执行中位数 0.163 → 0.064 ms。不能据此说高负载让算法更快，单笔仅一个样本，但可以看到并非每笔业务计算涨到了数百毫秒。
2. **成员提交路径的尖峰最值得调查。**更新排队 P95 234.266 ms；本笔回调结束到提交返回 P95 82.637 ms。这两段平均共 56.394 ms，约占同一抽样“分发到三票齐备”平均 77.000 ms 的 73.2%。均值比较使用相同 900 条最后一票路径，不把分位数相加。
3. **NoSync 并未使所有状态更新并行。**更新排队包含 Group/写者等待和运行时调度；回调结束到返回包含同批其他更新、实际写入及返回调度。此处不能直接归因于 fsync，也不能仅凭跨度断言具体是哪类后台更新占用了写者。下一步可按签发、INSTALL、跟块等调用来源拆分同一状态写者的占用，保留本轮对照。
4. **还有一个独立的前置尖峰。**钱包实际发送到网关处理入口 P95 259.696 ms，包含客户端连接、HTTP 接收及运行时调度；这些进程都在同一台 Mac，不能称为纯网络传输时间。钱包验证保存 P95 210.007 ms 也仍需单独关注。
5. 43 次失败均为网关 `503 QUORUM_UNAVAILABLE`；对应网关日志均有成员 `429 LIMITED`。这说明负载尖峰仍会碰到成员接入限制，不能只公布成功样本延迟而忽略失败。

## 运行末状态与数据解释

- 89,957 次成功执行，未发现失败的区块执行；四委员状态哈希一致，全部 outbox 排空，审计通过。
- 实验节点已停止。失败请求仍在压测报告中记作 UNKNOWN，不能凭没有 TXCer 就推断其完全没有局部签名或额度占用。
- 报告中的 sampled_peak_unfinished=2083 和 oldest=153933 ms 包含已经返回错误但没有成功终态的请求，**不是实际 2048 任务信号量突破上限**；本分析按任务释放时刻另行计算在途窗口，不将错误请求永久当作正在执行的任务。
- 发送滞后 P95 14.517 秒，属于原计划时刻到实际发送的差值，不属于 80.02 ms 的快速到账计时。
- 这一轮只比较单笔与高负载，没有声称因果隔离所有竞争来源，也没有改变参数来追求更好数字。
