## 已确认

- 委员会接收 31.416 ms，交易池接收返回 32.323 ms，业务执行开始 756.359 ms。主要未细分区间为 724.036 ms。
- execute 函数 0.118 ms，应用 Commit 13.960 ms。这些不含此前的共识、区块保存和 WAL 同步。
- 同一付款采样时有 28 个投递 attempt，21 次已进入执行。不同随机 nonce 绕过交易池按字节哈希的缓存防重；账务身份仍相同。
- h+1 最终证明要求再出一块，不能通过改测量口径消除该等待。

## 已核对 v0.38.26 源码

- `P2P.FlushThrottleTimeout` 默认 100 ms，控制缓冲发送刷新。
- `Consensus.PeerGossipSleepDuration` 默认 100 ms，在数据/投票传播循环无工作时休眠。
- 原型把 `TimeoutCommit` 设为 100 ms，但这不是整个区块的耗时。
- `TimeoutPropose/Prevote/Precommit` 默认 3s/1s/1s，不能解释为每轮必然睡满。
- `finalizeCommit` 先保存区块、同步 WAL，再调用应用执行；这些工作也落在现有 725 ms 区间内。
- Comet cache 命中不等于仍在交易池，更不等于已得到业务最终证明。

## 分析边界

不改变成员签名前持久化、钱包 READY 前保存、委员会验签和同步提交。202、cache-hit 或普通节点状态只影响传输调度，不允许用来返还预算或核销。

本次已确认的是重复提交造成额外工作；尚未确认它占据上述 724.036 ms 的多少。传播刷新、提案时机、投票传播和共识写盘都是有源码依据的候选，不能把多个 100 ms 默认值直接相加当作测量结果。

## 收敛后的最小改动

1. 在现有 relay/outbox 上保存一次投递的原始封装和下一次允许补投时间。普通重试复用同一封装，不再每 100 ms 生成新 nonce。另保留本代投递开始时间或固定无进展期限，避免把重试调度时间误当进展时间；不引入完整收据矩阵或跨 QC 子集聚合框架。
2. 202/cache-hit 只让发送方短暂等待，同时继续查询证明。重复接收提示和未经验证的 SETTLED 查询不得无限延长无进展期限。超期仍无进展时，以有界退避补投，必要时换投递代际，业务身份始终不变。重启后先查询，再按持久状态恢复补投。
3. 已验证公共业务完成事实后停止补投付款，继续获取缺失的核销证明。outbox 仍按原公共保管完成条件出队；不能仅凭 HTTP 成功删除任务，也不能凭未经验证的状态释放额度。
4. 对已持久登记的 DEFERRED 交易沿用现有依赖唤醒；真实缺父时优先补父。未登记或未持久接受的失败请求保留补交能力。

原始封装复用能消除同一投递者不断制造的新命令；多个独立投递者之间仍可能重复。先测剩余重复数，再决定是否需要按业务身份合并在途请求。

## 验证顺序

1. **补齐测量基线。** 用业务 ID、attempt 哈希、节点和 height/round 关联 PrepareProposal 入选、四节点提案/投票阶段、ABCI 入口及执行前检查。区分未赶上本轮提案、共识传播与应用前写盘；提交到 h+1 证明可用的尾部另计。埋点保持可关闭、有界，不逐事件同步写盘。
2. **只修投递放大。** 保持当前共识和网络参数，比较单笔 attempts、实际入块副本数、钱包 READY、入池到提交、提交到证明耗时。校验重复交易没有重复扣款或返额；覆盖 202 后节点重启、缓存命中但交易已不在池内、重复提示不延期、缺父后父到达及 relay 重启续投。
3. **再单变量 A/B。** 固定投递实现，仅比较 FlushThrottleTimeout 100 ms 与 10 ms；若证据指向 gossip，再另开独立对照。保持验证和 fsync，先不改 TimeoutPropose。用多笔独立、逐笔发送的同条件样本报告分布，不用一次样本宣称优化有效。
4. **最后检查持续运行。** 用短时持续负载观察完成 TPS、积压数量/年龄和重复命令比例。单笔延迟降低不能直接证明持续 TPS 已提高或后台不再积压。
