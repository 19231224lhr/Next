# 委员会等待、同步持久化与 P2P 带宽对照

2026-09-20。基线源码 `a5987b0`；Mac Studio M4 Max，14 个本机进程。
成员固定 `GOMAXPROCS=16 / GOGC=200`。所有验签、同步持久化、BFT 法定人数和跟块认证保持不变。

**结论：定位到了实际等待，但本轮没有建立稳定的整体提速收益。**
保留现行实验参数 flush/gossip **10/10 ms** 和上游默认 P2P 带宽上限
**5,120,000 bytes/s**。新增可选带宽配置和精确诊断，未把候选参数应用到常驻网络。
17,775 笔交易（含 7 笔预热）全部通过业务和资金审计；原 100 笔、高度 7 的网络已恢复。

## 1. 两段时间究竟在等什么

用户引用的 **219.82 ms、272.51 ms** 来自之前 `gateway-dispatch` 的 fresh100。
它们不是协议规定的固定等待。本轮重新测量有波动，下列数值均注明本轮来源，不能与旧轮拼接。

### 接纳完成 → 提案开始

委员会接收交易不代表当前高度还能把它装进去。当前块已经取走交易池快照后，新交易要等下一次提案。
上一高度的共识、区块保存、结果保存、应用提交和状态收尾会延后下一次提案。

`diag-a` 的 100 笔诊断中：

| 区间 | 交易加权 P50 |
|---|---:|
| 入口接纳 → 提案者本地 mempool 检查完成 | 11.532 ms |
| 提案者已检查 → 提案开始 | 273.113 ms |
| 上一项中，处于前一高度 App Commit 完成之前的时间 | 256.217 ms |

累计等待的 **93.15%** 位于前一高度应用提交完成之前。这个时间重合用于定位，
不是“93% 全是无用工作”的因果结论。业务块大小为 **1、63、1、35**；
100 笔付款只产生四个业务块，不能当成 100 个独立共识样本。

首批 64 笔抵达委员会分布跨度约 170 ms，增加 1～10 ms 的空闲合批窗口并不能保证合成一个大块。
`TimeoutCommit=100ms` 从 CommitTime 起算，前一高度后续工作会消耗这个间隔；
不能把参数调成 1 ms 就声称每块减少 99 ms。

### 提案准备好 → 开始执行区块

仍需提案形成与传播、prevote、precommit、持久化和接收足够多有效票。
同一 `diag-a` 的 63 笔块，提案者为 committee1，执行终点取 committee0：

| 相邻事件 | 耗时 |
|---|---:|
| Prepare 完成 → 提案签署完成 | 35.871 ms |
| 提案签署完成 → committee0 收齐提案 | 47.127 ms |
| 收齐提案 → ProcessProposal 完成 | 0.292 ms |
| ProcessProposal 完成 → 本节点 prevote 签署完成 | 37.839 ms |
| prevote 签署完成 → 进入 precommit | 34.744 ms |
| 进入 precommit → precommit 签署完成 | 57.244 ms |
| precommit 签署完成 → 进入 commit | 19.661 ms |
| 进入 commit → FinalizeBlock 开始 | 69.007 ms |
| **总计** | **301.785 ms** |

这些是相邻墙钟区间，不是八类纯 CPU 工作。提案传播区间也含提案者本地 WAL 处理；
投票签署包含 WAL/FilePV 持久化；等票还含其他委员的执行、调度和持久化。
各委员并行或嵌套的操作时长不能再次叠加。

该块 **Prepare 0.210 ms，Finalize 4.920 ms**。Finalize 结束到 App Commit 开始另有
**33.978 ms**，其中 `SaveFinalizeBlockResponse` 实测 **33.949 ms**；
mempool Lock 和 Flush 分别约 **0.001 ms**。App Commit 本身 **18.973 ms**。
因此这一缺口主要在共识执行结果保存，并非 mempool 锁竞争，也不是整块业务执行慢。

已有的清洁 WAL 免重复同步、本地已就绪 Proposal/Parts 合批和应用提交减负均保留。
FilePV 防双签状态、WAL、BlockStore、ABCI 结果承担不同职责，本轮没有证据支持继续直接删同步。

## 2. 第一项候选：缩短传播间隔

同创世、同冻结二进制、100 笔 / 64 闭环并发、无预热、关闭埋点。
顺序为 A、Flush、Gossip、Both、Both、Gossip、Flush、A，各两轮：

| flush / gossip | 完整闭环平均 | 快速到账 P50 均值 | 快速到账 P95 均值 |
|---|---:|---:|---:|
| 10 / 10 ms，基线 | 1.863 s | 140.43 ms | 171.40 ms |
| 1 / 10 ms | 1.931 s | 116.09 ms | 134.35 ms |
| 10 / 1 ms | 1.810 s | 146.32 ms | 156.23 ms |
| 1 / 1 ms | 1.863 s | 129.74 ms | 150.10 ms |

每格分位数先按各轮计算再取均值，并非合并样本分位数。
gossip 单项有小幅差异，但重复数少、完整闭环收益不稳定；两项同时缩短也没有整体收益。
另一次开启埋点的 10/10→1/1 配对出现 2.091→1.822 s，不能挑出这一对作为正式优化结论。
这两轮 100 笔诊断均没有实际触发 P2P rate limiter 等待。

**决定：保留 10/10 ms，不采用 1 ms。**

## 3. 第二项候选：提高实际触发的带宽上限

扩大到 256 笔 / 256 闭环并发、1 笔预热后，原 `wide-a` 的 187 笔大块触发了
`flowrate.Limit → waitNextSample`，多个实际调用约 60 ms。
Comet 默认限额按 100 ms 采样，5,120,000 bytes/s 对应每个采样周期约 512 KB 预算。
只有实际进入等待分支才记事件；多个重合等待不能相加成关键路径耗时，也不能凭事件数推断连接数。

最小生产改动：委员会配置增加 `P2PSendRate` / `P2PRecvRate`，单位 bytes/s。
零值保持默认，正值覆盖，任一负值先报错且不部分应用。协议、数据库和认证路径不变。

### 同二进制的 256 笔诊断配对

两轮均使用 `consensus-bandwidth-bin/committee`，flush/gossip 10/10，其他条件相同。

| 指标 | wide-a2：5.12 MB/s | wide-r：51.2 MB/s |
|---|---:|---:|
| 四委员在测量区间内实际限速等待次数 | 8 | 0 |
| 接纳 → 提案 P50 | 263.605 ms | 212.158 ms |
| 提案准备好 → Finalize P50 | 225.549 ms | 151.133 ms |
| 钱包发送 → committee0 实际提交 P50 | 694.723 ms | 998.330 ms |
| 完整闭环 | 1.236 s | 1.268 s |
| 业务块中测量付款数，按高度 | 1 / 135 / 120 | 1 / 114 / 141 |

限速等待确实消失，但总体验证结果没有一起改善。块分组也变化，交易加权 P50
受哪一块装入超过半数交易影响很大。分段分位数不能相加，不能据局部 P50 宣称整体加速。

### 4,000 笔 / 256 并发，无埋点 ABBA

每轮额外预热 1 笔，网络与创世摘要一致，冻结同一批二进制：

| 轮次 | 带宽 | 完整闭环 | 观测闭环完成率 | 快速到账 P95 |
|---|---:|---:|---:|---:|
| load-a1 | 5.12 MB/s | 16.883 s | 236.93 笔/s | 257.93 ms |
| load-r1 | 51.2 MB/s | 16.737 s | 238.99 笔/s | 304.57 ms |
| load-r2 | 51.2 MB/s | 18.318 s | 218.37 笔/s | 293.96 ms |
| load-a2 | 5.12 MB/s | 17.144 s | 233.31 笔/s | 240.20 ms |

基线平均 **17.014 s**，候选平均 **17.527 s**，候选本次反而多 **3.02%**；
不能据两轮确认回归显著性，但足以不采用它作为已有收益的优化。
平均发送窗口分别约 16.173 / 16.526 s。测量包含钱包观察区块、成员跟块及客户端调度，
不是委员会纯提交 TPS，更不是持续吞吐上限。

离线读取 BlockStore：四轮分别 54 / 55 / 54 / 56 个高度，总交易数均 4,001；
含交易块的交易数中位数分别 64 / 79 / 64 / 50，最大块 216 / 217 / 191 / 201。
这些统计包含预热和认证结果所需的后继块。首块 AppHash 相同，原始数据见 `blocks.jsonl`。
不能把不同的打包结果全部归因为带宽参数。

**决定：保留可选配置，常驻网络继续使用默认带宽。**

## 5. 必须保留的实验限制

1. 原 `wide-a` 的旧采集器错误选择了预热 `bench-v4-0.json`。其委员会时间线、
   256 笔正式报告及审计有效，但 settlement 明细只覆盖预热，不能计算 256 笔阶段分位数。
   `wide-a2/wide-r` 已用修正采集器，不与旧诊断二进制混合求均值。
2. `long-a` 原计划 9,000 笔、150/s，在发送前因 network.json 达 16,835,642 bytes、
   超过 16 MiB 读取上限而启动失败，实际发送零笔。属于实验准备失败，不是系统压测失败。
   生成器改紧凑 JSON 后相同对象为 14,170,408 bytes，解码值与规范化摘要保持一致；
   生产读取上限未改。此长测没有重跑，不能声称通过 150/s 长稳态。
3. 所有节点同一 Mac，墙钟可在本轮对齐，但磁盘、调度和 CPU 也共享；不能外推到多机网络。
4. 100/64 与 256/256、4,000/256 的并发、预热、创世规模不同；较大负载的约 235 笔/s
   说明此实验观察到更高闭环速率，不能归功于本轮配置改动。

## 6. 后续优化应集中在哪里

先围绕真实持久化成本：`FilePV.save` 和 `SaveFinalizeBlockResponse` 的编码、写入与同步占比，
以及四委员共享一块磁盘造成的干扰。一次只改变一个存储或部署因素，使用关闭埋点的成对实验。
不能仅把同步改后台，就认为防双签或崩溃重放边界仍然成立。

高吞吐测量需要分开看付款供给、实际提交、钱包观察、成员排空；保持足够在途量，同时观察
队列是否随时间持续增长。本轮没有发现需要修改 UTXO/TXCer 规则的证据，也没有证明当前共识延迟不能继续优化。
