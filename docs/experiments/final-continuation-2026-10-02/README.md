# 最终版本连续支付重测

2026-10-02 · 评审修订第②项 · 冻结代码 `721800c7de0a6526f58501fb78823d99426b69cb`

**最终版本在成员同步提交的配置下完成了真实 100 跳续花：整链到账中位数为 4.557 秒，逐跳等待公共确认的对照为 64.476 秒，用时缩短 92.93%。六轮共 600 笔付款全部通过审计。**

本轮检验独立赔付决定、来源补交与输入证书校验均已集成的当前实现，是否仍支持正常连续支付。没有修改生产代码或共识参数，没有注入故障或人为拖慢来源。它补齐最终版本的正常长链证据；混合故障负载和历史读者成本属于后续计划。

## 1. 配置和对照

| 项目 | 本轮固定设置 |
| --- | --- |
| 主机 | Mac Studio，M4 Max，16 CPU 核，64 GiB；macOS 26.6.2；Go 1.27.1 darwin/arm64 |
| 服务 | 同机 9 个独立服务进程：1 网关、4 组织成员、4 委员；单组织付款 |
| 钱包与付款 | A→B→C→A 三个独立钱包存储；每跳转手同一条链的 100 CAL；每笔由用户自己的最终 FUEL 支付 |
| 成员存储 | bbolt **同步事务提交后签名**；成员 GOMAXPROCS=16、GOGC=200 |
| 其他存储 | 委员会应用状态、BlockStore、网关落盘；钱包 bbolt NoSync，保留验证与本地原子事务 |
| 共识参数 | commit=250 ms；flush/gossip=10 ms；相同定制 CometBFT v0.38.26 |
| 资金 | 固定且充足的创世资金；不自动补资，不考察最低资本 |
| 测量 | 不开启详细请求/runtime trace；开启轻量 `UTXO_SETTLEMENT_TRACE`，保留四委员应用提交时间 |
| 初始化 | 每轮复制同一份未运行的创世和实验密钥，只更新 GenesisTime；重新启动全部节点，统一预热 3 秒 |
| 次序 | fast/wait、wait/fast、fast/wait；每种模式 3 个独立运行，每条 100 跳 |

`fast` 在收款钱包验证 TXCer 并完成本地记录后，读取刚收到的输出在线构造下一笔。`wait` 使用相同签发路径，但在构造下一笔之前，再等待驱动观察到钱包已经验证该输出的公共执行。两组均未预生成整条链。

主要终点为 **Sent₁ → Ready₁₀₀**：从第一笔实际 HTTP 发送开始，到第 100 笔验证凭证并记录完成。包含第 2–100 笔在线构造和重试；不包含第一笔发送前构造。等待组在 99 个跳间等待，主终点不额外加入最后一笔公共确认。

主要对照的等待/快速比值为 **14.1493**。快速整链范围为 4.498–4.740 秒，等待为 64.461–64.627 秒。统计样本是每组 **3 条链**；600 笔是审计付款量，不是 600 个独立长链样本。P95 采用每轮 100 个数排序后第 95 项，表末为三个运行各自分位数的中位数。

公共观察和成员关闭时间含跟块、验证与驱动轮询；不能当作委员会内部提交时刻。最后一笔公共观察也不自动代表全部祖先都已被观察：三条快速链全部付款公共观察完成分别为 **5.228984、5.253720、5.114055 秒**，另列在 `all_public_observed_ms`。`ClosedChainMS` 取全部 100 笔成员关闭观察的最大值。

快速组三轮各 100 次请求；等待组三轮分别 149、116、142 次尝试，最终各完成 100 笔。重试时间已经计入首次发送到收款，本轮没有逐次归因所有重试原因。比较对象是实际两种驱动模式，不把总差值解释成精确的纯共识等待之和。

## 3. 真实续花，而非独立付款串发

每轮检查第 2–100 跳的输入恰为前一笔输出，构造开始不早于前一钱包 Ready。三个计数分别由不同记录判定，不能相加：

| 三轮合计（每组 297 条父子关系） | fast | wait |
| --- | ---: | ---: |
| 实际请求采用父输出 TXCer 作为证据 | 297 | 0 |
| 首次发送早于四委员最早的父交易应用提交记录 | 297 | 0 |
| 首次发送早于驱动观察到钱包已验证父公共结果 | 297 | 0 |

快速组 **297/297** 同时满足前两项。四委员所有 600 笔的应用提交记录均齐全；计算取四副本的最小 `CommittedUnixNS`，不选择最慢副本。最小发送提前量为 **224.785 ms**。时间戳来自同一 Mac 的系统时钟；这是发送与应用提交记录的先后关系，不是共识决定形成时间的测量。

记录位置为 `internal/committee/App.Commit` 在数据库更新成功后调用 `Settlement.Block(..., "commit_done")`；整链/到账用驱动进程的单调时钟计算。公共观察使用 `observeChainHop` 轮询已验证钱包状态的时刻，并非钱包内部验证的原始时间戳。

快速组实际产生、随后自然履行的缺失来源义务分别为 **3、2、4 项**，等待组为 0。这来自最终义务记录，而不是从“后继先发送”推断“后继先执行”。本轮没有发生赔付或表示修复。

固定付款形状下 TXCer 为 **779 B**，快速链首请求 **1,979 B**，后继请求 **2,766 B**，没有随链深度增长。每笔另带独立的最终 FUEL 输入；固定大小结论只对应这种输入/输出形状。

## 4. 状态与费用审计

- 六轮均完成 100 笔，费用状态全部 Closed；四委员每轮业务状态摘要一致。
- 每个链输入被对应付款消费一次，输出内容和最终所有者匹配；末跳输出未消费。
- 所有组织节点 outbox/Pending 为 0；Open、Repaired、公共 Gap 均为 0；没有赔付扣款或回款。
- 每轮 CAL 总量 **2,000,000,032,000** 与创世一致；FUEL 总量（余额＋Held＋报酬＋销毁）**4,000,000** 与创世一致。创世包含未参与此链的输出及第二组织备付，不把该总量当作活跃流通量。
- 每轮 100 笔实付费用 **9,400 FUEL = 8,400 节点报酬 + 1,000 销毁**，重复尝试未多收；两组织 CAL 备付各维持 10¹²，净 Spent/Reserved 均为 0。

Mac 上 `go test -tags=comet_v3 ./cmd/payctl ./internal/member ./internal/wallet ./internal/committee` 通过；随后每轮执行真实数据库 `payctl audit` 和 `chain-v4 -audit`。下载后运行 `analyze.py` 独立复核逐跳关系、全部副本提交记录、资金、配置与时间序列，六轮全部通过。

旧数据保留在[原报告](../../research/reviewer-revision-2026-10-02/experiment-report.md)。两批构建与实验时段不同，本表说明最终机制集成后的代表性结果，不将小幅数值差异解释成某一补丁的性能影响。旧内存配置的 158.846 ms 是另一种存储条件，不能直接与本轮同步提交比较。

本轮支持的核心结论是：**在签名状态同步保存的配置中，收款后立即续花仍能将公共确认等待移出连续支付的关键路径，且整条链最终正常结清。** 此配置钱包为 NoSync；无故障运行、充足固定资金与单机部署是方法条件。本轮不是最大 TPS、掉电恢复或有限资金持续服务实验。
