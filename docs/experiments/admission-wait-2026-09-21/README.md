# 接纳完成到提案开始：实际入池、取池机会与广播诊断

2026-09-21，Mac Studio、14 个本机节点。本轮调查和评审，没有启用新的性能补丁。

**主要等待发生在交易已经入池、但上一高度尚未结束时。不是交易池凑够交易才出块，也未发现交易已经可取却被提案漏选。**
少部分交易还存在节点间传播延迟，错过上一块取池窗口，进一步放大等待。

## 测量范围

- 复用上一轮 [单笔与 100 TPS 对照](../single-vs-100tps-2026-09-21/README.md) 的完整日志，重新按实际提案者分解。
- 新增私有 Go overlay 探针：一次单笔、两次 100 TPS × 10 秒；共 2,001 笔测量付款，加三笔预热共 2,004 笔。
- 同一 journal-buffer 候选作为基础；共识、验签、同步提交、费用和责任规则不变。flush/gossip 10/10 ms，实际 P2P 限额 5,120,000 bytes/s。
- 三轮全部付款完成，四委员最终状态一致，14 个节点 Pending 为零。广播诊断轮出现 7 次进度查询错误，最终观察及审计仍全部完成；不把它们称为付款失败，也不隐去。
- `probe-tests.log` 保留委员会 race 测试结果。探针只在实验 overlay 构建，未改变默认二进制。原常驻网络已恢复到原高度 7、100 笔付款的数据。

“接纳完成”是入口 committee0 已接纳，不代表所有委员均已入池；“提案开始”是实际提案者进入 PrepareProposal。
新增探针进一步记录实际 ReapMaxBytesMaxGas 开始、结束、选中的封装哈希，以及每个委员 addTx 完成和 Remove。
由此区分“还没到提案者”“已经可取但等高度推进”“已经可取却没选中”。

## 1. 主要时间在哪里

下表来自新增取池探针的同配置单笔及 1,000 笔负载轮，均为算术平均毫秒。
它们不是关闭诊断后的性能对照，不能把轮间波动当优化收益。

| 接纳到 Prepare 的连续区间 | 单笔 | 100 TPS |
|---|---:|---:|
| 入口接纳 → 实际提案者 CheckTx 入口 | 10.112 | 14.006 |
| 等待 mempool updateMtx | 0.004 | 0.465 |
| 进入 ABCI 锁前的处理 | 0.006 | 0.003 |
| 等待 ABCI 锁 | 0.002 | 0.177 |
| 检查及完成入池 | 0.802 | 0.756 |
| **已入池 → 实际取池** | **0.017** | **355.222** |
| 取池开始 → Prepare | 0.020 | 0.671 |
| **合计** | **10.963** | **371.300** |

约 95.7% 落在“已入池到取池”。1,000 笔全部在首次实际可用的提案机会选中：
未发现提前入池却漏选，未出现无法判断先后的边界样本。另一广播诊断轮也得到 1,000/1,000 的相同结论。
这里只对采样轮次成立，不宣称所有负载永不漏选。

单笔发生在空闲系统，入池即可唤醒提案；持续输入时，交易通常到达一个已经开始工作的高度中间。
一旦本块已经取池，新到交易不能再追加到它里面，需要等本块的投票、保存、应用提交和状态推进完成。
因此低负载和高负载还有“抵达块周期的时刻不同”这一因素，不能把整段增长都解释为交易检查能力不足。

## 2. 上一高度在做什么

对原始 1,000 笔日志逐笔取实际提案者的上一高度轨迹，将每笔的等待区间按相邻事件切开。
以下是**交易等待与这些阶段重合的平均时间**；不是各阶段独立执行耗时，不可当作可全部删除的开销。

| 等待落入的阶段 | 平均 ms |
|---|---:|
| 更早高度的处理 | 13.708 |
| 前一高度提案形成及到达 | 44.888 |
| prevote 签署路径 | 43.178 |
| 等待 prevote 法定人数 | 32.649 |
| precommit 签署路径 | 65.828 |
| 等待 precommit 法定人数 | 34.318 |
| 区块保存及相关 WAL 路径 | 48.214 |
| 业务执行 | 4.367 |
| Finalize 结果保存区间 | 29.346 |
| App Commit | 30.383 |
| Commit 返回后到下一高度，包括状态保存 | 31.357 |
| 其他相邻推进区间 | 约 0.636 |
| **总计** | **378.872** |

当前高度 newround→propose 仅平均 0.023 ms，propose→Prepare 0.525 ms。
缩短本高度唤醒或扩大块容量，不能消除之前正在进行的工作。
签署路径包括必要 WAL/FilePV 保存和调度，不是纯密码计算；等票也含其他委员处理，不是纯网络时间。

## 3. 为什么部分交易错过上一块

第一轮取池探针有 170 笔入口接纳早于上一块实际取池，但尚未到上一块提案者可用池中。
其中入口接纳→该提案者 CheckTx 入口平均 93.892 ms；此后的 updateMtx 等待 0.002 ms、ABCI 锁等待 0.510 ms。
这不支持先更换 ABCI 锁模型作为主要优化。

随后专门在广播 peer.Send 前后、对端 reactor.Receive 入口加入带交易哈希及对端标识的事件，再独立跑 1,000 笔。
这一轮有 124 笔错过上一块窗口。对齐实际最先收到该交易的来源节点，得到：

| 124 笔样本的传播区间 | 平均 ms |
|---|---:|
| 入口接纳 → 实际来源节点入池 | 4.394 |
| 来源节点入池 → 调用 peer.Send | 0.0108 |
| peer.Send 调用 | 0.00494 |
| **Send 返回 → 对端 Receive** | **66.202** |
| Receive → CheckTx 入口 | 0.00204 |

Send 返回→Receive 的 P50 为 60.329 ms，P95 为 142.441 ms，最大 191.087 ms。
这是**P2P 入队之后到对端处理入口**的综合区间，含发送排队、缓冲刷新、传输及接收调度，尚不能称为 socket 传输慢。
实际来源可能为中继委员，不能一律假定入口 committee0 直达。来源节点可能先入池后才记录入口接纳，微小负值保留而未裁零。

全网记录 9,008 次 Send/Receive；对端高度追赶等待、Send 失败分支均未触发。
已有 flowrate 等待诊断未记录实际限速等待。不能将这 66 ms 归因于 100 ms 高度等待或带宽限额。
此前 [传播参数对照](../consensus-propagation-2026-09-20/README.md) 也没有建立缩短 flush/gossip 或提高限额的稳定整体收益。

## 4. 对应代码路径与最小优化方向

实际代码链：

```text
入口 CheckTx → addTx → P2P Send 入队 → 对端 Receive → CheckTx → 对端 addTx
                                                            ↓
前一高度投票 → SaveBlock / WAL → Finalize → App Commit / state.Save
                                                            ↓
新高度 createProposalBlock → ReapMaxBytesMaxGas → PrepareProposal
```

- `cmd/committee/main.go` 使用 `proxy.NewLocalClientCreator`。共享 ABCI mutex 的确存在，但新增数据不支持它是本段的主要瓶颈。
- Comet `consensus/state.go` 在 `finalizeCommit` 之后推进新高度；`state/execution.go` 在调用 PrepareProposal 前已执行 Reap。
- `mempool/clist_mempool.go` 包含实际入池、取池和 updateMtx；本轮直接记录了这三个边界。
- `mempool/reactor.go` 的 Send 成功仅说明入发送队列；`p2p/conn/connection.go` 接收路径同步调用 reactor，存在阻塞可能，但还没有证据说明哪一笔共识消息被挡住。

建议按两个层次推进，暂不盲改参数：

1. **小范围定位 P2P 入队→接收。** 对现有 66 ms 区间补出队、实际 write/flush、完整消息接收和 Receive 返回时点，关联同一连接的共识消息。若确认接收 CheckTx 挡住后续共识消息，再考虑有界隔离；若只是缓冲刷新，则优先原生刷新路径的小改动。不能先添加另一套队列。
2. **主要收益仍需缩短真实块周期。** 对已定位的签署状态、WAL、区块/结果保存路径找可合并的重复工作或无必要串行，保留签前保存及提交顺序。复用已有 journal 合并候选，不全面异步化数据库。
3. **每次只验证一个假设。** 同配置、关闭细埋点做成对/ABBA，对比接纳→提案、实际块周期、发送→Commit、前台尾延迟和未完成队列斜率。若仅提前入池却仍进入同一块，不宣称端到端提速。

## 数据与可复核性

- `analysis.json`、`*-waits.csv`：原始对照重分解；运行 `analyze.py`。
- `probe-analysis.json`：单笔及第一轮负载的真实取池判断；运行 `probe_analysis.py`。
- `gossip-probe-analysis.json`、`gossip-analysis.json`：第二轮取池及广播关联结果；运行 `probe_analysis.py gossip100` 和 `gossip_analysis.py` 重算。
- 三个子目录保留 bench、audit、settlement 和四委员时间线；保存了 overlay 源码、构建清单与二进制摘要。不包含实验私钥或数据库。
- 诊断存在额外开销；1,000 笔并不是 1,000 个独立共识块。两次负载诊断的 371/342 ms 差异不作为优化收益。
- 本次没有证明吞吐上限，也没有证明持续积压。它解释了本组样本的等待机制，并缩小下一次优化的排查范围。
