# 侧边栏 GPT 三轮评审记录摘要

讨论对象：[评审两版支付系统](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)。
分享了当前代码路径、日志口径、测量数据和候选方案；以下是摘要，不是逐字引用。
外部评审意见作为待核实建议，不能替代本项目代码与实验依据。

## 第一轮：确认测量边界

GPT 建议用 actual addTx 完成、实际 Reap 开始/结束和逐封装选中记录，替代把 CheckTx 完成或 Prepare 当作取池边界。
还必须查看“上一块的实际提案者”，不能只看最终装入块的提案者。
若首次可用机会已经被选中，就不应把整段等待解释为调度器漏唤醒。

落实：新增私有 overlay 并完成单笔和 1,000 笔实际取池实验。

## 第二轮：检视小改动候选

讨论了三个方向：共享 ABCI 锁改为每连接锁、同步 reactor 接收导致的同连接阻塞、签署状态持久化成本。

GPT 要求：

- 换 ABCI 锁之前，需要证明跨连接锁等待影响关键路径；同连接串行或 mempool updateMtx 不会因此消失。
- 同步 Receive 可能挡住后续共识消息，但慢 Receive 本身不证明关键投票被挡住，需要同连接消息证据。
- 未发现 FilePV 重复保存，不能删除签前持久化或直接异步保存。

落实：新增探针显示 ABCI 锁均值仅 0.177 ms、updateMtx 0.465 ms，故不把换锁列为优先优化。
再跑一组广播诊断，定位到特定错窗样本的 Send 返回→Receive，而不是直接把责任归给 CheckTx。

## 第三轮：依据完成的探针收敛

提交两轮 1,000 笔均全部首次可用机会选中的结果，以及 124 笔错窗样本的 66.202 ms 传播综合区间。

GPT 同意：主要机制已解释——交易等待下一次可用提案机会，前一高度剩余周期占主导。
但这不等于已经完全解释了负载下块周期变长的底层原因；单笔空闲与连续输入的到达时刻也不同。

GPT 修正和保留了三点：

1. 66 ms 是 **Send 返回→Receive**，尚未记录出队，不能称为“出队→接收”。本报告使用正确口径。
2. 124 笔错窗样本不能代表全部交易，也不能按“124 × 一块时间”许诺收益。
3. 目标交易自身 CheckTx 不等锁，仍不能排除它前一个 Receive 曾挡住该连接。

收敛的最小下一步是增加三段诊断：

```text
Send 返回 → 实际出队
出队 → 最后字节 socket 写入 / 必要 flush
完整消息收齐 → Receive 进入 / 返回
```

按同 peer、通道、消息身份关联，并记录前一个接收回调的占用；不先做全量运行时追踪。
若存在未解释区间，再短窗口跟踪调度。必须区分用户态缓冲 Write 和实际 socket Write。

P2P 是较小的可验证切口；若它也拖住提案或关键票，才可能同时缩短块周期。
若没有明确冗余，继续核查存储实现成本，保留必要顺序。
当前没有已证实能直接删掉的大段等待；本轮不新增队列、不改共识、不继续压缩定时器。

验收看追回的取池窗口、实际块周期、Commit 延迟及队列斜率，不只看更早入池。
