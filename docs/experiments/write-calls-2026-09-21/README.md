# 实际 Write/WriteAt 与后台化边界

2026-09-21，承接委员会持久化调查。只增加诊断和独立文件 I/O 对照；未修改生产行为、同步策略或共识参数。

## 结果

Mac Studio、同一创世与配置，以 200/s 发送 4,000 笔，另有一笔预热。先做探索轮 `wc200`，修正诊断计数在 journal Reset/Close 边界的归属后，复测 `wc200b`。两轮共 8,002 笔，全部最终完成，资金审计和四委员一致性检查通过，pending 排空。第二轮完整闭环 20.814 s，快速到账 P50 106.836 ms、P95 165.930 ms；进度查询有 136 次错误并最终完成，不能叫所有 RPC 无错误。

主结论使用第二轮。31 个业务块 × 四委员：bbolt 全部 124 个块样本；LevelDB 可唯一归属 123 个批次，committee2/h18 有并发 journal 事件重叠，保留为 unmatched，不强行归属。

| 实际写入路径 | 每批平均调用次数 | 每批平均字节 | 写调用平均耗时 | 写调用外剩余 |
|---|---:|---:|---:|---:|
| bbolt 数据页 WriteAt | 359.97 | 5,897,711 | 8.888 ms | 0.0217 ms |
| LevelDB journal Write | 10.47 | 312,342 | 73.132 ms | 0.0748 ms |

两条路径中，累计实际写调用区间分别占外层循环时间的 99.76% 和 99.90%。LevelDB 的调用边界是 journal 底层 `iStorageWriter.Write → storage.Writer.Write → os.File.Write`，其中额外逻辑只有字节计数；这不是在给 CRC/组装时间改名。调用区间依然可能包含系统调用和 Go 调度等待，不能直接叫 SSD 设备忙时间。

- bbolt：44,636 次写入全部为 16 KiB，共 731,316,224 字节。相邻偏移连续的调用对为 13,620 / 44,512，即 30.60%；不能把全部页无条件拼成一次连续写。最慢样本 committee2/h24：476 次、7,798,784 字节，写调用累计 204.094 ms，循环外剩余仅 0.036 ms，最长单次 16.808 ms。
- LevelDB：1,288 次写入、38,418,045 字节，多数接近 32 KiB，为日志顺序追加。最慢 committee3/h17：14 次、426,856 字节，写调用累计 171.807 ms，剩余 0.127 ms，最长一次 45.920 ms。`adjacent=0` 是此路径未记录显式文件偏移，不能解释为不连续。
- 第一探索轮 bbolt 更大的尖峰（约 1.9 s）也主要落在多次 WriteAt 中；各轮峰值明显波动，不将某一峰值当固定成本。第一轮日志轮换混入了额外计数，因此不把其 LevelDB 均值作为主结论。

## 合并顺序写的小对照

`merge_probe.go` 使用标准库，在独立文件上做 A–B–B–A。四个并发写者，各写 32 批；每批相同的 384 KiB 数据，并且每批都执行原 `File.Sync`。每轮 48 MiB、128 次 Sync；A 拆成 32 KiB 写入，B 一次写入 384 KiB。数据文件的 SHA-256 全部符合相同期望值。未接入数据库，不宣称验证了 LevelDB 恢复或系统 TPS。

| 轮次 | 写法 | 文件 Write 次数 | 完整耗时 |
|---|---|---:|---:|
| A1 | 32 KiB 分段 | 1,536 | 489.019 ms |
| B1 | 384 KiB 合并 | 128 | 464.537 ms |
| B2 | 384 KiB 合并 | 128 | 411.039 ms |
| A2 | 32 KiB 分段 | 1,536 | 425.744 ms |

A 均值 457.381 ms，B 均值 437.788 ms，约缩短 **4.3%**。各写者累计 Write 时间由平均约 778 ms 降至 75 ms，但累计 Sync 等待从约 974 ms 增至 1,605 ms；这些是跨写者累计值，不能与单轮墙钟直接相加。完整耗时包含相同的校验/关闭步骤。少量样本且轮间波动大，目前只支持“单看 Write 阶段会夸大改善”；不足以据此部署数据库合并写补丁或承诺收益。

## 所有数据库工作改后台是否适合当前原型

可以简化恢复和历史管理，但当前实现不能只给每个 Update 外面套 goroutine：

1. `App.FinalizeBlock` 从 `a.db.View` 读取前状态并创建 Overlay。前一块 Commit 如果尚未完成，后一块可能读到旧的 UTXO/消费状态；即使进程不崩溃也会影响执行。
2. bbolt 同库仍是单写者。增加 goroutine 只是增加排队，不能并发提交同一个数据库。
3. 网关保存、证书传播、成员/钱包跟块本来已有后台路径。非关键归档、统计、可重建索引适合继续后台合批；验证需要的读取、输入占用及块状态提交必须保持业务先后关系。

若明确只测“不考虑进程故障的内存确认性能”，可另设内存权威状态 + 有序异步持久化的实验模式，分别报告内存完成、持久完成与待落盘队列；这会改变当前架构和计时含义，不应混入现有持久化基线。并非一定不能实现，而是不能用简单全面后台化替代当前正确性。

当前判断：不用再优先调查写循环之外的编码/组装时间；热点已到实际 Write 调用。有限合并日志写入是候选，但小对照尚无强收益证据。保持生产版本，下一步如试完整系统候选，应只改同一 journal 批次的有限写缓冲，保留日志字节格式、Flush/Reset/Close、错误处理与 Sync 时点，进行有无缓冲的成对复测，并核对后台排空。

## 复现与边界

- `prepare.py`：独立 modfile/Go overlay；依赖私有副本沿用前一实验。每批在内存汇总，不逐 Write 输出日志。
- `calls.py`：按节点和块关联实际写入。对时间起点微秒精度容许 2 微秒误差，所有 unmatched 明列。
- `wc200b/physical-writes.json`、`physical-writes.csv`：主统计和逐批样本。
- `merge_probe.go`、`merge-probe.json`：独立 I/O 对照。原始二进制文件留在 Mac，不进入导出。
- 完整时间线、审计与独立实验 DB 保留在 Mac 同名目录及 `.run/group-cp-wc200*`。

store、committee、requesttrace 的诊断版本 race 测试通过。原 14 节点实验网络已恢复原二进制和高度 7 的数据。本轮没有生产优化，也没有关闭持久化。
