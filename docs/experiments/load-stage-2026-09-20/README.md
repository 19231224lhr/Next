# 20 TPS 与 200 TPS：各阶段耗时对照

实验于 2026-09-20 至 21 日完成。Mac Studio M4 Max，同机 14 个节点，使用已修复网关 HTTP 响应后串行保存问题的当前工作区版本（基线提交 a5987b0 加已有未提交改动，冻结二进制摘要见 binaries.json）。此次只测量和分析，没有新增业务优化。

**诊断轮中，增长主要集中在委员会接纳后等待提案、提案到执行，以及随后跟块。网关保存已经不是主要增量。** 但几段等待存在前后依赖，不能把它们视为彼此独立的根因，也不能把其中的全部时间都称为可删除的开销。

## 实验口径

- 每档发送 **4,000 笔独立、已最终 UTXO 的跨组织付款**，另各预热 1 笔。相同 48,002 输出创世、每轮新数据库和相同二进制；无其他实验并行运行。
- 20 TPS 的发送窗口约 200 秒，200 TPS 约 20 秒。按相同笔数比较，也按每 500 笔分组检查；两个窗口长度不同，不据此计算“总耗时提速百分比”。
- 快速到账并发 256，总未完成上限 2,048；收到、验证并保存 TXCer 后释放前台名额，后台观察独立继续。原有 25 ms 观察循环不变。
- 成员 `GOMAXPROCS=16 / GOGC=200`；Comet flush/gossip 10/10 ms，默认带宽。验签、同步持久化和共识门槛均保留。
- 首对顺序为 20→200，启用节点阶段埋点，前台固定随机种子抽样约 1/5（两档各 807 笔）。节点时间线及委员会记录扩容为有界诊断缓存；全部测量完成后才导出，未在发送过程中批量查询诊断接口。
- 随后以 200→20 倒序关闭埋点复核整体趋势。不能用无埋点轮的整体耗时拼接诊断轮的分段数据。
- 单笔起点为付款钱包发起 HTTP 请求；委员会提交终点为 committee0 应用同步 Commit 完成。钱包和成员跟块分别统计，组织四成员取该区块最后返回者。

## 诊断轮：整体与前台

| 指标 | 20 TPS | 200 TPS |
|---|---:|---:|
| 支付完成 / 测量笔数 | 4,000 / 4,000 | 4,000 / 4,000 |
| 快速到账 P50 | 73.62 ms | 73.83 ms |
| 快速到账 P95 | 110.86 ms | 145.21 ms |
| 计划发送→实际发送 P95 | 0.71 ms | 0.51 ms |
| 发送调度开始→全部观察完成 | 200.504 s | 21.108 s |
| 未完成任务采样峰值 | 41 | 631 |
| 委员会已接收、尚未提交峰值 | 29 | 511 |
| 已提交、钱包跟块调用尚未返回峰值 | 21 | 254 |
| 已提交、组织成员跟块尚未全部返回峰值 | 21 | 254 |

队列峰值不一定出现在同一时刻，不能相加。末尾均排空，没有触及两个并发上限。这里的 631 说明存在更多在途任务和局部堆积，不证明持续、无界增长；20 秒高负载也不足以宣称长期稳定 200 TPS。

快速到账中位数本次几乎不变，P95 增加 **34.36 ms**。没有复现“典型快速到账一定从 80 ms 变成 293 ms”的固定倍率。此前不同长度实验和不同分位数不可混比。

### 关闭埋点复核（实际顺序 200→20）

| 指标 | 20 TPS | 200 TPS |
|---|---:|---:|
| 成功笔数 | 4,000 | 4,000 |
| 快速到账 P50 / P95 | 77.82 / 115.76 ms | 110.20 / 156.79 ms |
| 发送→钱包观察上链 P50 | 1,101.03 ms | 1,859.49 ms |
| 发送→成员完成观察 P50 | 1,130.55 ms | 1,939.02 ms |
| 实际首笔→末笔发送窗口 | 199.949 s | 19.995 s |
| 末笔发出→最后完成观察 | 0.567 s | 0.883 s |
| 未完成任务采样峰值 | 38 | 824 |
| 计划发送→实际发送 P95 | 0.66 ms | 8.65 ms |
| 总完成时间 | 200.517 s | 20.878 s |

两轮没有触及发送或总任务限额，支付失败为零。200 TPS 有 **261 次进度查询失败计数**，随后重试完成；失败原因未按 HTTP 状态码细分，不能直接称为网络丢包或交易失败。

无埋点复核同样显示高负载尾延迟和在途量较大，但延迟幅度与诊断轮不同。这是重复运行波动，**不能声称关闭埋点使系统变慢**，也不能把诊断轮的 +111/+89 ms 外推成每次必然增加的固定成本。两种模式分别各一对，尚非充分的重复因果实验。

## 委员会路径：同一笔交易的相邻区间

单位 ms；平均值按交易加权。每笔相邻区间之和经过校验，等于该笔发送→committee0 提交。P95 不能相加；同块交易共享块级阶段，不能当作 4,000 个独立共识样本。

| 阶段 | 20 TPS 平均 | 200 TPS 平均 | 增量 | 20 TPS P95 | 200 TPS P95 |
|---|---:|---:|---:|---:|---:|
| 发送→组织完整凭证就绪 | 44.33 | 47.67 | +3.33 | 67.86 | 87.29 |
| 凭证就绪→开始发送委员会请求 | 0.84 | 14.14 | +13.30 | 0.84 | 22.67 |
| 请求发出→委员会接收 | 0.08 | 0.18 | +0.10 | 0.09 | 0.38 |
| 委员会接收→接纳完成 | 2.22 | 3.04 | +0.82 | 12.99 | 5.46 |
| **接纳完成→提案开始** | **276.72** | **387.60** | **+110.88** | **517.25** | **929.26** |
| 提案准备 | 0.04 | 0.41 | +0.37 | 0.06 | 0.92 |
| **提案准备好→开始执行** | **305.56** | **394.47** | **+88.91** | **405.78** | **967.21** |
| 整块业务执行 | 0.87 | 9.74 | +8.87 | 1.35 | 25.05 |
| 执行结束→应用 Commit 开始 | 30.95 | 22.41 | −8.54 | 49.88 | 47.75 |
| 应用 Commit | 30.37 | 64.73 | +34.36 | 45.87 | 227.25 |
| **发送→实际提交，总计** | **691.97** | **944.39** | **+252.41** | **997.02** | **1,983.98** |

两个粗粒度等待区间合计增加约 200 ms，占发送→提交平均增量约 **79.2%**。这是路径定位，尚不是“200 ms 都是共识算法计算”的结论。

### 再往里拆：这两段增长发生在哪里

按每笔实际提案者的前一高度 `commit_done` 对齐，“接纳→提案”的时间拆为：

| 子区间，交易加权平均 ms | 20 TPS | 200 TPS | 增量 |
|---|---:|---:|---:|
| 接纳后、上一高度应用提交尚未完成 | 255.79 | 365.71 | **+109.91** |
| 前一高度已提交后的剩余提案等待 | 20.92 | 21.89 | +0.97 |

增长几乎全部落在前一高度尚未提交的区间。它包含该高度剩余共识与持久化，说明新交易主要被上一块的推进拖住；不支持优先修改交易池扫描或投递调度。

“提案准备好→开始执行”继续以 committee0 相邻事件拆分：

| 子区间，交易加权平均 ms | 20 TPS | 200 TPS | 增量 |
|---|---:|---:|---:|
| 提案准备好→本节点收齐提案 | 78.25 | 121.92 | **+43.68** |
| 收齐提案→ProcessProposal 开始 | 0.10 | 0.22 | +0.12 |
| ProcessProposal | 0.03 | 0.38 | +0.35 |
| ProcessProposal 结束→本节点 prevote 已签署推送 | 49.54 | 47.73 | −1.81 |
| prevote 推送→进入 precommit | 40.71 | 59.89 | +19.18 |
| 进入 precommit→本节点 precommit 已签署推送 | 53.27 | 52.15 | −1.12 |
| precommit 推送→进入 commit | 33.48 | 31.21 | −2.28 |
| 进入 commit→finalizing 日志 | 0.09 | 0.10 | +0.01 |
| finalizing 日志→应用 FinalizeBlock 开始 | 50.09 | 80.88 | **+30.79** |

两轮四委员均只记录到 round 0，没有换轮超时证据。提案收齐前含提案者签署、持久化、传播和本地接收处理；最后一段位于 Comet 保存区块、结束高度 WAL 等工作所在的路径。此次没有为每个底层系统调用计时，因此不能将 +43.68 ms 全部称为网络耗时，或将 +30.79 ms 全部称为某一次 fsync。

具体慢块：200 TPS 的高度 45 装入 161 笔测量交易，业务执行 **11.370 ms**，应用 Commit **642.160 ms**。对应 bbolt 原生 WriteTime 为 **640.474 ms**，写锁等待在计时精度内为 **0 ms**、spill 约 **0.795 ms**。这里主要在实际写入与同步区间，不在业务验证或写锁排队。WriteTime 含多次写入/同步及其墙钟等待，不能称为一次 fsync。高度 43 也出现 Commit **227.246 ms**。共识其他持久化点的耗时需要独立辨别，不能从这一条记录推断其全都在做同一种写盘。

200 TPS 后 1,000 笔的发送→提交均值约 1.55～1.56 s，前 3,000 笔各组约 0.64～0.80 s。这与末段慢块同处一个时间窗口，说明平均数掩盖了明显的局部停顿；不证明数据库每增长 1,000 笔就必然变慢。

按独立业务块统计：20 TPS 为 533 个块，平均每块 7.50 笔、执行 0.801 ms；200 TPS 为 46 个块，平均每块 86.96 笔、执行 7.921 ms。单笔执行平均反而为 **0.083→0.070 ms**。因此整块执行变长主要伴随块变大，不应误判为每笔业务计算恶化。

## 提交以后：跟块和观察

下表是并行分支，**不能再把钱包列和成员列叠加**。

| 区间，平均 ms | 20 TPS | 200 TPS | 增量 |
|---|---:|---:|---:|
| 提交→钱包跟块 Update 返回 | 348.88 | 428.17 | +79.29 |
| 其中：等待/取得下一高度签名头 | 299.08 | 351.45 | +52.37 |
| 取得当前块与结果 | 1.34 | 10.36 | +9.02 |
| 钱包块处理预备 | 1.14 | 15.73 | +14.58 |
| 钱包写队列等待 | 10.39 | 9.62 | −0.76 |
| 钱包应用完毕→Update 返回 | 36.36 | 35.22 | −1.14 |
| 提交→四成员跟块全部返回 | 370.78 | 475.78 | +105.00 |

代码 `internal/transport/blocks.go:Block` 先请求 `/commit?height=h+1`，再取高度 h 的区块和执行结果；`internal/blockfollow/follow.go:Run` 在尚未可取时按现有 25 ms ticker 重试。因此第一行跟块等待大部分仍依赖下一个签名头的可用时机，并非成员在逐笔串行核销。它也包含轮询、HTTP 和解码，不能直接称为纯粹的“下一块共识时间”。

本次成员进度查询为 **22,830→27,093 次**，摊到测量窗口约 **114→1,284 次/秒**；每请求平均 **0.282→0.942 ms**。200 TPS 有 9 次暂时查询失败，最终观察全部成功。这说明观察器本身在高负载下增加工作，但本对数据不足以证明它是两段共识等待增长的主因。

### 一个测量边界

`follow_committed` 记录在同步 `Group.Update` 返回之后，而钱包/成员进度查询是另一路读事务。实测存在读到新状态早于这个返回埋点的样本。bbolt v1.5.0 的 `writeMeta` 在写入 meta 后释放 `metalock`，随后再进行同步；读事务此时可以取得新 meta。因此可见状态、写调用成功返回、观察器发现状态是不同的时点。

分析保留 `wallet_observer_minus_update_return_ms` 等**带符号偏移**，不把负值清零后伪造为“查询等待”，也不把读到完成状态宣称为已确认全部持久化返回。支付签发仍使用写调用成功返回后的证据，未删除同步。每轮退出后另做离线一致性与资金审计。后续若把“最后完成”严格定义为成员落盘回执，需要按已成功提交的进度定义测量终点。

## 网关及前台有没有再次拖慢

- 网关后台保存平均 **32.14→36.90 ms**，只增加 **4.77 ms**；它和公共投递并行。20 TPS 4,000 笔均先投递后保存返回，200 TPS 为 3,872 笔。不能把保存时间再次加到委员会路径里。
- 完整凭证→网关首次 Submit 平均 **0.63→13.94 ms**，但中位数 **0.48→0.58 ms**，说明增量集中在尾部。
- 抽样关键第三票路径中，请求已写出→网关 handler 进入，平均 **0.100→0.435 ms**，P95 **0.086→0.830 ms**。没有重新出现原来的几十毫秒 HTTP 连接串行阻塞。
- 成员写队列平均 **14.83→16.35 ms**，提交返回阶段 **27.84→25.57 ms**；钱包接收验证保存平均 **31.03→34.41 ms**。本对数据不支持把前台增长笼统归因于成员验签变慢。
- INSTALL 是独立可省略的后台分支；公共完成后可以不再安装。具有开始/结束样本的笔数为 3,998 和 1,466，不能用不同覆盖率的 INSTALL 均值宣称复制速度提高。

## 下一步优先级

1. **委员会推进路径中的持久化停顿。** 对高负载慢块，把已有 WAL、FilePV、BlockStore、结果保存和应用 bbolt 的区间逐一对齐，重点区分共享磁盘竞争、必要同步和重复工作。此次已经定位到实际 bbolt 写入/同步尖峰；不应先扩大交易投递并发或继续缩短 gossip。
2. **下一个签名头的等待及跟块成本。** 先解决上游推进停顿，再判断取块/结果可并发、解析可复用等本地减负是否值得做。保持现有证明验证语义。
3. **观察查询是独立优化项。** 查询频率、查询失败、实际成员完成和压测观察延迟分开记录；不可用降低观察频率掩盖积压。

## 数据与限制

逐笔原始区间见 `ls20/transactions.csv`、`ls200/transactions.csv`；块级工作见 `blocks.csv`，100 ms 队列重建见 `queues.csv`；总体分布见 `analysis.json`、`comparison.csv`。共识进一步拆分见 `detail.json` 和各轮 `consensus-details.csv`。脚本、诊断 overlay、二进制摘要和审计输出一并保留，不包含实验私钥和数据库。

原始大体积节点时间线和逐笔委员会记录保留在 Mac 的同名实验目录。各分段是墙钟耗时，不是纯 CPU 时间。单机共享资源、不同发送窗口长度及少量轮次限制了归因强度；目前可以明确下一步排查位置，不能据此承诺某项补丁一定降低多少毫秒。

诊断 overlay 的 requesttrace、blockfollow、payctl、gateway 的 `go test -race -tags=comet_v3` 通过，wallet 包成功编译且当前无独立测试文件。四轮加预热及 8 笔冒烟测试共 **16,013 笔**通过最终审计：14 节点待处理记录为零，四委员状态相同，Payments=Closed，缺口为零，CAL/FUEL、奖励及销毁核对一致。常驻网络已恢复到原有 100 笔、高度 7。本轮不修改共识参数、协议或业务实现。
