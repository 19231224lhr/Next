## Earlier findings

1. **Receiver identity and usable wallet — resolved.** `cmd/gateway/main.go:112-125` requires `RecipientKey`, validates it through `cfg.PrivateKey`, derives the owner from its public half and rejects a conflicting configured `RecipientOwner`. The resulting owner initializes the durable wallet at `cmd/gateway/main.go:166-182`. That wallet handles both collection and `POST /v3/recipient/prepare`. The new prepare path (`internal/recipient/collector.go:66-105`) saves an onward `DirectRequest` through the *same* wallet and returns 204 only for a local reservation. `DecodeDirectRequest` calls `DecodeFastTx`, which checks the owner's signature (`protocol/direct_request.go:37-47`, `protocol/v3.go:245`); an arbitrary caller cannot reserve this owner's inputs by naming the public key. The caller still needs to submit the same signed request to the next collector or gateway for approval, as the report states. The regression reaches the actual prepare handler after receiving a coin (`internal/recipient/collector_test.go:98-125`). This proves the local preparation path; it does not claim a completed onward payment.

2. **Benchmark comparability — disclosed limit, not a hidden result claim.** `cmd/gateway/recipient_collect_experiment_test.go:38-61,124-180` constructs the same three-owner payment workload in separate fresh labs. A dependent child contains the actual parent certificate, so signed request bytes can differ across runs even though the count, amounts and proof structure match. The revised `task4-report.md` says this explicitly. Its common measured endpoint is durable recipient-wallet acceptance with complete payment material retained locally. The baseline retains that material in its delivery outbox (`cmd/gateway/direct.go:103-119`); the recipient path persists it with the public relay outbox before wallet acceptance (`internal/recipient/collector.go:117-135`). Baseline public-relay persistence runs in the background (`cmd/gateway/direct.go:120-144`). The report identifies this difference and avoids claiming equal fsync work or public completion. The 20 ms delay applies only to the gateway-to-recipient link (`cmd/gateway/recipient_collect_experiment_test.go:79-88`), so any resulting benefit is a routing-topology effect, not an inherent same-org protocol gain.
