# 数据库优化：实现与对照测试

2026-09-20，Mac Studio M4 Max / 64 GB，Go 1.27.1，bbolt 1.5.0，项目固定 CometBFT 分支。基线提交 `23c4dc5`（生产代码等同 `8d605d3`）。

**本轮完成四项改动，保留全部验签和同步持久化。新库 100 笔／64 并发的三轮平均闭环从 2.267 s 到 2.089 s，缩短 7.8%；快速到账合并样本 P95 从 245.900 ms 到 173.953 ms。较大数据库上的端到端收益不稳定，不能据此宣称持续 TPS 上限已经提高。**

## 实现

1. `cmd/committee/main.go` 设置 `TxIndex.Indexer="null"`。删除未使用的交易／块事件搜索索引工作；保留 BlockStore、按高度执行结果、恢复响应。原版每个委员产生约 250 kB 的 `tx_index.db`，新版本不创建它。
2. `blockfollow.Commit` 先在事务外调用 `PrepareBlock`，再进入 Group／Bolt 写事务。成员保存原顺序的解析结果，钱包准备相关输出，网关准备已完成事实；当前批准、额度、消费状态及游标仍在同一个 Overlay 中重新读取、顺序更新。没有新队列或额外工作 goroutine，也没有删验签。
3. direct `Approval` 保持原始字节不变，累计核销量放到已有 `LocalProgress.Applied`。位置绑定原 Debits 的资源、版本、Worker 和上限；状态查询与离线审计使用统一读函数。首次兼容读取原累计值，不归零；后续仅按累计差额更新 Slice 与进度。旧 wire2 证明路径保持原行为，wire4 继续拒绝该接口。
4. bbolt `InitialMmapSize=16MiB`，`NoSync`／`NoGrowSync` 等同步语义不变。用于减少小库早期扩容；不是存储上限，也不是把全部映射预读进内存。低活跃数据库的文件也可能在初始事务后增长到约 16 MiB，磁盘占用比原来大。

成员本地 schema 从 4 升为 **5**，其他节点数据库及 wire 协议仍为 4。旧成员库拒绝直接打开，旧程序也拒绝新库；没有自动迁移。**不能手改 schema 标记或用旧二进制回滚新成员库。**旧实验完整保留，新版使用新实验目录。原累计值兼容读能力不等于提供了完整旧库迁移流程。

## 对照方法

五组是累积版本：base → index → prepare → credit → map。每组保留独立二进制，最终四个程序与被测 map 二进制逐字节一致。指纹见 [binaries.json](binaries.json)，源码快照差异见 [variants](variants/)。

每组三轮不埋点、另加一轮诊断，共 20 轮／2,000 笔付款。普通轮顺序为正序、反序、正序。固定 100 笔独立最终 UTXO 跨组织转账、64 闭环并发、10/10 ms 传播配置、相同配置／密钥／创世输入；每轮使用全新数据库和共识签署状态。测试期间暂停原空闲实验网，结束后恢复。复用实验密钥只发生在 Mac 本机，报告不包含密钥或数据库。

计时从付款钱包发出 HTTP 请求开始；快速到账终点是收款钱包验证并持久保存 TXCer；闭环终点包含钱包跟块及实验程序观察到四成员完成本地处理。闭环并发限制会控制发送速度，所以另记录首末发送窗口，不能用 `100/总秒数` 推断开放式持续 TPS。

## 新库结果（关闭埋点）

| 累积版本 | 三轮平均完整闭环 | 三轮范围 | 合并快速到账 P50 | 合并快速到账 P95 |
|---|---:|---:|---:|---:|
| 基线 | 2.267 s | 2.231～2.327 s | 156.755 ms | 245.900 ms |
| 关闭搜索索引 | 2.152 s | 2.095～2.230 s | 146.877 ms | 237.307 ms |
| 再移出跟块静态计算 | 2.083 s | 2.039～2.107 s | 165.880 ms | 226.782 ms |
| 再拆分核销小状态 | 2.228 s | 2.065～2.321 s | 182.358 ms | 260.142 ms |
| 再设置 16 MiB 初始映射（最终版） | **2.089 s** | 2.012～2.135 s | **137.511 ms** | **173.953 ms** |

P50/P95 来自每组 300 笔合并样本，P95 沿用 floor((n−1)×0.95)；交易样本不是 300 次独立实验。分组及逐轮值全部保留。**不是每加一项总耗时就下降：credit 的新库整轮与前台 P95 比 prepare 差；map 的整轮也没有胜过 prepare。**保留 credit 的依据是明确减少写事务内工作、避免重写证据，并有较大数据库测试支持其前台收益，不能把该项单独宣传为已证明提高闭环吞吐。

## 数据库关键路径确实减轻了什么

诊断轮中，四个付款成员都实际保存了 100 份批准。下表是每个成员处理这 100 笔业务块的**累计事务内 apply 时间，再对四成员取平均**，不是单笔转账延迟，也不含提交等待。

| 版本 | 付款成员累计写事务内计算 |
|---|---:|
| 基线 | 22.045 ms |
| 关闭索引 | 22.252 ms |
| 加事务外准备 | 9.734 ms |
| 加核销小状态 | 6.334 ms |
| 最终版 | **6.220 ms** |

最终版相对基线降低 **71.8%**。网关相应累计计算从 12.442 ms 到 0.079 ms，钱包从 15.346 ms 到 1.970 ms。静态解码认证仍在事务外执行并单独计时；这部分收益是缩短写者占用，不是凭空减少全部计算。

| 诊断轮阶段，中位数 | 基线 | 最终版 |
|---|---:|---:|
| 快速到账 | 181.144 ms | 139.242 ms |
| 网关后台保存待投递记录 | 124.995 ms | 45.608 ms |
| 凭证准备好 → 首次公共提交 | 16.471 ms | 48.172 ms |
| 接纳完成 → 提案开始准备 | 228.684 ms | 200.957 ms |
| 提案准备好 → 开始执行 | 262.603 ms | 308.400 ms |
| 应用 Commit | 106.096 ms | 28.970 ms |
| 委员会提交 → 四成员本地应用完成 | 398.996 ms | 318.028 ms |

该轮 63 笔大块的 Commit 从 106.096 ms 到 28.970 ms，但这是各一个块的观测，不能推广为所有提交都快 73%。同块交易共享 Commit 时间，不是 63 个独立同步样本。后台阶段存在并行，表内中位数不能相加当作总延迟。网关首投等待和共识传播阶段仍有波动；本轮没有修改共识参数。

## 较大数据库测试与反向复测

新增五个实验网：prepare 一轮，credit/map 各两轮，并反转后两者顺序。每轮同一节点数据库先处理 1,200 笔，再处理 300 笔，共 **7,500 笔**。创世扩大到每个付款人 2,048 个最终输入，CAL／FUEL 与费用逐项核对。

| 版本 | 后续 300 笔闭环 | 快速到账 P95 |
|---|---:|---:|
| prepare | 5.230 s | 145.551 ms |
| credit 第一次 | 5.402 s | 137.469 ms |
| map 第一次 | 5.119 s | 149.544 ms |
| map 反向复测 | 5.355 s | 142.477 ms |
| credit 反向复测 | 4.972 s | 149.057 ms |

credit/map 两轮均值分别 **5.187／5.237 s**，差约 1%，方向随轮次变化。不能声称初始映射在较大数据库上持续加速。该组测量开始时，委员会应用文件已约 16 MiB、付款成员约 32 MiB；credit/map 后续 300 笔期间原节点应用文件均未增长，详见尺寸记录。

**压测钱包的限制：**每次 bench 使用新的钱包数据库，后续 300 笔包含它追赶此前区块的工作，不能称为全系统完全热态。另单独统计同一次 1,200 笔运行最后 300 笔：credit 快速 P95 为 124.917／121.051 ms，map 为 147.352／109.804 ms，同样显示轮次波动。原始样本和两种口径都在 `comparison.json`。

因此保留初始映射用于已观察到的新库改善，不宣称长期收益；核销小状态保留其减少重复写入的作用。没有进一步增加并发、缩短共识超时或跨块延迟持久提交来改善数字。

## 正确性、故障路径与收尾

- 20 轮新库加五轮较大数据库，**9,500 笔性能测试全部成功**。四委员业务状态一致、费用与余额精确、14 节点 outbox 排空、无资金缺口。
- 新测试先在旧代码观察到“静态解码进入写事务”和“结算重写 Approval”，修改后通过。补充同块子先父后、累计值保留、schema 隔离、同库重启不重复释放、上限及绑定检查。原有部分赔付、迟到、重复块及事务回滚测试继续通过。
- 搜索索引关闭后的同库重启，四委员的 `/block`、`/block_results`、`/commit` 共 12 次按高度请求全部成功，重启前后审计结果一致。
- 另在已完成 100 笔的 credit 实验网上执行故意扣留父交易：自动赔付、真实历史改写、迟到父交易均通过；再重启并发送 8 笔。最终各委员 **110 笔闭环、1 次修订、0 缺口**，见 [repair](repair/)。最终 map 版本额外变化仅是初始映射，完整 tagged 修复测试及 race 测试也通过。
- Mac 完整默认测试、`go test -race -tags=comet_v3 ./...`、`go vet -tags=comet_v3 ./...`、四程序构建通过。最终程序与 map 候选二进制 `cmp` 一致。验签、同步提交及安全 WAL 未关闭。

另有两次随机创世预跑共 200 笔均成功，保留 `db-base-1`／`db-index-1`；第三次尚未发送交易，在生成门限密钥时主动中止，随后采用固定配置、新库对照。预跑不混入上表。原空闲实验网在测试后已恢复。

与 GPT 的实现复核见 [gpt-review.json](gpt-review.json)。按其提醒复查了 LocalProgress 的所有生产写入口：只有 finishLocal 写回，其他路径均先加载原记录，保留 Applied；没有其他旧结构体覆盖入口。GPT 基于提交给它的代码说明审查，没有独立运行仓库。

## 复现与证据

- [comparison.json](comparison.json)：每轮、阶段、块、跟块工作和尺寸统计；[analyze.py](analyze.py)可从报告重算。
- 每个 `dbo-*/reports` 保存原始钱包样本、14 节点审计；五个 `*-trace` 另保存四委员及各组织时间线，以及生成的交易／区块／成员 CSV。
- `warm*/reports` 保存全部 1,200＋300 笔样本、前后文件尺寸和最终审计；`validation` 保存测试与运行日志。
- [run_sequence.py](run_sequence.py)、[run_one.py](run_one.py)、[run_warm.py](run_warm.py)、[run_repair.py](run_repair.py)为实验工具，不参与节点业务。新库复用的是停止实验的配置和密钥，不复制数据库、WAL 或委员会最后签署状态。

各版本需要先由基线及 `variants` 累积补丁构建到独立 `db-*-bin` 目录；脚本使用 Mac 固定实验路径，避免覆盖已存在实验目录。分析无需访问密钥：

```sh
python3 docs/experiments/database-optimization-2026-09-20/analyze.py
```

保留的主要瓶颈仍包括共识等待、区块传播和必要同步持久化。当前结果是单机、有界闭环实验；持续开放负载及跨机器部署还需要独立测量。
