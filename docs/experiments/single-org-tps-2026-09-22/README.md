# 单担保组织整机 TPS 优化与验证（2026-09-22）

代码基线 `e3870e1`，保留的实现提交 `a083ff6`。这是完整快速支付闭环测试，包含组织签发、钱包接收、公共结算和成员跟块处理，**不是纯共识 TPS**。

## 结果与可用范围

同一台 Mac Studio M4 Max（16 核、64 GB），9 个服务进程：4 委员、1 组织的4成员和1网关，另有压测钱包进程。收款人与付款人不同，但同属一个服务组织；创世配置仍登记一个未启动的第二组织，并保留它的初始资金。每轮从新状态开始，使用150000个独立、已最终确认的输入。

列出的实验均零失败，150000笔均完成钱包快速接收、公共区块观察及全部成员的逐事实完成检查。目标2200的两轮约为2104–2106完整闭环TPS；目标2400时出现背压，不称为稳定承接2400。目标2000提供更低的到账尾延迟。这里只证明这些约69–77秒实验内的表现，不把目标发送速率当成实际吞吐，也不外推为无限期运行能力。

### 如何计时

- 快速到账：付款钱包调用HTTP发送之前，至收款钱包验证TXCer及输出绑定、完成本地原子保存。连接等待包含在内；事先生成、签名、准备输入与请求保存不计入。
- 实际发送TPS：首次到末次HTTP发送时刻之间的发起速率；目标速率受计时调度、并发和背压影响。
- 完整闭环TPS：成功笔数除以测量开始至全部任务完成的时间。末尾上链、跟块、全部成员观察及观察器排空均包含在内；初始化和停机导出不包含。
- 钱包公共块时间包含H+1认证、跟块和查询；成员时间还包含精确状态观察。二者均不是共识内部的精确Commit时刻。
- `compact.json`按10秒统计发送、观察到的成功执行、待办、最老年龄和延迟。Commit数据是250ms轮询观察值；不足10秒的末尾窗口单独标出。

2000和2200两档完整窗口中的发送与完成进度基本平稳，后台待办波动后排空；2400档出现4096上限阻塞。最后一次发送至全部成员观察完成，2000首轮约0.62秒，2200两轮约0.78/0.70秒。不能用最终排空单独推断输入期间没有积压。

## 保留的修改

1. **复用完全相同的收款地址签名验证结果。** 1024项有界缓存，完整ReceiveDescriptor（含网络、owner、公钥签名和路由）作键，网络及路由规则仍逐次检查。只缓存成功的不可变结果；逐笔付款授权、三份成员签名、输入消费状态和额度仍按原规则验证。复用已有LRU依赖，命中只读，不新增依赖或资金状态缓存。
2. **合并压测器对成员的状态读取。** 每成员一个有界队列、每批最多128个事实、一次只读View、保留bg32限制。HTTP响应离开View后编码。仍逐Fact检查 `Observed && (!Signed || Closed)`，不以区块高度替代完成，不新增委员会通知。旧GET接口及`-batch-progress=false`保留。
3. **显式实验参数 `UTXO_EXPERIMENT_COMMIT=250ms`。** 默认保持500ms。250ms缩短当前负载的后台观察等待，不改变三票门槛、H+1认证或持久化规则，也不宣称纯共识容量提高。
4. `bench-v4 -same-org`及独立的批HTTP/排队统计，便于复现单组织工作负载。

批量查询的主要价值是减少观察开销。例如早期1500目标/2048名额的诊断对照中，HTTP查询从377363次降到1904次，批查询错误为0；吞吐并未明显提高，所以没有把这一阶段称为协议吞吐提升。早期诊断埋点会增加负担，不与表中的正式结果直接比较。

描述符缓存的整机证据来自少量地址复用。微基准中热地址由约25.2微秒/496B/7次分配降至22ns/0分配；轮换2048个描述符时仍需真实验签，缓存约25.1微秒/912B/9分配，无缓存约25.4–25.7微秒/496B/7分配。轮换会增加分配，**没有进行多钱包地址轮换的整机容量验证**，不推广热地址收益。

## 实验模式与正确性

- 委员应用、成员、网关使用已有Ephemeral模式；Comet区块/状态存储为实验内存模式。钱包为bbolt NoSync。仍保留原子更新顺序、所有付款授权和共识签名；Comet WAL/FilePV原有同步未关闭。
- 无进程崩溃恢复承诺；内存状态只在干净停机时导出供审计，每次重新创世。导出耗时不算在线吞吐。
- 每轮校验4委员状态哈希相同、Pending=0、Gap=0、Payments=Closed=笔数，并检查CAL/FUEL供给、成员原占用约束。额外检查Rewards=84×笔数、Burned=10×笔数。
- 原始基准保留逐笔时间、错误和终态；成员是否完成依据自己的事实记录，未签署该笔的成员不伪造额度恢复。
- 64GB单机中，这些较长测试的进程RSS合计后段约40GB，内存与历史状态仍随实验增长；没有新增历史裁剪。本轮不是长期容量或故障恢复验证。
- 早期`pending1500`遇到磁盘不足导致停机导出失败，整轮排除，不能计入有效结果。后续在审计成功后清理实验数据库，保留结果与必要源码信息。

## 收敛与未采纳方向

Gateway新profile中JSON解码约占自身CPU的0.95%，不增加新二进制应答协议。连接诊断198000次批准请求记录26704次新连接、169989次复用、32298次取消；新建与复用是GotConn事件计数，另有1307次请求未记录到GotConn；取消与这些分类可以重叠，三者不能相加。允许第四请求延迟取消需要额外生命周期管理，当前没有收益对照，未合入。三票就返回的流程保持。

稳态进程CPU累计约15个核，已接近这台16核主机的实际并行资源。继续修改调度/协议前，应重新定位更高负载，不能仅增大排队上限。当前保留简单、有反向对照支持的改动。
