# 同组来源续付：实现、对照结果与 GPT 讨论

本轮已经实现两项可独立启用的改进。同组来源续付在受控带宽条件下有可分离、可重复的延迟收益；本机低传输成本环境没有稳定的延迟提升。它适合作为 Next 的实现优化，现有证据不足以把它另列为一个核心协议创新。

## 1. 实际改了什么

**同组来源续付（308）。** 上一笔付款由当前组织认证时，签过上一笔的成员已经保存了交易内容。下一笔向这些成员发送完整父 QC 和输出索引，让成员用已有记录补回父证书的其余部分。成员仍检查全部父 QC 签名，再执行原有输入锁定、额度预留和签票流程。无需等后台 INSTALL 把完整父证书送回来，便能使用紧凑请求。

网关仍联系四名成员、收集三票；没有签过父付款的成员直接收到完整请求。找不到本地记录时才回退。成员最终保存完整父证书，公开执行、来源恢复与担保规则保持原样。

**紧凑响应（309）。** 成员返回资源分配向量和签票，网关用原始交易重建签名覆盖的完整摘要，再独立验签和组装正常证书。省去的是四份响应中的重复字段。这是通用优化，跨组也能用。

这里的“同组”精确指：所有认证父付款的发行配置等于本次付款的认证配置。它不是只判断当前付款人和收款人是否同组。外组刚转入的钱，在第一次向本组另一用户续付时仍可能需要完整父证书；来源由本组认证时，即使新收款人属于外组，也可利用本组已有记录。整个支付链都在同组时，从第二笔起自然满足条件。

## 2. 对照结果

每个条件做四组：原路径、仅同组续付、仅紧凑响应、两者组合。每组八轮，每轮 100 笔依赖前一笔输出的付款，轮换运行顺序。同一个条件内使用完全相同的预签名交易；不做 INSTALL 预热。六个条件共 **19,200 笔付款，全部完成，性能实验没有发生引用缺失回退**。

下表是八轮各自 p50 的中位数，单位 ms。

| 条件 | 原路径 | 仅同组续付 | 仅紧凑响应 | 组合 |
|---|---:|---:|---:|---:|
| 同组，本机内存 | 2.7964 | 2.7889 | 2.7176 | 2.7525 |
| 跨组，本机内存 | 2.8726 | 2.9575 | 2.8023 | 2.8113 |
| 同组，双向各 10 Mbps | 6.9307 | 6.4778 | 5.9143 | 5.3462 |
| 跨组，双向各 10 Mbps | 7.0039 | 6.9644 | 5.9393 | 5.8971 |
| 同组，双向各 1 Mbps | 41.8961 | 36.1987 | 28.8953 | 23.3360 |
| 同组，原持久存储 | 7.1730 | 7.1649 | 6.9983 | 7.1998 |

带宽条件通过每条成员连接的 HTTP 请求体/响应体读取限速构造，**属于合成链路实验，不是实际 WAN 部署**；未计网络头部、TLS 开销或另加 RTT。计时包括收集三票与收款钱包验收/提交，不包括交易构造、签名和发送钱包保存请求。四组边界相同。

在同组 10 Mbps 下，仅同组续付八轮均快于配对的原路径，配对 p50 降幅中位数约 **6.9%**；在跨组相同条件下仅四轮更快，幅度围绕零波动。这区分出了同组来源复用的额外作用。组合在同组 10 Mbps 下约降低 **22.8%**，同组 1 Mbps 下约降低 **44.3%**，但组合收益包含通用响应优化，不能全部算作同组机制的贡献。

普通本机环境中，原路径与同组续付的差异落在轮次波动范围内，不能据此宣称本机稳定变快。持久存储对照也如此。此次未修改任何存储配置来制造优化收益。

每 100 笔的成员请求体总量从 **1,119,404 B 降为 908,237 B，减少 18.86%**。完整紧凑响应为 **317 B/成员**，对应原 JSON 响应约 1,930 B，减少约 **83.6%**。慢速条件下第四名成员的一些响应会在三票完成后被正常取消；这部分额外减少不计作编码压缩收益。

完整 p95、轮次范围、实际请求数与字节数见 [MEASUREMENTS.md](MEASUREMENTS.md)，原始逐笔结果与统计见本目录 JSON 和 `analyze.py`。三个 pilot 文件只用于探索，没有混入正式对照。

## 3. 与侧边栏 GPT 的讨论结果

讨论链接：https://chatgpt.com/g/g-p-6a97957ba6e88191b1e922255a89ceeb-utxodan-bao-zu-zhi-mo-xing-kuai-su-zhuan-zhang-akan/c/6acbc870-be1c-83ec-b253-9f1277f79ac5

- **采纳**：复用签票成员保留的父付款资料；完整 QC 不省略；向未签父付款的成员直接发完整请求；恢复资料仍保存完整证书。
- **采纳**：响应只传资源向量与签票；网关按原交易重建完整 Fact；单独测量通用收益与同组收益。
- **采纳**：旧端点直接回退完整请求；仅明确的 `PARENT_APPROVAL_MISSING` 或 `UNSUPPORTED` 允许特定回退，不把任意 400 当成重试理由。
- **采纳小补强**：零容量缓存保护。构造器原本只在正容量时创建缓存，所以它不是既有构造路径中可触发的漏洞。
- **未采纳钱包合并提交**：它可以另行研究，但属于通用钱包路径调整；当前单笔计时在 SaveDirectRequest 后开始，也不符合本轮避免数据库调优的重点。
- **未采纳自己的旧签票免验**：若做，必须绑定实际签名字节或安全验证凭据。为了微小收益新增这套状态不划算。
- **未采纳提前联合认证、减少票数或担保净额化**：前者需要预先授权后续付款，后两者涉及认证或经济规则变化，不能作为现有普通转账路径的简单优化。

GPT 最初引用过项目里的旧代码资料；本轮随后直接提供当前函数和新实现，后续字段绑定审查以这些代码为准。最终共同结论是保留这两项通信路径优化，不夸大本机收益，也不包装成新认证协议。

## 4. 验证与实现位置

新测试覆盖：无 INSTALL 立即续付、伪造/重复票、索引越界、截断/尾随字节、双花、重试幂等、重建成员后从持久资料读取、缺资料/旧端点回退、一个父签票成员掉线后由第四成员加入、多个输入、反向公开执行资金闭合、紧凑响应篡改以及跨组对照。缓存条目拥有自己的数组副本。

成员重建测试清空内存缓存并复用保存的状态；它没有冒充操作系统断电恢复测试。原来的持久化和源恢复测试也继续运行。

- `protocol/direct_continuation.go`：308 编码、签票者交集、一次准备完整/紧凑请求。
- `internal/member/direct_continuation.go`：已提交摘要缓存、Approval 重建。
- `protocol/direct_approval_compact.go`：309 编码及完整摘要重建。
- `internal/gateway/direct.go`、`internal/transport/direct.go`：分发、回退、响应协商。
- `internal/sameorglab/*continuation*test.go`：集成、对抗测试和四组对照。

验证命令和输出：`go test ./...`（`test-all.log`）、相关五包 `go test -race`（`test-race.log`）、`go build ./cmd/member ./cmd/gateway`。本轮没有提交、推送或改写论文。

## 5. 如何启用

两个开关独立、默认关闭。成员开启摘要缓存，网关开启对应传输路径：

```powershell
go run ./cmd/member -config <成员配置.json> -same-org-continuation
go run ./cmd/gateway -config <网关配置.json> -same-org-continuation -compact-direct-approvals
```

四个成员分别使用自己的原配置。仅测试通用响应优化时，网关只加 `-compact-direct-approvals`；关闭两个网关开关恢复原请求/响应路径。无需迁移账本或钱包数据。这里只实现并验证开关，没有替换正在运行的服务。

## 6. 论文参照与定位

[FastPay Fig. 2](https://sonnino.com/papers/fastpay.pdf) 区分本地收款更新与跨分片通知；[Sui Lutris](https://docs.sui.io/paper/sui-lutris.pdf) 的依赖可用性论证说明签票者持有相关输入材料。这些支持“利用已在正确位置保存的资料”的设计方向。[Stingray](https://arxiv.org/abs/2501.06531) 的并发计数器设计对应另一种状态模型和并发负载，不直接解释本实验的串行依赖链。

可采用的准确描述是：**复用同一认证配置下成员保留的来源付款资料，降低连续付款的通信成本，并在受控带宽受限条件下取得可重复的延迟改善。** 本轮没有进行新的文献新颖性证明，因此不建议直接把它增加为 C4。
