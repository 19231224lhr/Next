# 网关独立投递：第一步实现与对照

2026-09-19，基线 `8b39df1`。本目录记录网关调度改动；成员延迟备用的独立结果见 [第二步](../gateway-relay-fallback-2026-09-19/README.md)。

## 实现

wire4 网关在 outbox 持久成功后发送有界、非阻塞提示。公共 Submit 与逐目标 INSTALL 分开滚动执行；旧任务由各自的分页游标推进，启动和定时扫描补齐丢失提示。使用现有 outbox，不另建持久队列。未到期动作不进入解码、验签或更新路径。

同事实、同动作不重叠；四个 INSTALL 目标可以共享一次验证结果。执行前重查持久任务，重试更新在事务中重读最新记录，只更新调度时间；公共完成后的迟到写入和 ACK 不能复活任务。停机取消并等待在途任务，之后才关闭存储。

A 为原网关四笔等齐版本；B 为独立公共 4 槽、INSTALL 16 个目标 RPC；C 把 INSTALL 限为 4 个目标 RPC。后续实现采用 C 的小配额。共识、成员和压测程序均使用相同二进制，保留验签与同步持久化。

## 结果

Mac Studio，14 进程；每轮新创世状态、100 笔已最终 UTXO、并发 64，10/10 ms 传播。13 轮共 1,300 笔，均成功、待办排空、四委员状态一致、资金审计通过。原有另一个实验网仍在运行，机器并非完全隔离；不把短时闭环速率称为持续 TPS。

| 关闭埋点 | 轮数 | 100 笔全部后台完成平均时间 | 各轮快速到账 P95 |
| --- | ---: | ---: | --- |
| A | 5 | 4.038 s | 186.84 / 161.82 / 197.87 / 209.37 / 188.64 ms |
| B | 2 | 3.451 s | 244.92 / 312.19 ms |
| C | 2 | 3.534 s | 193.78 / 306.71 ms |

另四轮开启埋点。A 两轮“物理持久提交返回→首次实际 Submit”中位为 865.11、708.60 ms；B 为 215.10 ms；C 为 153.55 ms。原先的“保存处理返回→relay_enter”在 C 为 153.51 ms，但主指标采用真实 Submit，避免靠提前埋点制造改善。物理提交返回由 store_update 与 persist_callback 对应关系确定，防止持久化唤醒早于 handler 返回标记而产生解释错误。

C 中 HTTP 提交往返中位 1.54 ms，返回后重试状态更新仍占 41.43 ms。其网关保存中位 131.83 ms，较 A 的 48.95、68.41 ms 高；说明调度变化仍影响共享存储。C 的总 Submit 为 373 次，部分成员安装前已跟块完成，因此少了一些备用提交。

结论：投递前置等待明显缩短，C 的短批总时间比 A 平均减少约 12.5%；但快速到账尾延迟仍有波动，不能声称所有延迟都改善或持续积压已经解决。继续按已评审方案减少成员重复提交，而非继续增加并发。

## 验证与复算

两项回归测试先在旧版失败：一个 INSTALL 卡住会阻挡 Submit；一笔 Submit 卡住时只完成同组另外三笔。修改后通过，另覆盖跨扫描页滚动推进、持久后通知及漏通知补扫、未到期动作跳过、在途任务与公共完成竞争、关闭排空。实际 Group/跟块测试核对不存在任务复活。

Mac 上 `go test -race ./internal/gateway ./cmd/gateway` 和 `go test -tags=comet_v3 ./...` 通过。后续成员备用修改的追加验证单列在第二步报告。

运行 `python3 analyze_relay_step1.py .` 可从归档报告重建 `relay-step1-comparison.json`。三个 shell 脚本记录 A/B/A、补测及 C 系列顺序；原始数据保留全部样本，包括较慢的 B、C 运行。实验程序、日志、二进制摘要与各轮 reports 一并保留，不归档节点私钥或数据库。
