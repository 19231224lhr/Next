# 全系统 500 TPS：2048 未完成任务占满调查

## 结论

2048 是压测器整笔任务并发限制。任务在快速到账后释放 256 中的一个快速名额，但仍占用总名额，直到钱包确认最终上链、再查询四成员确认本地处理结束。名额持续占满反映等待周转不及目标流量；不是委员会交易池满 2048，也不是两千笔都还在申请 TXCer。

已有证据支持三项最小优化候选：钱包同一已提交高度只检查一次最终状态；压测发送禁止积攒欠额后集中补发；记住已经查证完成的成员。首项已有重复工作与 CPU 证据，收益大小仍待对照。不能仅把 2048 加大或把尾部观察取消后宣称积压解决。

## 一、90,000 笔原始长测：名额用于哪些阶段

对 89,951 笔成功任务累计各阶段占槽时间，比例为：

| 阶段 | 占成功任务总占槽时间 |
|---|---:|
| 付款钱包发送 → 快速到账 | 5.99% |
| 快速到账 → 钱包观察上链 | 90.34% |
| 钱包观察上链 → 四成员完成观察 | 3.67% |

这不是 CPU 分布，也不是共识服务时间分布。平均成功任务生命周期 3.876 秒。

| 实验时刻 | 尚未快到账 | 已快到账、待钱包上链观察 | 待成员完成观察 |
|---|---:|---:|---:|
| 60 秒 | 160 | 1888 | 0 |
| 90 秒 | 0 | 2048 | 0 |
| 120 秒 | 70 | 1978 | 0 |
| 150 秒 | 216 | 1832 | 0 |
| 180 秒 | 0 | 1264 | 784 |

错误请求归还名额。原始 unfinished=2097 包含 49 个已经返回但结果未知的请求；按任务退出时间重算，实际活动峰值为 2048。

## 二、其中有真实的上链等待，不只是查询慢

只读提取四个已停机成员数据库，89,951 个成功 Fact 均映射到 LocalProgress.Height，四成员高度无冲突。与原实验约 250ms 一次的区块结果观察按高度关联：

- 发送 → 首次采样到所属 H 区块成功结果：P50 2439ms，P95 7342ms。
- 采样 H → 采样 H+1：P50 655ms。
- 采样 H → 钱包观察 Final：P50 636ms。
- H+1 采样 → 钱包观察：P50 12.5ms，P95 248ms；37,413 笔为负，原因是两条独立观察路径的采样先后，不能把它当执行时间或将负数裁掉冒充精确阶段。

例如 120 秒时，1978 笔已快到账、未钱包确认的任务中，1817 笔的 H 尚未被采样到、161 笔 H 已出现但 H+1 尚未采样到。不能把这些全部称为钱包跟块落后。

代码 internal/transport/blocks.go 先取 /commit?height=H+1，再取 H 的 block 与 block_results。H+1 的认证头绑定 H 的执行结果，这是当前验证规则。删除这项等待涉及结果认证设计，非本轮最小优化。

发送至 H 的区间还包含网关投递和委员会处理；原长测没有逐笔接纳时间，尚不能进一步把 2.44 秒全部归给共识。

## 三、补充 30,000 笔、约 60 秒诊断：重复查询有实质成本

业务节点二进制与全部参数不变，仅测试 overlay 增加钱包 CPU profile、DirectFinal 调用次数和调用耗时、钱包按高度 follow timeline。29,985 笔完成，15 笔网关失败，完整任务耗时 63.189 秒。四委员状态一致，outbox=0，节点已停止。这一轮有采样开销，不与无 profile 长测直接比较性能。

| 指标 | 实测 |
|---|---:|
| DirectFinal 查询次数 | 3,117,866 |
| 每请求平均查询次数 | 103.93 |
| 每请求查询次数 P50 / P95 | 83 / 217 |
| 平均本地查询速率 | 49,342 次/秒 |
| DirectFinal 累计 CPU 样本 | 22.62 秒 |
| 占钱包压测进程 CPU 样本 | 22.66% |
| 成员进度 HTTP 查询 | 229,295 次 |

DirectFinal 经 Group.View → bbolt.View → state.Load[DirectCoin]，读取并 JSON 解码整份 DirectCoin；未最终确认时包含 OutputCertificate。只是检查 Final 字段，却反复解码其他字段。约 22.7% 是这个进程的累计 CPU 样本占比，不能相加嵌套函数占比，不能外推全系统 22.7% 提速。累计轮询 wall time=3921 秒包括并发等待，也不能当 CPU。

钱包 82 个块的阶段 P50：VerifyBlock 0.939ms，Prepare 63.77ms，等待 Group 回调 11.22ms，Apply 6.98ms，Apply 结束至 Update 返回 32.94ms（P95 286.67ms）。最后一段还可能包括同批其他操作、写入同步和运行时调度，不能统称 fsync。

## 四、发送不是始终平滑 500/s

原长测的固定窗口最大实际发送量：10ms 内 256 笔、100ms 内 321 笔、250ms 内 529 笔。

cmd/payctl/direct_pace.go 始终用 start+i/rate 计算发送时间。2048 名额满时阻塞，恢复后历史 due 已过，便立即补赶。这个循环会把后台等待放大为前台突发；49 次网关 503 的日志均包含两成员 429，但尚无逐请求因果证据证明全部 429 都由补赶造成。

## 五、最小实现顺序与验收

1. 钱包观察按本地提交高度过滤。首次保存 TXCer 后必查一次；以后只有钱包已提交高度变化才调用 DirectFinal。高度必须在钱包 coin 与 cursor 的 Update 成功返回后发布；用 atomic/锁同步，记录查询前读到的高度。保留现有 Final 判断和 25ms 观察节拍。确认 Final 先于凭证到达、检查与提交交错、末块不再出新块、提交失败都不会丢观察。
2. 独立限制发送补赶。发放名额后仍遵守实际发送节拍/小突发上限；保留原计划时间、未发数量、实际发送滞后。仅在生产任务通道前 sleep 不够，已经排到 acquire 后方的任务不能再集中发出。此项改善的是突发，不凭空提高后台吞吐。
3. 成员查询保留完成记忆。每笔四位标记保存已经按原业务条件查证完成的成员；只重查剩余者。不能用单纯高度、INSTALL ACK、202 替换完成条件。后续若需要再评估共享批量观察，本轮不新增接口框架。

各项分别做对照，保持业务验证、存储策略、256/2048、共识参数相同，记录本地查询次数、CPU、实际发送节奏、限流数、钱包落后高度、成功上链数及积压年龄。先短对照验证实际工作减少，再跑 500 TPS × 180 秒确认是否改善周转。

本轮仅调查与方案评审，未实施以上优化。没有调大 2048，也没有改变委员会业务或新增逐笔通知。没有证据保证这些小修足以解决全部持续负载问题；如真实入块前等待仍主导，再补网关首投、委员接纳、提案三个边界。

## 证据

- occupancy.json：长测逐笔占槽重算。
- fact-heights.json、heights.go.txt：只读提取与四成员高度映射。
- commit-vs-observation.json：按高度对齐既有区块采样。
- bursts.json：长测固定窗口发送突发。
- profile/diagnosis.json、profile/cpu.pprof、profile/cpu-cumulative.txt：补充诊断。
- profile/run.py、profile/overlay.json：可复现实验设置。
- code/：调查时实际 Mac 源码快照。
- GPT 对话：评审两版支付系统（6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90）。已讨论高度过滤及所需语义，明确不把占槽比例当 CPU 或共识容量。
