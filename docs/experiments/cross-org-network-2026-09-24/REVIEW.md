# E7 评审与采纳记录

评审渠道：[既有 GPT 会话](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)。以下为讨论摘要，评审意见不替代原始数据和审计。

## 工作点冻结

200 TPS、100 ms 预检出现投递饱和与未发机会，退出后的内存 BlockStore 无法支持赔付历史的离线审计。讨论后统一以 100 TPS 重做最高延迟与零注入预检，再冻结全部正式条件；保留失败预检，不调整单组并发来改善结果。

核对两组织实际发送量、接收事件触发续花、过期机会不追赶；不得把丢失离线历史材料解读为运行时修订成功或失败。完整说明见 [实施口径](METHOD.md)。

## 前两轮结果的中间评审

在 16/24 轮已通过、其余仍运行时提交实测结果，GPT 建议：

- 零注入同/跨组织 ACK 中位数接近，只说明所测快速路径延迟处于相近量级，不说明容量门槛或零跨组织成本。
- D 组新增约一次 RTT 是当前拓扑与实现的观测，不是任意跨组织协议的固有上界。
- 公共观察与快速 ACK 分开，不将二者差值全部当作共识开销。
- 单个正常解除的缺失来源责任可作为具体边界案例，不用于估计发生概率或网络延迟的显著因果效果。
- 仅最终排空不足以支持无持续积压，应补提每十秒公共完成速率、待办数量及最老待办年龄。
- 按站点与 endpoint 归类已有代理请求，核实注入范围。
- 携带 TXCer 的输入比例与委员会执行时缺失来源的比例分别报告。

采纳上述口径，补充 `analyze.py` 的公共完成时间窗，以及 `tables.py` 的链路计数和资源分组。完成时点由同一发送进程的 `SentElapsedNS + Monotonic.PublicNS` 重建，不跨进程相减墙钟。

讨论中 GPT 一度把 INSTALL 计入跨站延迟；已明确纠正并得到确认：本实验 INSTALL 在同组织站点内，委员会 P2P 也不注入延迟。跨站路径为公共投递、跟块、状态查询和 D 组的收款交付。

首次付款补充保留预置信任和创世验证，只比较新进程首次与后续付款，不能称为纯密码缓存或动态组织发现实验。

## 完整结果最终评审

24 轮正式实验和十次首次付款对照结束后，再次提交完整计数、三重复分位数、五分钟待办与完成窗口、实际缺失来源及失败预检。GPT 认可 E7 可标为“按既定范围完成”，无需扩大实验。

最终结论限定为双组织互操作、因果续花和指定 HTTP RTT 下的稳定工作点。169,677 个 TXCer 输入不等于缺失来源责任（实际仅一项）；新增约一个 RTT 是当前拓扑的观测；公共观察不是共识延迟；五分钟稳态不代表无限稳定。平均 P50 为三个运行中位数的平均，首次付款只作描述统计，200 TPS 失败预检单列保留，不作为容量上限。上述边界已写入最终报告。
