# E7 实施口径与预检决策

## 已冻结的共同配置

两组织各运行四成员和一个网关，共享四委员；两独立钱包进程各持有 32 个钱包身份的私钥。所有组都运行相同的 14 个服务、64 个钱包身份和 64 条活动 lane。正式总速率为 **100 TPS**，每站点 50 TPS；快速任务上限每侧 128，未完成任务上限每侧 1,024。

主矩阵为同/跨组织与独立/十跳四组零注入对照，以及两种十跳负载的 20/100 ms 延迟组，共八个条件、三个独立重复。普通轮 120 秒，跨组织十跳的 100 ms 组每次 300 秒，主延迟比较只取首次发送落在前 120 秒的付款。正式机会总数为 342,000，不含每轮 10 秒、总 50 TPS 的独立预热。预热必须排空，正式才启动。

用户自付最终 FUEL；每个付款 CAL 输出固定 100。所有正式轮使用相同大小创世池（capacity=65,000，按既有 E8 方法向上取整并留余量），资金总额和分配相同。密钥逐轮生成，身份数量、路由分组及各身份资金量不变。委员会、组织使用原有显式内存实验模式，钱包 NoSync；验签、原子状态更新和共识规则保留。不是耐久性或重启恢复实验。

## 因果与计时

- 发送进程从第一次实际 HTTP 发送到收到收款 ACK，使用同一进程单调时钟计量。它包含回程，名为**收款确认往返时间**。
- 接收进程运行真实 `wallet.ReceiveDirect`，核对证书与输出绑定，原子接收成功后才响应 ACK。ACK 绑定付款事实；重复交付复用结果。
- 十跳负载由接收事件将指定输出加入本地就绪队列，不等 ACK 回到前一发送者。正式窗口结束后仍接收、观察已有付款，但不新发后继付款。
- 下一跳按本地已验证钱包状态选输入：已最终则普通 UTXO，未最终才携带 TXCer。证书输入比例不等于“委员会当时尚未收到前置交易”的比例。
- 两侧独立限速，不追赶过期发送机会。64 lane 在 100 TPS 下每条链平均间隔约 640 ms；十跳总时间包含这个实验负载等待，不能解释为协议最短十跳延迟。
- 十跳为偶数，交替跨组织付款的终点回到起始站点。起始站点用本地首发与最终接收时刻计算整链时间，无跨进程墙钟相减；它不包括再回给最后付款人的 ACK。整链统计单列完整运行窗口，不将 300 秒轮与 120 秒轮冒充等长样本。
- 公共确认、成员完成均为跟块/查询观察时间，不是委员会内部 Commit 耗时。成员观察与核销审计只针对实际签发组织，不能要求八名成员都签过每笔。

## HTTP 延迟边界

站点 A/B 分别放组织及所属钱包，站点 C 放四委员。代理在跨站请求转发前、响应交付前各等待 RTT/2；同站点为零。零注入组也经过相同代理。范围包含公共投递、跟块、状态查询、收款交付；配置记录来源/目标映射，代理记录调用次数、字节数、并发峰值、取消和错误。

这是 HTTP 消息延迟实验，不模拟 TCP 拥塞、带宽或丢包，委员会 P2P 未加延迟，不是 WAN 共识实验。收款交付是跨组织组额外经过 A↔B 的路径，因此加延迟后的差值不能全部归于跨组织验签。

## 为什么从 200 TPS 调整为 100 TPS

保留四次预检，不能与正式轮混合：

| 预检 | 实发 / 计划机会 | 结果 |
| --- | ---: | --- |
| D0，200 TPS，10 秒，小创世池 | 2,000 / 2,000 | 完成，账务与双组织审计通过；仅初始功能预检 |
| D100，200 TPS，30 秒 | 5,306 / 6,000 | 付款观察最终完成，但后台积压并触发赔付；离线历史审计缺证，**未通过** |
| D100，100 TPS，30 秒 | 3,000 / 3,000 | 全部闭环及审计通过，无配额阻塞 |
| D0，100 TPS，30 秒 | 3,000 / 3,000 | 全部闭环及审计通过，无配额阻塞 |

当前网关公共投递并发为 8。100 ms 的往返下，忽略其他服务时间和重试，每组织主投递路径理想上限约为 80 次请求/秒；两组织约 160。它不是全系统含成员补投的精确吞吐上限，但说明 200 TPS 不是合适的非饱和共同工作点。因此统一降低正式负载，不分组修改并发或协议。该调整已与 [GPT 评审会话](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90) 核对。

200 TPS 失败轮的 `missing revised block` 有明确的证据边界：实验 Comet BlockStore 为 MemDB，退出后消失；应用状态单独导出快照，旧离线历史审计从磁盘读修订块，因此材料不足。它既不能证明运行时改写失败，也不能标为历史审计通过。正式轮继续执行原审计，不跳过这个检查；一旦出现同类问题，保留失败，不自动纳入成功统计。

## 复现与证据

`reproduce.py` 创建新创世、配置三站点代理、启动服务及双钱包、预热、测量、停机和审计。只有账务、状态一致性、双组织签署额度、输入唯一消费、链尾及退款检查通过，才删除该轮临时运行目录；日志和报告保留。

`suite.py` 固定矩阵、重复顺序和种子，遇到失败立即停止，不覆盖已有轮次。`analyze.py` 计算发送端单调耗时分位数、实际发送窗及输入类型分层。`figures/gen_fig_e7.py` 要求 24 轮齐全且已审计才生成正式图，展示每轮分位数而非把所有付款当独立重复。

冷启动补充由 `cold.py` 单独进行十次新进程运行，比较首次与后续独立付款。创世验证可能已预热部分缓存，连接也随进程新建，因此只称“首次付款与后续付款”，不归因为纯密码缓存收益，不声称动态节点发现。

Mac 实验目录从已有本地检出复制，再同步当前代码，因此 `build.json` 原始 `commit` 字段是旧检出身份，不能单独作为本轮源码版本。正式矩阵启动前按 `source-manifest.json` 逐文件校验源码（统一换行符），`verified_source_commit` 为 `13be8566ff972598506c54b011455bd2a8c7f2ae`，并核对相应源码目录不存在清单外的 Go 文件。二进制 SHA-256、清单 SHA-256 和环境变量同时保留；后续仅修改分析及文档，不重编正式运行二进制。

持续性图中的公共完成速率按 `SentElapsedNS + Monotonic.PublicNS` 落入的十秒窗口计算，是钱包观察到公共完成的速率，不是委员会内部出块 TPS。两个发送进程各使用本地正式阶段起点，再按相对窗口汇总；不将两进程墙钟相减。后台待办还包含成员完成观察，和只等公共确认的队列不是同一对象。
