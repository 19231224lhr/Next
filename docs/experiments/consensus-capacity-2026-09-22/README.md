# 四委员共识吞吐优化（2026-09-22）

本轮只测委员会：四个独立委员进程运行在同一台 Mac Studio M4 Max（16 核、64 GB）。担保成员、网关和钱包不参与计时，因此这些 TPS 不是整个快速支付系统的 TPS，也不能外推到广域网。


**最终工作点：3000 TPS、每轮 3 分钟、每轮 54 万笔，两次均全部成功；3500 TPS、54 万笔约 154.3 秒输入，单次全部成功。4000 TPS 大样本两轮均未全部成功。**

3000 的两轮含收尾分别为 180.829272 / 180.827739 秒，平均成功吞吐约 2986 TPS；3500 单轮含收尾 155.119592 秒，平均约 3481 TPS，停发后 0.833571 秒排空。3500 为单次通过，不替代两次独立复现的 3000 档。

## 保留的改动

1. 私有深拷贝替代交易冻结时的编码/解码往返，省掉两次重复授权验签。后续完整校验、组织认证、CH、金额与消费裁决保持。冷验证由约 558 μs 降至 379 μs，分配由约 157 KB/760 次降至 118 KB/570 次；回切复测约 558 μs。32% 是冷验证耗时改善，不是整体 TPS 提升比例。
2. 不可变证据验证缓存由 8192 项/32 MiB 编码预算调至 32768 项/128 MiB，覆盖 10000 交易池及传播、提案中的近期交易。只按完整报文字节复用验证结果，不缓存可消费性或余额。编码字节预算不等于整个缓存实际内存。
3. 新增显式 `UTXO_EXPERIMENT_COMMITTEE_MEMORY=1`，复用已有 Ephemeral 后端，默认仍为同步 bbolt。该模式要求 direct 协议及 `UTXO_EXPERIMENT_MEM_BLOCKSTORE=1`。四委员各自独立保存状态，整块原子提交和提交顺序不变。停止后台任务后导出审计快照，导出错误传播给退出状态。它不提供崩溃恢复，不是相同持久保证下的提速。

## 工作点与边界

3000 TPS、3 分钟首轮：540000 笔全部成功，含收尾约 2986 TPS，约 0.80 秒排空。10 秒采样的接纳未观察上链量在 1318～3810 间波动，没有观察到增长性积压。四委员合计 RSS 峰值约 30.03 GiB；RSS 不等于活堆，内存模式仍保留历史数据，不能承诺无限时长或恒定内存。

4000 TPS 的 180000 笔短测全成功，但 540000 笔长测出现 5454 次 HTTP 拒收及 8 笔接纳未上链，不作为稳定 4000 TPS 的证据。拒收限制队列增长，不等于系统持续处理能力匹配输入。5000 档仅用于记录过载边界。

## 定位依据

- 单入口高负载受接纳、传播集中及小缓存影响。四入口仍为同一个复制账本，每个委员处理同一批交易，不是分片。总 HTTP 在途仍为 128。按完整报文哈希路由，与普通网关同类，因此入口分摊属于测量拓扑修正。
- 8192 缓存诊断中，最多 90000 独立输入引发节点 0 共 123305 次冷验证；9223 笔提案准备约 6.28 秒。该轮因诊断查询超时中止，只作定位证据，不作容量结果。
- 旧代码仅改四入口也能通过 2000 TPS，不能把入口收益算成缓存收益。扩大缓存独自不能解决单入口瓶颈。
- 相同大缓存和入口下，clone 使单入口 1500 TPS 从拒收 11832 笔变为 90000 笔全成功；四入口 3000 TPS 的成功数从 158256 提升至 177615，仍未全通过。
- clone+bbolt 在 3000 TPS 诊断中，整块 Finalize 中位 263.24 ms，App.Commit 中位 259.88 ms；仅切换应用内存后端后第一轮 180000 笔全部成功。不能把整个 Commit 都称为磁盘时间，其中还有编码、应用修改和内存管理。

## 固定条件与口径

- Go 1.27.1，四真实 CometBFT 委员、同机 loopback；交易池 10000；commit 500 ms（与执行重叠）；flush/gossip 10 ms；P2P 51.2 MB/s。未修改 BFT 门槛、WAL、FilePV；Comet block/state/evidence 已为实验 MemDB。
- 真实签名的独立最终 UTXO 付款。付款人签名与三成员认证离线生成，委员会仍完整验证。不是重复同一交易或以幂等返回充数。本负载不测缺父/赔付吞吐，这些路径另作功能回归。
- 每轮新目录、冷验证缓存。四节点脱离 catching_up、连接三个对等节点并具有一致已提交块后发压。创世初始化、生成及预加载、最终导出和离线审计不计在线吞吐。
- 发送器总并发 128、固定目标速率、失败不重试。实际发送速率及滞后单列。约 50 ms 轮询观察区块，完成时刻为观察上界。
- 四委员审计须状态哈希一致、付款数和终结数等于成功上链数、资金缺口为零，每笔成功付款报酬 84、销毁 10。`Pending=0` 仅描述已提交业务状态，不等于所有 HTTP 接纳项上链。
- 带埋点、CPU 采样的诊断轮与正式轮分开。540000 模板扩大了初始状态，因此大样本 3000/4000/5000 使用相同模板相互比较。
- 准备时曾误以为旧样本只有一个 owner；生成器拒绝超额请求后已纠正：180000 原样本包括两 owner 各 90000，没有拼接重复输入。新 540000 样本由唯一新创世 ID 扩展后独立生成。

## 验证与复现材料

实际源码范围为 `./cmd/... ./crypto/... ./finality/... ./internal/... ./protocol/...`，执行 tests/vet，并对委员会、规则、存储、修订、协议和委员会命令执行 race。根目录 `./...` 会误收历史实验中混合包的源码快照，因此日志保留首次失败及明确范围后的结果。

校验覆盖八个 slice 冻结隔离、签名/金额/费用/认证篡改拒绝、与旧方式的规范编码及执行等价、结构长度边界、两后端每高度账本与 AppHash 一致、Finalize 隔离、重复与空块，以及真实缺父、到期赔付、CH 历史修订、迟到父和重放。审计导出错误不视为通过。

`comparison.csv` 汇总各轮，`results.json` 含分窗、二进制 SHA256、配置与四委员审计。原始发送、区块、资源、诊断记录保留于 Mac 本目录各轮子目录；不上传大型交易样本或实验密钥。测量工具为 `committee_load.go`、`generate_fixture.go`、`harness.py`、`runtime.py`、`run.py`。大型创世使用实验 overlay 将配置读取上限提高到 512 MiB，生产默认未改。
