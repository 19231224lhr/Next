# Next 请求准备优化与实测结果

2026-10-13。已实现两项优化：发送客户端复用钱包成功保存的签名请求字节；百笔连续付款的上链观察默认使用钱包提交通知。五轮成对测试中，优化后的准备时间和整链收据时间均小于优化前。

## 实际改动

### 1. 一次校验、保存，随后复用请求字节

新增 `Wallet.SaveDirectRequestBytes(req) ([]byte, error)`。它保留原来的绑定检查、请求编码与付款签名验证、钱包描述符检查、精确重试检查、输入消费锁、已回收资金检查和费用输入锁。只有配置的 `Store.Update` 成功返回后，才把本次保存的字节返回给发送方；任何错误均返回 nil 字节。

原 `SaveDirectRequest` 调用新方法并保留原来的 error 接口。连续付款、普通独立付款、故障负载、资金责任实验、E7/E8、预算实验及演示的 HTTP 发送处使用保存返回的字节，省掉发送前的第二次编码和付款验签。网络服务仍执行原有验证；发送失败后的重试仍使用完全相同的签名请求。

资金容量、证书格式、服务器执行和迟到来源处理没有改变。本项是发送客户端的通用优化，同组织和跨组织 HTTP 发送都能使用；本轮性能测量是同组织 Direct 链。

### 2. 区块提交后通知观察者

连续付款客户端默认订阅对应收款钱包的提交通知。只有正常 follower 验证区块并成功提交本地钱包状态后才广播；观察者先订阅，再检查真实钱包状态，避免漏掉查询附近的提交。付款的公开完成和成员闭合仍全部检查。

保留 `UTXO_CHAIN_COMMIT_NOTIFICATIONS=0` 作为明确的轮询对照开关。原先的 5 ms 轮询可以复现，默认模式已切换为通知。其他实验没有接入该钱包通知源时继续使用原来的观察方式。

## 五轮同条件对照

冻结修改前的客户端二进制，构建修改后的客户端。两者使用完全相同的成员、网关和真实 Comet 委员会二进制。所有进程共同限制在 CPU 0–3，`GOMAXPROCS=4`；成员/网关/委员会沿用实验内存模式，客户端使用 ext4 上的 NoSync Bolt。正常公开执行、钱包区块验证、成员跟随和资金闭合保持运行。

每轮新建实验目录，三钱包轮流发送 100 CAL，只有第一个钱包初始有这笔本金。后 99 笔均使用实际收到的上一笔证书输出。两组都开启相同的分段计时。服务器未开启短来源引用或精简批准，未启用 Pool。

同一轮还重测官方 FastPay：4 个 authority、1 shard、quorum 3、内存状态、原生 TCP，使用上一轮相同的 `receiver-confirmed` 客户端及真实接收/同步路径。该模式包含付款资金检查，收款后还执行下一笔可花费探针与本金守恒检查。所有系统独占执行，运行顺序轮换，避免固定的先后顺序。

发送前原有第二次编码阶段的五轮累计中位数由 14.403 ms 变为 0.032 ms；该阶段现在只剩取得已有字节后的诊断记录等工作，完整编码/验签已删除。后台完成检查的五轮中位次数由 29,985 降到 200，减少约 99.3%。两项优化同时启用，这一轮不能单独把整链降幅分配给其中某一项；此前通知单项对照另有独立记录。

## 与本轮 FastPay 的结果

本轮 100 笔链的整链中位数为：优化后 Next **555.53 ms**，FastPay **638.23 ms**，Next 低 **13.0%**。五轮 Next 均更短，逐轮差距约 0.5%–15.6%，配对降幅中位为 9.1%。

收款阶段 p50 的逐轮中位统计为 Next 4.625 ms、FastPay 6.291 ms；p95 为 Next 7.585 ms、FastPay 6.724 ms。Next 的尾部收款延迟仍较高。本轮证据支持这个单机、固定资源、同组织连续付款场景下的中位改善，不能扩写为所有部署、负载或网络条件下全面更快。

各自使用原生 HTTP/TCP 传输。FastPay 钱包为内存状态，Next 钱包为 NoSync Bolt；相同主机资源和统一收款端点不意味着内部存储、后台服务或 SDK 完全相同。旧竞品数据和论文数值没有被覆盖。

## 正确性和补充路径

主矩阵包括 Next 1,000 笔与 FastPay 500 笔计时收款。Next 所有链逐笔链接正确、先收款再准备，输出为 100 CAL，收款、公开执行和成员闭合全部完成，五轮两组均一次请求成功。FastPay 所有 500 笔接收完成，五次末笔可花费探针和本金守恒检查通过。

优化后普通独立付款另完成 30 笔，全部收款并闭合。逐笔等待公开执行的补充路径完成 5 笔，每笔使用最终确认输入；下一笔准备晚于前一笔真实钱包最终确认，通知唤醒正常。其 HTTP 尝试次数为 `[1, 2, 2, 2, 1]`，含 3 次原请求重试。该补充路径不纳入百笔性能比较。

等待路径的适配器最初错误地要求每笔只能尝试一次，因此校验报错。原生运行已经完成 5/5 且报告无错误。修正校验为允许原有的重试行为后，直接读取同一份保留的原生报告完成验证，没有用新运行替换这些记录；适配器报错后未保存原生退出码，该字段如实置为 null。

单元与回归验证：

`go test -count=1 -tags=comet_v3 ./internal/wallet ./internal/member ./internal/poollab ./cmd/payctl`

四个包均通过。新测试验证 Memory/Bolt 的字节一致性和所有权隔离、精确重试、相同编号的不同请求拒绝、错误签名拒绝、存储失败不返回字节及更新完成前不释放字节。通知测试覆盖默认/覆盖开关、真实提交后唤醒、验证阶段不提前唤醒以及多个订阅者。钱包方法和整体 CLI 集成分别经独立代码复核，没有重要缺陷。
