# WAL 重复同步优化：实现与实测

2026-09-20，Mac Studio M4 Max / 64 GB，Go 1.27.1 darwin/arm64，基础提交 `6aa0d71` 加本补丁。

## 改动

只在 CometBFT AutoFile 原互斥锁内增加一个 `synced` 状态：同一打开文件上，最近一次 Sync 成功且随后没有 Write，下一次 Sync 才直接返回。任何 Write（包括失败或短写）、重新打开文件都会使状态失效；Sync 失败不会标记成功。

Group 仍先 Flush，再调用 AutoFile.Sync。绝不把 `Buffered()==0` 当作已落盘：自动刷出缓冲的字节仍必须同步。轮转后新句柄也必须先成功同步。生产写入均经过 AutoFile.Write；不支持外部程序同时修改活动 WAL。

生产补丁由 `third_party/cometbft/overlay.py` 生成；回归测试在 `third_party/cometbft/libs/autofile/sync_test.go`。没有新增依赖或配置。WAL 格式、共识消息处理顺序、FilePV、BlockStore、账户数据库、验签、出块参数保持原样。提案和分片合批未实施。

## 先诊断，再修改

A 保留每次真实 Sync，仅记录是否覆盖新写入。四委员记录到 176 次调用：169 次需同步，7 次无新写入的重复同步；后者合计 **40.833 ms**。7 次均位于投票前 `vote_wal_flush`，高度 1～7，包含启动和后继证明块；业务块为高度 2、3、5、6。除启动高度 1 的一次约 0.003 ms 外，其余重复同步约 4.6～9.8 ms。

B 的对应诊断：**169 次需要同步的操作照常执行，7 次直接跳过**。这是确定消除的工作量。40.833 ms 是四节点累计操作时间，不能直接当作整轮实验节省时间。必要 Sync 总耗时也在变化，磁盘和调度波动仍存在。

## 100 笔、64 闭环并发对照

固定同一创世配置，独立最终 UTXO 跨组织转账，每轮全新数据库。14 个本机进程：4 委员、2 组织各 4 成员与 1 网关。网络刷新/gossip 10/10 ms，所有必要同步和验签保留。旧实验节点压测前停止，结束后恢复。

无埋点依次执行 A1 → B1 → A2 → B2 → A3 → B3：

| 轮次 | A：原同步方式 | B：跳过重复同步 |
|---|---:|---:|
| 1 | 2.102103 s | 2.072033 s |
| 2 | 2.119391 s | 2.002735 s |
| 3 | 2.089570 s | 1.913046 s |
| 三轮平均 | **2.103688 s** | **1.995938 s** |

本次平均缩短 **5.12%**。时间口径是整个 100 笔实验闭环：压测开始到全部交易完成钱包跟块和成员核销观察，不是单笔到账时间。

| 三轮统计量的平均值 | A | B |
|---|---:|---:|
| 第一笔发出到最后一笔发出 | 1.110445 s | 1.069735 s |
| 最后一笔发出到闭环结束 | 0.993144 s | 0.926136 s |
| 快速凭证到账 P50 | 143.127 ms | 129.369 ms |
| 快速凭证到账 P95 | 167.102 ms | 152.617 ms |
| 钱包公共上链观察 P50 | 1023.667 ms | 999.990 ms |
| 成员核销完成观察 P50 | 1086.670 ms | 1045.105 ms |

这里是每轮统计量取平均，不是将 300 个样本合并重算百分位。A 同样包含状态跟踪和未启用的诊断钩子，以隔离跳过同步这一变量；只有委员会二进制不同，其他角色相同。

## 单独埋点两轮的阶段

诊断轮 A/B 完整闭环为 2.197787 / 2.129049 s。各行是阶段中位数，不能相加，并行路径不能串加。

| 阶段 | A | B |
|---|---:|---:|
| 钱包发送到保存快速凭证 | 152.883 ms | 165.385 ms |
| 组织收齐认证 | 87.098 ms | 126.118 ms |
| 完整凭证准备好到首次公共提交 | 53.273 ms | 44.987 ms |
| 委员会接纳 | 2.109 ms | 2.062 ms |
| 接纳到开始准备提案 | 234.205 ms | 239.327 ms |
| 提案准备完成到开始执行 | 320.671 ms | 234.680 ms |
| 单笔业务执行 | 0.052 ms | 0.053 ms |
| 块执行完到应用 Commit 开始 | 32.451 ms | 37.327 ms |
| 应用 Commit | 25.870 ms | 17.688 ms |
| Commit 后等待并获取后继头 | 233.209 ms | 308.332 ms |
| Commit 到钱包上链观察 | 287.338 ms | 357.986 ms |
| Commit 到四成员应用区块 | 341.563 ms | 409.941 ms |

63 笔的高度 3：整块业务执行 4.649 → 4.924 ms，提案准备后到执行 320.671 → 234.680 ms。这是两次观测，不能将 86 ms 的差全部归因于一次约 6.5 ms 的重复 Sync。前台及跟块阶段在诊断轮中反而增加，不支持“所有阶段都变快”。许多交易共享区块，100 笔不等于 100 个独立共识样本。

## 复现与结论

`python compare.py` 从原始报告重算校验、阶段及汇总，结果在 `comparison.json`；两份 `sync-analysis.json` 给出逐次调用归属。`run_series.py` 复用前轮固定负载启动器，记录每个二进制 SHA-256。A 可用 `build_baseline.py` 在生成目录临时恢复“只测量、不跳过”分支；构建后自动恢复生成源文件。B 正常运行 overlay 后编译委员会即可。测量二进制保留在 Mac `.run/wal-base-bin` 和 `.run/wal-skip-bin`。

保留这个小补丁：确定消除了重复工作，短时对照观察到改善。**目前不能声称稳定低于 2 秒，更不能推导持续 TPS 或说后台等待已解决。**下一候选仍是同一已准备好提案及分片的有界合批，需独立验证重放顺序。
