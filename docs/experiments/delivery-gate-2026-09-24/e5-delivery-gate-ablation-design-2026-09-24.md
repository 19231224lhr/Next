# E5：快速交付门槛的对照与消融实验方案

状态：实验已完成，见[正式报告](README.md)。以下保留实施前方案；当时基线为 `re/cb341ec`，wire 4。本文只安排交付门槛这一项消融；E1—E4 的原始结果不计作本轮新数据。讨论结论见[评审摘要](e5-delivery-gate-review-2026-09-24.md)。

## 1. 要回答的问题

收集三份有效批准后立即交付 TXCer，相比继续等待额外条件再交付，能减少多少到账等待和连续续花时间？在相同计划输入负载下，是否改变后台完成速度、排队和实际工作量？提前交付时，完整材料传播还落后多少？

本实验允许出现“本机正常条件下差别很小”或“延迟改善、后台吞吐相近”的结果。成功标准是对照可信、账务正确、差异可解释，不预设必须获得多少倍提升。

## 2. 代码依据与比较范围

- `cmd/gateway/direct.go`：当前先取三票、编码凭证、Write/Flush，然后 Offer 后台任务并异步保存 outbox。
- `internal/gateway/direct_relay.go`：公共 Submit 与各目标 INSTALL 独立调度；公共完成可取消剩余安装任务。
- `internal/member/direct.go`：INSTALL 校验材料并执行本地原子事务；如果该 Fact 已经 `Observed`，可直接成功返回而不新增材料。
- `internal/transport/direct.go`：当前成功响应只有 `installed`，不能凭 HTTP 200 区分上述两条路径，也不是成员签名的复制证明。
- `internal/gateway/blocks.go`：在本地跟块事务内写入 `KeyObserved` 并清理 outbox。实验通知不能在事务成功之前发布。
- `internal/blockfollow/follow.go`：已有成功本地 Commit 后的回调，可用于唤醒公共终态观察，避免另加逐笔委员会查询。

因此，基线不能简单定义为“等任意三个 HTTP 成功”，也不能把无符号回执称为旧版第二阶段结果证书。主比较是同一 wire 4 实现中的两种交付策略；内存副本不提供断电耐久性保证。

## 3. 候选与推荐

| 方案 | 能测什么 | 取舍 |
| --- | --- | --- |
| 测试代理暂扣钱包响应 | 同一后台实现下的交付门槛取舍 | 推荐；保留网关原有执行顺序，两组都走相同代理 |
| 网关实验交付开关 | 真实响应等待、请求槽占用及整体运行影响 | 会改变后台启动时点及 handler 生命周期，本轮不做 |
| 恢复完整旧版两阶段协议 | 两套协议的总体差异 | 同时改变过多因素，本轮不做 |

## 4. 两组定义

| 组别 | 交付条件 | 后台行为 |
| --- | --- | --- |
| A：QC 后交付 | 相同 Fact 的三份有效批准已经形成 TXCer | 立即推进原有 INSTALL、Submit 和保存 |
| B：等待复制或公共确认 | 三个不同成员已实际完成完整材料的本地保存，或者实验观察器已验证并本地应用该付款的公共成功事实 | 与 A 使用同一流水线、并发配额、重试规则 |

这里的“保存”是所测内存模式下的本地原子更新。三成员必须属于该组织、对应同一 Fact，重复回执只算一个成员。`Observed` 返回不算一次新材料保存；它可以触发公共终态复核，但不能直接充当三副本证据。

B 若因公共终态先到而释放，记录 `public`；因三份实际保存完成而释放，记录 `install3`；观测分辨率不能区分先后则记录 `tie`。各类数量、比例和延迟分开列出，避免将公共等待误称为安装开销。第四个成员不成为交付门槛；剩余正常后台工作继续。

两组都经相同测试代理。代理立即完整读取并关闭真实网关的上游响应体，A 随即转交钱包，B 只暂扣下游响应；不能通过停止读取上游来阻挡网关 Flush 后的后台工作。网关仍按原来的 Flush → Offer/Persist 顺序执行。代理自身的额外传输与观测开销通过第 7 节校准检查。

这个对照量化交付等待的作用，不模拟真实网关 handler 等待导致的占槽，也不测该架构的最高 TPS。

## 5. 最小实现范围

仅在未来的 E5 实验分支增加测试代理、默认关闭的完成观测和驱动；不改 TXCer 编码、委员规则、预算及费用。

1. **成员完成分类。** 在真实 INSTALL 事务成功返回后区分完整材料保存与已公共观察。向原有 RPC 附带实验结果分类，默认调用保持兼容；不能另发一轮 INSTALL 取得“回执”。同一个实验代理透明转发原有成员 INSTALL 请求与结果以采集分类，两组都经过它，不新增扇出或逐笔轮询。分类不是拜占庭可验证的成员签名证书。
2. **有界完成记录。** 转发之前按 Network+TxID 登记请求，并保留原始签名请求的不可变副本或摘要，不能混合 Funding/Auth 不同的材料。再由实际 QC/INSTALL 材料校验并绑定 Summary/Fact 与对应 Payment，不提前猜 Fact。不同合法 QC 的签名子集可以不同，不要求整份证书字节相同。记录四成员保存位和公共完成位；事件早到先保留并完成认证绑定，不盲置完成。它独立于可被清理的 `installAck` 调度 hint；完成记录只用于实验等待和统计，不是资金权威。
3. **公共终态。** E5 代理/驱动进程在发送前启动一条共享块流，沿用完整块验证及执行结果认证，按登记 Network/TxID 再核对 Fact 和实际成功效果，本地应用成功后更新实验状态；不能以高度、HTTP 202 或重复命令的空成功代替。不依赖钱包 READY 才启动观察，否则会循环等待。不在 Overlay 回调中提前放行，不新增逐笔委员会证明请求。原钱包与四成员收尾观察保留。
4. **响应及收尾。** 仅 B 暂扣下游响应，Submit 和 INSTALL 都继续正常推进。通知只唤醒，释放前重查条件。请求超时或取消后，已签出的付款仍继续后台处理，不能清锁、退权限或丢弃；不能超时后退化为 A。单次 HTTP 结束不回收逻辑付款记录，同字节重试沿用保存位、公共位和最早时间，整轮结束才回收。未收到但公共已成功的付款单列。
5. **有限测量。** 复用 E4 的发送与观察分离方式、E1 的真实续花方式及 E2 的用户自付费用构造；不照搬 E1 的组织代付配置。后台数据收集使用有界记录，不逐笔同步写测量日志。

最小验证涵盖：三个不同保存完成放行；两份与重复回执不放行；公共先到及 Observed 空操作；事件早到与调度清理；请求取消后后台继续；公共先于钱包接收时不把最终状态降回未确认。并检查没有第二套安装扇出、重复收费或新增消费效果。

## 6. 固定环境与计时

- Mac Studio M4 Max，16 核、64 GB；同机回环网络，单组织四成员、一个网关、四委员。
- 应用与委员会 BlockStore 使用实验内存模式，钱包 bbolt NoSync；验签、本地原子更新与已有 Comet WAL/FilePV 行为保持一致。
- Commit 250 ms、Flush/Gossip 各 10 ms；GOMAXPROCS=16、GOGC=200。记录实际生效配置，不从历史报告推定。
- 独立付款每笔 100 CAL；每笔用户有独立最终 FUEL 输入 10,000，最大预留 1,000，无组织代付。CAL 与工作权限固定充足，不补资、不串行取证。
- 两组相同请求、创世模板、节点与 Worker 数、后台配额、缓存、驱动并发、重试和观察频率；每轮使用全新运行状态。
- 正式独立负载采用 64 个发送 worker，任务名额在钱包接收完成后释放；保留全部公共与四成员债务，不使用 2,048 个后台任务上限压低发送。
- 预热与正式交易用不同输入。每轮 100 笔预热后排空；正式最多 30,000 笔，加预热共 30,100，有限记录与创世容量明确设为至少 30,100，不能误撞 E4 原来的 30,000 上限。
- 单请求 HTTP 期限 2 秒，原字节间隔 50 ms 重试，总请求期限 30 秒；从首次发送计快速延迟。30 秒计划发送期结束后最多 60 秒收尾，保留未发、未知及未完成样本，不通过延长计划发送期掩盖背压。

钱包快速到账从付款钱包实际开始发送 HTTP 到收款钱包验证 TXCer、核对输出并完成本地事务。构造/签名在独立负载中提前完成，另报计划发送滞后；链条只能在收到上跳后构造下一跳，整链时间包含这些真实步骤。公共完成采用验证区块后的观察时刻，不能命名为精确 Commit。

## 7. 实验矩阵

| 部分 | 设置 | 重复与数量 | 用途 |
| --- | --- | --- | --- |
| 行为冒烟 | 单笔、并发、公共先到等上述边界 | 小规模功能测试，不纳入性能结论 | 确认交付条件真实生效 |
| 无等待校准 | 原版直连 vs 代理 A，各 100 笔、计划 200 TPS | 每种三轮，交错顺序 | 判断代理与观测是否造成可见扰动，不作正式收益样本 |
| 独立付款主对照 | A/B × 200/1000 TPS × 30 秒 | 每设置三轮，共 12 轮、216,000 笔正式计划付款 | 到账延迟、相同负载的完成率与后台成本 |
| 连续续花主对照 | A/B × 100 跳，三个钱包轮流转手 | 每设置三轮，共 6 条链、600 笔 | 每跳等待如何累积到实际链条 |

主对照按配对顺序 AB、BA、AB 执行，并在第二次重复交换负载档顺序。固定种子 23/37/59 只用于预先确定的独立输入排列；两组复用同一轮请求计划，不宣称覆盖随机网络或用户分布。

续花每跳使用上一跳当前钱包状态中的输出：尚未确认时携带对应 TXCer，已确认则使用最终输入；不人为强制父交易延迟，不停止共识。每跳费用由当前付款钱包的独立最终 FUEL 支付，另报使用未确认输入的实际比例及父交易已确认比例。

首轮不加入人工网络延迟、慢节点、同步刷盘、多组织或极限 TPS 扫描。若本机差异小，照实报告；后续是否追加敏感性实验单独决定，不根据初测收益挑选漂亮档位。

## 8. 最少必须记录的数据

| 层次 | 数据 |
| --- | --- |
| 逐笔 | 计划发送、首次实际发送、QC 完成、后台启动、代理完整收到上游响应、各成员实际保存/Observed 分类、代理观察到条件满足、代理交付释放、钱包 READY、公共观察、四成员完成；TxID/Fact、请求次数与结果 |
| 到账 | READY P50/P95/P99、最大值；QC 前耗时与 QC 后等待；B 的放行原因 |
| 工作量 | 实际 INSTALL/Submit 调用数、重复/失败次数；代理等待数量、发送 worker 占用与 429；发送滞后与未发送量；网关槽仅作辅助，不能推算真实等待式网关容量 |
| 后台 | 每秒公共未完成、四成员未完成、最老未完成年龄；输入停止后的排空耗时 |
| 链条 | 每跳发送/到账/构造耗时、100 跳最后钱包可用时间、最终收尾、实际未确认输入比例 |
| 审计 | 四委员状态一致、输入唯一消费、用户费用与退款、成员原始占用/解除、残余 outbox 和局部批准 |

CPU/RSS 每秒采样一次用于解释，不以诊断 trace 全开后的数字代替正式性能结果。两组使用相同的轻量事件采集；若发生丢事件，报告测量不完整并先修观测，不填零。

对每笔令 `Tg` 为代理/驱动观测到三份实际保存完成或已验证公共成功的较早时点。A 额外报告 `max(0, Tg - READY)` 的分布与非零比例，称为“相对额外交付门槛的观察窗口”。同时记录首次完整材料保存的时点；这个窗口不能直接等同于没有任何副本或发生资金风险的时长。没有三副本时不伪造该时间，按公共释放或截止仍未知分类。代理收到上游至释放的时间单列，不把代理排队或观察传播时间全部归为 INSTALL 执行成本。

## 9. 分析与验收

1. 先检查每笔 B 转交钱包前确已满足记录中的门槛，再比较延迟。任何提前放行、双重消费、重复收费或错误恢复权限都属于实现失败。
2. 每档逐轮展示计划/实际发送、READY/公共/四成员完成数量及排空；200/1000 是输入工作点，不是测得的最大持续容量。
3. 配对报告每轮分位数差与链条总时间差，展示三次重复；不把多个分位数平均当总体分位数，不把逐笔样本当几万个独立系统重复。
4. 联合检查公共与成员待办曲线。前台提前交付而后台工作量近似相同，是合法结果；不能凭钱包更快宣称公共 TPS 按同倍率提高。
5. 如果校准偏移与主比较差异相当，或发送器不能按期提供负载，先报告混杂因素；不把它归因于协议收益，也不只展示成功请求的延迟。
6. 费用按实际有效付款逐笔核对，不预设续花与最终输入付款收费完全相同。未决结果及占用单列，不清锁凑“全部通过”。

交付物：一张设置/完成率表、独立负载延迟对照图、100 跳累积到账曲线、额外交付门槛窗口及后台待办图；报告、逐笔数据、汇总 CSV、源码与二进制指纹、复现脚本和校验清单。沿用 E4 做法，归档验证后清理运行数据库，保留公开原始证据且不提交私钥。

## 10. 实施顺序与论文表述

从已合并的 `re` 新建独立 E5 分支。依次完成测试代理与必要观测测试、无等待校准、独立负载、用户自付续花、统一审计与报告。每一步通过后再推进，保持正常默认路径与 E1—E4 兼容。此文是实施前方案；实际执行和驱动修正以正式报告为准。

预期可回答：在所测环境和输入负载下，提前交付相对等待额外复制/公共确认，给钱包与连续续花带来多少收益，并留下多大的观察窗口和后台负担。它不证明完整旧版两阶段协议被等价替代，不证明崩溃耐久性、广域网表现、最大 TPS 或相对外部系统的性能优势。E4 的网关材料尚未扩散边界仍然适用。
