# 前台延迟调查（不修改业务/共识）

已观察：上一轮 B 的延迟增量集中在第一批 64 笔的“发送→收到证书”；钱包保存均值没有增加，后 36 笔也未整体变慢。

假设：突发时的认证持久化/调度波动，或者共识推进提前后对前台共享资源的影响。现有数据尚不能区分，也不能断言 WAL 合批导致稳定退化。

1. 保存所有旧样本的两段时间，按首 64 笔/后 36 笔分组；均值用于可相加分解，不相加各阶段分位数。
2. 用原 A/B 二进制做带埋点闭环 ABBA，每次 100 笔/64 并发。比较决定三票形成的成员路径：到达、验证、数据库排队、回调、持久返回、签名。
3. 同二进制执行 50 笔/秒的无埋点 ABBA；检查实际 dispatch lag，防止把发不出去的目标速率误当固定负载。必要时补同速率埋点。
4. 全部实验保留四委员状态、费用、outbox 审计；结束恢复原网络。结果支持到哪一步就报告到哪一步，不增加生产优化补丁。

复用已有 bench-v4 的 `-rate` 和前台响应埋点，仅给实验启动脚本透传速率。

完成：旧 1,200 笔复算；新增 4 轮突发埋点、4 轮 50/s 无埋点、4 轮 20/s 无埋点及 2 轮 20/s 埋点，共 1,400 笔。50/s 发现反压，保留原结果并补 20/s 控制负载。没有生产优化，所有审计通过，结果与未确定的因果边界见 README。
