# 前台延迟上升调查

2026-09-20。只调查，不叠加性能优化。沿用上一轮 A/B 原二进制，没有重编译生产程序；SHA-256 核对确认两个版本仅委员会不同，组织、网关、钱包压测程序相同。

## 当前判断

此前六组样本中的前台上升是真实观测，增量集中在**第一批同时发出的 64 笔交易，收到证书之前**。本次进一步复测显示，这个增量对发送方式敏感，还不能确认为 WAL 合批造成的稳定退化。

突发下的主要等待集中在网关向成员分发、成员验证过程中的墙钟等待，以及成员数据库排队和持久化返回。固定到达率后，分发与验证的墙钟耗时明显下降；数据库等待仍占较大比例。现有记录不能进一步把所有等待精确拆成 CPU 调度、磁盘设备等待和其他进程竞争，不能直接断言“都是 fsync”或“都是共识抢资源”。

## 旧数据：增加的时间在哪里

完整复算上一轮 12 个无埋点报告的 1,200 个样本。均从付款钱包发出 HTTP 交易请求开始计时。

| 可相加的逐笔均值 / ms | A | B | B−A |
|---|---:|---:|---:|
| 发送 → 完整凭证收到 | 90.35 | 100.89 | +10.55 |
| 凭证收到 → 钱包验签并持久保存 | 40.47 | 39.11 | −1.36 |
| 快速到账全程 | 130.82 | 140.00 | +9.19 |

这些是均值，不是先前报告的 P50；因此可用于分解总增量。

| 按实际发送时间分组，快速到账均值 / ms | A | B |
|---|---:|---:|
| 首批 64 笔 | 137.81 | 152.81 |
| 后续 36 笔 | 118.39 | 117.25 |

旧数据不支持把增量归因于钱包保存，也不支持“后续交易越来越慢”。它也不足以单独证明某个共识函数造成了前台增量。

## 新实验：原突发和固定速率对照

每轮 100 笔独立最终 UTXO 跨组织付款、64 个最多在途槽，相同创世配置与全新数据库、14 个本机节点、10/10 ms 传播配置，sync 与验签保留。

- 突发带埋点：A1 → B1 → B2 → A2。
- 目标 50 笔/秒无埋点：A1 → B1 → B2 → A2。
- 目标 20 笔/秒无埋点：A1 → B1 → B2 → A2。
- 另补 20 笔/秒 A/B 各一轮埋点，只用来定位阶段，不混入无埋点均值。

| 发送方式 | A 到账 P50 / ms | B 到账 P50 / ms | A 到账 P95 / ms | B 到账 P95 / ms |
|---|---:|---:|---:|---:|
| 原突发，带埋点 | 140.24 | 145.70 | 170.30 | 178.94 |
| 目标 50 笔/秒，无埋点 | 117.12 | 121.74 | 173.31 | 165.88 |
| 20 笔/秒，无埋点 | **87.75** | **81.75** | **135.28** | **126.82** |

表中是同一版本两轮分位数的平均，不是合并样本的分位数。每组样本量有限，不做显著性或普遍性能保证。

**50 笔/秒组存在压测端反压**：四轮 P95 dispatch lag 为 219.68、277.79、143.24、190.16 ms，不能称为严格固定到达负载。原因是当前压测的 64 个槽会一直等到跟块及核销观察结束才释放；目标发送时刻已到而所有槽忙时，任务等待。此等待在发送计时之前，单独记录，没有混入本笔 FastMS，但会改变实际发送形状。

20 笔/秒组 P95 dispatch lag 为 1.00、0.55、0.71、1.43 ms，负载控制有效；B 没有复现前台升高。100 笔按 20 笔/秒发送本来就需要约 4.95 秒，因此约 5.5 秒的整轮时间不能与突发组的约 2 秒直接比较，也不是持续吞吐上限。

原突发复测仍有很大波动：B 两轮到账 P50 分别为 161.94 和 129.46 ms，P95 则为 163.30 和 194.58 ms。不能只选较快的一轮宣布回归消失，也不能用上轮固定的 12/16 ms 差值推断永久损耗。

## 代码与埋点定位

调用链为：`benchDirect` 发送 → `Collector.CollectDirect` 并行请求四成员 → `Member.ApproveDirect` 验证、数据库更新、持久返回、签名 → 网关取得三票 → `Wallet.ReceiveDirect` 验证并持久保存。

成员签名前必须完成持久占用，代码中没有新增等待 INSTALL 或委员会出块的前台门槛。`store.Group.run` 不等待凑批，只合并已经排队的更新，再统一持久返回；等待项中包含此前批次、其他本地写任务和实际存储耗时。

每笔前台响应携带返回成员的阶段时间。部分请求收到四个成员的诊断信息，但报告未保存证书内实际选定的成员编号，不能准确推断选择了哪三个。因此，下表使用**恰好三个完整成员记录**的子集，并取其中最后完成签名的成员作路径分解；它不是所有交易或所有成员的总体分位数。

| 最后完成签名成员的阶段，墙钟均值 / ms | 突发 A 两轮范围 | 突发 B 两轮范围 | 20/s A 诊断 | 20/s B 诊断 |
|---|---:|---:|---:|---:|
| 网关 handler 进入 → 该成员 handler 进入 | 20.50～24.46 | 26.18～40.95 | 1.96 | 1.13 |
| 成员进入 → 验证完成 | 5.08～25.34 | 11.26～26.99 | 1.65 | 1.12 |
| 请求数据库更新 → 回调开始 | 21.43～23.00 | 16.27～21.12 | 15.05 | 13.23 |
| 本笔数据库回调 | 0.08～0.13 | 0.07～0.14 | 0.10 | 0.09 |
| 回调结束 → 持久更新返回 | 20.41～25.99 | 23.70～25.16 | 28.04 | 26.94 |

突发列取首 64 笔中的三记录子集，A 样本数为 62/60，B 为 64/51；20/s 列在全 100 笔中各取到 83 笔。表中不含签名前后等小段，因此不能把这一部分表格加总当完整到账时间。完整可相加路径和样本数见各轮 `foreground.csv`。

这里的“分发”包含网关自身授权检查、goroutine/HTTP 分发和接收调度，不是纯网络传输。“验证”是墙钟时间，不等于验签 CPU 时间。“持久更新返回”还含本批剩余回调、提交和唤醒，不能当作单次磁盘 Sync 的精确测量。

阶段数据说明：首批大量并发请求时，成员开始处理的时刻及验证完成时刻分散，之后还要等待同步提交。单笔回调本身只有约 0.1 ms，暂不支持优先重写 UTXO 业务计算。20/s B 诊断中，成员数据库排队约 13.2 ms、回调后等待约 26.9 ms；钱包验签和保存全 100 笔均值约 30.1 ms。这些是当前前台继续深入采样的具体位置。

## 结论边界与后续

保留上一轮的退化观测；此次证据将它收窄为负载形状相关的首批认证波动，尚未确立 WAL 合批的稳定因果影响。固定 20/s 结果也不能证明更高并发下一定无回归。

本轮不回滚、不追加生产优化。若继续调查，最小的下一步是对成员和钱包的**同一个同步事务**补充只读诊断：区分 Group 等待、真实数据库提交和返回唤醒，并在突发时记录网关请求发出与成员接收边界。当前成员/钱包没有底层物理事务日志，不能把已有粗区间进一步硬拆。该诊断尚未实现。

新跑 **14 轮共 1,400 笔全部成功**；每轮四委员会状态哈希一致、14 节点 outbox 排空、缺口 0，本金与 FUEL 总额及报酬/销毁均通过审计。实验结束恢复原常驻网络。

变更仅限报告、分析脚本，以及已有实验 `run_one.py` 对 `UTXO_BENCH_RATE` 的透传；直接复用现有 `bench-v4 -rate`，无生产代码变更。
