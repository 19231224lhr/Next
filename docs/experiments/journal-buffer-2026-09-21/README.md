# 委员会日志合并写：小范围候选验证

本轮仅给委员会 GoLevelDB 的 journal 增加标准库 `bufio.Writer`（256 KiB）。同一次日志提交的多个小写入可合并；沿用原有 `Flush`、`Sync`、`Close` 和状态提交顺序。bbolt、共识参数、业务认证、钱包与成员处理均未修改。非关键后台保存沿用原实现，没有全面异步化，也没有增加恢复机制。

候选在 Mac 的私有依赖副本中构建，仓库默认依赖和正式二进制未切换。实现、构建脚本与实验报告保留在此目录。没有提交或推送 Git。

## 关闭细分埋点的 A–B–B–A 对照

每轮新创世，200 笔/秒、4,000 笔最终 UTXO 支付，另有 1 笔预热；快速到账并发 256，总未完成上限 2048。A 是基线，B 是合并写候选；其他角色二进制与运行时依赖版本相同。成员 `GOMAXPROCS=16/GOGC=200`，共识传播设置 10/10 ms。保留全部验签与同步持久化。

每轮实际首笔至末笔发送约 **19.995 s**，均未触及发送或总未完成上限。因此总时长受固定发送速率约束，不能用这组数据推导吞吐上限。候选的主要收益是这组负载下的后台观察等待与在途数量下降。观察时间包含跟块、验证、轮询，不能直接称为委员会提交耗时。进度查询出现可重试错误，全部交易最终完成；错误计数并非交易失败数。

## 实现与验证

`journal_buffer.go` 为实际候选实现模板，`build.py` 只在私有 GoLevelDB 的 `DB.newMem` 中包装新日志文件。现有 journal 编码器会调用包装器的 `Flush`；`Sync` 先排出缓冲再执行原同步；`Close` 即使遇到 Flush 错误也关闭底层文件，并返回错误。每个日志缓冲上限 256 KiB，不跨原提交边界等待凑批，不引入后台写线程。

测试先验证未包装版本无法满足“减少文件写入次数”的断言，再启用候选，覆盖日志字节一致性、写入错误传播、Flush 失败不继续 Sync、关闭文件、有限缓冲及多次日志轮换后的关闭重开读取。三个候选测试以及委员会、store 包的 race 测试均通过。日志格式未改，运行时依赖版本未升级。正常关闭重开测试不等于掉电测试，本轮没有新增复杂恢复功能。

四轮正式对照共 **16,004 笔（含预热）** 全部完成。每轮四委员状态哈希一致、14 节点 Pending 为 0；委员会 Payments/Closed 为 4001，Gap 为 0，CAL/FUEL 总量及费用分配检查通过。详见各轮 `reports/audit.json`。

`analysis.json` 保存逐轮指标、均值和变化比例；`analyze.py` 可从原始支付样本及审计报告重新计算。Mac 上保留完整运行数据，本目录导出报告，不包含节点私钥或数据库。

## 结论边界

补充一组相同速率与笔数、开启诊断的 A/B（不混入前述四轮均值）：

| 四委员业务块的 BlockStore 批写阶段 | A 平均（ms） | B 平均（ms） |
|---|---:|---:|
| 完整 WriteSync | 99.24 | 31.28 |
| 日志写入（包括 journal.Flush） | 78.47 | 11.59 |
| 日志 Sync | 20.28 | 19.23 |

匹配样本 A 为 116 次、B 为 144 次，分别对应 29、36 个业务高度，没有歧义匹配。候选块数增多、每块平均交易数减少，单块均值并非完全等量工作对照。四委员全部匹配批写的累计耗时 **11,511.55 → 4,504.21 ms**；其中日志写入 **9,102.10 → 1,669.25 ms**，Sync **2,353.04 → 2,769.67 ms**。这些是跨节点累计工作时间，不能当作端到端墙钟时间。累计 Sync 因批次数增多而上升，仍不足以抵消写入阶段的下降；没有证据表明收益只是从 Write 移到了 Sync。

真实诊断中的日志写入阶段包含编码、缓冲及文件写入，不能全部称为设备 I/O；候选缓冲外侧的 Write 也不能冒充底层文件调用数。减少文件调用次数、相同字节输出由受控 Writer 测试直接验证。当前结果支持合并写的性能价值，但不归因于某个具体 SSD 或操作系统机制。

两轮诊断同样通过交易数、费用、状态一致及排空审计。本轮合计 **24,006 笔（含六次预热）** 全部完成；诊断 B 的进度查询次数和错误次数分别为 35,922/212，高于诊断 A 的 25,679/89，因此不把减少查询作为稳定收益。原活动网络已恢复，仍使用原版二进制和原有数据库。

这是一项有限的候选实现验证：当前证据支持继续保留合并写候选，尤其是后台排队改善；没有证明持续运行不积压，也没有证明吞吐上限提高。保持既有必要提交顺序，后续不因这次结果而全面异步化数据库。
