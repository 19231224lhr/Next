# Lightning/LND 同机实验记录

状态：**同机单笔付款延迟实验已完成，三轮共 300 笔正式付款全部成功。** 按用户最新要求，本轮只测延迟，不测 TPS；原先的持续负载与路由拓扑计划不再继续。下方预扫与续花记录保留为历史附录，不作为 Lightning Network 的容量上限或与 Next 的最终排名。

## 正式结果：同机单笔付款延迟

三次独立创建双节点、单条直接通道，每轮预热 20 笔后顺序付款 100 笔；每笔 10000 sat，方向交替，上一笔发送端报告成功后才发送下一笔。使用 LND 默认同步存储和默认 50 ms 通道提交间隔。预热、建通道、生成发票和事后审计均不计入单笔延迟。

| 独立轮次 | 成功数 | 收款确认 P50 | 收款确认 P95 | 付款完成 P50 | 付款完成 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 100/100 | 282.60 ms | 323.84 ms | 326.04 ms | 364.09 ms |
| 2 | 100/100 | 281.07 ms | 316.96 ms | 320.93 ms | 360.73 ms |
| 3 | 100/100 | 283.17 ms | 319.24 ms | 324.00 ms | 360.88 ms |
| 合并 300 个样本 | 300/300 | **282.12 ms** | **320.17 ms** | **324.54 ms** | **362.11 ms** |

这里的“收款确认”是实际调用付款 RPC 前，到测量驱动收到收款节点 `SETTLED` 事件；“付款完成”到发送端 `SUCCEEDED` 事件。全部节点与驱动均在 Mac 本机，SSH/Tailscale 不在计时路径上。这是已建立通道、已准备发票的低负载单笔测量，不包含开通道时间，不代表公网路由表现，也不是 TPS 测试。

300 个 payment hash 唯一，逐笔发票审计全部为 SETTLED、实收均为 10000000 msat，路由费为零。每轮收尾静止检查均为零未决 HTLC。即时 `after.json` 中第 1、3 轮仍各有一个待收尾 HTLC，随后 `quiescent-after.json` 确认清空；不能把付款成功事件等同于所有通道收尾完成。分位数按排序后最近秩法计算，合并行由全部原始样本重算，非三个分位数平均。

证据：[第 1 轮](direct-latency-r1/serial100/summary.json)、[第 2 轮](direct-latency-r2/serial100/summary.json)、[第 3 轮](direct-latency-r3/serial100/summary.json)、[合并审计](latency-audit.json)。各目录包含逐笔时间、发票核对、环境参数、前后通道快照和资源采样；不提交钱包、密钥及节点数据库。实际运行的测量二进制来自 `69d6e5a` 版本，其串行路径与本轮口径一致；本轮使用新增的 Python `--latency-only` 调度选项。

复现：`python3 tools/lnbench/suite.py --latency-only --repeats 3`。每次重复使用独立新目录，已有同名结果时拒绝覆盖。

### Next 补充负载测量：100 TPS，3 秒

2026-09-24 在同一 Mac 上，从 `re` 对应代码 `b2f823e` 的独立工作树构建并运行现有完整闭环脚本；单组织 9 个服务进程，300 个独立最终输入，组织代付 FUEL，保留实验内存/钱包 NoSync 配置，commit=250ms，关闭细粒度埋点。该轮为固定速率输入，**与上方 LND 顺序付款的负载不同**，作为额外实现性能参考，不据此计算同负载加速倍数。

快速到账从钱包实际 HTTP 提交前，到收款钱包验签并完成本地接收；公共确认与成员完成均包含观察等待。四委员业务状态一致，成功执行 300、失败 0、待投递 0，账务审计通过。本轮说明短时 100 TPS 输入下能及时快速交付并排空后台，不证明长期稳态或最大容量。0.9625 ms 相比历史三次单笔 2.017 ms 的变化不能直接归为新优化：本轮没有修改业务代码，负载、连接复用与测量批次不同。

### LND 配置

- Mac Studio M4 Max，16 核 CPU、64 GB，macOS 26.6.2；原生 ARM64、节点与驱动均在 Mac 上通过 loopback 通信。
- Bitcoin Core 31.1 regtest、官方 LND v0.21.3-beta（官方二进制 Go 1.26.6）；安装包按官方 HTTPS SHA256 清单校验。
- 测量驱动 Go 1.25.13，常驻 TLS gRPC 与 macaroon 认证。Windows 仅远程控制，不在付款路径上。
- 默认 bbolt 持久化；没有关闭 Sync，没有使用 RAM disk。通道提交间隔默认 50 ms、批量上限默认 10。
- 发票、链上充值、通道开启与确认均在计时前完成。测量期间不挖块、不充值、不关闭通道。
- 接收延迟：付款 RPC 调用前 → 收款节点的 `SubscribeInvoices` SETTLED 事件到达驱动。
- 发送完成：同一起点 → `SendPaymentV2` SUCCEEDED 到达驱动。二者是不同的观察终点。
- TPS 为双向合计的唯一逻辑付款数；不按 HTLC 尝试数计数。末尾查询发票核对金额，不用查询时间补造通知延迟。

## 默认配置预扫

两节点一条 1600 万 sat 通道，初始推送 800 万 sat 给另一端；每笔 10000 sat，普通发票、单路径单分片。20 笔预热不纳入下表。

| 负载 | 计划/实际/成功 | 接收 P50 | 接收 P95 | 发送成功 P50 | 从首发计划到末笔发送成功 |
| --- | --- | ---: | ---: | ---: | ---: |
| 100 笔串行 | 100/100/100 | 282.97 ms | 317.63 ms | 323.98 ms | 32.697 s |
| 5 TPS，10 s | 50/50/50 | 517.04 ms | 650.41 ms | 584.82 ms | 10.361 s |
| 20 TPS，10 s | 200/200/200 | 5310.65 ms | 6488.38 ms | 6266.59 ms | 16.048 s |

20 TPS 档实际发送速率约 19.996 TPS，派发滞后 P95 2.16 ms；发送窗口内完成 79 笔，剩余发送成功约再等 6.05 秒。含该排空时段的完成率约 12.46 笔/秒，**这不是已确定的系统最大 TPS**。所有已发付款 hash 唯一，发票均结算且实收金额匹配，直连费用为零。

末笔 SUCCEEDED 后，通道快照仍可能包含待收尾的 HTLC。预扫的时间列不等同于全部通道状态清空。后续驱动外层已增加组间静止检查与 `quiescent-before/after.json`，分别记录清空等待，不将其混入单笔结算通知时间。

## 最小核查

1. 排空后同负载重跑，并用 macOS `sample` 辅助观察，200 笔全部成功、总计 16.580 秒，重现积压。采样轮单列，不当作无诊断基线。
2. 采样出现较多 `fcntl` 等待。bbolt 的 Darwin 同步路径调用 `File.Sync`；[LND 所用 Go 1.26.6 的实现](https://raw.githubusercontent.com/golang/go/go1.26.6/src/internal/poll/fd_fsync_darwin.go) 使用 `F_FULLFSYNC`。这支持重点调查存储同步，但采样栈符号不完整，不能把全部 `fcntl` 样本直接等同为付款关键路径耗时。
3. 新建环境，仅将两端 `channel-commit-interval` 从 50 ms 改为 10 ms，批量上限仍为 10，Sync 保留。100 串行接收 P50 280.15 ms；20 TPS、200 笔总计 16.041 秒，接收 P50 5254.31 ms。没有明显改善，正式轮恢复默认 50 ms。
4. GPT 复核建议保留全部尝试与实际路由，并用单方向足额短负载区分双向状态交错；`MaxParts=1` 并不意味着只尝试一次。驱动已补充状态更新保存和单向诊断选项，待对照。

## 真实续花预跑

使用独立通道，容量 1000000 sat，初始推送 Bob 20000 sat；Alice 与 Bob 交替付款 950000 sat，共 100 笔。

每步发送前验证收款方只有这一条通道、没有未决 HTLC，且本地余额小于 950000 sat；后继付款真实成功证明其依赖上一笔收款。100 笔对应 **99 次后继资金依赖**，首笔使用启动资金。

本轮 100 笔全部成功，整链 **35.412 秒**；接收 P50 **266.23 ms**、发送成功 P50 **307.20 ms**。整链包含逐步余额查询与静止等待。下一笔等上一笔发送端成功后才发，因此这是保守的串行续付测量，不是 SETTLED 瞬间的最快续花能力，也不表示 LN 存在逐笔可追踪的同一 UTXO。

## 当前结论边界

正式实验支持当前 Mac、LND 版本与默认持久化配置下，低负载直接通道收款确认约 282 ms、付款完成约 325 ms 的可重复观察。历史预扫和资金依赖预跑另列，未进行容量确认；不能宣布最大 TPS。

历史 Next 内存/NoSync 实验与这里的正常持久化 LND 不具有相同存储条件，不能直接用延迟或 TPS 比值宣称同等保障下的协议优势。对照主表还需要 Next 同步存储路径的同条件重测。
