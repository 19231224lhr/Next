# 网关并行保存与投递：实现及实验

2026-09-19，Mac Studio M4 Max，14 个本机进程。已完成获批计划的网关 A/B、委员会耗时细分、故障验证与短时定速探测。**后台实际工作减少，整批完成加快；前台 P95 出现回退，尚不能称为全面提速。**

## 实现

- **A：网关重试时间不写盘。** 原有 4 个公共投递执行位置在 Submit 返回后立即释放。两秒冷却、同事实防重留在 Relay 的单循环内，最多 8192 项；满时不淘汰执行中或未到期项，正式任务仍留在持久 outbox。重启可以提前重发同一封装，HTTP202不结束补投。成员首次备用期限及其持久处理保持原样。
- **B：保存与首投并行。** 钱包响应 Flush 后，handler 将完整 DirectPayment 的不可变字节交给暂存入口，然后继续执行原 PersistDirect。原 4 个 Submit 和 4 个目标 INSTALL RPC 可直接使用暂存材料，不等网关保存。入口上限 128 项/32 MiB，满了走原保存与扫描；内存、扫描和通知共用防重及冷却。持久 outbox 或已提交 Observed 接管后释放暂存。
- **终态与关闭。** 执行前检查已提交 Observed；晚保存、晚 INSTALL 仍在原事务内检查终态。保存继续由有界 HTTP handler 和 Group 管理，中继退出等待自己的任务，之后才关闭存储。没有新增中间件、数据库、共识规则或费用规则。

成员签票前的输入/额度同步提交、所有验签、钱包保存后才算快速到账，都保留。内存入口不代表断电恢复成功；完整材料持有人均暂不可用时，原一轮异步方案仍可能等待。收款钱包目前只有输出与 TXCer，不能声称它已经能自动重建并补发完整原交易。

源代码检查点：`9172750`（A）、`56c79f9`（B）、`2d0c2b0`（委员会观测）、`59f9c4b`（定速测量）、`f71f64c`（进程退出切点测试）。Mac A 的等价提交为 `2dd9a06`，后续已统一历史。实验二进制的实际 SHA-256 见 [binaries.json](binaries.json)。

## 无埋点对照

每轮新创世、100 笔独立最终 UTXO、跨组织、闭环并发 64，传播 10/10 ms。暂停另一套旧实验网，保留其数据库。各版本共用委员会、成员和压测端二进制，仅替换网关。运行期间无编译或另一实验网；全部样本保留。

| 版本 | 轮数 | 整批完成均值 | 各轮时间范围 | 各轮快速到账 P95 的均值 |
| --- | ---: | ---: | ---: | ---: |
| 基线 `2f8fc24` | 4 | 3.100 s | 2.928–3.279 s | 213.34 ms |

A 的工作减负证据最明确。B 确实提前了首投，但目前不能单独证明它在 A 之上带来稳定的整批增益。补跑后 B 的前台尾延迟仍高于基线，保留为后续要解释的回退；不能用后台收益遮住这个结果。

完整运行顺序、逐轮数字、资金审计由 [comparison.json](comparison.json) 和 [summarize.py](summarize.py) 给出；首次两轮对照后，因为前台存在疑问，又增加两组基线/B，未挑选最好样本。

## 100 笔阶段测量

以下为独立诊断轮的中位数，不能把中位数相加当作端到端耗时；基线保留两轮，额外剖析轮不混入上面的无埋点结论。

| 指标 | 基线两轮 | A | B |
| --- | ---: | ---: | ---: |
| 完整认证材料准备好 → 首次 Submit | 372.46 / 322.13 ms | 66.78 ms | 33.16 ms |
| 网关保存全耗时 | 261.10 / 116.26 ms | 58.75 ms | 116.42 ms |
| 网关实际改变数据的物理事务数 | 64 / 67 | 19 | 18 |
| 网关累计 bbolt WriteTime | 1688 / 1645 ms | 587 ms | 577 ms |
| 网关 Submit 次数 | 100 / 100 | 100 | 100 |

B 有 **48/100** 笔在保存事务回调尚未开始时已经 Submit，是绕开保存依赖的直接证据。另有 96 笔早于存储返回时间标记，但提交后进程可能稍晚才记录日志，不能把这 96 笔都解释为早于物理持久化。A 也有少量此类日志交错，实际提前于保存回调的数量为零。

保存仍然消耗资源，B 诊断轮保存中位数并未下降；变化是发送不再以它为前置。各个完整阶段、逐笔时间和块级时间分别保存在 `group-*/stage-summary.json`、`transactions.csv`、`blocks.csv`。负的“保存返回标记→发送”是先后偏移，不是负耗时；新的主要投递指标从认证材料准备好开始。

## 委员会定位

新增可关闭的实际调用耗时：提案构造/分片、WAL FlushAndSync、内部消息 WriteSync、FilePV.Save、签名、BlockStore 保存、EndHeight WAL；另记录实际提案者 CheckTx 和应用 Commit 的锁、准备、写入阶段。通过 `UTXO_SETTLEMENT_TRACE=1 UTXO_COMET_PROFILE=1` 开启，默认 hook 为 nil，诊断仅进已有有界内存记录器，不增加同步日志。

一次 100 笔剖析轮、委员 0 的代表性单次中位数：

| 实际调用 | 中位耗时 |
| --- | ---: |
| 提案构造（含调用应用准备提案） | 11.84 ms |
| 提案分片构造 | 0.079 ms |
| 投票前 WAL FlushAndSync | 14.28 ms |
| 本地消息 WAL WriteSync | 12.18 ms |
| FilePV 签名状态保存 | 15.77 ms |
| 投票签名（包含上项） | 21.77 ms |
| BlockStore 保存 | 15.77 ms |
| EndHeight WAL | 14.49 ms |

入口委员接收交易到实际提案者完成 mempool 检查，中位 17.92 ms；其后到 PrepareProposal 入口约 213.11 ms。应用 Commit 的入口锁相关时间只有数微秒，主要耗时在数据库更新。原先出现的单块 136 ms Commit 没有在该轮复现，不能给那一次峰值编造唯一原因。

这些调用分别承担共识恢复、防双签、区块保存等职责；**多次同步不等于重复同步**。签名包含 FilePV 保存，不能重复相加。当前只做定位，没有删 sync、改超时或跨文件合并持久化。完整调用次数、各委员会与各块结果见 [profile-summary.json](group-parallel-profile/profile-summary.json)。

## 定速与故障验收

`bench-v4 -rate` 使用有界在途量，记录计划时刻、实际发出时刻及单调时钟发包延迟。容量不足会表现为发包落后，不隐藏为低延迟；未发出的样本也不计成功。最终版本在每档约 20 秒、最大在途 128 下实测：

| 指标 | 20 笔/秒，400 笔 | 40 笔/秒，800 笔 |
| --- | ---: | ---: |
| 成功/唯一公共提交 | 400/400 | 800/800 |
| 实际发送速率 | 约 20.00/s | 约 40.00/s |
| 快速到账 P50 / P95 | 85.88 / 121.66 ms | 109.92 / 162.80 ms |
| 发送 → 实际 Commit P50 / P95 | 813.00 / 1084.68 ms | 1027.33 / 1395.69 ms |
| 发包落后 P95（单调时钟） | 0.69 ms | 0.67 ms |
| 采样中的委员会未提交峰值 | 22 | 55 |
| 预热后未提交量拟合斜率 | +0.017 笔/s | +0.051 笔/s |
| 停发 → 最后一笔实际 Commit | 468 ms | 570 ms |
| 停发 → 最后一笔成员完成观察 | 643 ms | 883 ms |

这支持所测短时负载能跟上、停止输入后能排空，不是最大 TPS 或长期稳定性证明。两档实验相关进程 RSS 合计峰值约 814/1024 MiB；运行文件分别增长约 128/174 MiB，包含数据库、WAL 和日志及启动开销，不能当作每笔长期净存储成本。逐半秒曲线、最老任务年龄、逐笔记录和资源采样均保留。

网关 POST 持续返回 503 的 16 笔测试全部由成员提交并结清；网关共 32 次被拒投递，成员备用期限未被推迟。还补了真实子进程退出切点：完整材料已进入内存、保存被阻塞，首次 Submit 时退出；重开数据库确实没有 outbox，由保有完整原交易的持有人重投同一字节后恢复投递。这不是对收款钱包自动补发能力的声明。

全部实验合计 **3916 笔**成功；各轮四委员会状态一致、Payments=Closed、缺口为零、14 个节点 outbox 排空，CAL/FUEL、费用报酬和销毁检查通过。Mac 上相关包 race 测试与 `go test -tags=comet_v3 ./...` 通过，日志见 `final-race.txt`、`final-tests.txt`、`crash-test.txt`。
