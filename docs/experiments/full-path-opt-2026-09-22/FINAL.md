# 完整快速支付系统优化结果（2026-09-22）

当前版本在Mac Studio同机实验中完成了500 TPS和约599 TPS的完整快速支付负载。每轮90,000笔均取得TXCer、被公共账本成功执行并完成成员观察，零交易失败。800 TPS目标未达成，不能把最终排空等同于承接了该速率。

## 最终复测

三轮全部从当前源码重建四类节点；每轮新数据库、相同创世模板。内部阶段每100笔采样一次，钱包阶段逐笔记录；额外CPU、数据库、共识诊断关闭。

800轮窗口发送速率约763、684、651、621 TPS，公共成功观察约717、684、637、620 TPS；计划发送滞后P95达19.47秒。实际679.66 TPS既不是800达标，也不是严格测得的系统极限。

## 计时定义

- 快速到账：付款钱包开始实际HTTP发送，至收款钱包验证TXCer并完成本地事务。当前钱包NoSync，“保存”不代表已耐久刷盘。
- 实际发送TPS：(发送笔数−1)/(末笔实际发送时间−首笔实际发送时间)。
- 完整闭环：压测开始至最后任务观察到钱包已跟块、四个签发组织成员已观察并处理；包含观察延迟，不等于共识单独执行时间。
- 上链观察包含H+1认证头等待、钱包验块/应用及25ms轮询。委员会不生成逐笔私有通知。
- 交易准备与正常停机后的审计导出不计入支付时间。fresh600关机及导出10.35秒，另列metadata。

## 保留的修改与证据

1. **成员使用显式实验有序内存状态。** 原bbolt诊断在一个活跃成员测到646,459次WriteAt、11.629GB写入、13.623秒调用耗时；freelist仅0.149秒、mmap约1.8ms。复用已有google/btree，保留Group、原子更新和更新后签名。长测第三票的状态排队P95约93.28→3.68ms、更新收尾49.56→0.82ms。调用耗时包含OS/调度等待，不全是设备写入时间。
2. **实验钱包可显式NoSync。** 同步→NoSync→同步的短对照快速P50约42.90→4.84→41.43ms。保留验证和事务完成门槛，收益包含放弃同步刷盘。
3. **去掉重复工作。** 网关同一请求只编码一次用于四路扇出；成员HTTP入口只解码验证一次；进度查询只检查签署记录存在，不再解码完整付款。输入/资金检查和每成员独立验签仍在。
4. **Darwin实验NoSync也禁用扩容同步。** NoGrowSync还改变预分配行为，不把收益全归因于fsync。正常同步Open不变。

4KB页、描述符缓存、outbox正文引用均未显示稳定整机收益，已撤回。本轮没有增加中间件、调整共识超时或扩大256/2048并发上限。

任务开始时90000笔、实际460.21 TPS、43失败、快速P50/P95=80.02/703.16ms；当前工作点明显改善。这是多项修改和实验存储条件共同作用的结果，不把整体差异归因于单个补丁；机器状态和轮次也有波动。

## 实验边界及正确性

- Mac Studio M4 Max、16核CPU、64GB，Go1.27.1；同机14进程，4委员、2组织各4成员、2网关。独立已最终UTXO输入、跨组织收款，没有把所有付款串成未结算TXCer链。
- 成员GOMAXPROCS16/GOGC200，显式UTXO_EXPERIMENT_MEMBER_MEMORY=1；钱包-wallet-no-sync。网关及委员会应用仍同步bbolt；Comet块/状态/证据库MemDB，WAL及私有验证者签名文件仍持久化。
- 成员内存模式只供每轮从头开始的实验。关闭后按批导出只读审计文件；.pending和最终audit-only文件均不能用正常写模式重开。崩溃后使用新目录，不支持恢复签署状态。历史内存会增长，本轮未实现长期裁剪。
- 四委员最终状态哈希一致，outbox总数0，90000笔唯一成功执行。审计检查CAL/FUEL账目、可用+占用=授权、占用对应原签署记录的剩余值。
- 500/600/800的成员进度查询未成功计数为48,239/55,611/67,005。这是HTTP失败、非200或解析失败的合并计数，原始计数没有细分原因，不能全部称作正常未完成响应。观察会重试，最终交易失败均0。后续可细分查询限流，本轮不扩大查询并发。
- 未证明公网、恶意故障、稀缺备付或任意时长下仍有相同性能。
