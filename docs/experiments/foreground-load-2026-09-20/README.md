# 200 TPS 下快速到账延迟：定位结果

2026-09-20，Mac Studio M4 Max，14 个本机节点。**主要新增时间在同步提交及其排队，另发现网关 HTTP/1 连接上的隐性串行等待。** 当前只增加独立实验与诊断，没有应用生产优化。

## 口径与方法

快速到账从付款钱包开始 HTTP 发送，到收款钱包验证并同步保存 TXCer 为止。此前 293.50 ms 是 24,000 笔的 **P95**，中位数为 148.68 ms；不能说每笔都变成 293 ms，也不能直接用历史某一笔的 80 ms 与 P95 比较。

本轮冻结委员会、网关和成员程序，沿用 10/10 ms 传播、成员 GOMAXPROCS=16/GOGC=200；快速到账配额 256，总未完成配额 2048。每轮新数据库、相同 48,002 输出创世、另预热一笔，请求预构造及保存不计入发送窗口。

实验版 payctl 通过 Go overlay 增加钱包验证、写入排队、回调与提交返回时间。四轮高负载每 20 笔记录一条现有完整前台 trace，所有交易均记录到账时间。先跑每两秒一笔的 20 笔低负载参照，再做以下 ABBA：

| 顺序 | 成员进度查询 | 笔数 / 目标发送窗口 | 到账 P50 | 到账 P95 | 查询请求数 |
|---|---|---|---:|---:|---:|
| A1 | 原 25 ms 检查循环 | 12,000 / 60 s | 151.77 ms | 272.72 ms | 175,981 |
| B1 | 成员查询最小间隔 200 ms | 12,000 / 60 s | 154.33 ms | 284.79 ms | 69,841 |
| B2 | 成员查询最小间隔 200 ms | 12,000 / 60 s | 128.86 ms | 258.50 ms | 65,086 |
| A2 | 原 25 ms 检查循环 | 12,000 / 60 s | 153.66 ms | 280.04 ms | 137,669 |

四轮全部成功，两种配额均未触顶，发送滞后 P95 分别 1.07/2.94/0.69/1.97 ms。B 只降低压测器成员 GET 频率，钱包本地 25 ms 检查、节点跟块、INSTALL、结算与最终完成条件均未改。较低频率会推迟成员完成的**观察时间**，不能把它解释为真实结算变慢。

查询总数减少 **56.98%**，但快速到账尾部没有稳定改善：两轮 P95 平均仅从 276.38 变为 271.65 ms，B1 较差、B2 较好。两轮均值不足以建立显著性结论。查询有成本，当前证据不支持把查询量认定为主要原因，亦未采用 200 ms 参数。

## 前台时间花在哪里

低负载 20 笔到账中位数 **35.31 ms**、P95 **41.28 ms**、均值 36.43 ms。以下组织侧数据按**实际凑齐第三份有效票的成员**逐笔关联，均为平均阶段耗时；正常负载列是 A1/A2 两轮范围。

| 阶段 | 低负载 | 200/s 正常查询 |
|---|---:|---:|
| 钱包发送 → 网关 handler 开始 | 0.10 ms | **32.59–34.90 ms** |
| 网关处理、分发 → 关键成员 handler 开始 | 0.47 ms | 4.33–4.54 ms |
| 成员校验，至申请写入 | 0.59 ms | 1.47–1.50 ms |
| 成员等待写入回调开始 | 0.01 ms | **27.03–27.38 ms** |
| 本笔成员状态回调 | 0.08 ms | 0.08–0.09 ms |
| 本笔回调结束 → Group.Update 返回 | 16.14 ms | **38.48–42.37 ms** |
| 返回签名、网关凑票、钱包收到证书 | 0.39 ms | 4.91–5.56 ms |
| 钱包解码、验证及持久保存 | 18.66 ms | **55.37–55.71 ms** |

这张表使用 20 条低频及 1,200 条正常负载抽样关键路径，不把各阶段 P95 相加。全量 A1/A2 到账均值为 165.00/167.12 ms；抽样均值为 167.79/168.50 ms。钱包全量测量进一步分出：验签约 **0.18 ms**，等待写回调约 **20.43–21.34 ms**，回调约 **0.02 ms**，回调结束到提交返回约 **34.15–34.91 ms**。

固定每 20 笔抽样可能与周期任务存在相位偏差。这些阶段值用于定位；随后单独诊断改用固定种子随机约 1/5 抽样，验证机制，不把两种抽样或不同长度实验混算性能收益。

## 已确认：网关保存会阻塞同一连接的下一笔

当前 `cmd/gateway/direct.go` 的 handler 顺序为：

```text
认证完成 → Write + Flush 完整凭证
         → OfferDirect
         → PersistDirect 等待同步保存
         → handler 返回
```

客户端已根据 Content-Length 收完响应，可以立即复用 HTTP/1 连接；但服务端尚在前一笔 handler 内。Mac 使用的 Go 1.27.1 `net/http/server.go` 2129–2144 行在同一连接中同步执行 ServeHTTP，返回后才处理后续请求。

独立 4,000 笔诊断通过客户端 `httptrace` 的本地 TCP 地址与网关 `RemoteAddr` 关联前后请求，保留前一笔保存完成与 handler 返回时间，得到 803 条完整连接链：

- 取得连接 P95 **0.005 ms**，此处并未出现明显连接池等待。
- 请求已经写出 → 网关 handler 开始：平均 **28.99 ms**，P95 **69.43 ms**。
- 其中 664 条等待超过 1 ms；累计等待的 **97.57%** 与同一连接前一个 handler 尚未结束的区间重合。
- 前一笔 `persist_done` → handler 返回：中位 **0.002 ms**，P95 **0.008 ms**。

这里同时有同连接逐笔时间关联及标准库顺序执行代码，支持“上一笔后台保存阻挡下一笔 handler”的因果解释。97.57% 仅针对所述慢连接等待区间，不是全部到账延迟的比例，也不是预估优化收益。

## 已定位：成员主要等待前批提交及本批写入同步

同一独立诊断启用 bbolt 原生计时，并通过单写者内不可重叠的物理事务时间范围，把 807 条关键成员请求匹配到各自真实提交批次：

| 关键成员区间 | 平均耗时 |
|---|---:|
| 进入写入队列 → 本笔回调开始 | 20.316 ms |
| 上一行中，前面物理事务正在提交的部分 | **19.453 ms** |
| 上一行中，其他业务回调执行的部分 | 0.805 ms |
| 本笔回调结束后，同批余下回调 | 0.629 ms |
| 应用整批键值修改 | 0.091 ms |
| 本批物理提交 | **31.143 ms** |
| 物理提交结束 → 请求恢复返回 | 0.102 ms |

四个签署成员的 bbolt 原生 `WriteTime` 均值 **30.24–30.83 ms**，相应物理提交 **30.45–31.00 ms**，spill 约 0.09 ms。钱包原生 WriteTime **29.904 ms**，物理提交 **29.959 ms**，整批业务回调平均 0.219 ms。

因此，这轮的主要存储等待集中在写入与同步阶段。长业务回调和提交后的协程唤醒不是本轮均值的主要部分。**WriteTime 包含写入和同步，不是一次 fsync 的时间，也不能据此断言 SSD 带宽饱和。** 本轮没有进一步拆开系统调用、文件系统及多进程共享磁盘的影响；也不声称所有尾部样本都与 GC 无关。

## 下一步建议

1. **先修网关连接上的串行等待。** 在 handler 返回前，让有界后台明确接管保存任务，使 handler 不必等待保存完成。首补丁可在队满时沿用原同步保存兜底，保留失败记录、Observed 终态重查、关机等待及已保存 outbox 的重试；后台不使用会随 handler 返回取消的请求 context。先测试同一连接上的下一笔能在前一笔保存完成前进入，再做性能对照。内存接管不等于持久化，也不增加新的耐崩溃保证。
2. **再独立优化同步提交负担。** 保留成员“输入/额度持久化后才签票”和钱包保存门槛，核查每笔产生的真实提交次数与批量合并机会；必要时用同配置分机器/磁盘实验区分同机 I/O 竞争。当前不据此换库、关 sync 或增加 worker。
3. 查询减量保留为后续候选；不能期待只改查询间隔就把 200/s 到账降回低负载水平。

尚未实施上述生产修复，不能预报修复后具体 P95 或极限 TPS。
