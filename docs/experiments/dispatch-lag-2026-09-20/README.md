# 200/s 发送滞后：压测器并发槽追踪

后续已实现发送与观察配额分离，见 [实现与实测结果](RESULTS.md)。下文保留实施前的定位记录。

结论：804.72 ms 的 P95 主要由压测器的 **256 个完整闭环槽位**造成。
槽位从发出交易一直占到钱包跟块、四个成员进度查询完成，才允许发送下一笔。
这不是支付协议要求用户等上一笔上链才能发送另一笔独立 UTXO 交易。
但槽位占用时长包含真实后台工作及观察等待，不能反过来说与系统运行完全无关。

本轮没有新发交易、改生产代码或重启节点。重读当前代码，离线核算上一轮
100/150/200 每秒共 54,000 笔成功交易的完整逐笔时间戳。输入 SHA256 保存在
`analysis.json`；运行 `python docs/experiments/dispatch-lag-2026-09-20/analyze.py`
即可重算。原始结果位于相邻 `committee-storage-2026-09-20/sustained-*` 目录。

## 代码路径

- `cmd/payctl/direct_pace.go:11`：`jobs` 是无缓冲 channel。按 `start+i/rate`
  安排时间，到期后在 `jobs <- i` 等空闲 worker；不是到点就无条件发送。
- `cmd/payctl/direct_bench.go:152`：创建固定数量 worker，每个 worker 在同一循环中
  依次完成发送、收款、跟块检查、成员进度检查。
- `cmd/payctl/direct_bench.go:203`：钱包保存 TXCer 后只记录 Fast 时间，没有释放 worker。
- `cmd/payctl/direct_bench.go:206`：25 ms ticker 检查钱包是否已观察该笔上链。
- `cmd/payctl/direct_bench.go:224`：之后依次查询四个成员 `/v4/progress/{fact}`；
  任一未完成就继续等，下轮重新查询。
- `cmd/payctl/direct_bench.go:243`：四个成员观察完成后返回，worker 才领取下一笔。

请求构造、签名、编码和待发请求保存发生在测量窗口前，不是本项延迟的来源。
`SentUnixNS` 在调用 HTTP client 前记录，HTTP 连接池／网络等待属于发送后的指标，
不能解释这次发送前的 805 ms。

## 原始时间线核算

把每笔的 `[SentUnixNS, MemberObservedUnixNS)` 视作已知占槽区间，扫描全部开始／结束事件。
它略微低估实际占槽，因为完成时间戳之后还有退出当前循环的微小开销。
所有记录满足阶段先后顺序，没有失败，占槽数未超过 256，最终归零。

| 指标 | 100/s | 150/s | 200/s |
|---|---:|---:|---:|
| 原报告发送滞后 P95 | 0.49 ms | 279.25 ms | 804.72 ms |
| 首笔到末笔发送窗口内平均占槽数 | 178.0 | 244.3 | 251.9 |
| 256 槽全部占满的时间比例 | 1.57% | 52.04% | 87.92% |
| 累计发送滞后与全槽占满区间重合比例 | 68.41% | 99.48% | 99.85% |
| 计划到期且按顺序具备容量后，剩余等待 P95 | 1.177 ms | 1.132 ms | 0.320 ms |

最后一项按实际发送顺序计算：第 k 次发送至少需要之前 k−256 个任务已完成。
将该容量条件与计划时刻取较晚值，再与实际发送时刻比较。
这是容量约束下界，不是通过 worker ID 直接跟踪的调度事件。
时间重合本身不证明因果；本结论结合了无缓冲 channel、worker 生命周期以及
容量可用后迅速发出的三项证据。没有证据支持将 805 ms 主要归因于 GC 或定时器。

报告原有 DispatchLagMS 使用 Go 单调时钟，本次离线区间来自 Unix 时间戳。
两者相差最多约 1.06 ms，不能混作完全一致的纳秒测量；不影响数百毫秒排队结论。
分位数不可相加；表内“重合比例”按全部交易累计等待计算，并非 P95 的分解。

## 200/s 的具体一笔

第 15,261 笔，恰好对应原报告 804.722584 ms 的 P95 样本：

| 事件 | 相对测试开始 |
|---|---:|
| 计划发送 | 76.300000 s |
| 按已完成任务数量推算，该笔所需容量可用 | 77.105391 s |
| 实际发送 | 77.105393 s |

具备容量后约 0.002 ms 就发出了；发送后快速到账为 112.789 ms。
约 805 ms 发生在发出前，不是这笔请求进入网关后耗费的时间。

## 槽位被什么占住

200/s 轮次的逐笔平均值（不是中位数）：

| 区间 | 平均耗时 |
|---|---:|
| 发出→钱包验证并保存 TXCer | 138.69 ms |
| 快速到账→钱包观察到上链 | 1,084.32 ms |
| 钱包观察上链→压测确认全部成员处理完成 | 50.02 ms |
| 整个槽位占用 | 1,273.03 ms |

约 **89.1% 的槽位占用发生在快速到账之后**。后两个区间包含结算、认证区块可用、
跟块和测试程序观察，不能全部称为委员会执行时间，也不能全部称为无效开销。
本次数据没有细分这些区间内部的贡献，不据此声称成员查询本身成为主要瓶颈。

按这次平均占槽时长，200/s 需要约 `200 × 1.273 = 254.6` 个槽，几乎用满 256。
区块和跟块按批推进，释放时刻不均匀，容易出现全满以及计划任务滞后。
这只是当前压测流程下的容量关系，不是委员会吞吐上限。

## 下一步建议

压测器分离“发出并取得快速到账”和“观察后台完成”：发送配额在收到并保存 TXCer 后
释放；钱包与成员完成情况由独立、有限的观察流程继续记录。共识、签名、持久化和
完成判据保持不变。保留原完整闭环压测模式用于同条件回归。

不能只删等待，也不建议简单变成无限 goroutine。应继续记录发送计划滞后、实际发送率、
快速到账、后台未完成数量和最老年龄，观察能力不足时明确报告限制。
解耦后的改善需要另做同条件实测；本轮只定位原因，不预告更高的可持续 TPS。
