# 最小方案：发送配额与后台观察分离

状态：已实现并完成验证；实测收益、后台波动及旧模式拒绝样本见 [RESULTS.md](RESULTS.md)。
目标是修正压测器的阶段耦合，不将压测器变化称为服务端性能优化。

## 选择

- 仅把完整闭环槽从 256 提高到 512：改动最小，但发送和后台观察仍然耦合，
  可作为辅助对照，不作为长期测量方式。
- **采用两道有界配额**：快速到账配额和总未完成任务配额分别管理；复用现有观察流程。
- 暂不引入中央 pending 扫描、单独观察 worker 池或新队列框架；有查询瓶颈证据再处理。

## 具体流程

保留原始绝对发送计划 `start+i/rate`。一个派发循环按以下顺序处理：

1. 可取消地取得总任务配额，首轮上限 2048。
2. 可取消地取得快速到账配额，首轮上限 256。
3. 先 `wg.Add`，再启动该笔 goroutine；不能先创建无界 goroutine 再等配额。
4. 执行原来的发送、TXCer 验签和钱包同步保存，记录快速到账时间，释放快速到账配额。
5. 同一 goroutine 继续原有钱包跟块检查、四成员进度检查，完成后释放总配额。
6. 停止派发后等待所有任务结束，再汇总数据并关闭资源。

必须移除旧的“256 个 worker 每个跑完整流程后才领取下一笔”限制，否则不能解耦。
每个 sample 仍由该笔任务独占写入。配额保证只释放一次；等第二道配额时取消，
归还已经取得的第一道配额。请求、证书、节点业务、同步持久化及完成判据均不改变。

保留原闭环模式用于回归。新模式标为“有界定速发送＋独立后台观察”，不是无界开环。
旧默认行为不静默改变；具体命令行入口在实现时沿用现有 bench-v4 风格。

## 不能隐藏的等待与错误

继续保留计划发送→实际发送总滞后，分开记录派发交付、总配额、快速到账配额等待。
不能在拿到配额后重置计划时刻。区分已占总配额但尚未发出、已发送未取得快速到账、
已快速到账但后台未完成，报告各项数量及后台最老年龄。

2048 是压测器的资源上限，不是系统容量保证。若总配额耗尽，需要明确报告，不能将
受限的实际发送量当作达到计划速率。单纯降低发送滞后而后台队列持续增长不算成功。

发出后的超时／断连不能算业务完成。首轮遇到不确定结果就停止新增，保留未决记录，
不一边释放容量继续发，一边宣称真实未完成业务受总配额约束。
后台失败也不能抹掉此前已测得的快速到账阶段；分开报告阶段结果与全闭环成功数。

观察逻辑先保持 25 ms 检查和现有成员 HTTP 接口，增加进度查询次数、响应耗时统计，
判断观察流量是否反过来影响被测节点。本轮不同时改查询策略。

## 验证顺序

先检查：后台观察挂起时快速配额能复用；总任务不超过上限；两处配额等待的取消；
快速保存失败、后台观察超时以及正常结束无名额泄漏、无样本并发改写或提前关闭。

再用相同节点程序、创世、200/s、120 秒做旧→新→旧对照，保持验签和同步持久化。
同时比较实际发送率、计划滞后、快速到账 P95、公共提交观测、后台未完成数量与
最老年龄、查询负载和末尾排空；继续核对费用、四委员状态和 outbox 排空。
公共提交仍按原采样口径标注观测上界，不伪装精确 Commit 时刻。

先验证解除压测限制后 200/s 是否跟得上，再讨论提高速率。
评审原文见 `gpt-review.json`，GPT 未执行代码或测试。
