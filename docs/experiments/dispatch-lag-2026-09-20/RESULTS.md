# 压测器发送与后台观察分离：实现与对照结果

已实现并在 Mac Studio 验证。改动集中在 `cmd/payctl`；委员会、网关、成员二进制冻结，
验签、同步持久化、费用与完成判据保持原样。新模式解除快速到账与完整闭环的配额耦合，
不等于服务端或共识获得了新的性能优化。

## 使用与实现

```sh
payctl bench-v4 -dir "$LAB" -start "$UNUSED_START" -count 24000 \
  -rate 200 -concurrency 256 -max-pending 2048
```

实验目录须有足够的独立、未使用创世输入。`-max-pending 0`（默认）保留旧的完整闭环
worker 池，用于回归。新模式先取得总任务和快速到账配额，再启动该笔 goroutine；
钱包验签、同步保存 TXCer 后释放快速配额，继续原来的跟块及成员进度观察；结束时释放
总配额。取消、提前失败不会泄漏名额。发生未确认结果时，新模式停止新增并保留结果。

每笔仍由自己的 goroutine 写入样本；全部任务退出后才汇总，避免额外测量线程读写竞争。
保留原发送计划与实际发送差，新增派发交付、两种配额等待、阶段完成数、成员查询次数
及耗时。每 250 ms 重建已发未完成数量、最老年龄及发送前预留数量，时间线在报告 `Queue`。
这些是采样峰值，不保证捕捉所有瞬时峰值。旧模式没有两个信号量，其等待由交付延迟体现，
`total_limit_hits` 等配额字段只适用于新模式。

## 200/s、120 秒，旧→新→旧

各轮相同 48,002 个输出的创世、相同节点程序；预热一笔，预生成请求在测量窗口之外。
快速到账仍从付款钱包调用 HTTP 发送开始，到收款钱包验证并持久保存 TXCer 结束。

| 指标 | 旧模式 A1 | 新模式 B1 | 旧模式 A2 |
|---|---:|---:|---:|
| 请求数 | 24,000 | 24,000 | 24,000 |
| 完整成功数 | 24,000 | 24,000 | 23,989 |
| 实际首末发送速率 | 195.77/s | 200.00/s | 失败对照，不计为全成功结果 |
| 计划发送滞后 P95 | 2,246.07 ms | 0.575 ms | 563.82 ms |
| 快速到账 P50 | 149.40 ms | 148.68 ms | 141.93 ms¹ |
| 快速到账 P95 | 233.94 ms | 293.50 ms | 221.42 ms¹ |
| 本轮测量耗时 | 123.605 s | 121.104 s | 121.391 s² |
| 成员进度查询总数 | 138,662 | 385,518 | 138,121 |

¹ A2 的到账延迟仅来自成功子集。² A2 在报错退出时仍有 11 个未确认完成的样本，
不能称为 24,000 笔完整闭环时间。A2 的 11 笔均收到 `gateway 429: LIMITED`，索引
3732、3742、3743、3745、3747、3748、3750、3752、3753、3754、3767。
源码 `cmd/gateway/direct.go` 的 128 槽入口在解码和组织认证前返回该响应。
没有为获得漂亮结果而重试覆盖这一轮，也没有将拒绝交易计入成功吞吐。

新模式每个 10 秒窗口都发出 2,000 笔；首末发送跨度 119.996 s。
快速配额与总配额的阻塞次数均为 0，观察到的快速阶段在途峰值为 110。
这支持“压测器不再被 256 个完整闭环槽挡住”，而不是“协议已经提升吞吐上限”。

## 后台并没有因此变轻

| B1 指标 | 结果 |
|---|---:|
| 已发未完成采样峰值 | 1,401 笔 |
| 其中已快速到账、等待后台的采样峰值 | 1,350 笔 |
| 20～110 秒未完成平均数 | 587.76 笔 |
| 最老未完成年龄峰值 | 7.014 s |
| 末笔发出→所有成员完成观测 | 1.109 s |
| 末尾未完成数 | 0 |
| 每笔平均成员进度查询 | 16.06 次（A1 为 5.78 次） |

队列有回落：80～90 秒平均约 952 笔，90～100 秒回落到约 524 笔；
最后全部排空。有限两分钟内没有单调增长到 2048 上限，但存在明显的后台波动。
快速到账 P95 也比 A1 上升约 25.5%，不能把该改动描述成所有延迟都改善。

B1 的平均阶段耗时为：发出→快速到账 164.15 ms，快速到账→钱包观察上链
2,416.68 ms，钱包观察上链→全部成员完成观测 176.59 ms。阶段分位数不可相加。

额外使用已持久提交的 `/healthz` 高度和离线区块 Fact 对应来检查公共提交。
B1 尚未观察到提交的采样峰值为 978，但实际采样最大间隔达到 2.44 秒，故它是保守观测，
不能当成精确实时待提交数量，更不能直接将全部后台等待归因于委员会执行。
原有逐笔 25 ms 观察被保留；更多在途任务伴随更多查询，需要后续分别定位真实提交、
跟块与查询负担。此次没有继续叠加观察聚合或节点调参。

`progress_errors` 包含网络、非 200 响应及解码失败，三轮分别为 2020 / 3862 / 2199；
观察循环允许重试。这不等于业务付款失败，本轮未逐项记录这些查询的响应状态码。

## 验证、失败记录与部署

- 全项目 `go test -tags=comet_v3 ./...` 和 `go vet -tags=comet_v3 ./...` 通过。
- `go test -race -tags=comet_v3 ./cmd/payctl -count=5` 通过，覆盖快速名额提前释放、
  总上限、两处等待中的取消、提前返回，以及未知结果不误记为完成。
- 两次 100 笔冒烟均完成付款。第一次发现汇总末点使用单调时钟重建 Unix 时间，
  导致末尾队列误报 1 笔；已改为直接记录结束时的 Unix 时间，第二次及正式轮正确归零。
  首次原始记录保留为 `smoke-decoupled`，不拿它的队列末点作有效结果。
- 共尝试 72,205 笔（含 5 笔预热），其中 11 笔在旧模式 A2 被入口拒绝。
  **72,194 笔已接纳付款通过资金审计**：每轮 14 节点 outbox 均排空，四委员状态一致，
  已接纳付款全部关闭、缺口为零，CAL/FUEL、费用分配与燃烧匹配。
- A2 的共享脚本因非零退出停止，没有导出该轮资源采样；保留逐笔报告、错误日志，
  并单独对停止后的数据库完成审计，见 `coupled-a2/failure-summary.json`。
  原始 `unknown=11`/末尾未完成字段是保守的未确认完成分类；已结合入口代码及审计
  确认这些是拒绝请求，不代表 11 笔链上资金悬而未决。
- 新 payctl 已接入原实验网工具入口，运行中的节点和原 100 笔数据保持原样，四委员高度 7。
  节点二进制、相同创世摘要、源文件摘要及健康状态见 `provenance.json`。

本轮结论：发送阶段的人为限制已解除，真实 200/s 下的后台波动和观察开销也被更清楚地
暴露出来。新模式适合继续定位瓶颈；当前结果不支持“后台积压已彻底解决”或无限期容量承诺。

## 文件

- `run-summary.json`、各轮 `result-summary.json`：统计结果及时间序列。
- 各轮 `reports/bench-v4-1.json`、`audit.json`：完整逐笔记录和资金审计。
- `binaries.json`、`provenance.json`：实际运行程序及部署记录。
- `run_series.py`、`run_checks_and_trials.sh`：复现实验，非零结果会停止，需保留并审查失败轮。
- `analyze_runs.py`：分析成功轮；失败轮要求单独审计与分类。
- `tests-project.log`、`tests-race.log`、`vet.log`：验证记录。
- `gpt-review.json`、`PLAN.md`：实施前评审和方案。
