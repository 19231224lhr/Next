# 单笔与 100 TPS × 10 秒：全路径阶段对比

结论：本轮快速到账增加主要在成员持久化排队、提交返回和压测钱包保存。后台最大增量位于等待提案、共识推进及等待后续高度提交头，交易金额规则和逐笔执行本身仍很短。单笔只能作为本轮参照，不能当作低负载的稳定分布。

## 实验条件与口径

- 两组使用相同的日志合并写候选委员会、相同其他角色二进制；SHA-256 见 `binaries.json`。这不是原版与候选对比。
- Mac Studio 单机运行 4 委员、2 网关、8 成员及压测钱包。共识传播 10/10 ms；成员 GOMAXPROCS=16/GOGC=200。验签和同步持久化保留。
- 每组使用独立新数据库和相同创世配置（48,002 个初始输出），先完成一笔预热。正式组依次为 1 笔、1,000 笔；后者目标 100/s，快速并发上限 256、总未完成上限 2048。
- 采用已有阶段埋点，不开 Go runtime trace。前台全部采样，单笔和负载组分别取得 1/1、1000/1000 条完整关键成员路径；委员会与跟块时间线均未溢出。
- 计时从付款钱包实际发送开始，交易预构造、签名和发送前请求保存不计入。每个阶段先逐笔计算，再求均值/P95；只有非重叠路径的均值可以相加，各阶段 P95 不能相加。
- 快速到账终点是钱包验证并保存 TXCer 后返回；上链观察终点包含获取和验证公共区块及本地观察；委员会应用提交终点取 committee0 的 Commit 返回。
- 本压测付款和收款钱包共用一个 Group/bbolt 数据库，1000 笔的收款保存与跟块共用这条写入路径。因此钱包排队是本压测部署的真实耗时，不能全部归因于担保组织，也不能直接外推到分散在不同设备的用户。

## 前台：从发送到可续花

以下成员是完成所选三票法定人数的关键成员，不是四成员平均。

| 阶段 | 单笔 ms | 100 TPS 均值 ms | 100 TPS P95 ms | 均值增量 ms |
|---|---:|---:|---:|---:|
| 钱包发送→快速到账（总计） | 51.853 | 107.566 | 148.961 | +55.713 |
| 钱包发送→网关处理入口 | 0.360 | 2.169 | 13.073 | +1.809 |
| 网关处理→准备扇出 | 0.250 | 0.871 | 0.632 | +0.621 |
| 准备扇出→关键成员处理入口 | 0.174 | 1.802 | 12.756 | +1.628 |
| 成员验证→请求写入 | 0.618 | 0.788 | 0.899 | +0.170 |
| 成员请求写入→进入事务回调 | 0.007 | 19.503 | 35.215 | +19.496 |
| 成员事务回调 | 0.077 | 0.086 | 0.193 | +0.009 |
| 成员回调结束→提交返回 | 20.321 | 31.884 | 44.870 | +11.563 |
| 成员提交返回→票被选中 | 0.160 | 2.716 | 16.250 | +2.556 |
| 票被选中→钱包收到凭证 | 0.226 | 1.622 | 11.724 | +1.396 |
| 钱包验证并保存凭证 | 29.660 | 46.125 | 70.636 | +16.465 |

快速到账总增量约 **55.71 ms**。成员写入排队增加 19.50 ms，成员提交返回增加 11.56 ms，钱包保存增加 16.47 ms，合计约占增量 **85.3%**。成员验证只增加 0.17 ms，网关扇出到成员入口只增加 1.63 ms。

成员和钱包的 `Group` 会合并当前已排队的修改，再等待同一底层事务返回；没有为了凑批而主动睡眠。请求增多后，等待前批及本批完成会反映在上述两个阶段。提交返回区间包含该批剩余工作、存储提交和唤醒，不全部等于一次 fsync。

钱包细分：写入队列 **10.44 → 16.64 ms**，回调完成到提交返回 **18.99 → 29.22 ms**，验证 **0.12 → 0.17 ms**。本轮新增时间主要不是密码学验证。

## 持久化与后续高度等待的证据

四委员按业务高度计数：单笔为 1 个业务块/4 次提交；负载为 20 个业务块/80 次提交。单次整块应用提交平均 **18.81 → 30.99 ms**；数据页写入 **0.028 → 0.402 ms**，数据与元数据 Sync 合计 **18.69 → 30.00 ms**。本轮 bbolt 的这些提交主要时间在 Sync，不能沿用以前另一轮“小写调用占绝大多数”的结论。

同口径每节点每业务块：BlockStore.WriteSync **5.47 → 29.45 ms**，投票前 WAL Flush 累计 **13.04 → 48.27 ms**，签名状态文件保存累计 **8.42 → 115.03 ms**。签名状态保存与 vote_sign 是嵌套区间，不能相加。测量窗口内单次原子文件替换的 rename 环节均值 **0.71 → 30.09 ms**，单次签名状态保存 **2.89 → 49.58 ms**；这些是含运行时/系统等待的墙钟时间，不是密码学计算耗时，也不足以判定硬件原因。

这些证据把后续共识排查目标缩小到**签名状态文件的原子保存与 WAL 同步路径**；不能只凭本轮数据删除必要持久化。

提交后钱包的分解：

| 区间 | 单笔 ms | 100 TPS 均值 ms |
|---|---:|---:|
| 尚在处理前面高度 | 0.00 | 5.60 |
| 等待/获取后续高度提交头 | 125.73 | 436.57 |
| 获取区块与结果 | 0.32 | 9.23 |
| 区块验证 | 0.09 | 0.22 |
| 本地修改准备 | 0.14 | 9.15 |
| 请求本地更新→观察到上链 | 26.03 | 47.76 |

跟块器实际请求 `commit?height=H+1` 来验证 H 的结果承诺。多出的 356.22 ms 中，等待/获取提交头增加约 310.84 ms（87.3%）。这包含后续高度形成、节点可提供查询及轮询/请求耗时，不能全部叫网络传输。单笔快照缺少 H=4 的钱包 `follow_committed` 回调，所以最后一行使用实测“观察到上链”终点，没有估算缺失回调时间。

## 发送速度、排空与正确性

- 单笔：快速到账 51.85 ms，委员会应用提交返回 200.91 ms，钱包观察上链 353.20 ms，观察全部成员完成 354.48 ms。
- 100 TPS：实际首笔至末笔发送 **9.990028 s**；全轮 **10.901696 s**；末笔发送后 **0.911642 s** 完成。快速到账均值 107.57 ms、P50 103.89 ms、P95 148.96 ms。
- 实际发送滞后 P95 **0.653 ms**，发送和总未完成上限均未触发，排除了压测器限流导致本轮大段等待。
- 压测器未完成采样峰值 **197 笔**。按独立时间线每 100 ms 重建峰值为 198 笔，采样相位不同；其中委员会已接收未提交峰值 134、已提交待钱包观察峰值 127，峰值不同时发生，不能相加。
- 按发送时间每秒分组，快速到账均值约 96–121 ms、提交均值约 729–1120 ms，无持续单调上升。10 秒短测不足以证明长期稳态或吞吐极限。
- 正式 **1,001 笔**全部成功，另两笔预热，合计审计 **1,003 笔**。每组四委员状态一致、14 节点 Pending=0，Gap=0，CAL/FUEL 与费用核对通过。负载组有 17 次可重试进度查询错误，交易最终完成，不将查询错误写成交易失败。
- 本轮只运行实验与分析，没有修改支付、存储或共识代码。完成后恢复原活动网络及数据库。
