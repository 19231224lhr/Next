# E4：故障可用性与冲突安全实验方案

状态：已完成实验，限定范围内的既定检查通过。代码基线为 re 分支 fb95f5e；采用 wire 4，延续用户自付 FUEL。目标是检验故障时的实际可用范围，不测最高 TPS、不增加恢复协议。见[方案评审](e4-fault-conflict-review-2026-09-23.json)、[实施复核](e4-implementation-review-2026-09-24.json)与[完整实验报告](README.md)。下文保留原方案，最终测量与边界以报告为准。

## 1. 要回答的问题

1. 四成员、三票签发时，一个慢成员或暂停成员是否阻挡其他三人服务？
2. 网关在不同交付阶段中断后，已有付款由谁继续提交，何时完成？
3. 并发冲突、篡改和重复请求是否产生重复支付、重复收费或错误返还权限？

已有 E1—E3 结果与历史故障测试只作为基础，不冒充本轮新实测。

## 2. 代码依据

- CollectDirect 向四成员并行请求，收到三份同一 Fact 的合法批准即返回，不等待第四份。
- 网关响应 Flush 后，将完整付款交给 Early relay，同时后台保存 outbox；Flush 不代表钱包已经验证、接收。
- 公共 Submit 与各成员 INSTALL 独立推进，不能用固定 sleep 推断它们的先后。
- 成员第一次 INSTALL 保存固定备用投递期限，当前为 2 秒加成员编号乘 250 ms。重复 INSTALL 不刷新期限；实际完成时间还包含调度、网络及公共结算。
- 钱包接收接口保存输出与证书；不能据此假定收款钱包有完整父交易或已经实现自动补投。
- 网关 SIGTERM 会优雅收尾，不能当成突然失效。内存实验用 SIGSTOP/SIGCONT，保留原状态；不测试清空内存后以同身份重新签发。

关键位置：cmd/gateway/direct.go、internal/gateway/direct.go、internal/gateway/direct_relay.go、internal/member/direct.go、internal/wallet/direct.go。已有 wire4 单测 TestDirectDurableApprovalAndBackgroundInstall 可复用，旧协议测试需逐项确认。

## 3. 最小实验矩阵

| 组 | 场景 | 核对重点 |
|---|---|---|
| A0 | 无故障对照 | 相同代理、负载、配置下的正常表现 |
| A1 | 一个成员批准响应延迟 250 ms | 三名正常成员是否仍能快速成证；核实慢成员确实被延迟 |
| A2 | 一个成员进程暂停 30 秒再恢复 | 故障期间 READY 与公共结算；恢复后的跟块追赶 |
| B1 | 钱包已接收，尚无成员 INSTALL、也未公共提交，网关暂停 | 区分已有可花凭证与自主后台完成能力；缺补投路径如实记录 |
| B2 | 钱包已接收，至少一成员 INSTALL 成功，尚未公共提交，网关暂停 | 成员有限延迟备用能否独立完成提交 |
| B3a | 任何批准请求转发前，网关暂停 | 尚无 QC；钱包自己的请求锁仍可能存在 |
| B3b | 仅部分批准、尚无完整凭证交付，网关暂停 | 不提前宣告到账、不擅自清锁；恢复后同请求推进情况 |
| C | 冲突、篡改、重复请求 | 至多一个有效冲突凭证、至多一次成功花费和收费；权限不重复释放 |
| C 的边界小例 | 两成员同时暂停 | 无三票时不能交付合法新凭证，作为预期边界 |

首轮不混入委员会故障、跨地域网络、最大吞吐或断电恢复。跨组织消费权绕过只做少量定向验证，不扩成 E5。

## 4. A 组的负载与观测

单 Mac 多进程：一个组织、四成员、一个网关、四委员。使用独立最终 CAL UTXO 和充足用户 FUEL，固定充分 CAL、Execution、Bytes；关闭自动补资与串行取证。存储及共识参数在预跑后冻结，三组一致。

候选负载 200 TPS；每轮 30 秒正常、30 秒注入、60 秒恢复，输入持续 120 秒，共计划 24,000 笔，再允许最多 60 秒收尾。先几十笔冒烟及短预跑，确认基线无明显积压、没有资金限制，再冻结参数。A0/A1/A2 各重复三次，种子 23/37/59，轮换顺序，每轮重新创世。

慢节点只延迟批准响应路径，不同时延迟 INSTALL、跟块；记录真实成员处理完成与代理返回两个时刻，代理等待支持取消。取消响应不意味着撤销成员已经完成的批准或占用。暂停节点用进程状态和探测确认实际停止；释放后确认同一进程恢复。注入事件不只记录发出信号的时刻。

压测发送资格以快速接收释放，不等全部四成员。公共完成与成员进度分别观察；暂停成员的未跟块债务按交易清单和块游标保留，恢复后审计，不为每笔暂停债务创建高频轮询。若复用驱动仍将全部成员完成绑定总在途上限，须先拆分观察或改用专用有限实验驱动，不能让 2048 上限把故障期输入压低后宣称正常承接。

记录计划发送、实际发送、READY、公共成功观察、各成员进度；每秒采样，按 10 秒窗口汇总。保留发送滞后、背压、未启动、超时与最老未完成年龄。延迟分位数与未完成数量一起给出，不能只看成功样本。公共观察时刻与精确 Commit 区分。单请求网络错误不取消整轮；重试政策各组一致，响应丢失先记结果未知，再按事实查明，不能直接视作账务失败。

## 5. B 组用事实门控，而非猜时间

每场景少量独立交易、三次重复。故障前先验证要求的阶段实际成立，暂停网关后观察 10 秒，再恢复同一进程并最多等待 30 秒收尾；超时仍保留记录。

使用实验端 HTTP 门控覆盖网关公共提交、四成员 INSTALL，以及必要的批准/响应边界：
- 公共阻断必须发生在请求到达委员会之前；HTTP 未收到成功不等于委员会未接收。记录转发清单、在飞请求和公共查询证据。
- B1 要有钱包 ReceiveDirect 成功记录；所有 INSTALL 都尚未成功。网关暂停后不得由代理积存请求、测试驱动或另一入口代替它完成发布。
- B2 必须有目标成员 INSTALL 成功及本地 outbox 证据；网关暂停期间只允许该成员原有补投路径推进。控制起点应早于其首次备用期限，期限以实际 INSTALL 记录为准。
- B3a 在任何批准请求转发前暂停；不要求钱包请求记录或本地输入锁为空。B3b 只允许 1—2 名成员实际批准，其余请求尚未转发；保留真实部分占用。恢复后重试原字节，不另造冲突交易。
- 若 B1 没有原生自动补投能力，结果是“已快速可用，但自主结算受限”；恢复网关后完成另记，不能改成故障期间自动成功。

门控只控制可达性与时序，不伪造批准、证书、账本事实。每次有界停止后核对输入锁和预算，不把“查不到证书”当成释放依据。

## 6. C 组：小规模定向正确性测试

每类先选 20 个独立输入，保留可观察到的成员批准、完整证书及公开执行结果；两个冲突候选各用独立、充足的用户费用输入，防止把费用冲突误认成本金防双花。冲突请求由测试付款方分别合法签名并实际发到网关、成员，不能用钱包第二次 SaveDirectRequest 的拒绝代替成员检查证据；不关闭服务端验签或输入检查。

- 同本金输入两笔不同付款并发取证；另测已有合法 QC 后再请求冲突付款。
- 不同 CAL 输入共用同一最终 FUEL 输入，单独核对费用防双花，不与本金冲突混测。
- 合法证书绑定的金额、收款人被修改；验证钱包和成员实际拒绝，保留准确拒绝层次。
- 同一原始请求、同一公共交易重复发送：HTTP 尝试可多次，业务成功及费用效果只发生一次，核销不重复。
- 对不被消费权配置允许的组织入口请求签发；先确认当前 wire4 规则，再验证不能绕过。合法跨组织收款不应被误归为攻击。
- 两成员暂停时发送少量全新请求：不能得到三票；解除故障后原请求再试。

并发冲突得到零份或一份完整 QC 均可能；零份时的部分批准、锁和权限残留单列，不强行清空。安全判据是绝不能同时存在两份合法冲突 QC，而不是每次攻击必选出赢家。普通非法请求拒绝不得混进合法支付吞吐。

## 7. 实施范围与产物

复用 payctl 的真实签名、钱包接收、公共块验证及审计逻辑；实验目录中增加一个驱动和最小门控代理。只有现有接口确实缺少可观测阶段时，才补实验专用观测，不改协议、共识、预算释放或重试规则。

实施顺序：定向控制及门控自检 → A 组预跑并冻结配置 → 正式九轮 → 全量账务与状态核对 → 报告。
输出：故障时间线图、三阶段 READY/公共完成分布、网关交付边界表、冲突正确性表；保存 SHA、配置、种子、原始交易、故障事件、逐事实结果、请求重试和审计清单。

成功标准分开：A/B2 检验故障期间服务进展与后续收尾；B1/B3 及两成员暂停如实界定可用边界；C 检验冲突与幂等。B1 在有界观测窗内没有接管不等于证书失效或永远无法结算。报告不能将暂停期间未跟块副本写成一致，也不能将暂停恢复写成崩溃恢复。

论文可支持所测单成员延迟/暂停、受控网关交付中断与定向冲突条件下的可用性和账务正确性。它不替代一般拜占庭安全证明，也不证明任意网络分区、任意长期故障或丢失状态后恢复安全。
