# 数据库交互审查与优化顺序

日期：2026-09-20；审查代码：`8d605d3`。本轮没有修改生产代码、数据库格式或同步配置。完成了调用路径审查、历史 trace 重新统计、Mac 上保留数据库的只读检查，以及六轮隔离 bbolt 小实验。

**有明确优化空间：关闭未使用的搜索索引、缩短写事务中的静态计算、避免为了更新少量核销状态而重写整份批准记录。** 加更多写入 goroutine 不能让同一 bbolt 文件同时提交多个写事务；已有独立数据库和读事务本来就可以并行。

## 1. 当前实际数据库交互

范围覆盖当前 wire4 的组织、钱包、委员会、跟块及历史修复路径，并追到所固定 CometBFT 分支的主要持久化点。代码图用于发现符号，接口间接调用及 `comet_v3` 条件编译、排除索引的依赖源码另以源码核对。旧 wire2 路径不作为这轮性能结论的依据；这不是全部故障组合的形式化验证。

| 路径 | 实际数据库工作 | 当前并发／持久化边界 | 判断 |
|---|---|---|---|
| 成员 `ApproveDirect` | 消费占用、Worker 额度、批准与意图记录 | 静态验证在事务外；原子更新、持久完成后签票 | 基本顺序正确，已用 Group 合批 |
| 成员 `InstallDirect` | 消费终态、完整付款、备用 outbox | 验签／编码在事务外；首次备用期限同事务保存 | 已后台执行；正文有重复存储 |
| 网关收集及保存 | 完整材料、outbox | early inbox 已让提交／INSTALL／保存并行，保存使用 Group | 不重复实施已完成优化 |
| 网关普通投递 | 查 outbox／Observed，再 HTTP 提交 | `runDirect` 的 2 秒重试节流已在有界内存中 | 正常路径不再逐次写重试时间 |
| 成员备用投递 | 查 outbox，补投后更新重试时间 | 尚走 `submitDirect` 持久更新；首次固定备用期限不能反复延后 | 可后续减负，正常 100 笔实验没有触发 |
| 钱包发送／收款 | 意图与输入占用、收到的输出凭证 | 事务外验证，Group 提交后认可本地结果 | 不将尚未持久的数据声称为已保存 |
| 成员／网关／钱包跟块 | 解码、验签、业务更新、跟块游标 | 完整 `apply` 在同一个写事务内 | **静态计算不必占用写者，是优先改点** |
| 委员会 `FinalizeBlock` | 只读账本，在内存 Overlay 顺序计算整块 | 保留块内消费／资金依赖；尚未落盘 | 不是逐笔写数据库 |

| Comet 搜索索引 | 交易哈希／高度和块事件索引 | 默认 kv，独立服务内同步写入 | 当前业务未见查询依赖，可独立关闭对照 |

## 2. 发现一：跟块静态计算占用写事务

现有调用：

```text
blockfollow.Commit
  → Group.Update → Bolt.Update
    → ApplyBlock / ObserveBlock
      → Transactions() 复制块内交易
      → DecodeDirectSubmission
      → DecodeFastTx → VerifyAuth（含所有者及接收地址认证）
      → 本地核销、消费／输出状态和游标更新
    → 同步提交
```

Group 只合并落盘，不会并行执行回调。跟块在写事务内处理整块期间，新批准、INSTALL 及其他额度更新只能等待。

重新统计此前 `cache-store-profile` 的 63 笔业务块：

| 跟块节点 | 写事务内 apply | apply 完成 → Group 返回 |
|---|---:|---:|
| 付款组织四成员 | 12.351～13.506 ms | 36.962～81.573 ms |
| 收款组织四成员 | 8.142～8.249 ms | 25.255～64.589 ms |
| 两个网关 | 7.302／7.806 ms | 44.448／39.271 ms |

后一列还包含同批其他回调、数据库提交和调度，不能全部叫 fsync。该轮返回的 307 份成员投票 trace 中，批准排队 P50 19.759 ms，批准回调计算 P50 0.050 ms，计算结束到持久返回 P50 29.666 ms；缺失的第四票不能按零计入。这些是请求样本，不能作为独立实验重复数。

另从保留的网关数据库提取 100 份真实公共报文，在 Mac 独立执行相同解码／认证五轮，每轮 **12.038～12.171 ms**。这支持把其中约每笔 0.12 ms 的静态工作移出写事务；实际改善仍取决于并行请求的到达时序。

最小改法：

```text
取得并认证公共块
→ 事务外准备不可变的解析、认证结果
→ 事务内读取当前游标、批准、消费状态与额度
→ 顺序应用更新并原子提交
```

先不加缓存、预取线程或通用调度框架。准备结果直接绑定同一份块材料和执行结果；变色龙哈希场景不能只凭不变的 BlockID 复用其他版本的材料。失败交易、修复命令及无效编码保持原处理语义。

这是**释放写者占用，让静态计算与其他请求的写盘重叠**，不是减少全部验签次数，也不会直接消除委员会那次 131 ms 的提交。不能把余额等动态结果在事务外算完后无条件覆盖回来。

## 3. 发现二：没有业务依赖的搜索索引

当前 `cmd/committee/main.go` 使用 Comet 默认配置，未改 `TxIndex.Indexer`，因此启用 `kv` 搜索索引。

源码核对结果：

- 生产提交用 `BroadcastTxSync`，不靠 `BroadcastTxCommit` 等待索引。
- 钱包、成员和修复流程按高度取 `Block`、`BlockResults`、`Commit`；分别使用 BlockStore 和 StateStore。
- 在当前 `cmd`、`internal`、`finality` 生产路径未找到 `Tx(hash)`、`TxSearch` 或 `BlockSearch` 查询依赖。
- Comet 索引服务分别调用块索引 `Index` 和交易索引 `AddBatch`，各有同步批写调用；索引还保存交易结果中的交易正文。
- 它是独立 goroutine，但订阅使用无缓冲通道，事件分发可能产生背压，不能认定永远不影响共识推进。

候选只改 `cc.TxIndex.Indexer = "null"`，独立测试。它删除实际索引工作，并牺牲通过搜索索引查询交易／事件的能力；当前公开支付接口不需要此能力。[Comet 官方索引说明](https://github.com/cometbft/cometbft/blob/v0.38.26/docs/app-dev/indexing-transactions.md)确认 `null` 会禁用索引服务。

必须保留按高度的执行结果及最新恢复响应；不设置 `DiscardABCIResponses`。`SaveFinalizeBlockResponse` 的 `Set + SetSync` 不是两次同步：前者保存历史结果，后者同步保存恢复所需的最新响应。本轮尚未测量关闭索引后的网络收益，也未将源码调用次数当作实际内核同步次数。

## 4. 发现三：批准证据与可变核销状态混存

只读检查已停止的 `group-cache-store-profile`：

| 节点与记录 | 数量 | 键＋值总字节 |
|---|---:|---:|
| 付款成员 Approval | 100 | **934,955** |
| 同成员 LocalProgress | 100 | 24,400 |
| 同成员已安装完整材料 | 66 | 159,522 |
| 网关完整 405 材料 | 100 | **241,700** |

Approval 不是与 405 完全同义的对象，上表不能解释成有 74% 字节可直接删除；它还含额度与其他元数据。但当前 `state.Approval` 混合完整 `Direct` 交易、旧版 `Tx/Effects` 字段及可变 `Debits.Applied`，经 JSON 存储，固定数组会展开。

`member.finishLocal` 仅更新各项 `Debits.Applied`，却再次 `state.Put` **整个 Approval**。因此正常核销重新编码、写入了没有改变的完整批准证据。bbolt 是页级写入，键值少改几个数字也可能产生多页写入。

候选：先保留原批准证据与现有 JSON 编码，将累计已核销量放入小型进度记录；核销时同事务只更新该累计值、对应额度和 LocalProgress。保持原批准事实、资源、授权版本及 Worker 的绑定，不将证据只放内存。全部累计值读取者要同步改用同一权威记录，不能留下两份独立变化的账。已有 schema 必须迁移原 Applied 或明确拒绝打开，不能默认为零。紧凑 direct 编码另作一个补丁，不同时重写全库 codec。

它可以同时减少 JSON 工作和实际更新字节，优先于普遍改造 Outbox。Outbox 中与 KeyInstall／KeyCollected 重复的正文仍是后续候选：同事务建立引用，引用必须绑定确切材料字节，在任务和证据保管结束前不能删除目标。

## 5. 文件扩容：确有机会，但不是全部根因

上一轮 63 笔块 App.Commit 131.785 ms，其中事务提交 131.638 ms，原生 `WriteTime` 117.991 ms。bbolt 1.5.0 的顺序是先 spill／freelist／grow，之后才统计数据页写入、同步、meta 页写入与同步的 WriteTime。**扩容不在这 117.991 ms 内**，不能拿扩容解释全部耗时。

本轮在 Mac 新建六个隔离数据库，默认与 `InitialMmapSize=16MiB` 各三轮交错测试。按 1／63／1／35 的批次写入，每个合成付款 7 个 1 KiB KV；所有同步保留，最终 700 个键值的摘要一致。

| 三轮中位数 | 默认 | 16 MiB 初始映射 |
|---|---:|---:|
| 初始化（Open＋建 bucket 提交） | 15.211 ms | 18.709 ms |
| 63 个合成付款的整批 Update | 13.041 ms | 7.937 ms |
| 四批 Update 合计 | 42.054 ms | 31.984 ms |
| 初始化＋四批合计 | 58.002 ms | 50.648 ms |

各行分别取中位数，不能逐行相加。默认组在 63 批由 128 KiB 文件增长到 2 MiB；映射组在建 bucket 的初始化提交后文件已为 16 MiB。**Mac 的 Open 设置初始映射本身不等于物理空间已预分配**，本次是在首次写事务时增长了文件。

这证明可以把小文件反复增长的一部分工作提前，不能视为真实支付网络的性能提升。后续应分别在新创世与已增长数据库上对照，记录 grow／remap、数据同步、meta 同步及真实文件大小。超过初始映射窗口仍会增长，不承诺长期消除。

还核对了 Mac 所用 Go 1.27.1 的 `internal/poll/fd_fsync_darwin.go`：`os.File.Sync` 在该平台尝试 `F_FULLFSYNC`，bbolt 的 Unix 同步实现调用它。WAL 使用 File.Sync，FilePV 的原子文件写另有 `O_SYNC`。不能把这些不同同步路径一概当作一个相同的 fsync，更不应为跑分替换成较弱同步。

## 6. 后续两项：跟块合批、缩短修复的长读事务

**跟块有积压时机会合批。**目前每个高度拉取、认证、提交后才取下一个。保留记录中，没有业务的第二网关仅保存 69 字节游标，却在六个高度进行了六次物理提交；普通网关已有 Group，100 笔工作期间只提交了 15 次，四个委员则各 6 次，不能再按“逐笔 100 次落盘”制定方案。

后续可少量预取认证块，把已经准备好的连续高度在同一事务内顺序应用、共同推进游标；限制块数、字节数和占用写者时间。没有积压立即处理，不为了凑批延迟当前块。大批跟块也可能反过来拖慢新付款，故排在写事务瘦身与记录减负之后。

**修复长读事务。**当前 `repair_runtime.go` 在应用库 `View` 回调里执行 `Materialize`，后者会调用另一 BlockStore 的 `ReviseBlock/WriteSync`。长读事务可延长应用库重映射时的等待。正常这轮没有修复，所以不是其 131 ms 提交的已证实原因，也没有证据证明现已死锁。

最小方向：短 View 复制必要材料及预期版本 → 关闭 View → 完成 BlockStore 改写 → 再保存本地游标。需要复核最新修订版本，且“BlockStore 已改、游标未保存”时重复执行必须幂等；不能先推进游标。

## 7. 哪些并行已经有，哪些不应直接并行

- `Bolt.View` 可以并发读取；`Group.Update` 的读锁允许多个调用者入队，不是把请求入口逐笔互斥。
- 静态解码／认证、编码及读取网络材料可以与数据库提交重叠。写事务内的当前状态裁决仍须遵守输入、共享额度和块内依赖。
- Group 已把排队更新合为一次提交；委员会已每块一次提交。把这些改成多个同时写同一文件的 goroutine，只会继续排队。
- `Bolt.writeMu` 还保证“不确定存储错误后阻止后续写入”的状态转换，不能因为 bbolt 内部也有写锁就直接删掉它。
- 委员会的资金状态、块元数据和应用提交回应不能随意拆开；成员输入占用与 CAL/FUEL 额度也不能各自异步成功。
- 不把每 Worker 拆成独立数据库作为本轮方案：它会新增跨库输入／额度原子性问题，并增加同步次数。
- 不把钱包保存、成员批准等关键写入改成未落盘先报成功，也不通过关闭 sync 或延迟多个已确认区块的落盘来换取数字。

## 8. 实施建议与验收

按独立补丁验证：

1. **关闭未使用的 Comet 搜索索引。**全项目依赖核对后，这项改动最小且直接删除工作。核对按高度接口、后台结算、真实修复及重启；统计实际索引工作消失后，应用 Commit 和总闭环是否改善。
2. **跟块静态预处理移出写事务。**观察写者占用、批准排队和快速到账 P95，保留全部验证与核销语义。
3. **拆开 Approval 不变证据与小型核销状态。**比较逻辑写入字节、页写入量、回调计算和前台排队；完整核对额度、防重、重启和存储版本。
4. **初始映射尺寸独立对照。**只改这一项，分别测试冷库和已增长库，不改变同步强度。
5. **根据持续负载决定有限跟块预取／合批。**用写者占用上限约束批量，不能把排队搬到另一个缓冲区。修复长读事务作为单独的边界改进。

每个补丁都保留：唯一输入消费、原批准成员累计核销、CAL/FUEL 余额与费用一致、四委员状态一致、outbox 排空；覆盖并发批准与跟块、重复／乱序块、提交后响应丢失、合法 CH 修订及同库重启。

性能统一分开记录“排队／回调计算／物理提交”，以及逻辑更新数、真正提交数、更新字节、页分配、快速到账 P50/P95、实际 Commit、成员应用时间、首末发送窗口。前台和后台同时改善才算全面收益；以持续负载与队列斜率判断容量，不能用本轮合成小实验推导 TPS。

## 9. 与侧边栏 GPT 的两轮复核

已在[评审两版支付系统](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)提交实际调用链、代码片段、历史统计及新增只读／小实验结果，进行了两轮讨论。

第一轮优先建议跟块静态计算移出事务，并核对了上游 bbolt 的 WriteTime 边界与 Comet 索引依赖。第二轮在全项目索引依赖检查和 Approval 写放大证据补齐后，建议将关闭索引前移，Approval 小状态拆分优先于 Outbox 去重，紧凑编码单独实施。我接受这一排序。

双方一致区分：索引关闭是删除工作；静态预处理是改变计算位置；Approval 拆分是减少重复编码与写入；初始映射是提前部分增长成本；跟块合批是减少提交次数。各项的实际网络收益必须分别验证。

GPT 无法读取本次仓库提交，项目判断依据我提交的源码与证据，并自行核对了上游依赖；它没有独立运行系统。本报告结论以本地源码和可复查数据为准，讨论原文见 `review-messages.json`。
