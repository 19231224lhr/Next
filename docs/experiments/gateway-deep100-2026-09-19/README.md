# 网关保存与投递排队：100 笔深入诊断

2026-09-19。基线 `538acc2`，增加存储和中继调度埋点，未修改付款、验签、同步持久化或调度行为。

## 结论

原来的“保存 218 ms、保存后排队 1,523 ms”主要是两处串行等待相互放大：

1. **保存慢主要在等写锁。** 网关使用单写者 Bolt，每笔新证书各自提交一次同步事务，没有使用成员已有的 Group 合并机制。100 笔复测中新付款保存中位数为 251.15 ms，其中等待网关写锁中位数 223.18 ms，实际数据库提交约 14.95 ms。
2. **投递排队主要在等前面的处理组结束。** 每次扫描最多 16 条，每组最多 4 条；一组全部结束才推进。任务先完成 INSTALL、提交委员会，再同步保存重试时间，最后才算完成。这个重试状态保存又争用新交易保存所用的同一把写锁。

因此，不是保存一份小记录本身必须花两百毫秒，也不是扫描数据库需要一秒半。当前实现让大量小事务依次等待同步提交，又把投递队列推进绑在这些写入返回上。

## 实验设置与完整性

- Mac Studio，本机两组织共八成员、两个网关、四委员会；独立创世目录 `.run/trace100-deep-v4`，端口 27000 起。
- 已最终 UTXO 跨组织付款，100 笔、64 并发，无预热付款；与上一轮相同闭环负载。
- 保持 flush/gossip 各 10 ms，启用诊断。新增事件仅记录在进程内存；网关存储事件包含等待写锁、事务回调、修改应用、提交返回以及 bbolt 原生统计。其他角色不启用这层存储埋点。
- 100 笔全部成功，整轮 5.677 s。四个委员会各 100 笔付款全部结束、状态哈希相同、缺口为 0；全部网关和成员投递队列排空。
- gateway0 共采集 2,139 条事件，未触及 4,096 上限；261 次存储调用均有业务归属，100 笔付款都有完整保存和排队分解。
- 本轮用于解释原因，不是性能优化 A/B。不同轮次的 218/251 ms、1,523/1,408 ms 有波动，不能将差异归因为优化。

## 第一段：后台保存到底在干什么

| 分段 | 样本数 | 中位数 ms | P95 ms |
|---|---:|---:|---:|
| 保存整体：含证书检查、编码、存储调用 | 100 | 251.146 | 736.409 |
| 进入存储前的证书检查与编码等 | 100 | 0.197 | 12.707 |
| **等待网关写锁** | 100 | **223.181** | **720.229** |
| 持锁后构造业务更新 | 100 | 0.0115 | 0.026 |
| 应用键值修改 | 100 | 0.003 | 0.006 |
| 数据库提交至返回 | 100 | 14.951 | 29.671 |
| 其中 bbolt 写入及同步统计 | 100 | 14.931 | 29.662 |

各中位数不可直接相加。按 100 笔累计存储调用时间计算，写锁等待占 **95.00%**。其余主要是实际持久提交，业务字段构造和树节点整理耗时很小。

bbolt 的 `WriteTime` 从写脏页前计时，覆盖写脏页、同步、写元数据和再次同步；不能把它称为单次 fsync 或纯磁盘硬件延迟。本机使用的 bbolt Unix 同步实现调用 `db.file.Sync()`。本实验未关闭任何同步。

网关本轮共做了：

| 操作 | Update 调用数 | 实际有修改的事务数 | 累计 bbolt 写入及同步时间 |
|---|---:|---:|---:|
| 保存新付款记录 | 100 | 100 | 1.603 s |
| 保存投递重试状态 | 145 | 100 | 2.000 s |
| 跟块清理与游标更新 | 16 | 16 | 0.489 s |
| 合计 | 261 | 216 | **4.092 s** |

剩余 45 次重试状态检查未改变值，存储层跳过提交，**不能说它们又做了 45 次落盘**；但这些调用仍进入写锁通道。216 次真实提交共占约 4.09 秒写入及同步时间，明显限制了这一轮网关单写通道的推进速度。

## 第二段：保存后为什么还排队一秒多

| 保存返回 → 首次投递处理期间的分解 | 中位数 ms |
|---|---:|
| 总等待 | **1,408.173** |
| 等待区间与投递组运行区间重叠部分 | **1,391.481** |
| 等待区间与数据库扫描重叠部分 | 0.052 |
| 剩余：定时唤醒、空页回绕及调度间隙等 | 0.009 |

按所有付款累计排队时间计算，**99.09% 发生在投递循环仍被前面的处理组占用期间**。这是一种时间区间归属，不是 CPU 占用率，也不能再与其中的数据库等待相加。

单次扫描的中位耗时只有 **0.0145 ms**。100 ms 外层定时器并非本轮主要等待来源：当处理组已经超过一个周期，下一次 tick 通常已到达，循环主要仍卡在组内操作。

本轮 38 个处理组，中位处理时间 **118.56 ms**。其中有新提交的 27 个组，从本组最后一次提交调用返回到整组结束，仍额外等待中位数 **72.74 ms**，最慢 **803.75 ms**。投递成功并没有及时释放这组处理能力。

一个可逐事件核对的具体例子：

```text
相对实验开始约   73.06 ms：首个处理组开始（当时只扫描到一笔）
约              151 ms：INSTALL 结束
约              152 ms：向委员会提交调用已经返回
此后            795.742 ms：等待保存重试状态所需的写锁
再花              7.990 ms：实际数据库提交
约              956.22 ms：整个组终于结束，可以推进后续任务
```

在这笔任务等待写锁的 795.742 ms 内，埋点显示 **61 次新付款保存**占用写锁累计 **795.110 ms**，几乎覆盖整个等待区间。因此这次停顿已定位到明确的锁竞争，不能再归因于委员会响应慢或网络发送慢。

另外，扫描使用交易事实键排序，不是付款到达顺序。游标已越过的位置若新插入了任务，要等下一轮回绕。这解释了为什么等待很大，却不严格按付款发送次序增长；它不是本轮最大的时间消耗来源。

## 最小优化方向

优先复用现有 `store.Group`，把网关同一时刻排队的更新合并进一次真实提交，保持所有调用成功返回前完成持久化。成员和钱包已有同类实现，不需要换数据库或另造存储框架。

随后独立检查“每组等齐”和投递后的状态更新：减少一个任务等存储时拖住整组的情况，同时保留不重叠执行同一任务、重试和关机等待语义。先测批量提交的效果，再决定是否需要改调度；当前证据不支持只增大并发或只缩短扫描间隔。

本次**仅完成诊断，没有实施上述优化**。已通过 `go test -race ./internal/store ./internal/gateway ./cmd/gateway`、全项目 `go test -tags=comet_v3 ./...` 和这轮真实闭环、停机审计。
