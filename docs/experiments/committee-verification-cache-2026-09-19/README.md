# 委员会静态验证复用：实现与实验结果

日期：2026-09-19。代码基线：`3cacd61`；实验前的文档提交：`db86d0f`。

**结论：重复解析与静态验签明显减少，100 笔闭环平均耗时下降约 6.8%，但前台到账延迟没有同步改善。** 接纳后等待与共识推进仍占较多时间；新的细分测量表明，应用数据库提交和 Comet 的同步持久化值得继续调查。本轮没有修改这些持久化边界。

## 1. 实际改动

委员会在同一个 Engine 内复用完整公共报文的静态验证结果。缓存键是 `Digest("VERIFIED_DIRECT_SUBMISSION_BYTES", raw)`，覆盖原始报文全部字节，不能用 TxID 或变色龙交易哈希替代：OwnerAuth 和合法历史修复可能改变报文而保持交易身份。

- 仅缓存验证成功的不可变对象；未命中仍执行完整验证。组织认证、所有者签名及输入担保认证均保留。
- 每次执行仍按当前账本检查消费状态、余额、费用授权、责任和赔付终态；缓存不代表交易已执行或资金仍可用。
- 复用原有 FIFO 容器，每份缓存最多 2048 项、8 MiB 编码字节。旧证书与直接付款各有一份；这不是 Go 堆内存精确上限。超大项正常验证但不缓存，不驱逐已有项。
- 短锁只用于查找、插入和统计；冷 miss 允许并发重复验证，不引入新的调度框架。Engine 的配置快照固定，重建 Engine 即重新验证。
- 执行末尾通过已验证对象的只读 TxID getter 记录交易位置，省去再次解码。ClockTick、RepairInput 不进入此缓存。

`UTXO_EXPERIMENT_DISABLE_DIRECT_CACHE=1` 只用于实验绕过直接付款缓存，在创建 Engine 时读取；它不关闭任何验证，也不改变账本规则。默认启用缓存。

第二步只扩展已有诊断开关：开启 trace 时，委员会也记录 bbolt 的写锁、修改和提交阶段；关闭 trace 时无此统计工作。没有关闭 sync、WAL、FilePV，也没有调整共识超时。

## 2. 实验口径

Mac Studio M4 Max，64 GB，Go 1.27.1，14 个本机进程：4 委员、2 个组织各 4 成员及 1 网关。每轮新创世，100 笔独立已最终 UTXO 跨组织付款，64 个闭环并发任务。发送刷新与 gossip 均为 10 ms，`timeout_commit=100ms`。所有验签和同步持久化保留。

共完成 **13 轮、1,300 笔，全部成功**。每轮停止节点后核对：14 个 outbox 排空、四委员应用状态一致、100 个付款完成并关闭、无未决缺口；CAL 总计 2,000,000,025,600，FUEL 总计 2,000,000,000,000，报酬 8,400，销毁 1,000，均与预期一致。

主要性能对照使用同一套二进制，仅切换缓存开关。初始 A1→B1→A2→B2，补测 A3→B3→B4→A4，每组四轮，均关闭埋点。另有一轮原始二进制、两轮 trace A/B、一轮 Comet profile，以及一轮新增存储细分的 profile。最后一轮使用单独二进制清单，不混入主性能对照。

时间定义：

- **快速到账**：付款钱包开始 HTTP 发送，到收款钱包验证并持久保存可续花凭证。
- **整批闭环**：压测运行开始到全部任务完成钱包跟块和成员应用结果的观察；不是单笔上链延迟。
- **实际 Commit**：委员会执行后提交应用状态完成；钱包、成员观察时间另外统计。
- 64 个任务完成闭环后才接着发送余下付款。因此 `100 / 整批耗时` 不是持续 TPS 上限，也不能代替开放负载测量。

## 3. 无埋点主对照

| 指标 | A：禁用缓存 | B：启用缓存 |
|---|---:|---:|
| 每组轮数／交易数 | 4／400 | 4／400 |
| 整批闭环四轮平均 | 2.4056 s | 2.2411 s |
| 四轮整批耗时 | 2.4981 / 2.3788 / 2.3678 / 2.3778 s | 2.3115 / 2.3145 / 2.2340 / 2.1044 s |
| 快速到账 P50，合并组内交易 | 163.893 ms | 203.121 ms |
| 快速到账 P95，合并组内交易 | 252.557 ms | 274.281 ms |

整批闭环平均缩短 **6.84%**。前台 P50、P95 反而增加，不能宣称所有延迟都改善。合并的 400 笔只是描述分布，不是 400 次独立实验；目前没有建立统计显著性结论。14 个进程共享存储、后台工作时序改变可能影响前台，但原因尚未定位。

原始二进制参考轮为 2.6265 s，仅一轮；不能用它与四轮新版本均值比较后宣称稳定的更大收益。缓存关闭组仍包含新 getter 和报文摘要计算，主对照隔离的是缓存复用收益。

## 5. 新测量：剩余时间在哪里

新增存储诊断轮同样 100/100 成功。其 63 笔块应用 Commit 为 **131.785 ms**：准备修改 0.015 ms，进入数据库回调前 0.006 ms，数据库应用及提交 131.758 ms，收尾 0.006 ms。

bbolt 内部进一步记录：写锁等待 0.001 ms，开启事务 0.003 ms，构造修改 0.001 ms，键值 Put/Delete 应用 **0.115 ms**，事务提交 **131.638 ms**；原生 `WriteTime` 为 **117.991 ms**，`SpillTime` 0.170 ms。其他 1 / 1 / 35 笔业务块的提交约为 16.090 / 24.023 / 28.739 ms。

因此这一块主要卡在实际数据库写入和同步路径，不是应用写锁或业务键值修改。`WriteTime` 包含写入与同步，不能称为一次 fsync；`write_count=46` 也不等于 46 次 fsync。剩余时间尚未完全分解。

另一轮 Comet profile 中，委员 0 的提案 WAL flush 中位 10.902 ms（2 次），FilePV 保存 19.308 ms（10 次），内部消息 WAL WriteSync 16.696 ms（13 次），投票 WAL flush 19.661 ms（8 次），BlockStore 保存 23.402 ms（4 次），EndHeight WAL 12.455 ms（4 次）。签名与 FilePV 保存等统计有嵌套，不能直接求和解释整个共识区间。

下一步优先沿实际持久化调用路径调查：哪些写入属于同一安全边界、哪些确实重复，以及前后台共享磁盘的竞争。现有证据没有证明可以删除同步或合并双签保护边界，故本轮不修改它们。接纳后等待还包括区块时序与前块处理，也没有被这个缓存彻底消除。

## 6. 正确性与复现

新增测试覆盖同 ID 下 OwnerAuth、Funding/opening、认证材料变化；合法不同三票集合；并发同键插入；条目与字节预算；超大项；外部原始缓冲变化；暖缓存下双花和费用授权改变；重复提交幂等；冷热、驱逐及重建 Engine 的完整状态一致。

另在真实历史修复测试中预热原付款缓存，执行合法赔付与区块材料修复，再把原报文、修复后报文和重复修复命令交给暖缓存及禁用缓存 Engine 对照：两者裁决和状态变化一致。既有迟到父交易、担保账户扣款及从原历史重放测试继续通过。

侧边栏 GPT 对实现摘要和测试方案的评审没有提出正确性阻碍，并建议补充上述合法修复交错测试；已补齐。它没有独立运行整个仓库，结论以本地测试和留存日志为准。
