# 委员会与 TPS 优化实验

工作开始：2026-09-21 北京时间 02:34；04:09 用户续期，后续验收另记。Mac Studio M4 Max，16 核、64 GB；单机多进程、回环网络。原始负载和失败实验均保留；以下区分可复核数据与尚未证明的长期容量。

## 测量范围

两种工作负载分开：

- **委员会容量**：四个真实委员会进程。独立的已最终 UTXO 输入，真实付款授权与三成员组织认证，经过真实 mempool、CometBFT、执行及同步持久化。预先准备公开交易字节不计时，不预热委员验证缓存。总 HTTP 在途上限始终 128，不按入口倍增。
- **完整系统**：四委员、两组织各四成员和一网关，以及实际钱包。快速到账限位 256，总未完成限位 2048；快速到账、成功上链、钱包跟块与成员核销分别统计。

`HTTP 202` 只是接纳响应。最终成功数来自成功执行结果、持久化交易所在高度以及停机后的四副本状态和资金审计。HTTP 成功却没有最终结果的交易单独列出，不计入 TPS。提交时刻通过持久应用高度轮询观察，是上界，不冒充精确的 `App.Commit` 时间。

`commit_observed_tps` 是首笔实际发送到最后一笔成功提交观察之间的唯一成功数/秒，包含尾部排空。另存实际发送率、拒收数、P50/P95、分秒成功率、未完成量与最老等待时间。短窗口峰值不等于长期容量，委员会 TPS 不等于钱包支付 TPS。

## 保留的实现方向

1. 静态验证缓存由 2048 项/8 MiB 编码字节增至 8192 项/32 MiB，覆盖 5000 项 mempool 和近期传播。缓存不保存余额、输入可消费性或资金裁决；32 MiB 不是堆内存总上限。
2. Direct 模式使用 Comet 原生按 ABCI 连接互斥，昂贵静态验证不再与整个 Finalize/Commit 共用客户端全局锁。App 的账务锁、mempool Commit/Flush 屏障和同步提交保留。
3. 四个有界预检槽在原请求协程中预热静态缓存，再调用原 CheckTx 客户端。没有自建 mempool、持久队列、额外工作协程或验签豁免；回调、拒绝与 Recheck 仍走原路径。
4. 组织按已封装交易摘要稳定选择一个委员会入口。正常一次提交；网络错误、429/5xx 才在总期限内有限备用，同 raw/nonce 不变。202 不删除 outbox，业务终态仍由可信公开区块决定。查询仍使用原 BaseURL，本轮未声称消除观察入口单点。
5. 未改写历史的区块补发直接读目标分片，不再每取一片都重建整块。判断与读取持有 revision 读锁；已改写历史继续发送不可变原执行字节。
6. 正常节点 flush/gossip 默认 10/10 ms；`init-lab -v4` 为本机实验写入 51,200,000 B/s 的 P2P 收发配置。其他部署的带宽仍由配置决定，未把本机结果外推到 WAN。

四委员/三票门槛、交易规则、资金与费用核销、变色龙哈希改写约束、WAL 和必要同步均保留。没有扩大块上限来掩盖积压。

## 已完成的定位与反例

| 候选 | 实测结论 |
|---|---|
| FilePV JSON 原子保存改独立同步 KV | 200 TPS 的 ABBA 没有稳定端到端收益；退出正常代码，原型归档在 `rejected-signing-store` |
| 发送队列排空即 flush | 部分低负载延迟略降，没有解决高负载容量；未选入 |
| 关闭 mempool Recheck | 改善部分旧配置，但在更好组合上无一致增量；保留 Recheck |
| 仅增大缓存 | 消除了明显循环淘汰，但仍受其他阶段限制 |
| 仅放开 P2P 带宽 | 高负载有实测节流等待，1200/s 时明显改善；100 TPS 原先没有该证据，不能倒推 |
| 仅并行预检，仍单入口 | 实际能更快发出，但下游过载、拒收，不作为成功方案 |
| 仅四入口，CheckTx 仍串行 | 2000/s 短测仍拒收，不等于四倍容量 |
| 四入口＋并行预检 | 24k/2000/s 短测全部持久成功，13.300s 含排空；更长结果见验收数据 |
| 委员会 GOMAXPROCS 16→4 | 差异不足以支持默认改变 |
| 委员会 bbolt 页 16 KiB→4 KiB | 72k/1200 的完成时间相同而延迟、峰值积压上升，撤回；旧库不自动转换页大小 |
| bbolt 相邻页合并 WriteAt | 诊断可减少约 25% 数据写调用；1200/s 合并版与回切原版均约 61.4s，P95 均约 1.74s；没有稳定收益，不引入 bbolt fork |

最初单入口诊断发现：默认 P2P 5.12 MB/s 在 1200/s 下发生真实节流；缓存容量小于在途工作集产生大量重复冷验证。针对它们的单变量实验与后续组合实验均保留，不能把最终组合收益归于单一参数。

### 更长循环负载与统计纠正

更长的循环最终 UTXO 实验另列：`generate_committee_fixture.go ... count cycle` 在离线准备期间让两个账户轮流花费前一轮输出，输入仍是普通最终 UTXO；它不是全部使用创世输入的独立负载，也不测试组织前台签发。

评审会话：[评审两版支付系统](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)。其建议经过源码、回归与实测核对，不作为独立正确性证明。


`iso-cycling1200` 以1200/s发送300,000笔，约250s发送窗口；最终成功266,508笔、执行失败12,654笔、提交报告503且未入块20,769笔、202后未入块69笔，四类合计300,000。成功提交率1041.38/s、P95 6648ms；成功延迟三段中位658 / 3660 / 4337ms。该轮不算全成功容量。

循环语料按预先计划继续发送，没有删去失败链。父交易拒收、执行失败或尚未成功时，后继普通FinalInput可能不再有效，故**不能把12,654笔执行失败全算成有效交易的共识容量不足，也不能单独将退化归因于数据库历史增长**。`analyze_cycling.py` 在事后按发送时间分类父结果是否已经观察到；观察时间是上界，“尚未观察到”不等于“实际上尚未提交”。本轮不改真实业务输入验证来迁就语料。

旧离线工具仅导出入块高度，独立且全部执行成功的负载不会显露区别。新增循环反例后，工具改为读取每笔Comet执行结果码，成功TPS只计code=0；执行拒绝退出等待队列但保留失败统计。成功事实数还必须与四副本账本审计一致，缺少结果码且存在执行失败的旧记录拒绝计算。`test_analysis.py` 验证成功、执行拒绝和202后未入块三种事实不会混算。

正常验证曾因实验生成目录被Go包发现而报错，已将其整理为下划线开头的实验目录；另一次从上游子模块测试触发依赖下载超时，改为从根模块测试实际使用的依赖版本后通过。最终发布测试日志保存在 `release-*.log`，并非忽略这些失败。


`iso-cycling1000` 使用正常发布构建，约1000/s发送300,000笔，最终成功287,852笔、执行失败4337笔、提交报告503且未入块7798笔、202后未入块13笔。成功速率957.52/s，最后成功提交观察在300.62s，成功P95为7213ms，仍不算稳定千TPS。成功延迟三段中位711 / 2794 / 2530ms。

事后核对输入就绪证据：1000/s轮有222,558笔的父交易在发送前已经观察到成功，其中仍有6694笔提交拒收、13笔202后未入块；这一组没有执行失败。全部4337笔执行失败都来自父成功尚未观察到、父提交已报错或父已执行失败的组。1200/s同样没有“父已观察成功”组的执行失败。因此既要保留有效交易的拒收问题，也要区分预生成循环链的连锁无效输入，不能混算。

这些委员会容量压测采用单次提交，没有应用层outbox重投；正常组织路径仍保留相同封装的重投，直到观察到可信公共完成。本轮未用扩大队列、删除失败链或放松FinalInput检查来提高数字。


最终正常构建复测 `full-release200`：12,000笔全部成功并排空，61.44s（约195.31笔/s包含尾部），快速到账P50/P95为138/365ms；发送滞后P95 13.30ms，未完成峰值1174，无前台/总任务限位命中。四委员状态一致、Gap=0、费用及outbox审计通过。这轮与前一轮的延迟有波动，不能挑选较小的数声称每个阶段都稳定提升。

本轮收敛：保留可验证的共识/传输优化；现有数据支持短测容量明显改善，但不支持持续千TPS或完整系统300TPS稳定无失败。下一步应针对长负载的接纳排队/拒收和组织观察开销做定位，不再用单笔或一分钟峰值代替持续能力。
