# 当前版本 100 笔全阶段复测

2026-09-20，Mac Studio M4 Max，代码 `6aa0d71`。**100 笔全部成功，完整闭环 2.132 秒；上一轮同版本、同埋点口径为 2.110 秒，相差约 22 ms（1.0%）。这不是一次新的代码优化，也没有测得稳定低于 2 秒。**

## 方法与计时口径

- 固定 100 笔独立最终 UTXO 跨组织付款，64 闭环并发，4 委员、2 组织各 4 成员和 2 网关，全部运行于同一台 Mac。
- 使用上一轮最终版二进制，四程序 SHA256 逐项一致；全新数据库、相同创世配置、10/10 ms 传播参数，全部验签、同步持久化保留。原空闲实验网测试时暂停，测试后恢复。
- 仅跑了一轮 100 笔，开启全部现有前台、投递、结算、共识及跟块埋点。没有额外改变共识参数、并发或生产代码。
- 对照是 `database-optimization-2026-09-20/dbo-map-trace`，不是关闭埋点的三轮平均 2.089 秒。
- 单笔从付款钱包发出 HTTP 请求计时；快速到账终点是收款钱包完成 TXCer 验证和持久保存。委员会提交使用 committee0 应用 Commit 完成标记；钱包跟块与成员本地处理分别另计，四委员最终一致性由离线审计核对。
- 下表 P50 为标准中位数，P95 为排序后 `floor((n-1)*0.95)`。压测原始 Summary 的 P50 使用下分位样本，因此本轮原始 fast_p50=142.934 ms，标准中位数=143.040 ms，微小差别仅来自统计定义。
- 同块交易共享区块阶段，100 笔并不代表 100 个独立区块样本。后台分支并行，各行中位数不可相加得到总时延。

高度 3 装入 63 笔，是本轮交易加权中位数对应的块。以下是该块的一次实际观测，不是 63 次独立共识实验：

“进入投票阶段→本地票推送”包含该阶段的计算、持久操作与调度；“票推送→下一阶段”也可能包含其他委员完成处理的等待，不能分别宣称是纯签名 CPU 或纯网络时间。现有事件边界不足以进一步把它们精确归因到 WAL、签名状态文件或具体数据库操作。

该块真正的 `ProcessProposal` 仅 0.200 ms，`FinalizeBlock` 总计 4.757 ms。因此本轮较长的共识阶段不能概括为“63 笔交易验证需要 283 ms”。如果继续定位，应围绕上述几十毫秒区间补测实际持久化与调度路径，不能依据这些粗边界直接删除同步步骤。

## 对比结论

1. 总体与上一轮接近：闭环只增加约 1%，不能凭单轮断言性能退步或改善。快速到账 P50 增加约 3.8 ms，P95 增加约 17.6 ms。
2. 组织公共投递保持轻量，后台保存不再是其强制前置。之前的大量重复提交和成组串行等待没有重现。
3. 当前较大的等待仍集中于提案周期、共识阶段以及跟块取得可验证区块头；其次是必要持久化及其排队。单笔委员会状态执行约 0.06 ms，不是主要耗时。
4. 第一批和后续批次的单笔提交时延并未一路增加，最后发送后的排空尾段也比上轮短。不过这仍是 100 笔闭环负载，不能证明持续开放负载下永不积压。
