# 单笔后台延迟定位：35 笔回切实验

状态：已完成定位实验与侧边栏复核；保留诊断能力和实验覆盖参数，正常默认配置与 relay 业务逻辑尚未改变。

## 结论

原先“入池后等待约 724 ms”的主要成分，已定位到提案时机与共识传播调度。实验支持 100 ms 发送刷新和 100 ms gossip 休眠的组合是显著的延迟因素。应用执行前的锁与预检只占微秒级，不能解释这段等待；共识及应用持久化仍有数十毫秒成本。

同一付款反复生成新 nonce 并提交的实现问题仍存在。缩短结算时间会减少重试次数，这是参数实验的伴随结果，并不代表已修复重复投递。新 nonce 放大了共识工作，但本实验没有单独测出其延迟贡献。

## 方法和结果

Mac Studio 单机 14 个独立进程；CometBFT v0.38.26；普通已最终 UTXO 输入、每笔 100 CAL、无父凭证依赖。每组 5 笔，逐笔发送并等最终证明；共 7 组、35 笔。每次回切重启同一账本，等待节点就绪后预热 3 秒。顺序为：

`100/100 → 10/100 → 100/100 → 10/10 → 100/10 → 100/100 → 10/10`

数值依次为 `FlushThrottleTimeout / PeerGossipSleepDuration`，单位 ms。保留 `TimeoutCommit=100ms`、FilePV、WAL、bbolt 同步与全部验签。没有修改重试、数据库或协议。

下表按配置合并样本，全部为中位数，单位 ms。提交终点是委员会 0 的应用 Commit 完成记录；最终证明为钱包成功验证 h+1 头及输出证明。起点都是付款钱包 HTTP 发送。

| 刷新 / gossip | 样本数 | 钱包持久 READY | 应用提交完成 | 最终证明验证 | 提案选中→共识决定 |
|---|---:|---:|---:|---:|---:|
| 100 / 100 | 15 | 39.891 | 824.851 | 1223.821 | 358.874 |
| 10 / 100 | 5 | 41.925 | 466.851 | 772.149 | 186.371 |
| 100 / 10 | 5 | 34.038 | 826.126 | 1136.983 | 267.420 |
| 10 / 10 | 10 | 41.994 | 342.932 | 546.165 | 78.957 |

默认三组提交中位分别 572.887、889.468、596.979 ms；两组 10/10 分别 341.943、366.054 ms。默认全部样本范围 453.577–1044.867 ms，10/10 范围 238.984–433.915 ms。独立组结果及每笔原值见 `summary.json`，避免只看合并中位数掩盖提案相位差异。

默认配置下，入池到选中中位 412.848 ms，选中到共识决定 358.874 ms；决定到 ABCI 入口 12.576 ms；ABCI 入口到业务 execute 0.017 ms；execute 到应用 Commit 完成 23.063 ms。各阶段中位数不能相加还原某一笔交易。

10/10 组决定到 ABCI 入口中位 17.932 ms，execute 到 Commit 32.487 ms：并未消除或减少必要的持久化。35 笔的四节点目标高度均为 round 0，没有超时换轮。入池到提案可能包含错过当前提案后的等待，不能全部解释成网络传输。

## 最小修复方案

1. **传播配置单独改。** 先把 10/10 用作 Mac 实验配置候选，关闭诊断后成对复测 100/100 与 10/10。不调整 `TimeoutPropose` 或关闭 fsync，也不把这组单机参数直接当成公网通用最佳值。只缩短 gossip 而维持刷新 100 ms，没有表现出稳定的整体改善。
2. **投递逻辑单独改。** 冻结传播配置，在现有 outbox 保存一次投递封装、下一次补投时间与不会被接收提示无限顺延的无进展期限；普通重试复用字节，超期才有界补投或开启新代际，业务身份不变。接收提示与等待证明分离，可信业务完成后停止补投付款，按原条件收齐核销/保管证明再出队。202/cache-hit/未验查询不能释放额度或永久停止补投。已持久 DEFERRED 沿用依赖唤醒，缺父补父。
3. **按原开发顺序验证。** 在固定配置比较投递修复前后；覆盖 202 后节点重启、缓存有而池中无、重复提示不延期、缺父到达及 relay 重启。单笔通过后再测连续转账，最后测持续唯一付款 TPS、队列增长和排空。本轮未测持续 TPS。

## 证据与复现

- `summary.json`：七组每笔分段时间与中位/范围。
- `raw-traces.json.gz`：35 笔原报告与四节点记录；共识记录只保留目标高度前后各一块及配置记录，包含全部捕获的该付款 attempt。压缩包不含钱包或节点私钥、数据库。
- `run.py`、`analyze.py`：在仓库根目录运行的实验与分析脚本。先编译四个程序到 `bin/`，用 `bin/payctl init-lab -dir experiments/latency-phase-001 -port 21000 -outputs 64` 创建新实验账本；随后按上面的顺序调用 `python3 docs/experiments/latency-phase-2026-09-18/run.py LABEL UNUSED_INPUT 5 FLUSH GOSSIP`，每次使用不同 LABEL 和未消费输入。分析用 `python3 docs/experiments/latency-phase-2026-09-18/analyze.py`。脚本退出时关闭自己启动的实验节点。
- 诊断开关 `UTXO_SETTLEMENT_TRACE=1`；实验覆盖 `UTXO_EXPERIMENT_FLUSH=10ms` 与 `UTXO_EXPERIMENT_GOSSIP=10ms`。未指定时保持 Comet 默认 100/100。
- 新增 `/debug/consensus` 只在诊断启用时存在；最多 4096 条内存事件，不逐事件写盘。提案时间可按相同 attempt 哈希在四节点记录中关联，阶段日志按 height/round 关联。

限制：顺序执行的小样本，同机回环网络、开启埋点、无故障，不是随机化性能基准。重试反馈、提案时机和机器调度都会影响差值；证明时间包含 100 ms 查询轮询。阶段时间用同机墙钟比较，不适用于未校准的跨机器时钟。这里只测委员会 0 应用提交，不能解释成四节点都提交完毕。阶段日志取既有 Comet 边界，不能将“决定到 ABCI”进一步声称为某次纯 fsync 耗时。
