# 钱包观察与发送节流优化：实现和验证

## 结论

已实施三项小改：钱包仅在首次观察或本地已提交高度变化后重新读完整 coin；实际 HTTP 发送前限制集中补发；成员状态检查从第一个尚未完成的成员继续。没有新增依赖，没有改变本金、TXCer、委员会结算或同步策略，没有增大 256/2048。

快速到账中位延迟明显下降，突发得到控制，但持续吞吐基本不变。本轮不能宣称已稳定承接 500 TPS，也不能将满额次数减少解释为后台容量提高：发送节流增加了发送前的等待。

## 实现边界

- internal/blockfollow/follow.go：可选本地提交回调，仅 Commit 成功返回之后调用。原调用方行为保持。压测钱包用 atomic.Int64 发布高度。
- cmd/payctl/direct_observation.go：每笔保存检查前高度；首次必查，同高度不重读，读错不推进。成员观察只记录已经成功检查的连续前缀，不再重复请求前面的成员；仍验证原 Observed/Signed/Closed 条件。
- cmd/payctl/direct_pace.go：全局单个可取消的发送门限在实际发出前应用，最多保留四笔额度，原计划时间仍保留；不预分配几百个过期发送时间。
- cmd/payctl/direct_bench.go：在现有观察循环中接入上述机制。快速名额仍到钱包验证保存成功后释放，总名额仍到观察任务退出后释放。
- cmd/payctl/direct_bench_metrics.go：记录 WalletQueries、PacingWaitMS 及相应汇总；没有移除原积压和发送滞后统计。

未知错误仍保留 UNKNOWN 标签。原始 unfinished 包含已返回 UNKNOWN，因此最终 D 的 sampled_peak=2072 不是实际活动任务超过2048。按信号量获取/归还时间重构的峰值也只是估计：记录时间在 channel 交接之外，A 曾得到2049，不能以此声称实际越界。真实限制由容量2048的 channel 保证，相关并发测试保留。

## 验证与可复现材料

已通过：全部应用包（cmd、internal、protocol、finality）测试；cmd/payctl 和 internal/blockfollow 竞态测试；这两个包的 go vet。

新增测试覆盖首次 Final 先到、同高度去重、查询期间发生提交、读错重试、提交失败不发布高度、实际提交后才发布、停发后的补赶上限、并发节流与取消、成员未完成/查询错误不得记成完成。

直接 go test ./... 扫描了历史实验目录中的不完整 Go 源码快照而失败，记录在 all-tests.log；全应用包使用明确包范围执行并通过，见 application-tests.log。当前变更的备份保存在 Go 忽略的 _before/ 中；源码展示文件使用 .go.txt。

实验仍复用上一轮相同的14节点业务二进制、NoSync成员、其余应用同步存储、Comet内存块库、10000交易池与共识参数。每轮独立创世。测试 overlay 只处理大创世、预生成保存、90,000总数和独立输入遇错继续，不重试失败交易；准备阶段不计时。生产默认错误处理未放宽。
