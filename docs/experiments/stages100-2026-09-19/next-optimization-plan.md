# 下一阶段优化计划：网关并行投递与委员会推进

2026-09-19，基于 `2f8fc24` 和本目录的 100 笔实测。网关 A/B 已实施，委员会细分埋点及定速测量接口已补齐；执行结果见[实现与对照记录](../parallel-relay-2026-09-19/README.md)。以下保留获批计划及原验收标准。

## 一、先明确这次要取消的等待

目前 `directPaymentHandler` 已先写出并 Flush 钱包响应，再执行 `PersistDirect`，所以网关保存本来就不在“收款钱包拿到凭证”的前置路径上。但 `NotifyPersisted` 只在保存完成后触发，`runDirectTask` 又必须先读到 outbox，公共 Submit 和 INSTALL 因而仍被保存阻挡。

网关保存两项内容：`KeyCollected` 下的完整 DirectPayment，以及 `KeyOutbox` 下的待投递任务。完整材料包括原交易、该交易的输出凭证、使用到的输入凭证；这次保存用于留存材料和补投，不负责新的本金扣减或输入批准。

成员在 `ApproveDirect` 中已经先同步持久化输入候选、批准记录和 CAL/FUEL/工作额度占用，再签票。委员会接纳完整 DirectPayment 不依赖网关的本地保存回执。因此，完整三票材料已经形成后，**公共投递、成员 INSTALL、网关留存可以并行推进**。

不采用“完全不保存”：保留现有 outbox 是最小的可靠补投办法。也不只增加保存线程：当前 Group 本身已经合批，问题在于发送必须等它完成。推荐给已有中继增加携带完整材料的内存入口，持久队列继续兜底。

## 二、执行顺序

### 0. 固定实验基线

- 安排暂停另一套实验网，保留其数据库，记录恢复命令；只运行本轮 14 个进程。
- 新创世、100 笔独立最终 UTXO、闭环并发 64、传播 10/10 ms，保留验签、sync、现有 4 Submit/4 INSTALL 配额。
- 当前版带埋点用于定位，无埋点重复运行用于对照。后续每个补丁独立记录版本和二进制哈希。

### 1. 网关：去掉前后两处非必要的写盘等待

拆成两个可以单独比较的小补丁，先 A 后 B；它们共同完成用户要求的“边保存、边发送”。

**A．重试节流内存化。**

`Public.Submit` 返回后，只在现有中继调度器记录下次允许重发的时间，立即释放投递执行位置。去掉网关仅更新 `NextSubmitUnixNS` 的 DB.Update；成员首次备用期限及其现有备用处理保持不变。

去重覆盖排队、在途与冷却，同一事实始终复用相同封装。内存状态有界，未到期项不因淘汰而立即重发；容量满时新任务留在持久队列等待公平补扫。重启可提前幂等重发，但一次 HTTP202不能永久停止补投。这个补丁准备好共享的去重与冷却状态，供后续内存首投入口复用。

**B．首次公共投递和 INSTALL 不等网关保存。**

- 组装完整、已经验证的 DirectPayment 后，钱包响应保持立即写出。当前 handler 在 Flush 后，先非阻塞地将完整不可变材料交给中继，再继续调用原 `PersistDirect`。保存仍由现有 handler 生命周期和 Group 管理，不另开每笔无界保存 goroutine。
- 中继接纳内存材料后，复用原来的 4 个 Submit 和 4 个目标 INSTALL 执行位置。这两路可以在本地 outbox 尚未写完时开始；不等保存回执或 INSTALL ACK。
- 原 `Wake` 的 FactID 只是“请去数据库找”的提示，不够支持提前投递。新增入口必须携带完整封装，或者携带指向暂存完整封装的引用；只把通知移到保存前不会实现优化。
- 内存入口只提供加速。容量满时不影响钱包响应，不丢正式保存，退回当前“保存后唤醒＋扫描”路径。暂存按数量和字节数有上限；优先沿用现有接纳上限，不创建无界后台队列。
- 内存入口与持久扫描共享同一 Fact/动作去重与冷却。不能内存提交一次、保存通知又立即提交一次。完整材料在保存成功或可信公共完成之前由暂存/原 handler 保有；已移交给持久 outbox 后可以释放内存材料。
- 任务执行时检查已提交的 Observed 状态；不能再把“尚无 outbox”直接判为无任务。已有合法暂存材料且没有可信终态时允许执行。可信终态已经出现时跳过。
- 若公共块先于网关保存完成，`PersistDirect` 在原事务内检查 Observed，不能重新创建已完成的 outbox。在途完成、迟到 INSTALL 和迟到通知都不能让任务复活。
- 网关保存仍执行，即使公共 HTTP 已接收。保存错误沿真实错误路径处理，不记为成功、不释放资金锁；不能声称内存任务已经具备断电恢复能力。

主要涉及 `cmd/gateway/direct.go`、`cmd/gateway/main.go`、`internal/gateway/direct.go`、`internal/gateway/direct_relay.go`，必要时调整 `collector.go` 的内部通知接口。尽量复用现有 Relay、Group 和终态检查，不改变交易线格式、委员会结算或认证门槛。

这里保留原一轮交付方案的边界：如果网关和成员都尚未保存完整材料就发生进程崩溃，不能仅凭成员各自的单票承诺完整证书一定可重建。当前收款钱包保存的是输出与凭证，不能直接当作已经实现了完整原交易的自动补投。此优化不增加用户等待安装回执的门槛，也不删除已有保存与备用机制。

**必要检查只围绕这个改动：**

| 场景 | 应看到的结果 |
| --- | --- |
| 人为阻塞网关 outbox 更新，保持读取可用 | 钱包先得到响应；Submit 和至少一个 INSTALL 已开始，保存尚未结束 |
| 保存完成、首次投递及通知交错到达 | 同事实同动作不重叠，正常成功样本仍以一次公共首投为目标 |
| 内存入口满或提示丢失 | 原保存与公平补扫最终接续，已经接纳的任务不会静默丢弃 |
| 成功区块先到，保存/INSTALL 后到 | outbox 不复活，费用和权限只处理一次 |
| HTTP202后长期未上链、投递失败、重启 | 仍按有限间隔补投相同封装，成员备用期限不被延长 |
| 正常关闭或保存失败 | 先停止接纳，等待受管理任务退出，再关闭 Group；错误不冒充持久成功 |

验证命令沿用 Mac 环境：`go test -race ./internal/gateway ./cmd/gateway ./internal/member`、`go test -tags=comet_v3 ./...`。先增加可复现旧等待的测试，再分别实施 A/B，运行相关回归。

### 2. 委员会：测准每轮固定成本，再改最大项

当前接纳到提案约 401 ms、提案到 Finalize 约 340 ms。已有日志显示正常 round 0 内推进，多数后续块没有再等完整的 100 ms 新高度期限；不据此盲调超时。

在实际 Comet 适配层为以下调用增加可关闭的耗时采样：提案/分片构造、WAL FlushAndSync、FilePV 签名与状态保存、内部消息处理、BlockStore SaveBlock、WAL EndHeight WriteSync、应用 Commit。再对齐实际提案者收到交易、取池和前块结束的时间。采样保留每块摘要，避免每笔同步写额外诊断日志。

同时拆高度 4 的 136 ms Commit：锁等待、状态准备、写入同步及变更字节量。按每块固定开销、每笔摊销和块间推进判断优先级。明确原因后才安排一个对应补丁；现阶段不预定换库、换共识或放松持久化。

代码关注 `cmd/committee/main.go`、`internal/committee/app.go`、`internal/requesttrace/` 和 `third_party/cometbft/`。需要保留的 Comet 修改写入适配源码/overlay，不只改生成的 `.scratch/comet-src`。

### 3. 前台与持续负载验收

先沿用 100 笔测试确认单变量收益，再运行有界在途、固定目标输入速率的持续负载。分别记录尝试、接纳、快速到账、唯一实际 Commit 和成员权限恢复速率；同时记录队列长度、最老任务年龄、内存、磁盘增长。不能只看发出凭证的速率。

委员会路径之外，前台目前主要是组织认证组装 116 ms、钱包验签保存 52 ms。后续沿既有成员/钱包 Group 观察排队与批大小，检查完整工作路径中的重复编解码与重复计算；在实测前不预定删除验证，也不把钱包“已持久保存可续花”的终点改成仅收到网络响应。

## 三、计时与成功标准

提前投递后，Submit 可能先于网关保存完成；旧“保存完成→Submit”不再适合作为主指标，更不能把负值称为负耗时。

统一以以下几项比较 A/B：

1. 完整认证材料准备好 → 第一次实际 Submit、委员会实际接收；另记提前于保存完成投递的比例。
2. 网关保存全耗时、逻辑更新数、真实物理提交数；Submit 执行位置被占用的时间。
3. 钱包发送 → 快速可续花、实际 Commit、钱包/成员观察完成，各自 P50/P95；整批最后提交与最后观察完成分别统计。
4. 网关未投递与委员会未提交两个队列的峰值及持续负载斜率。前者下降、后者持续增长不是整体优化成功。
5. 每轮审计四委员一致、无资金缺口、无重复执行，停发后 outbox 能排空；保留网关故障与成员补投检查。

此次网关改动主要瞄准后台投递与整体周转。原先 90.65 ms 的保存、186.21 ms 的投递等待、40.88 ms 的重试更新存在并行和负载关联，不能把三个中位数相加当作保证收益，也不能从 171 ms 的快速到账时间中直接扣去 90.65 ms。

实施按 A、B、委员会定位、定速验收逐项进行，每项保留独立对照结果；短时定速探测不能代替长期稳态或最大 TPS 测试。
