## 已经证明的收益

| 优化 | 对照证据 | 可以得出的结论 |
| --- | --- | --- |
| 网关接入现有 Group 合并提交 | 无埋点平均 5.859 → 4.034 秒 | 该测试下批次完成时间缩短约 31%，真实同步提交减少 |
| Submit 与 INSTALL 解耦、滚动调度 | 无埋点平均 4.038 → 3.534 秒 | 该测试下批次完成时间缩短约 12.5%，移除了不必要的前置等待 |
| 网关先投、成员有限延迟备用 | Submit 372/378 → 100 次；成员重试更新请求 634/720 → 0 | 确实减少重复工作；无埋点 3.541 → 3.496 秒的差异在波动范围内，未证明明显提速 |

这些是逐项对照，不能把百分比相加。最新 3.141 秒是带埋点的新样本，不能直接与前面的无埋点结果相比并声称又有提升。前台快速可续花延迟的全面改善、持续最大 TPS，仍未由这些数据证明。

## 当前较长的段在哪里

按 100 笔交易加权的中位：网关持久保存到 Submit 为 186.21 ms，委员会接纳到提案准备开始为 401.07 ms，提案准备完成到区块执行入口为 340.29 ms。单笔最终检查和执行分别为 0.633/0.803 ms。

同一份日志进一步按 6 个业务块分解，以下是按块等权的中位，不能与交易加权中位相加：

| 区间 | 中位，ms |
| --- | ---: |
| 提案准备完成 → 提案签出日志 | 51.26 |
| 提案签出 → committee0 收到完整提案 | 49.96 |
| 本块 ProcessProposal | 11.18 |
| Process 完成 → 本地预投票签出 | 55.54 |
| 本地预投票签出 → 进入预提交 | 24.37 |
| 进入预提交 → 本地预提交票签出 | 43.96 |
| 本地预提交票签出 → 进入共识 Commit 步骤 | 28.76 |
| Commit 步骤 → 应用 FinalizeBlock 入口 | 40.31 |

`review_consensus.py` 校验每块所有分段之和与原时间段一致。日志中所有块均为 round 0；高度 3～7 的 committee0 新高度计时器计划时刻均已过去。因此，不能推断减小 `TimeoutCommit=100ms` 就能直接省下 100 ms。

100 笔中 92 笔在 committee0 接纳时，该副本的前一高度仍未完成 Commit。累计接纳到提案等待有约 86.95% 与前块未提交区间重叠。这是时间重合，尚未证明它们都已到达实际提案者，也没有证明这部分等待可全部消除。

Mac 上实际 CometBFT v0.38.26 适配源码确认：

- `defaultDecideProposal` 经过块/分片构造、`wal.FlushAndSync`、`SignProposal` 和内部消息排队。
- `signVote` 经过 `wal.FlushAndSync` 和签名；FilePV 的 `saveSigned` 保存防止重复冲突签署所需的签名状态。
- `finalizeCommit` 在应用执行之前经过 BlockStore 保存及 `wal.WriteSync(EndHeightMessage)`。

所以应具体测量这些调用的耗时。现有粗段包含 CPU、存储、线程调度和传播，不能把整个区间认定为 fsync，更不应仅凭它删除共识持久化。接收节点的入池时间也不能代替实际提案者的入池时间。

## 后续行动顺序

1. **先取得同硬件隔离基线。** 后续实验安排暂停另一实验网，保持本轮 14 进程、交易类型、并发和配置不变，重复当前版本。带埋点用于定位，无埋点用于比较完成时间。共享 SSD 竞争目前只是合理假设，先确认是否可重复；此次评审没有停止原实验网。
2. **完成一个局部减负补丁：仅网关的重试节流改为内存状态。** HTTP Submit 返回后更新内存并释放执行位置，省去纯重试时间的 DB.Update。当前该尾段中位 40.88 ms，占着 4 个投递位置之一。保持原始 outbox 创建、可信终态删除、金融状态的持久化；保持成员首次备用期限的持久化。复用现有循环、有限冷却记录和公平补扫，重启允许相同封装提前幂等重发。HTTP202仍不是完成。实现后预计少 100 次逻辑更新请求，实际少多少物理提交、延迟下降多少需实测。按原版→补丁→原版比较物理提交、实际 Commit、两处队列峰值和快速到账 P95。
3. **重点定位委员会推进，再决定优化。** 把提案构造、WAL 同步、签名及签名状态保存、内部消息处理、BlockStore、应用提交分别计时；把实际提案者入池与选取时点对齐，并区别各副本进度。针对 136 ms 的 Commit 异常块拆写锁、状态准备和实际数据库提交。看清每块固定成本、每笔摊销和块间推进，再决定保留同等持久化语义的合并提交、减少重复处理或部署资源调整是否值得。暂不据粗段换共识、换数据库或调小超时。后续用有限在途量、固定输入速率的持续测试核验唯一最终完成速率、队列斜率和权限周转；另测后续认证块头实际可取时刻，区分区块形成和客户端跟块落后。

第二、三点分别是“最小可实施的改动”和“当前最重要的排查方向”。401/340 ms 是当前测试中较长的延迟段，还不是委员会吞吐容量上限的证明：本轮 64 个闭环执行槽要等成员观察完成才继续发交易，输入本身受到这个等待限制。只减少网关等待但委员会队列扩大，不代表整体吞吐提升。
