# 成员 GC 与调度参数对照

2026-09-20，Mac Studio M4 Max，16 核、64 GB，Go 1.27.1。
本轮接续“HTTP 请求已写出，但成员 handler 迟迟未开始”的诊断。

**已采用本机成员 GOGC=200，保留 GOMAXPROCS=16。** 当前常驻网络已经用该设置重启，仍为原来高度 7、100 笔交易的状态；本轮实验交易没有混入其中。采用的是启动配置，不把本机取值写成跨硬件的协议或程序默认值。

## 实验方法

同一组冻结的程序文件，只通过成员启动包装器改变 Go 标准环境变量。
委员会、网关、钱包、业务验证、三票门槛、同步持久化和 10/10 ms 传播均一致。
真实二进制 SHA-256 在 [binaries.json](binaries.json)，每轮 8 个成员实际启动参数在各目录的 `member-settings.json`。

性能比较关闭请求/共识详细埋点和 runtime trace。相同频率每 0.5 秒采样进程 RSS、累计 CPU 时间；RSS 含数据库 mmap，并不是 Go 堆大小，也不等于可相加的物理独占内存。

第一组按 `A,P4,P2,G200 / G200,P2,P4,A / P4,A,G200,P2` 交错运行，每组 3 轮。A 为成员 `GOMAXPROCS=16,GOGC=100`；P4/P2 仅改变前者；G200 仅改变后者。随后 A/G200 再做 A→G200→G200→A 确认，共计 16 轮无埋点短测、1,600 笔交易。

每轮新建数据库和共识签署状态，从创世开始，100 笔独立最终 UTXO 跨组织付款，64 个闭环在途槽，零预热。槽位在钱包跟块与成员应用观察完成后释放；这不是开放式极限吞吐测试。

## 无埋点短测结果

以下是每轮指标的平均值，分位数没有混为一个总体分位数；全部慢样本和无收益候选都保留。

| 成员设置 | 轮数 | 到账均值 / ms | 到账 P50 / ms | 到账 P95 / ms | 整轮闭环 / s | 8 成员峰值 RSS 合计 / MiB |
|---|---:|---:|---:|---:|---:|---:|
| 16 / 100，基线 | 5 | 136.47 | 136.30 | 163.08 | 1.975 | 302.95 |
| 4 / 100 | 3 | 137.54 | 145.74 | 173.13 | 1.973 | 276.30 |
| 2 / 100 | 3 | 148.08 | 142.10 | 193.72 | 2.006 | 267.71 |
| 16 / 200 | 5 | **123.30** | **131.80** | **149.91** | **1.952** | 329.49 |

降低并行度虽然降低了 RSS，但没有达到改善前台的目标，P95 反而上升，因此不采用 2 或 4。

GOGC=200 的到账均值降低 **9.64%**，P50 降低 **3.30%**，P95 降低 **8.08%**；完整闭环只降低 **1.17%**。8 个成员峰值 RSS 合计平均增加 **26.54 MiB**。五轮结果有波动，不能保证每一轮、每一笔都更快，也不能据此声称 TPS 提高相同比例。

到账仍从付款钱包发出 HTTP 请求计时，到收款钱包验证并持久保存 TXCer 为止。均值分解：请求发出到凭证收到 **96.09→87.28 ms**，钱包验证保存 **40.36→35.99 ms**。后者虽未直接改参数，但共享机器上的工作重叠与调度会改变其墙钟等待，不能说其业务计算被删减了。

## 持续三分钟：收益能否保持

基线与候选各一轮：目标 30 笔/秒，5,400 笔，64 个闭环槽，关闭诊断。每轮另有 1 笔预热，使用相同扩充创世输出，保证全部付款使用不同输入。预先构造并保存请求的时间不计入正式发送的三分钟。

| 指标 | 16 / 100 | 16 / 200 |
|---|---:|---:|
| 成功 / 失败 | 5400 / 0 | 5400 / 0 |
| 到账均值 | 115.16 ms | **102.67 ms** |
| 到账 P50 | 112.21 ms | **98.57 ms** |
| 到账 P95 | 164.56 ms | **149.20 ms** |
| 发送 → 钱包观察上链 P50 | 1331.09 ms | 1210.15 ms |
| 发送 → 成员应用观察 P50 | 1370.51 ms | 1235.63 ms |
| 发送端排队 P95 | 0.44 ms | 0.47 ms |
| 全部闭环完成 | 180.674 s | 180.743 s |
| 8 成员峰值 RSS 合计 | 1153.02 MiB | 1229.81 MiB |

这一对持续实验的到账均值降低 **10.85%**，P50 降低 **12.15%**，P95 降低 **9.34%**。最后的整体结束时间几乎相同，因为两组都按 30 笔/秒发送约 180 秒；不能拿它来估计极限 TPS，也不能把更早的跟块观察等同于直接测到了更早的共识提交。

每 30 秒一个窗口，按该窗口实际发送的交易计算到账 P95。各窗口末“在途”是已经发送、尚未完成钱包及成员观察的笔数，**不是委员会交易池大小**。

| 窗口 / s | 基线到账 P95 / ms | G200 到账 P95 / ms | 基线末在途 | G200 末在途 |
|---|---:|---:|---:|---:|
| 0–30 | 144.05 | 135.12 | 35 | 39 |
| 30–60 | 162.77 | 155.73 | 41 | 42 |
| 60–90 | 160.71 | 146.56 | 38 | 40 |
| 90–120 | 172.01 | 149.74 | 42 | 44 |
| 120–150 | 166.60 | 152.77 | 38 | 42 |
| 150–180 | 166.82 | 149.25 | 38 | 33 |

两组每窗口约发送 900 笔，发送反压 P95 都小于 0.52 ms，窗口末在途未持续扩大，结束后的持久 outbox 全部排空。候选六个窗口的到账 P95 均较低；持续实验只有一对，不声称跨设备或所有负载均有相同幅度。

RSS 随交易历史增长，不能称为绝对不增长：基线首/末窗口成员 RSS 均值约 **790→1112 MiB**，候选约 **860→1188 MiB**。相同窗口的差额约 **68～77 MiB**，候选主要增加了一段内存余量，没有在这三分钟出现额外差距不断扩大的趋势。RSS 包含 mmap，未单独测 Go 存活堆，不能把本实验当成无限期无泄漏证明。

## 诊断轮，不混入性能收益

另外 A/G200 各跑 100 笔，打开请求/共识埋点和成员 `gctrace=1`，不打开 runtime trace。A 这一轮到账 P50 **289.81 ms**，明显慢于所有无埋点基线；G200 为 **135.01 ms**。保留该异常波动，不能用这两个数字宣称性能翻倍。

诊断轮中，四个签署成员整个进程生命周期的 GC 次数由 **41/34/30/29** 变为 **13/13/13/14**，含启动和后台工作。按实际凑齐第三票的请求统计，写完请求到成员 handler 开始的平均间隔为 **27.82→13.05 ms**；这支持“降低 GC 频率可能减轻等待”的解释，其幅度仍受诊断开销及单轮波动影响。

原始时间线、GC 日志和第三票归因分别在 `diag-a/`、`diag-g200/`。部分 GC 日志与启动日志交错，次数采用日志里的最后周期编号，不能把残缺行当完整停顿样本。

## 已落地的改动与核验

当前 Mac 8 个成员的启动设置为：

```sh
GOMAXPROCS=16 GOGC=200 member -config <成员配置>
```

`apply_mac.py` 为这台实验机创建固定参数的成员启动包装器；委员会、网关、钱包链接到对照中使用的同一组二进制。有效入口记录在 Mac 的 `/Users/richz/lab/man/utxo-fastpay-v12/.run/active-lab.json`，节点参数有逐个启动日志核验。业务 Go 代码没有因为这轮参数优化而修改。

**20 轮共 12,602 笔全部成功**，包含 16 轮短测的 1,600 笔、两轮诊断的 200 笔、两轮持续测试的 10,800 笔及 2 笔预热。逐轮四委员状态哈希一致、所有 14 个节点 Pending=0、缺口为 0、本金守恒，FUEL 总额、每笔 84 报酬和 10 销毁均通过审计。启动参数切换前还审计了原常驻链，保留其 100 笔历史，重启后 14 节点健康、四委员高度均为 7。结果见 `active-audit.json`、`active-after.json`、`active-restored.json`。

本轮采用已验证的最小改动，没有把尚未做分配热点排名的重复编解码重构混入对照。它仍是后续候选，不能把已观察的 13 ms 收益归功于任何未实现的代码改动。
