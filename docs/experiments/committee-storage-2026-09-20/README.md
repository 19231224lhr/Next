# 委员会执行结果合批与持续负载

本轮从上一轮实际代码出发，只修改执行结果保存的数据库写入方式。所有验签、
同步持久化、FilePV 防双签状态及 BFT 法定人数保留，flush/gossip 10/10 ms、
默认 P2P 带宽不变；成员固定 GOMAXPROCS=16、GOGC=200。

## 拆测发现

100 笔／64 并发的 `storage-diag`：

| 路径 | 四委员各自 P50 的范围 |
|---|---:|
| FilePV 编码 | 0.011～0.015 ms |
| 临时文件 Open | 0.176～0.241 ms |
| O_SYNC Write（含同步） | 3.179～3.928 ms |
| Close | 2.889～3.905 ms |
| Rename | 5.537～12.055 ms |
| 结果历史编码 | 0.0001～0.0003 ms |
| 结果历史 db.Set | 1.529～8.710 ms |
| 最新恢复信息编码 | 0.0006～0.0010 ms |
| 最新恢复信息 db.SetSync | 20.220～27.266 ms |
| 完整 SaveFinalizeBlockResponse | 25.223～38.078 ms |

分位数不能相加。结果来自同一次运行，不是多轮稳定分布；Close、Rename 等
墙钟区间也会受到共享磁盘和调度影响。编码不是本轮重点。

## 最小修改

原逻辑是历史记录 `Set`，然后恢复记录 `SetSync`。现在两项编码放入同一个
原生 Batch，检查每次 Set 的错误，最后 `WriteSync`。每个高度独立提交，
没有跨高度等待，没有放到后台后提前返回。

键名、字节编码、nil TxResults 过滤、DiscardABCIResponses 分支保持一致。
批次在所有返回路径 Close。减少的是一次独立写 API 及数据库写者交接；
原先只有一次显式同步，不能称为把两次 fsync 变成一次。大批次可能触发
GoLevelDB 的其他内部写路径，也不能保证只有一次物理磁盘写。

同步失败可能已经写入完整批次，调用方仍收到错误并按既有规则停止推进／恢复；
没有删除补偿、回退双写或错误后继续 App.Commit。

`storage-batch-diag` 中历史 Batch.Set 约 0.0005～0.0007 ms，完整结果保存
约 24.331～27.871 ms。不过这轮 FilePV 更慢，整体 100 笔反而从 1.848 s 变为
1.981 s。因此不拿这个单独的埋点配对证明端到端收益。

每轮新数据库、相同创世，额外预热一笔，所有非委员会程序冻结。

| 轮次 | 版本 | 完整闭环 | 快速到账 P95 |
|---|---|---:|---:|
| storage-a1 | 原写入 | 16.220 s | 215.771 ms |
| storage-b1 | 批次写入 | 15.781 s | 190.458 ms |
| storage-b2 | 批次写入 | 16.127 s | 248.563 ms |
| storage-a2 | 原写入 | 16.216 s | 224.976 ms |

统计显著、大幅加速或已解决主要共识等待。

## 验证边界

结果合批测试覆盖真实 GoLevelDB 关开、两个读接口、nil 过滤、Discard 两分支、
历史保留，以及超过刻意缩小 WriteBuffer 的大批次。错误注入分别覆盖组批失败、
写入前失败，以及底层写成功后上层仍收到错误的情形。
“写入前注入失败后数据库不变”不等同于“真实同步失败必然没有写入”。
正常 Close/Open 也不等同于任意断电验证；既有 state/consensus 恢复测试继续运行。

全项目 `go test -tags=comet_v3 ./...`、`go vet -tags=comet_v3 ./...` 通过。
Comet state、consensus、privval、tempfile 包 `-count=1` 全部通过。详见测试日志。

## 三档持续负载

仅测试候选 B 的运行能力，不是 A/B 吞吐提升证据。每档计划持续发送 120 秒、
最多 256 笔在途，采用相同的 48,002 个输出创世、相同程序版本，额外预热一笔。
诊断埋点关闭。输入和请求预生成在测量窗口之外；单笔耗时从钱包 HTTP 发送开始。
总闭环统计从发送调度开始到全部成员处理完成的观测，首笔发送与调度开始仅相差微秒级。

| 目标发送率 | 笔数 | 实际首笔→末笔发送窗口 | 完整闭环 | 发送滞后 P95 | 末笔发出→成员全部完成观测 |
|---|---:|---:|---:|---:|---:|
| 100/s | 12,000 | 119.991 s | 121.033 s | 0.49 ms | 1.043 s |
| 150/s | 18,000 | 119.994 s | 120.958 s | 279.25 ms | 0.965 s |
| 200/s | 24,000 | 120.771 s | 121.779 s | 804.72 ms | 1.009 s |

三档全部成功。快速到账 P50 分别为 142.129 / 128.607 / 137.945 ms，
P95 分别为 216.759 / 197.687 / 196.329 ms。这些是本次负载下的结果，
不能与不同创世规模、不同负载形态的短轮混算收益。

队列统计来自约 0.5 秒一次的 `/healthz` 已提交高度，再与停机后的 BlockStore 逐笔 Fact 对应。
已核对 `App.Info` 返回 `a.committed.Height`，该值在 `a.db.Update` 成功后才更新；
不是仅仅写入 BlockStore 的高度。首次观察到高度是 Commit 时刻的**上界**，
不能作为精确毫秒级提交时间。实际测量窗口内最大采样间隔约 1.36 / 1.36 / 0.63 秒。

| 指标 | 100/s | 150/s | 200/s |
|---|---:|---:|---:|
| 20～110 秒已发送待提交数中位数 | 114.5 | 154 | 163 |
| 已发送待提交数峰值 | 195 | 218 | 205 |
| 20～110 秒最老待提交年龄 P95，上界观测 | 1.566 s | 1.299 s | 0.839 s |
| 已到计划时间但尚未实际发送的峰值 | 21 | 55 | 215 |
| 最后一次观测剩余待提交数 | 0 | 0 | 0 |

100/s 的后半段待提交数量没有持续增长；150/s 出现发送抖动，但末尾能跟上计划窗口。
200/s 的发送端队列则有增大迹象：每 20 秒窗口中“计划到期但未发出”的峰值
依次为 **50、96、101、189、170、215**。该档实际平均发送速率约 **198.72/s**，
包含末尾闭环排空的完成率为 **197.08/s**。

因此，所测条件下完成了接近 200/s 的两分钟运行，但**不声称严格、长期稳定支持 200 TPS**。
256 个槽会对发送施加反压，待提交队列有界并不证明不存在过载。
槽要等钱包／全部成员观察结束才释放，发送端受限也不能直接等同委员会吞吐上限。
后续若继续提高负载，应先分离压测器、跟块观测和委员会实际服务能力，保持时间口径清楚。

## 最终状态与复现

本轮共 **70,207 笔（含 7 笔预热）**通过审计：每轮 14 节点 pending=0，
四委员状态哈希一致，Payments=Closed，缺口为零，CAL/FUEL 总额及费用分配匹配。
保留 Batch.WriteSync 修改，不继续改 FilePV。已将完整测试版本部署回原实验网，
成员维持 16/GOGC200；原 100 笔、高度 7 数据保留，没有重置历史。

为支持长测，将 `bench-v4` 单轮笔数上限 10,000→30,000、本地配置读取上限
16→64 MiB；网络请求大小和协议规则不变。三档使用同样的 36 MiB 左右实验创世，
规范化配置摘要相同。正式 4,000 笔 ABBA 仍使用原冻结的非委员会程序。

- `summary.json`、`analyze.py`：全部轮次审计、配对和持续指标；分位数均注明逐轮口径。
- 各轮 `reports/bench-v4-*.json`、`reports/audit.json`：原始逐笔记录及资金审计。
- 两轮诊断的 `storage-summary.json`、`phase-summary.json`：真实保存路径及整体阶段。
- 持续轮次 `sustained-summary.json`：每 10 秒发送／提交观测／跟块数量、逐采样队列。
- `committed-facts.jsonl`、`inspect_commits.go`：停机读取实验账本，将 Fact 对应到块高度；
  该工具使用同一网络的公开变色龙哈希配置读取自定义区块格式。
- `run_series.py`、`run_sustained.py`：独立实验目录、顺序运行、原网络恢复。
- `finish.py`、`provenance.json`：二进制 SHA256、相同创世摘要及原网络升级后健康状态。
- `red-test.log`、`green-test.log`、`tests-project.log`、`tests-comet.log`、`vet.log`：测试记录。
- `gpt-review.json`、`gpt-result-review.json`：与[侧边栏 GPT](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)
  的两轮评审。GPT 支持保留窄补丁，同时要求将 1.6% 限定为本组小幅收益迹象，
  不包装成已解决主要瓶颈。其没有运行本仓库测试。

全为单机 14 进程、最终 UTXO 跨组织支付；尚不能外推为多机部署或长期容量承诺。
