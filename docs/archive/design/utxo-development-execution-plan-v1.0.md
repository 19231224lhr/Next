## 1. 目标与依据

从现有设计落地一套 Go 支付系统原型，完成同组织与跨组织快速支付、散户普通转账、公共结算、担保履行、费用与额度周转，并完成持续运行测试和交付。

以 [系统设计终稿](utxo-fast-payment-system-design-final.md) 为协议依据，以 [Go 工程架构规范](utxo-go-engineering-architecture-v1.0.md) 为代码、数据和接口依据。本计划只安排模块、开发顺序与验收，不重复架构中的字段、状态机和逐条规则。技术栈沿用 Go、bbolt、CometBFT、HTTP/TLS，初始化时验证兼容性并锁定版本。

首版范围沿用架构规范：统一 UTXO 账本、组织间直接互通、原担保责任不转移、散户直接提交委员会；采用一轮持久签票形成 SpendQC，钱包保存后可续花，INSTALL 与委员会登记在后台并行；保留真实资金/费用检查、累计核销和轻量归档。候选取消、授权退役释放、复杂恢复、动态成员及安全记录裁剪不纳入本轮。

## 2. 功能模块

### 2.1 工程基础、协议与存储

**对应架构：** 第 2–6、8 节；`protocol`、`internal/state`、`internal/store` 及公共工程配置。

建立 Go 工程、依赖锁定、节点配置与数据目录、基础 CI；实现 ProtocolVersion=2/WireVersion=2 的共享协议对象、规范编码、SpendFactID/SpendQC 与签名校验，以及内存参考状态、bbolt 原子存储和正常同库重启。工程初期验证真实 CometBFT 的连接、提交和证明适配，尽早确认技术栈能够连通。

**交付与验收：** 工程可构建运行，核心编码有独立黄金向量，金额与存储契约测试通过；为其他模块提供统一类型、状态访问和提交接口。

### 2.2 担保组织与快速签发

**对应架构：** 第 5–7 节；`internal/member` 和相关 `internal/rules`。

实现独立成员验证、Worker 私有额度、CAL/FUEL/工作及政策联合占用、第一轮签署确定效果及完整资源向量、后台 INSTALL 和原事实累计核销。签票前持久保存正文、父证据、输入锁及占用；完整 SpendQC 才形成可用输出。同组织可将父证书导入与子批准合并提交，复用父验证与机会式组提交。

**交付与验收：** 四成员组织能够真实持久签发，钱包取得并保存完整 TXCer 后不等安装回执即可继续支付；并发消费、重复请求、额度不足、正常重启和一个成员失联的结果符合规范。性能优化不得省略必要授权和认证。

### 2.3 委员会结算与担保履行

**对应架构：** 第 9 节及相关公共规则；`internal/committee`、`finality` 和相关 `internal/rules`。

实现并行预检、CometBFT 排序、确定性执行、块末提交和最终事实证明；支持 READY 登记、散户 DirectTransfer、按依赖结算、根资金唯一落实、原组织备付履行及真实回款。委员会接纳以 SpendQC 和必要依赖为依据，不等待发行组织安装或三份 ACK。先接通普通支付与最小费用执行，再补齐担保分支。

**交付与验收：** 四委员会节点得到一致状态，快慢路径共用唯一消费事实；资金不重复落实，原担保责任不迁移，凭证与最终 UTXO 不重复计余额。合法原根夹具只用于相应兼容规则测试，不冒充真实业务来源验证。

按需出块验收覆盖空闲停块、交易唤醒、末笔最终证明与核销、超过单块 Drain 上限的依赖收尾，以及持久队列重开后继续处理。跨块收尾测试应隔离中继补投并确认交易池为空，避免外部流量掩盖推进缺口。

### 2.4 费用、额度核销与资金补充

**对应架构：** 第 10–11 节；费用/奖励/核销规则、成员与委员会 outbox、钱包补资任务。

实现预存 FUEL 代付、最终 FUEL 自付、费用托管、分阶段奖励与领取、退款和 FeeClose；将真实公共证明接到原成员的累计核销，并实现低水位授权补资。资金覆盖、工作额度和商户累计限额分别按各自规则周转。

**交付与验收：** 多轮支付能够完成结算、费用关闭、证明交付和权限恢复；重复/乱序事件与补款重试不重复扣款或返还，未到账资金不能提前使用，实际净支出如实保留。费用模型从快路径开始即纳入，后台安装成本计入原计划，ACK 不计为核销证明且 FeeClose 不等待全员 ACK。完整周转在公共结算接通后验收，包括公共核销早于本地安装的交错。

### 2.5 网关、组织互通与钱包

**对应架构：** 第 4.7、7、10 节；`internal/gateway`、`internal/transport`、`internal/peers`、`internal/wallet`。

实现交易接入、证书收集、可靠中继、查询与事件接口；钱包管理身份、收款描述、输入选择、交易意图及凭证。接通组织首次通信的配置验证与缓存，支持组织用户快转和散户最终收付。收集器组装并验证完整证书后立即交付，本地保存和传播待办移至后台；钱包报告可续花前仍原子保存完整证书与传播待办，并运行可在重启后继续的补交中继。复用既有中继直接向发行成员及委员会补交；验收网关慢盘不阻塞交付、网关保存失败后持证钱包仍能补交。

**交付与验收：** 至少两个组织之间能够连续转账和拆分合并，散户可直接付款及收款；网关替换或客户端重试不改变业务结果。最小钱包与网关随快路径一起开发，再逐步接入委员会和费用功能。

### 2.6 后台调度、历史归档与运行维护

**对应架构：** 第 8.4、9.2、14–15 节；现有运行时调度、存储归档与遥测模块。

实现按依赖唤醒、累计通知合并、后台完成反馈及高低水位准入调节，为结算、证明和核销保留资源。实现活动库加只追加分段归档，可靠交接后迁移已终结正文与证据，保留必要安全状态，并提供正常启停、容量观测和历史查询。

**交付与验收：** 稳定负载下后台不持续积压，过载时限制新增、降载后待办消退；归档前后旧凭证验真、查询、防重和核销一致。分别测量活动库、归档和共识数据的空间增长。完整证书隐藏时等待持证者补交，始终无完整 QC 的局部候选允许持续占锁/额度，纳入未决水位，不以超时取消。

### 2.7 测试、基准与参考工具

**对应架构：** 第 12–15 节；`internal/testkit`、`internal/telemetry`、`cmd/bench`、`cmd/archgen`。

测试夹具和最小 bench 随核心模块建设，记录阶段耗时、业务速率、队列、资金和磁盘；集成后开展故障与持续负载测试，依据剖析优化热点。加入无安装 ACK 续花、隐藏完整证书、只有局部票、父子与核销乱序的 Q 系列测试；同一 SpendQC 额外等待 q 安装 ACK 仅用于隔离性能对照。协议对象稳定后完成 archgen 的类型骨架、接口/键目录及规则追踪生成，提供可重复配置和运行手册。

**交付与验收：** 测试与报告能对应实现提交，基准可重复，生成器输出稳定且不覆盖手写业务逻辑。archgen 属于最终交付，但不阻塞支付功能开发和系统测试。

## 3. 开发流程

各模块按“明确接口与验收场景 → 编码与模块测试 → 集成联调 → 评审修正 → 更新进度”推进。按可运行的增量提交，不要求整个模块写完才集成，也不预先拆成逐文件、逐命令任务。

金额、身份、状态转移和原子提交优先建立关键测试；配置和普通连接代码按需实现并验证。每次改动运行受影响测试，每次合入执行格式、静态检查、构建和基础回归。发现问题保留复现场景并补回归，资金、授权、持久性及一致性缺陷优先解决。

协议或接口发生变化时，同步更新对应规范和测试映射；局部实现调整无需重新设计整个系统。优化以测量为依据，保持优化前后的业务语义一致。

## 4. 集成顺序与里程碑

模块是职责划分，里程碑是可运行能力，不要求按模块编号全部串行完成。

| 阶段 | 集成重点 | 完成标准 |
|---|---|---|
| 工程基础 | 协议与存储、配置与 CI、最小 CometBFT 提交/证明验证 | 类型和持久契约稳定，基础工程可运行 |
| 快路径原型 | 担保组织＋最小网关/钱包＋早期测量 | 四成员一轮取证，跨组织用户在安装尚未完成时也可续花；此时不宣称完整支付闭环 |
| 日常支付 MVP | 公共结算＋散户付款＋代付＋费用关闭/核销＋后台反馈与补资 | 至少两个组织和四委员会组成完整日常支付闭环，经历多个周转周期 |
| 功能候选版 | 完整担保履行与回款、快速交易最终 FUEL 自付、奖励领取、轻量归档与参考工具 | 本轮约定功能完成，对应架构用例覆盖齐全 |
| 原型发布版 | 全量回归、持续负载、干净部署和收尾 | 验收达标，报告、手册与发布产物一致 |

散户自付实际委员会费用随公共结算实现；快速交易的最终 FUEL 自付随后接入，不阻塞日常代付闭环。原责任及费用数据结构从基础阶段固定，不等相关业务全部实现后再补入模型。

MVP 跑通时，根据实测基线与需求固定验收环境及目标，记录在 `docs/acceptance-profile.md`；后续性能优化按这个目标验收。未给定人员与投入，暂不承诺日历工期，开始开发后按实际进度调整。

## 5. 测试与最终验收

用例身份和详细断言统一沿用架构规范第 13 节的 C/M/B/R/F/P/A/X/S/L/O/Q 系列。模块开发同步补充相应用例，集成验证模块间组合，发布前在同一候选提交完成下列检查：

| 类别 | 验收重点 |
|---|---|
| 功能与资金 | 同/跨组织续花、散户收付、拆分合并、担保履行与真实回款、两种费用来源、奖励退款及核销；按业务身份最终对账 |
| 持久与可用性 | 重复/乱序、并发消费、提交后丢响应、同库重启、一个成员失联、网关替换；无重复支付、越权或状态不一致 |
| 持续运行 | O01–O04：后台反馈、补款防重、归档一致性与交接中断；满载时可执行旧义务继续推进 |
| 一轮取证 | Q01–Q06：无 ACK 续花、隐藏证书后补交、无完整 QC 的保留占用、父导入/子消费/核销先到、版本隔离及持久传播 |
| 性能与容量 | 真实签名和同步写下的 READY/证书保管/SETTLED/证明/核销速率、p99、安装成本、队列、资金与磁盘；覆盖冷/热缓存、充分/受限供资、归档开/关及过载后恢复 |
| 工程与交付 | 单元/集成测试、race、协议解码 fuzz、构建与依赖检查；生成器检查、干净部署和手册演示 |

持续负载预热后至少运行 30 分钟并覆盖至少 5 个核销/补资周期；若仍未稳定则继续观察。记录 offered/admitted/完成速率、拒绝与超时，区分快路径和散户路径，停发后核对排空及资金。正常负载须有完整证书传播和必要材料可取；不能将积压持续增长的峰值算作持续 TPS，也不要求真实净支出恢复为零。故障场景中的无 QC 局部候选与隐藏证书占用单独报告，不以清锁或清库制造排空。

统一检查入口为 `go test ./...`、`go vet ./...`、`go build ./...`、`go test -tags=integration ./internal/testkit -count=1`；在适用环境运行 race 和协议解码 fuzz，工具交付运行 `go run ./cmd/archgen --check`。测试必须实际执行；性能测试保持正常持久化与验证设置。具体场景命令随代码写入运行手册。

发布前冻结候选提交，修复阻断缺陷并完成回归，在干净环境部署至少两个四成员组织、四委员会成员及网关/钱包。功能和性能目标达到、关键缺陷关闭后，交付源码与依赖锁、二进制、配置、运行手册、测试/性能报告、已知限制及版本标签。公共生产部署另行安排。

## 6. 进度维护

开发时按第 2 节的七个模块维护一张进度表，记录“未开始／进行中／待验收／已完成”、当前交付、实现提交、验收结果及剩余问题即可。模块覆盖多个里程碑时记录已完成能力，全部约定能力通过后再标记完成。

当前各模块均未开始；本文件为开发安排，文档中的验收要求不代表已有测试结果。后续以可运行增量和验证证据更新进度，不再维护逐操作勾选清单。
