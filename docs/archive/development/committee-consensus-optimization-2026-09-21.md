# 委员会共识：针对现有延迟的优化评审

> **历史材料，不是当前规范。** 保留设计来源与旧版行为，勿用于覆盖当前 wire 4 实现。当前入口：[系统设计](../../design/system.md)。

日期：2026-09-21。范围：源码审查、已有单笔／100 TPS 日志重算、与侧边栏 GPT 评审。本轮未运行新负载，未改共识生产代码。1000 TPS 仍是后续验收目标，但不作为修复当前延迟的前置条件。

## 已确定的方向

交易在实际提案者完成入池后，基本都在首次可用的取池机会被选中。当前 21 MiB 块上限没有把这批交易限制成几十笔一块。连续负载下，交易经常错过本高度取池时点，等待前高度结束；应缩短真实块周期，而非扩大交易池或添加凑块等待。

现有四委员均为第 0 轮完成，没有触发提案／投票超时。负载下，多处同步保存耗时同时增长，FilePV 防双签状态保存最突出。它是优先优化候选，但这些数据还不能证明换存储后全部耗时都会消失。

## 数据与口径

来源：`experiments/single-vs-100tps-2026-09-21`。只统计业务块，排除预热和空证明块；单笔为 1 个业务块，100 TPS 为 20 个业务块，合并四委员的操作调用。以下是每次调用平均毫秒，不是每笔交易耗时，不可相加为共识关键路径。

| 操作 | 单笔 | 100 TPS |
|---|---:|---:|
| 投票前 WAL 刷新 | 6.521 | 24.137 |
| FilePV 签名状态保存 | 3.744 | 51.126 |
| 本地共识消息 WAL | 8.235 | 22.874 |
| BlockStore 保存 | 5.521 | 29.491 |
| EndHeight WAL | 8.734 | 22.299 |
| Finalize 结果保存 | 13.881 | 32.805 |
| 共识状态保存 | 19.109 | 29.657 |

`vote_sign` 包含 FilePV 保存，不能重复累计。单笔样本少；两个负载的对比是定位证据，不是存储替换的因果 A/B。

FilePV 保存当前执行：JSON 编码 → 创建带 O_SYNC 的临时文件 → 写入 → 关闭 → 重命名。将通用文件操作按同节点、完整包含于本次 FilePV 保存的时间区间关联：

| FilePV 内部操作 | 单笔平均 ms | 100 TPS 平均 ms |
|---|---:|---:|
| 编码 | 0.010 | 0.015 |
| 创建／打开 | 0.302 | 4.781 |
| 同步写调用 | 0.822 | 7.405 |
| 关闭 | 1.274 | 8.040 |
| 重命名 | 1.320 | 30.850 |

这些是调用墙钟时间，包含系统等待／调度，不能把重命名的 31 ms 全部解释为文件系统实际计算，或保证换存储能省掉 31 ms。

## 参数选择

| 项目 | 当前有效值 | 本轮建议与依据 |
|---|---|---|
| 委员／门槛 | 4／3，容忍 1 故障 | 保留 |
| 提案超时 | 3 s，递增 500 ms | 保留；当前没有触发 |
| prevote／precommit 超时 | 各 1 s，递增 500 ms | 保留；不是每块必等的延迟 |
| TimeoutCommit | 100 ms | 暂保留，存储改善后再独立评估 |
| SkipTimeoutCommit | false | 不作为首修；提前推进分支要求收齐 4 票，不是收到 3 票就跳过 |
| 空闲出块 | false，间隔 0 | 保留按需推进，仍允许必要证明块 |
| P2P flush／gossip | 实验配置 10／10 ms | 保留数值，另评估队列排空立即 flush |
| queryMaj23 | 2 s | 不动；不是当前正常第 0 轮完成的主因 |
| MaxBytes／MaxGas | 21 MiB／-1 | 不扩大、不设每块固定笔数 |
| mempool | flood，5000 条，1 GiB，cache 10000，recheck=true | 暂不扩容／关闭检查；未发现容量筛选导致等待 |
| P2P 收发上限 | 各 5,120,000 B/s | 本轮不再盲目增大，既有诊断没有节流等待证据 |

`TimeoutCommit` 从进入 Commit 的时间起算，保存工作会消耗这段时间；不是落盘之后还固定等 100 ms。重新分析 `admission-wait-2026-09-21` 探针日志，取每个业务高度之后 H+1 的 NewHeight 定时：100 TPS 共 80 个节点／高度样本，只有 1 个剩余正等待 4.082 ms，其余均已到期；非负剩余均值仅 0.051 ms。单笔 4 个样本均值 8.022 ms。该值是调度时的定时余量，不包括后续线程调度延迟，不能代表所有实验的固定收益上限。

## 实现候选的最小边界

**A：优化 FilePV 保存。** 保留原签名和 CheckHRS 逻辑，只更换最新签名状态的保存后端，优先评估已有 KV 库的同步事务，避免逐票创建／重命名文件。不异步发布签名，不删除 WAL，不自研日志系统。必须完整保存高度、轮次、步骤、SignBytes、Signature；相同 H/R/S 的签名重用、冲突拒绝和失败后禁止继续签名都保持。

与 GPT 评审后，第一候选具体定为每委员独立的小型 GoLevelDB，复用现有依赖，以同步写保存一条 `latestSignState`；不挂在业务 bbolt／Group 的写锁上。私钥文件、签名算法不变，仍在签名对外返回前完成保存。数据库绑定链与验证者身份，已有身份缺失记录不能自动初始化或回退到过期 JSON。首轮只在独立实验目录对照，不直接切换运行中的节点。原 `saveSigned` 先更新内存再保存，保存失败不能改成允许继续运行的普通错误，避免下一次误复用未可靠保存的内存签名。

**B：发送队列排空即刷新。** `MConnection.sendRoutine` 当前在队列排空后仍可能等 flushTimer。候选仅在本轮成功排空且缓冲非空时即时 flush；有积压时保持现有批量／定时刷新。需要区分“队列空”和写入失败，保持原连接错误处理。它可能增加 socket 写次数，不能把既有 Send→Receive 的全部耗时算成可消除的定时等待。

**C：块间等待参数。** A/B 改善以后若正剩余定时明显，再单独比较更短 TimeoutCommit。现在不把它作为高负载增量的主修复。

**D：接收侧解耦／并行冷验证。** 目前同步 mempool Receive→CheckTx 确有同连接阻塞的可能，但缺少它拖住关键共识消息的证据。暂不新增队列或自管 mempool；并行冷验证仍是后续目标负载下的候选。

## 验收边界

候选一次改一个，用原单笔和 100 TPS／10 秒条件对照；先确认真实块周期、接纳→提案、提案→执行改善，再看快速到账和停发排空。必要同步、验签、交易内容和硬件条件相同。记录实际成功提交、四委员状态、失败和未完成量，不能只看一个函数的耗时。

A 需覆盖同 H/R/S 重用、冲突拒绝、保存失败、重启加载最新记录及旧状态迁移；B 需覆盖空队列及时刷新、积压下有界批量、写失败和停止行为。保留原方式可对照，不同时叠加参数调整。

最终顺序：A 的隔离实现与验证 → B 的独立对照 → 改善后再看 C；D 暂缓。A 先保留旧 JSON 后端供新实验目录对照，正常节点的迁移在候选确认有效后单独处理。额外核对一委员失联时继续推进、停发后的必要证明块收尾。GPT 第一轮评审支持这一优先级，明确未复跑本分支，收益仍待实现后的对照确定。

第二轮补充文件操作分解和 80 个定时余量样本后，GPT 确认无实质反对，继续支持 A 先行、B 独立对照、C 暂不动；强调以整段签署保存、真实块周期和两段长等待改善为验收，不以重命名调用消失作为成功标准。本文采纳该意见。
