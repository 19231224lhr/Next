# 面向持续 1,000 TPS 的委员会架构评审

日期：2026-09-21。状态：代码与已有实验的设计评审，尚未完成 1,000 TPS 验收；本轮未修改共识或运行参数。

后续优先级更新：按用户要求，先针对单笔到 100 TPS 已暴露的延迟开展具体优化，不以 1,000 TPS 容量测试为前置条件。当前实施候选与参数依据见 [共识优化评审](committee-consensus-optimization-2026-09-21.md)。本文保留为后续目标容量验收参考。

## 目标与结论

委员会的目标明确为：对指定硬件、网络和付款负载，持续完成每秒 1,000 笔唯一、业务执行成功的付款，且积压不持续增长。
快速 TXCer 到账仍由担保组织独立完成；公共结算速度用于保障后台持续跟上、额度周转和长期运行。

当前采用四委员、三票门槛、CometBFT 排序、确定性业务执行及块级提交。没有证据说明此协议必然达不到 1,000 TPS；也没有实验证据证明现有实现已经达到。
目标负载的容量预算和独立委员会测量作为后续验收；当前先修复已定位的共识存储／推进成本。

## 已核对的实现

本地与 Mac 的 main.go、app.go、direct.go、precheck.go 内容摘要一致；核对的是当前工作树，不只是 GitHub 已提交版本。

| 项目 | 当前实现 | 对目标的含义 |
|---|---|---|
| 块容量 | 默认 22,020,096 bytes（21 MiB），MaxGas=-1 | 不是每块几十笔的限制；本轮没有扩容理由 |
| mempool | flood，5,000 条、1 GiB 总字节、单笔 1 MiB | 是有界缓冲，不是吞吐保证；堵塞时扩大它只能延迟暴露问题 |
| 委员通信 | 实验 flush/gossip 10/10 ms；5,120,000 bytes/s 限额 | 目标档需量流量与真实限速，不根据原始付款字节单独判断够用 |
| 初次验证 | HTTP/peer 入池走 CheckTx，local ABCI 共享锁 | 冷验证尚未形成独立有界并行流水 |
| 验证缓存 | 精确公开字节＋固定规则，2,048 条/8 MiB | 已避免后续完整重验；高负载需观察淘汰和重复冷验 |
| 执行 | Finalize 在 Overlay 中按块序处理，Commit 一次业务数据库事务 | 保留简单单写执行；没有证据需要并行改余额和消费状态 |
| 共识持久化 | FilePV、WAL、BlockStore、结果、应用状态及共识状态 | 职责不同，不能以轻量为由统一删除或提前确认 |
| 可替换边界 | 业务 Engine 与 ABCI 分开；VerifiedBlock 已抽取部分通用结果 | 区块认证、跟块和历史修订仍与 Comet 耦合，尚非任意后端即插即用 |

主要代码：`cmd/committee/main.go`、`internal/committee/{app,direct,precheck}.go`、`finality/block.go`、`internal/blockfollow/follow.go`、`third_party/cometbft`。

## 容量预算：区分计算与实测

上一轮普通独立 UTXO 付款的公开封装为 2,378 bytes。1,000 TPS 原始付款流量约 2.378 MB/s。
如果实际稳定块周期为 0.5 s，平均每块需要成功处理 500 笔，约 1.189 MB 付款正文。
这小于当前块上限，但不是达标证明：更大的块会增加传播、验证、执行和落盘时间。

目标关系是 `成功付款数 B / 实测完整块周期 T(B) >= 1,000/s`，并为波动保留余量。
不能只看最大块字节，也不能只把超时参数改为某个数。
flood 转播、提案再次发送、共识票、客户端跟块和协议封装都另占资源。
上一轮广播探针对 1,001 笔（含预热）记录全网 9,008 次交易 Send，约每笔 9 次；重复到达多数由池去重，不等于每笔完整验签 9 次。
若此传播倍率维持到目标档，仅交易广播正文的全网合计就约 21.4 MB/s，提案等另计。这个数不是单连接带宽，不能直接与每连接 5.12 MB/s 限额相比；它说明需要量真实传播倍率，而不能只看 2.378 MB/s 的原始输入。

原 100 TPS 测试的块只有 1～74 笔，不表示容量只有约 100 TPS：输入本来只有每秒 100 笔。
两轮真实取池探针中，每轮 1,000 笔都在首次实际可用的取池机会入块。
此前接纳到提案的长等待主要是前一高度剩余周期，不是块满后连续落选。

新核对的冷验证数据：每委员 1,001 次，均值约 0.64～0.68 ms；每委员总验证调用 5,125～5,346 次，命中缓存约 0.00145 ms，淘汰为零。
这不能解读为完整验签做了五遍。若粗略保持原冷验证耗时，1,000 次/s 已占串行路径约 640～680 ms/s，余量值得关注；这只是预算推算，不是目标负载实测或 CPU 占用率。

## 推荐路线

**先保留当前 BFT，测出委员会本身的容量，再补确实限制容量的实现。**

1. 委员会独立容量测试：提前生成合法、组织认证完整的独立付款，以开环速率直接提交现有公开入口；真实四委员、验签、账本执行与同步持久化全部保留。预生成、发送、接纳、执行成功分别计数，不将 HTTP 202 当结算。
2. 再测带组织、钱包及跟块的完整系统。委员会通过不等于端到端通过。两种部署分别报告，不能把移走八成员等带来的共享磁盘减负称为代码优化。
3. 目标档出现验证饱和才落实有界并行冷预检：复用现有验证和缓存，覆盖 HTTP、peer、提案缺失缓存等入口；已有同字节工作可复用。余额/消费/责任仍按块序复核。只把 HTTP 工作搬出去而 peer 路径继续串行，不算完成设计中的并行预检。
4. 按实际瓶颈处理传播和块级保存。优先复用原生批量写、已存在的缓存与公开块读取，减少确实重复的处理。保留签名前持久化和业务提交顺序。

并行预检是当前设计与实现的缺口，但不是凭空承诺收益的必做大重构；实现位置与并发数由目标档的瓶颈决定。
在 CheckTx 内启动 worker 后仍持全局锁等待，不会形成跨请求并行；仅换每连接锁也不会让同一 mempool 连接并行。
批内验证结果应按原序直接复用于执行，不能仅塞回全局 FIFO 缓存后逐笔重新查找，以免大块驱逐自身尚待执行的材料。
缓存未命中仍执行等价验证；不能因某节点本地队列满、缓存未命中或预检尚未完成而改变对同一提案的有效性判断。
缓存容量、Recheck、带宽和块大小都应由目标负载证据决定，不一次性全部调大或关闭。

不增加为了凑够固定笔数而等待的合批定时器。高负载利用已有待办自然组块，低负载保持及时推进。

## 验收安排

- 基础负载：有效组织认证、独立已最终 UTXO、足额本金及 FUEL；输入/输出数、单笔字节、组织数、签名数固定并记录。
- 预生成只排除发送端材料准备，不能提前把测量付款放入委员会验证缓存。独立测试不运行成员核销时，签署预算、费用和工作授权必须覆盖整批，不能假设未运行的周转已返还额度。
- 初筛：100/250/500/750/1,000 请求每秒，各跑约 60 秒。目标档再预热后持续至少 300 秒，并做重复轮；不是只发送 1,000 笔就宣称 1,000 TPS。
- 每秒采集计划发送、实际发送、接纳、成功提交、拒收/失败/重试、未完成数和最老年龄。报告稳定窗口成功业务 TPS、延迟 P50/P95/P99、块周期/字节、首次可用机会入块率、缓存冷验率、队列斜率和停止发送后的排空。
- 生成器必须实际达到计划速率。若发送受限或输入不足，该轮是负载未达标；不能用实际发送较少掩盖服务端能力问题。
- 正确性：真实成功交易去重计数；四委员状态、金额/费用一致，最终全部审计，重复封装、无效命令和空块不算 TPS。
- 目标验证后再补未最终 TXCer 输入、跨组织连续续花、多输入和赔付混合负载，分别给出能力，不把普通独立输入结果代表全部业务。
- 完整系统长测还需覆盖费用真实补回、签署权限多次周转；委员会独立预生成负载不替代这项验收。
- 一委员失联/重启作为独立可用性场景报告；不默认为故障期间也已证明 1,000 TPS。
- 单 Mac 的四委员容量与 14 进程端到端容量先分开测。多机结果以后另报；共享 SSD、CPU 的诊断不能直接外推独立服务器部署。

## 后续共识区接口的实际边界

保留现有模块，先明确三个契约，不新增只有一个实现的通用框架：

1. **提交契约**：同一规范付款字节的提交与重试；接纳不等于最终确认。
2. **执行契约**：认证的有序批次及确定的高度/时间上下文，驱动相同 Engine/Overlay 规则，提交结果和状态承诺。
3. **读取契约**：按高度读取可独立验证的交易、执行结果及最终性材料，供钱包和组织自行跟块。

`finality.VerifiedBlock` 可作为复用点；原始 Comet Block/SignedHeader 的验证继续留在对应后端。
当前结果由后续高度认证会增加观察延迟；持续有业务时后续业务块也可承担认证，并不是必须每笔或每个业务块额外插入一个空块。
历史输入修订还涉及稳定交易/区块身份、分片承诺、授权修订、原始版本重放及追块；未来共识区必须支持等价契约，不能只替换排序接口就宣称迁移完成。

## 其他路线与切换条件

| 路线 | 判断 |
|---|---|
| 保留 Comet，补容量验收和必要流水/批量实现 | 推荐。复用已通过的交易、赔付、历史修订与跟块规则 |
| 应用自管交易池/批次，改变传播与提案组织 | 仅在现有池/传播成为实测主瓶颈时评估；会增加待办、传播和提案一致性职责 |
| 替换成熟 BFT 或自研共识内核 | 当前证据不足；迁移包括最终性和历史修订，不只是更快投票 |

若独立委员会在目标硬件下仍达不到目标，且已排除压测器、前台资源竞争、冷验证和可避免的存储/传播开销，剩余瓶颈确实是当前共识推进结构，再进行同安全条件的新后端对照。
固定四委员不意味着可以退化成单节点排序确认；维持最多一故障和三票门槛。

## 与 GPT 的评审结论

已分享当前实现片段、配置、验签缓存统计和之前的取池/持久化实验。GPT 同意先补容量模型和验收，不支持据 100 TPS 运行结果直接更换共识。
它另外提醒：500 笔/0.5 秒只是一个候选运行点；全局 FIFO 缓存不能代替批内结果复用；目标压测必须保留真实认证及预算覆盖。
GPT 阅读的公开代码为 `a5987b0`，当前工作树变化及运行数据由本次本地/Mac 核对提供，不能把公开旧版本评审当作当前分支的完整代码审查。
第二轮对上述最小路线完成复核：同意不预设固定 500 笔一块或合批等待；准备不能预热全部验证缓存，预算须覆盖整批；以稳态成功应用 Commit 和队列趋势验收，不能用停发后才补齐作为达标依据。
