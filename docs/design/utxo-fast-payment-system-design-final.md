## 1. 系统要交付什么

组织用户提交一次签名付款，由付款方的服务组织并行认证并签发标准 TXCer；其他组织依据缓存的发行节点信息验签后接收，其用户可继续付款。原担保责任始终由原组织承担。散户无需加入组织，直接向委员会提交普通 UTXO 交易，等待最终确认，不生成或使用 TXCer。两种方式共用同一公共 UTXO 账本，没有支付域、资产兑换或用户退出操作。

**前台转移可执行的支付权利，后台把同一权利落实为公共状态；转手不复制本金，结算不重新付款，核销不凭空补钱。**

本设计整合三份基础文档，并具体化它们之间尚未闭合的接口：

### 1.1 首版的确定选择

| 关注点 | 采用的设计 | 明确的代价 |
|---|---|---|
| 快速到账 | 一轮并行取得三份持久批准形成 SpendQC，钱包保存后可续花 | 后台 INSTALL 及结算仍须完成；证书传播前不承诺组织独立恢复 |
| 高吞吐 | 独立 UTXO 并行、Worker 私有额度、验签与持久提交流水 | 热输入仍串行，日志与带宽仍有上限 |
| 资金利用 | 真实最终资金直接支撑，已有根担保不随转手重复占用 | 按条款需备付的未落实根整体履行 |
| 持续运行 | 资金、费用和未完成工作分别核销 | 后台、证明与补资能力决定持续容量 |
| 可用性 | 任意持证者可补交，已有承诺有专用推进容量 | 完整证书未传播且持证者均离线时可能等待；不能靠超时撤销支付 |
| 实现规模 | 不同组织直接互通，散户直接提交委员会，单写者结算 | 固定成员配置，不运行任意合约 |

文中的 DAG 是交易输入输出形成的**有向无环依赖图**：先有父输出，再有消费它的子交易。它用于后台确定执行先后，不是另一套共识，也不要求每次续花等待公共结算。

## 2. 最小系统边界

首版使用一个转账区公共账本、固定四成员委员会，以及一个或多个固定四成员担保组织。每组容忍最多一个拜占庭成员，认证阈值为三个；不同组的故障假设分别成立。成员应有独立密钥、存储和故障域，四个进程不等于四个独立信任主体。

用户归属与原担保责任分别记录：付款方服务组织认证本次交易，收款方可属于任何组织，也可为散户。不同发行组织的凭证可以成为同一用户一笔付款的输入；不要求兑换、重新担保或支付额外的跨组织手续费。正常 FUEL 交易费用仍按统一规则支付，跨组织不会减少 CAL 本金。

`CertifierOrgID` 标识本次 TXCer 的签发组织，`GuarantorOrgID` 标识某项根义务的原责任组织，输出的 `SpendOrg` 仅指定下一次消费的处理方。这三个角色不能混用。更换收款人及其服务组织不会改写既有根的责任组织。输入排他按不可变输出身份执行，签名有效性与当前未消费性分别检查。

首版只实现支付、拆分、合并、费用与资金管理，不运行任意用户合约。金额使用有溢出检查的整数最小单位；编码、哈希领域、配置版本和费用规则固定。

委员会账本是首版资金与权利的最终性来源。接入其他链时，必须另行定义托管、最终性验证和回款适配；组织签名不能替代外链实际到账。基础密码学、诚实节点持久状态、数据可取得和委员会最终能够推进是服务条件。

## 3. 架构与快慢两种付款方式

```text
付款钱包 → 网关广播 → 四个独立成员并行验证
                         ↓
          PREPARE：锁输入、占额度、保存正文/父证据/效果
                         ↓ 同步提交后返回 SpendVote
                  收集三个匹配签名 → SpendQC
                         ↓
                  TXCer → 钱包保存 → 下一笔付款
                         │ 完整证书可靠传播（不等安装回执）
                   ┌─────┴─────┐
                   ↓           ↓
             组织后台 INSTALL   委员会登记/按依赖结算
                               并行预检 → CometBFT
                               单写执行 → 块末原子提交
                                      ↓
                         资金 / 消费终态 / 费用 / 累计核销
                                      ↓
                         最终证明 → 原占用成员 → Worker
```

**快速付款：** 组织用户→付款方组织→标准 TXCer→任意组织用户；后台进入委员会。**慢速付款：** 散户→委员会→最终 UTXO，不经过组织认证。组织用户向散户付款时，组织仍完成自己的认证及可靠提交，但散户钱包只以最终 UTXO 显示可用余额。充值、额度授权及维护不进入每笔付款的前台。

网关、收集器和中继可合并部署，减少网络跳数；其故障不改变认证事实。委员会和组织使用不同签名域。成员先提交存储、后发送认证，后台通知采用持久 outbox。

## 4. 统一 UTXO、本金支撑与跨组织消费

### 4.1 两类交易，不设资产进出操作

| 类型 | 输入与处理 | 收款完成 |
|---|---|---|
| `FAST_TRANSFER` | 组织用户用真实 UTXO 或合法 TXCer 输出，经本次服务组织一轮持久认证 | 组织收款钱包验证并保存标准 TXCer 后可续花；散户等待最终 UTXO |
| `DIRECT_TRANSFER` | 散户只用已最终 UTXO，直接提交委员会，执行位置检查消费状态 | 委员会最终确认，生成普通 UTXO 和最终证明，不产生 TXCer |

输入不存在时不提供垫资开户或入金申请先消费业务。CAL 本金按输入输出守恒，FUEL 独立支付费用。钱包负责选择发送路径，用户只操作“付款”。跨组织收款、向散户付款及散户向组织用户付款都是普通转账。

真实输入必须核验创建事实、所有者授权及本次合法消费处理方；历史创建证明不等于当前未花费。使用既有 TXCer 时按缓存的原组织配置核验完整认证及确切输出，不重放全部历史，不要求原组织逐笔在线确认凭证真假。消费排他由 §4.4 的唯一处理方完成。

首次形成需要组织覆盖的本金义务时绑定真实输入并足额占用 CAL；后继凭证只延续该资金链，不因转手、换组织或最终落账重新担保同一份本金。已获得确定真实资金支撑且排他消费的部分不再新增本金覆盖；每笔新交易仍承担自己的费用和工作额度。

### 4.2 一次根担保与一次资金落实

只有确实新增、由组织承担的本金义务才创建 `RootID` 和 `RootObligation`；已最终且消费路由固定给组织的 UTXO 直接支撑付款，`c_CAL=0`，不创建空根。已有合法未结根继续按原批准条款履行，后继凭证沿用原根责任。根记录绑定原始真实输入、根本金金额、不可变 GuarantorOrgID、责任条款、回款目的地与原批准事实。CertifierOrgID 随后继交易变化时不得改写任何已有根的责任组织。新根的 GuarantorOrgID 必须是实际认证该根并提供覆盖的组织；不能指定另一组织承担新债。原批准成员按根金额占用 CAL 权限。

组织对规范 `SourceID` 建立跨授权版本的排他根索引，不能靠更换 TxID/RootID 给相同来源反复建立本组织担保。来源到账只凭可验证的真实入款，且来源最终支付目的必须与根签发或回收条款匹配。同一真实输入还须服从其消费权威的唯一消费裁决。

SourceID 从原始真实 UTXO 的网络、资产及 Outpoint 规范化派生，不使用本次请求 nonce 或可变证据封装代替。有效根建立后的 `SourceID→RootID` 关联跨版本保留；仅有局部批准而未成立的候选继续保留临时来源锁；本版不启用候选取消，不得超时释放。FundRoot 在一个原子业务事务中核对或建立唯一来源关联、记录资金落实终态、扣转真实资金并创建根输出。关联已存在时只能推进同一个根，不得另建第二个根兑现。迟到回款同样按真实入款身份防重，不能既回补垫付又计入自由充值和新 Grant。

根关联的作用域为原担保组织，即 `(GuarantorOrgID,SourceID)→RootID`；真实来源输出及实际入款则遵守全账本唯一消费和分配。不能用一个组织的本地排他索引宣称所有组织共同排他，也不能将同一笔真实入款落实或回收两次。不同发行组织的根保留各自责任，后台按实际依赖分别落实。

后继交易只消费父输出、产生等额子输出。根担保保护这一批价值，不为每一代持有人分别承诺一份新增本金赔偿。转手本身不能使根责任解除。

首次公共资金落实对根整体执行 `FundRoot`，只有两条互斥分支：

1. 来源资金已经最终可用：消费确切来源资金并落实根对应的公共 UTXO，根记录进入 `FUNDED_BY_SOURCE`，永久解除对应组织责任。
2. 原条款规定的备付条件已满足且来源资金尚不可用：从原组织覆盖支付根完整金额并落实相同公共 UTXO，进入 `FUNDED_BY_RESERVE`。未来责任归零，但已实际垫付仍占用签署权限；后续真实来源款进入原垫付回收路径。

委员会已能直接使用合法来源时选择 SOURCE；缺少来源材料只记 DEFERRED，不能把缓存未命中或取证超时当成 RESERVE 资格。已有义务不因本轮规则简化自动解除，也不凭空引入未成立入金授信。

两个分支共用唯一 `RootFundingID`。根一旦获得足额支撑，后继只转移已落实资金，不再次调用组织备付。首版不做根的部分垫付，避免逐份额责任谱系；较大根的整体垫付成本通过根本金金额上限、预拆分和定价控制。

两条分支落实的都是根 TXCer 已指定的同一组 OutputID，不另发一组“赔付款”输出。公开父输出后再消费到子输出，是同一权利的公共投影，不能让父持有人再次提取。任何人可以携完整根 READY 和原授权触发 FundRoot；原条款明确允许在原输入资金尚未完成公共落实时整体垫付，而非等待无法证明的“永久失败”。

凭证输出与最终 UTXO 是同一输出的两个阶段，沿用同一 OutputID；最终结算补齐资金事实，不给持有人另发第二份余额。用户资金不成为组织自由余额，也不集中到一个全局共享资金池。

### 4.3 拆分、合并与数据大小

快速交易按 CAL 输入输出守恒执行。付款人收到的不同组织凭证可直接拆分、合并；这些输出均按付款人收款描述指定的服务组织处理。输出引用直接父输入，认证整个交易；每次转手不携带不断增长的“全部根份额向量”。

组织成员验证有效父 TXCer 及其所属规则，按认证链的归纳关系确认输出成立；公共结算则取得尚未登记的必要祖先，按拓扑顺序验证到已落实的公共输入。历史已经结算的边界提供公共状态证明，后继从这个边界继续处理。

签发阶段设置输入输出数、单笔证据大小、未结算依赖深度及待完成工作量上限。到达边界时优先结算该依赖链，再继续新签发。一个根可以被很多独立输出共享，根状态是只读依赖；只有首次资金落实及回款修改根账目，不把每笔转手集中到根锁上。

具体做法是在认证结果中携带未结算深度和保守工作上界：深度取父节点最大值加一，工作上界取本笔工作加各未最终父节点上界之和。共同祖先重复计入只会保守限流；后台实际处理按身份去重。以公共 SETTLED 证明为边界可截断上界，仅有 REGISTERED 证明不能截断。交易正文固定本次采用的边界引用与规则，成员不能用各自最新缓存重新算出不同的 EffectsHash。冷启动缺少材料时先同步再准入，不将无界恢复藏进单笔低延迟承诺。

### 4.4 收款描述和输入消费路由

收款人确认的 `ReceiveDescriptor=(OwnerLock, SpendOrg)` 随地址或收款码提供；`SpendOrg` 编码为 `ORG(OrgID)` 或 `COMMITTEE` 的带标签联合类型。描述绑定网络和协议版本，由所有者签名确认，组织地址引用受信组织配置。收款描述可预先发布并长期复用，不要求收款人逐笔在线批准。付款签名及 TXCer 覆盖完整输出，付款方不能替换收款人的处理组织。

- 组织输出：FAST_TRANSFER 的全部本金及自付费用输入都必须指定本次 CertifierOrgID 为 SpendOrg，由该组织一次原子认证。甲向乙付款时甲签发，输出写乙的收款描述；乙之后认证该输出的消费。甲不再处理该输出的后继排他，但甲既有根责任不变。
- 散户输出：SpendOrg 为 COMMITTEE，只有最终成为 UTXO 后才能直接提交委员会消费；不能把尚未最终的 TXCer 当作散户输入。
- 委员会也执行相同路由条件：组织输出不能用裸用户签名绕过组织认证；最终落账不会将它自动改为 COMMITTEE。凭证态与最终态共用 OutputID 和消费墓碑。
- 来自甲、丙等不同发行组织、支付给同一个乙组织收款描述的输出，由乙一次原子消费，不增加跨组织交接轮次。不会让多个组织同时独立批准同一个输入。

创建钱包只需本地生成密钥。选择组织后使用该组织的收款描述，后续收款自然由该组织服务；散户使用 COMMITTEE 描述。已有散户 UTXO 不因修改钱包设置就改变消费条件：可以在一次普通 DirectTransfer 中付给任何组织用户，也可批量付给本人的组织收款描述，最终后使用快路径。已有组织输出同理通过原处理组织认证的普通付款产生新输出，不原地修改 SpendOrg；原根担保不迁移。这不是每笔跨组织付款的前置步骤，不设置专门的进入、退出或兑换命令。

组织服务暂不可用时可以继续查询与结算已有有效凭证；不能仅凭超时让其他组织改签同一个输入。复杂故障恢复仍不在首版实现范围。

### 4.5 首次通信保存配置，后续本地验签

首次通信交换组织 ID、节点地址、公钥、成员索引、阈值、纪元和配置摘要。组织身份及公钥以创世信任配置或委员会认证的组织登记为依据，验证后缓存；后续不逐笔请求委员会或原组织批准。

验证外部 TXCer 时按该父交易自己的 CertifierOrgID 和历史配置检查完整 SpendQC，不能误用本次付款组织或根担保人的公钥；同时检查不同成员签名数量、网络/规则/配置及输出绑定。有效后保存父输出事实，下一笔按该输出 SpendOrg 处理。同组织、跨组织使用同一种证书和同一种金额规则。初次取配置、网络距离与缓存会影响实际耗时，但不造成 CAL 兑换损耗或跨组织专属费用。

### 4.6 散户直接付款

散户向委员会 `POST /direct-transactions` 提交已签名的 DIRECT_TRANSFER；也可经普通转发网关投递，网关不认证付款。委员会并行预检，在共识执行位置核对最终 UTXO、COMMITTEE 路由、授权和当前未消费状态，一次原子提交本金、最终 FUEL 费用输入、收款及找零。

慢交易 FeeTerms 绑定 `OWNER_FINAL_UTXO、FeeRuleID、Fmax、确切 FeeInputs、ChangeTerms`，实际费用不得超过已签上限，找零归属和输出身份确定。输出收款人选择组织不会把付款方改成组织代付。

慢交易不创建 SpendQC、TXCer、组织本金/FUEL 占用或组织服务奖励，只支付其实际公共处理费用。接入成功显示“处理中”；取得最终证明后显示“已到账”。散户向组织描述付款后，收款人可用最终输出开始快转；组织用户向散户付款后，散户只认最终输出，不承担凭证续花操作。

## 5. TXCer、身份与状态

```text
TxBody
  NetworkID, ProtocolVersion, IntentID, TxKind
  TxKind=FAST_TRANSFER 时：CertifierOrgID, CertifierEpoch, OrgConfigHash
  Inputs[], Outputs[OwnerLock, SpendOrg, AssetID, Amount]
  快路径另带：RootTerms?, DependencyAnchors[]
  FeeTerms, RuleIDs；快路径另带 AdmissionRefs[], WorkLimit

IntentID      = H("INTENT", NetworkID, SubjectID, UserNonce)
RootID        = H("ROOT", NetworkID, GuarantorOrgID, SubjectID, RootNonce)
TxID          = H(CanonicalTxBody)
OutputID      = H("OUTPUT", NetworkID, TxID, OutputIndex)
AdmissionVector = (c_CAL, c_FUEL, E, B, ApplicablePolicyCosts[])
EffectsHash  = H(CanonicalCertifiedEffects)
SpendFactID  = H("SPEND", TxID, AdmissionVector, EffectsHash, RuleIDs)
FeeID         = H("FEE", TxID, FeeTermsHash)
ActionID      = H(NetworkID, BusinessID, ActionKind, ActionIndex)

OwnerAuth = required owners' signatures over domain-separated TxID
TXCer = TxBody + OwnerAuth + AdmissionVector + CertifiedEffects + SpendQC + OutputReference

RootRecord
  RootID, SourceID, SourceOutpoint, RootOutputs[]
  OriginalSpendFactID, Amount, GuarantorOrgID, CALAuthorization
  FundingState, RootFundingID, SourceReceiptID?, RecoveryDestination

WorkRecord
  SpendFactID, WorkPolicyID
  ReservedExecutionByStage[], CompletedExecutionByStage[], ReservedBytes
  Revision, FinalStateReference, CustodyTransferReference?
```

`SpendVote` 在 SPEND 用途域签署 SpendFactID；TxID 已绑定网络、协议版本、本次组织、纪元及配置。CertifiedEffects 固定输入消费、输出、根/费用/工作义务和依赖计量，认证的是权利与承诺而非宣称公共扣款或根资金已落实，不含自身 SpendFactID、签名、成员本地状态或收集器。签名集合、收集器身份和重传次数不进入业务身份；同一完整事实的有效签名子集可以互换。

`AdmissionRefs` 引用适用的 CAL、FUEL、工作及主体政策授权；`AdmissionVector` 包含本笔所有准入占用，成员认证同一个完整向量。Worker 本地编号和余额不进入它。用户签名覆盖规范 TxID，签名本身置于正文之外，避免哈希自引用；委员会取得并核验原始用户授权。多输入涉及多个所有者时须提供全部必要授权。

输出 ID 和费用 ID 在正文哈希后派生；正文不反向嵌入自身派生 ID。相同 `IntentID` 不得因超时更换正文；本版没有候选作废接口，仍按原身份重传或查询。

RootID 在原输入的付款交易构造前由独立 nonce 确定，因此该交易可以把它写入资金目的；避免“源交易哈希依赖 RootID，而 RootID 又依赖含源哈希的 TxID”的循环。RootID、SourceID 和不可变根条款共同被批准并排他保存，不能复用一个根身份更换金额或受益输出。

状态分别描述不同事实：

| 对象 | 状态 |
|---|---|
| 快速交易 | `COLLECTING → READY`，READY 以完整 SpendQC 为据；单成员另记 APPROVED_LOCAL，不能单独续花 |
| 本地安装 | `NOT_INSTALLED → INSTALLED`；只表示本节点已保存完整证书及结果，不是第二张支付证书 |
| 公共处理 | 快路径 `REGISTERED → SETTLED`，缺依赖 DEFERRED；散户 `SUBMITTED → FINALIZED / REJECTED`，不经过 READY |
| 输入 | `OPEN → CONSUMED_BY(TxID)`；局部准备锁另记，快慢路径共用输入身份 |
| 根资金 | `PENDING → FUNDED_BY_SOURCE` 或 `PENDING → FUNDED_BY_RESERVE` |
| 预算 | 长期 `ACTIVE`，同版本增量授权与核销；异常停签保留占用，本版不启用退役释放 |
| 费用 | 快路径 `RESERVED → ESCROWED → PARTLY_PAID → CLOSED`；散户成功执行时一次计费并关闭 |

TXCer 证明某输出合法形成，不证明它在任意时刻仍未花费。收款人必须是本笔认证输出指定的所有者；每次消费均由该输出 SpendOrg 指定的组织或委员会处理。

DIRECT_TRANSFER 直接产生最终 UTXO 与证明，不产生组织 READY。FAST_TRANSFER 先产生凭证，再把同一 OutputID 落实为公共 UTXO。组织钱包可使用这两种创建事实；散户钱包只使用最终 UTXO。

最小接口统一为：委员会散户入口 `POST /direct-transactions`、组织配置查询 `GET /organizations/{orgid}/configs/{hash}`；组织 `POST /transactions`、`POST /certificates`、`GET /txcers/{id}`；委员会 `POST /commands` 接收登记/结算批、FundRoot、真实回款和充值授权；恢复/退役释放命令返回 UNSUPPORTED；双方提供 `GET /outcomes/{id}`、`GET /receipts/{fact_id}` 及有游标的事件流。返回业务事实、证据和本地观察状态，事件通知本身不授权额度变化。

钱包先持久保存已签正文与 IntentID，再发送；超时后查询或重发同一正文。`UNKNOWN` 只表示该节点尚未观察到结果，不能据此换一个身份再付。组织快收款显示“可继续支付”须以钱包验证并持久保存完整 TXCer 及传播待办为准，不等 INSTALL_ACK；散户及直接交易收款以最终 UTXO 证明为准；缺少证据时显示“处理中”，不能用网关接收成功替代到账。

## 6. 一轮取证，后台 INSTALL

1. **接入与并行验证。** 网关广播完整签名交易。成员独立核对所有者授权、输入 SpendOrg、有效父 SpendQC 或最终创建证明、输入排他、金额、费用及工作界限，计算相同 AdmissionVector 和 CertifiedEffects。
2. **PREPARE 与签票。** Worker 在同一原子事务中复核输入和完整资源向量，保存正文、用户授权、必要直接父证书/最终边界、确切效果、输入锁、原预算占用、签署意图及 outbox；同步提交后返回 SpendVote。这里只保存候选，不凭一票把本笔输出开放使用。PREPARE 保留为内部操作名，其签名语义已升级为完整支付事实。
3. **组证与交付。** 收集器取得三个不同成员对同一 SpendFactID 的有效签名，形成并验证 SpendQC 和标准 TXCer 后立即交付，网关本地保存与传播待办在后台处理，不阻塞返回。钱包验证并持久保存证书及可靠传播待办后即可续花；不等待第四票或 INSTALL 回执。
4. **并行后台推进。** 网关响应已经发出而其后台保存未完成时若失联，收款钱包以已持久保存的完整证书独立补交；尚未取得并保存完整证书不得报告到账。钱包重新上线继续原待办，不清除未决锁或额度。收集器、收款钱包及持证成员可向发行组织提交完整证书，同时向委员会提交登记/结算请求。INSTALL 验证 SpendQC 后幂等保存完整证书、输入消费终态、输出及待办，持久完成后返回普通 INSTALL_ACK；委员会独立验真并按依赖处理，不等待组织安装或 ACK 数量。未参与批准的安装成员不补扣预算，也不领取不存在的原占用返还。

同一输入始终由其 SpendOrg 的固定成员组裁决。四成员中任意两个三票集合至少交叠两个成员，其中至少一个诚实；诚实成员持久保留原签署、拒绝冲突签票，因而不能形成两张冲突 SpendQC。这一交集论证保证唯一性，不保证局部票一定能形成证书或后台一定可取证。

首版采用普通独立签名与成员位图。锁内不做网络请求；同成员的读—检查—写保持隔离，不同成员和不同交易独立流水。机会式组提交只合并已到达请求，限制笔数、字节和处理时间，不设置凑批等待。签名必须等自身批准事务持久成功，后台化不减少这一要求。

### 6.1 父凭证直接续花与本地验证复用

每个成员独立保存 VerifiedParent，绑定父 SpendFactID、确切输出、发行组织历史配置与规则。缓存只复用已经完整验证的不可变事实，不缓存“尚未消费”的结论；新付款仍检查本笔用户授权、当前输入状态和所有资源。

父交易尚未在本节点 INSTALL 时，收到完整父证书即可导入其合法输出，并在批准子交易的同一事务保存父材料、标记子输入占用及父证书转交待办。导入必须重查所有 OutputID 的消费状态：创建与消费分键，迟到父安装不复活已花输出。同组织可合并父安装和子批准；跨组织只导入父证据/输出事实，不产生原发行者的预算占用或核销资格，也不联系父组织再做一次授权。

单份 SpendVote、候选输出或安装 ACK 均不能代替完整父 SpendQC。有效证书认证确切输出、费用/工作和有界依赖；本笔验证直接父，后台按已最终边界补齐必要祖先。前台不重放整条历史，但成员签名前必须保存其已使用的直接父材料，后继签发同时为父证书提供新的保存与转交路径。

只参与局部批准而尚未看到完整证书的成员，继续保留输入锁和原占用。若局部候选 U 与后来取得合法 SpendQC 的 T 冲突，输入裁决服从 T，但 U 的原占用不自动退还；安装 T 不是为 T 重新签一张冲突 SpendVote。已有公共完成事实先到时，后续 INSTALL 只补证据，不覆盖较新消费/核销状态。

### 6.2 证书传播、保管与可用性边界

收集器组证后在交付前保存完整证书和传播待办；收款钱包在报告可续花前也保存同一证书及待办。持证者可以相互独立重传，同一 SpendFactID 防重。成员收到子交易中的完整父证书时安排转交，避免依赖原收集器再次上线。签票记录也支持原票重传，但不保证在恶意成员隐匿签名且诚实成员分票时总能重建完整证书。

发行成员的 INSTALL 与委员会提交并行。安装 ACK 仅用于本次传输重试与本地安装观察，不构成公共最终性或额度释放依据。可靠公共投递的完成依据是委员会最终保管完整证书、必要材料及认证效果，并按工作表产生明确的 WorkCompleted/CustodyAllowed 事实；仅有 REGISTERED 状态或 FUEL 托管不够。该事实可替代已在工作表中规定的传播/安装同步义务，仅核销对应 E 阶段，不连带释放结算与收尾工作。未完成的逐成员推送随后由按需同步承担，不要求全员 ACK 才允许 FeeClose；同步成本仍有原计划/有限维护容量支持。本地占用成员仍完成自己的安全替代与持久交接后才能释放 B，不能因队列清理而释放资源。

成员在合法交接前保留正文、证据和任务。INSTALL 使用已预订的后台容量，不检查安装成员是否还有首次批准额度；容量考虑该组织所有可能成立的证书，以及子交易带来的父证据，不只按本成员投过票的数量配置。证明、核销和传播使用独立服务份额，限流新增不得阻断这些旧义务。

**交付保证的边界：** SpendQC 保证有效付款和防双花，不保证在钱包收到的瞬间已有三个成员保存完整证书。若传播前所有完整持证者均离线，后台可能等待，相关输入锁及额度继续保留。推进要求至少一个完整持证者最终重传、必要依赖可取、法定人数和委员会可用且调度公平；单有“委员会网络恢复”不足以弥补丢失的完整证书。已取得真实保管证明后，钱包无需持续在线。原第二阶段的交付时复制保证不再作为 READY 的含义。

两阶段只保留为隔离测试基线：在相同 SpendQC 上额外等待 q 个本地持久安装 ACK 后再向基准钱包交付，用于测量额外等待；该基线不是另一种线上凭证，也不声称提供已经实现的旧版退役恢复。默认客户端和公共规则只使用本版一轮证书。

## 7. 本金、费用与后台工作分别周转

本节的成员预算与工作预订用于 FAST_TRANSFER。DIRECT_TRANSFER 在委员会原子消费真实输入并支付实际费用，不创建这些组织占用。

### 7.1 CAL/FUEL 权限

两种资产使用同一组成员对完整向量签名，各自独立记账：

两项授权必须允许当前同一个组织成员配置处理该交易；配置不兼容则拒绝，不能拼接不同配置的票。本版固定成员，不提供在线配置迁移。

$$
\mathbf c(T)=(c_{CAL},c_{FUEL}),\quad
\eta=\frac{f+1}{2f+1},\quad
Q_i^a=\sum_{g\in Grants_a}\lfloor\eta Amount_g\rfloor.
$$

根担保占用 CAL，纯转手不新增 CAL 覆盖；组织代付占用 `Fmax` 的 FUEL。用户自付使用已最终锁定且可排他的 FUEL 输入，组织该项 FUEL 覆盖为零。首版不使用尚未落实的 FUEL 权利垫付费用，避免费用来源递归。

对每项原始占用 `c`，保持委员会 v1.1 的规则：

$$
c=Paid+Discharged+Remaining,\quad 0\le Returned\le Paid
$$

$$
Credit=Discharged+Returned,\quad
Residual=c-Credit=Paid-Returned+Remaining.
$$

只有永久解除的未来责任和真实回到相应覆盖的资金产生信用。实际垫付、实际 Gas 支出不能因“完成”而直接释放权限。新增充值与原支出补回必须选择唯一分类，同一入款不得同时恢复旧权限和产生新 Grant。

成员凭公共最终证明，仅对自己持久签过的事实应用 `max(0, Credit-AppliedCredit)`。原记录、防重、残余和 Worker 余额在同一事务提交。安装成员或观察成员只能同步状态。

统一处理框架不提供通用“交易完成、全部额度返还”操作。核销键至少包含原批准事实、资源类别、账户／政策、授权版本和适用阶段，各类返还遵守自己的上限与触发条件：

| 额度 | 可以恢复的依据 | 不构成恢复依据 |
|---|---|---|
| CAL 覆盖 | 永久解除本金责任，或真实回到原覆盖的回款 | 已垫付但未收回、权利转手、FUEL 尾款归属 |
| FUEL 覆盖 | 未用责任解除，或真实退款／补款回到原覆盖 | 外部钱包取得退款、仅完成工作 |
| E 执行工作 | 对应逻辑工作完成，或最终事实按工作表明确替代该项义务 | 仅收到登记事件而其余工作未做 |
| B 保留字节 | 获得合法交接依据，并完成本地安全替代与持久交接 | 仅有归档哈希、仅有 E 完成 |
| 商户累计限额 | 原政策允许的未用预留解除、退款或新授权 | 组织费用账户补款 |

核销与首次批准使用同一事实键串行化。成员已观察到该事实的公共处置后，只返回已有证据或进入同步路径，不再为它新建首次占用。历史压缩保留已消费输入、防重身份和累计核销检查点，避免“删记录后当新交易再扣、再退”。

各资产的本地恒等式为：

$$
Used_i^a+InFlight_i^a+\sum_jW_{ij}^a+Pool_i^a=Q_i^a.
$$

Worker 先使用私有额度，低水位时异步补充；闲置额度经过安全点和代际核对后调配。原 Worker 已退出时，核销返还公共池。正常交易不更新一个全局共享余额计数器。

调配只移动同账户、资产、政策与授权版本下尚未使用的份额，与批准、核销共用配额锁、代际检查和原子提交。已签残余始终归原事实，不能当成闲置额度搬走。节点全局统计异步汇总；代付与工作额度同样分配给 Worker，避免省掉 CAL 热点后又制造一个共享 FUEL 或政策计数器。

真实组织账户继续保持 `A = F + ΣR_active + ΣK_retired`，活跃覆盖 `R_v=G_v-P_v`；用户已落实的 UTXO 资金不计入组织 A。活跃覆盖也不能因委员会“目前只看见少量义务”而自由提款，因为仍可能存在未登记的合法承诺。释放活跃覆盖须有另行证明的安全退役协议；本版该入口不启用，不提供提现已授权覆盖或清空旧义务的操作。

每张有效批准至少有 `q-b` 个诚实签署者，且其保留残余不小于公共真实残余，因此对每资产：

$$
(q-b)\sum_T Residual_T\le\sum_{i\in Honest}Used_i
\le(n-b)\eta G_v,\qquad \sum_T Remaining_T\le R_v.
$$

这沿用 v1.1 的覆盖论证，前提仍是每次解除永久有效、回款真实唯一。新增根方案还需证明：合法消费 DAG 的当前未花权利总额不会超过根进入的价值，且每个根只由来源或备付落实一次；它不能仅由余额不等式自动推出。

### 7.2 向量供给不能拆开估计

调度使用“同一个成员是否同时满足全部需求”，而非各维余额的独立第 q 大。四成员分别有 `(10,0)、(10,10)、(10,10)、(0,10)`，CAL 和 FUEL 都有三个成员够用，但 `(10,10)` 只有两个成员可签。

压力预测统计共同可行成员集合，最终准入仍以真实本地事务为准。余额报告只帮助路由和补充，不构成花钱授权。Worker 调配优先同时满足当前交易的缺口，减少双资产碎片化。

共同集合还须满足适用的代付累计限额、各工作额度、输入状态及成员可用性，不能只检查 CAL/FUEL。

### 7.3 后台工作额度

`c_CAL=0` 不代表零成本。除两个资金维度外，在相同 PREPARE 事务中占用 `WorkCredit=(E,B)`：E 是按固定规则计算的执行工作上界，B 是需要继续保留的数据字节上界。E 覆盖必要验签、状态访问、证明处理及收尾，B 覆盖待办和证据；单命令字节、输入输出和验签数仍各有硬上限。它不是第三种资产，也不新增认证回合。

委员会为各组织配置工作容量，组织成员再按同样的保守法定人数比例与 Worker 分配方式限制未完成承诺。工作额度绑定原事实，只有认证相应逻辑工作已经完成后，原占用成员才能累计返还。

E 按登记、结算及收尾保存预订与完成明细，共用一个执行额度余额。公共登记只释放已经完成的登记工作；结算、根资金处理和收尾仍保留相应占用。B 只有在所保护的材料满足安全替代或保留条件后释放，不能在登记时一并清零。每笔子交易承担自己的工作，祖先工作仍记在祖先名下，不重复发放完成信用。归档不是消除物理存储，长期历史、未花输出和防重索引另做容量规划。

委员会按工作单位对组织加权公平服务，为已有结算、证明、核销和有限维护保留实际队列、执行与区块容量；类内按年龄避免饥饿。就绪祖先优先于等它的子任务，但不能用永久严格优先级饿死其他组织。按 TxID 合并依赖抓取，同一批材料不因很多子交易等待而重复下载。

依赖索引和等待边计入字节及内存限制。父状态改变后，按持久游标分批唤醒确实受影响的子项，限制每次唤醒工作量；不能遍历全队列或一次展开无界后继集合。抓取合并同时覆盖解析和不可变验证，避免共享祖先虽只下载一次，却被重复验证很多次。

委员会低频配置各组织上限 `E_g/B_g` 和最低服务份额 `μ_g`。扣除维护与尾延迟余量后的实测保守能力记为 `μ_safe`，规划积压时间记为 H，则采用 `Σμ_g≤μ_safe`、`E_g≤μ_g×H`、`ΣB_g≤B_safe` 作为部署约束。H 是规划参数，不是网络分区或任意故障下的时限保证；新增组织不能绕过总量上限。容量下调只限制新承诺，既有预订仍需兑现，不能追溯宣布原凭证无效。

减少已授予的可循环容量、释放旧覆盖或撤销可能仍有隐藏证书的授权，需要另外证明安全的版本屏障和保全流程，本版不启用。不能仅在委员会配置里调低甲组织额度就把差额分给乙：离线成员可能仍持旧授权签票。入口限速不构成全组织停止签署或隐藏证书不存在的证明；新增资金/授权与对新请求的本地限流仍按正常规则运行。

最老待办、积压字节或同步写延迟到达高水位时限制新增签发，降到低水位再恢复，避免反复开关。限速使用本地测量和已验证完成事实，余额报告只作提示；硬安全上限仍由本地额度事务实施，不新增逐笔中心批准服务。额度约束未完成承诺存量，最低服务份额保障推进机会，二者不能互相代替。

完成旧义务、安装合法 QC、同步必要证据、应用最终收据以及已启用的补证重传不再申请“新增业务”额度；其逻辑工作已经计入原计划，异常额外工作使用独立且受限的维护容量。恢复通道设独立队列和服务份额，防止“先取得新额度才能释放旧额度”的循环等待。

等待依赖的交易只保留有界待办记录，释放 Worker、数据库锁和执行槽。恢复通道校验已有业务身份、允许阶段及工作上限，不能让任意新请求冒充恢复流量。资金充足与处理资源充足分别检查。

工作预订保证的是已有承诺继续处理的资格。在法定人数可用、必要数据最终可得、就绪任务获公平服务且物理存储可持续的条件下，后台才能最终推进。未获 QC 的局部准备、入口垃圾和重复请求还需本地未决及速率限制，不能只靠有效证书的 WorkCredit 控制。

### 7.4 后台完成驱动持续准入

部署使用实测安全工作速率作为新增准入上限，再按待执行工作量、证明字节、待应用核销量及最老待办年龄的高低水位调整；E/B 继续提供本地事务中的硬上限。不同交易的工作量不同，不能只按交易条数估算负载。该反馈在后台更新，不为正常付款增加通信回合，也不改变已授授权或既有承诺。

提速优先采用已有请求的有界合批、块末一次提交、不可变验签/解析复用与按依赖索引唤醒。对同一原事实、资源、账户/政策、授权版本和阶段，只需投递最新的可验证累计核销值，多项共享认证头；接收方仍按原占用应用差额。原动作及证明材料继续保留，不能把不同事项合为一个无法核对的净额。

分别给结算、证明生成和核销应用保留处理资源并测量耗时。已有义务的推进不重新申请新增额度，避免等待自己的核销才能继续处理。稳定容量以整个闭环不持续积压为准；FUEL 实际净消耗导致额度下降须归入资金不足，不能误诊为核销堵塞。限流用于维持稳定，不能代替后台实际提速或在过载时承诺原 TPS。

## 8. 委员会：按依赖执行，按区块摊薄开销

组织后台提交 `SettleBundle`，包含已经 READY 的交易、必要未登记祖先和已最终边界引用。子交易可以先到达接入端；实际执行顺序必须先建立其父权利和根资金，不能只凭“先到”再支付一次备付。

委员会并行验证签名及不可变材料，CometBFT 确定命令顺序，单写者在块级 Overlay 中按确定规则执行：

1. 核验并登记 READY；按 FeeID 一次性建立费用托管。
2. 对必要根执行一次 `FundRoot`；对已完成根返回原结果。
3. 按依赖执行输入消费及普通 UTXO 生成，保持凭证输出身份和消费路由；散户输出最终后即可直接使用。
4. 在同一业务执行中更新义务、费用动作、收益与工作完成状态。
5. 块末归并同键变化，原子持久提交状态、结果、防重和恢复点。

登记、结算和费用关闭是逻辑阶段，不要求分别发三笔公共事务。材料齐备时可在一个规范命令内连续完成；条件不齐时只提交已成功的阶段，其他阶段保持待推进。批内动作顺序明确，每项保留 ActionID、结果与实际逻辑收费。后续重试不重收已完成动作的费用。

融合执行持久保存已完成的动作前缀，重试从尚未完成的动作继续；不能因为 REGISTER 已成功，就把整个 TxID 标为全部完成。业务终态、阶段终态与尝试结果分别记录。

父交易在块内创建、随后被子交易消费的输出，可以只把其最终消费状态写入热索引；完整交易与动作仍保存在公共历史中。该优化减少写入与传播重复，不省略每笔授权、守恒、收费和审计。

提案必须携带有界、可验证的实际材料或已提交引用。缓存命中不改变有效性；执行不能请求网络或依赖本地墙钟。依赖缺失返回可重试的待办状态，不能永久写成业务失败；重试复用身份，但允许补充证据封装，已经收费的工作不再收费。

并行预检只缓存不可变材料及其有效性，余额、输入消费、版本屏障和动作终态在顺序执行中复核。缓存按规范正文、完整配置与规则身份绑定；命中不降低协议应收费用，未命中也不额外收费。同一前置状态及规范命令序列必须得到相同状态、错误码和费用；任何批量折扣必须是显式确定规则。

单次批次上限不等于整条依赖链上限。合法已 READY 业务的祖先可以跨块分段登记和结算，每次从已最终边界继续；不能因为整包超过区块大小就永久拒绝履行。准入上界控制新承诺规模，后台分段机制确保已有承诺仍可推进。

同时，在 PREPARE 前检查每条不可分割命令的最小完整执行封装满足区块字节和工作上限；单条超大原子命令不能靠分段规避。FundRoot 可凭根证据、原授权和原费用计划独立执行，不等待子交易、客户再次签名或来源失败证明。在必要数据最终可得、委员会可用且调度公平的条件下，有限无环依赖才有最终推进保证。

`DEFERRED` 只记录尝试与待办，不封死 SettlementID；补证后仍可执行。输入消费、根资金落实及费用动作，仅在相应原子操作成功或明确终局裁决后写入业务终态。

资金业务使用子事务；合法 READY 的费用托管与已完成收费可先登记。根落实是独立幂等事实，不能因后续缺少另一父输入就重复扣款。只有用户所承诺的实际公共支付效果完成，才将付款标为 SETTLED。

核销采用“受信委员会配置＋认证头＋状态包含证明”，支持共享头和批量证明。对引用的 CometBFT 0.38 应用模型，执行高度 h 的应用状态由 h+1 头承诺；本地 Commit 或事件通知不等于已经取得该状态的公共证明，空闲时也应产生必要证明块。[R3]

委员会按需出块：真正空闲时等待新交易，保留状态变化所需的后继证明块。后台分批依赖处理的真实持久进度计入应用承诺，持续推进至收尾；无变化时保持 AppHash，避免连续空转。持续有交易时由后续业务块兼顾证明，不要求每个业务块后附一个空块。

同一认证根下批量生成核销证明；同一事实仅推送最新累计值，但核对事实、版本、资产和原额度范围后才能取最大值。成员按 Worker／配额分片合并应用收据，把记录、返还和防重同批持久化。事件推送配合游标补拉，不为每笔交易单独轮询。证明服务有保留 CPU、网络与存储读取容量，防止“已经结算，但没有证明可恢复额度”。

委员会仍逐笔承担逻辑工作。提高前台 TPS 不能让有限后台永久吞下更高到达率；批处理的价值要用稳定队列下的持续业务 TPS 验证。

## 9. FUEL 与激励：每笔付自己的生命周期费用

CAL 只承担本金、备付与本金损失；Gas 是工作计量单位，FUEL 是费用资产。代付方提前存入真实 FUEL，授权业务范围、累计金额和单笔上限。普通付款从已认证政策读取授权，无需联系在线代付服务器。

每笔签署的费用计划为：

$$
F_{max}=R_G+R_C+R_L+S_G+Burn+Tail.
$$

分别对应组织验证、委员会处理、中继、组织服务收益、基础销毁及有限收尾。费用政策固定每类动作及工作上界；根资金落实和有限回款登记由根签发的计划购买，每次转手购买自己的认证、结算和收尾，直接交易只支付其实际公共执行工作。后继不是无限消耗祖先的 Gas。

后台安装和父证书转交所需有界工作在原 FeePlan/E/B 中预留，不按 ACK 次数新增奖励或收费阶段，FeeClose 不等待所有成员安装，也不等待所有成员的本地 B 释放。委员会首次登记合法 SpendQC（即 READY 公共登记）时，将 Fmax 一次性转入该笔费用托管；不等待任何组织 INSTALL_ACK。费用来源扣款、FeeID、防重与本次确定发生的收费原子提交。未经授权的请求不能扣款；纯网络垃圾使用准入配额和限流处理。对已成立的承诺，不要求接收者临时补 Gas。

$$
F_{max}=PaidRewards+Burned+Refunded+Held.
$$

资源成本按已认证逻辑工作归属，不按重复包或 Worker 数量发奖。四成员预先各有有界报酬份额，合格成员在领取期限内提交工作证据；不因收集器挑选前三份签名而把第四份奖励转给前三位。收益先累计至领取账户，允许批量领取，避免逐笔制造大量奖励 UTXO。

中继动作按 `FeeActionID` 最多付一次，领取人按原服务策略确定；公开执行报酬只奖励实际推进的动作，不按重传次数支付。可证明的违规签名按固定规则处罚独立 FUEL 运营保证金和可处罚收益，不能扣用已保护用户的 CAL 覆盖；单次慢响应或客户端自报时延不作为自动罚款依据。

组织服务利润沿用可调整的 20%/40%/40% 实验规则：READY 公共登记、承诺的公共支付完成、本笔必需服务结束。根签发的最终阶段以根资金已落实及约定收尾完成为依据；普通转手完成自己的公共效果和费用收尾即可，不等整条后继支付链终止。组织已经真实赔付、未来责任为零时，不因本金追偿尚未成功而永久扣住服务利润。

费用关闭先检查“本笔业务及 FeeClose 自身之外的必需动作已完成，或已取得允许关闭的明确终局处置”，再原子确定尾款归属、未用预留退款和 CLOSED 状态。不能以 `Held=0` 或本次关闭尚未完成的动作作为前提，因为未归属尾款本来就包含在 Held 内。终局处置只支付已挣得且条款允许的收益，不能把未履约直接当成全额利润归属。服务完成、费用关闭和 CAL 剩余占用分别记录，不互相冒充核销依据。

费率/工作表在本版部署时固定，已签 SpendVote 和已 READY 的条款继续有效；旧授权安全退役未实现前，不提供在线撤销旧报价并释放覆盖的操作。维护使用独立预算，不挪用 CAL 用户覆盖。

本版不提供会释放旧占用的代付撤销或原地政策替换；停止新增接入不影响已签票、隐藏完整证书及已 READY 的费用支撑。首版每笔只选一个费用来源，独立商户累计限额复用按授权范围隔离的预算，白名单不能替代累计限额。

组织级商户额度先按拜占庭有界比例授权成员，再排他拆给 Worker，不能让每个成员各自使用商户完整总额。两种限制分别记账：资金覆盖按真实补回恢复；商户累计支出上限只按资金方授权的周期、退款与更新规则改变。`RestoreFeeCoverage` 不重置商户累计上限。累计支出型政策中，未使用预留可释放，已实际支出仍占累计限额，除非政策明确授权新一期或增加总额。

费用实际支出保留为净占用；退款或资金方真实补回原费用覆盖后，原成员才能恢复权限。例：上限 100，奖励 84、销毁 10、退款 6，实际费 94，权限仅恢复 6。之后资金方真实补入 40，权限再恢复 40，用户历史费用仍为 94。

上述恢复 6 的前提是退款真实回到同一活跃费用覆盖。若条款将退款直接付到外部钱包，只记录消费者退款，不同时增加组织覆盖；本版不产生新的退役版本，不启用相关资金释放分支。根垫付后的可选追偿不以成功为服务结束条件：本次有界收尾完成即可归属尾款，日后新增追偿工作由维护预算或新的服务授权支付。

持续运营可将真实补款通过 `RestoreFeeCoverage` 对应到原版本已确定、不可再退款的净费用支出，直接恢复原签署者的对应占用；不能把仅转入托管的全部 Fmax 当成最终支出再补一次。恢复值不得超过原占用，真实入款只能归类一次。补回还是新增 Grant 由共同可签集合的瓶颈决定：补回只帮助原签署者，新增 Grant 按 η 增加各成员上限，不机械地把某一种规定为永远最优。

首版以创世有限 FUEL 与实际服务收入运营，不按交易量增发。正额销毁只能证明特定自付联盟模型下刷量有不可回收成本，不构成完整抗串谋证明；固定总量与最低销毁也意味着有限累计业务容量，发行和销毁参数须在部署前做服务周期测算。FUEL 价格和保证金不能代替 CAL 足额覆盖与故障阈值。

经济验收单独测量费用收入是否覆盖计算、带宽、存储、资本占用和违约损失，以及更早取得尾款和恢复权限的收益是否超过推进成本。延后利润归属仅是激励方向，不自动构成参与者都会及时履约的均衡证明。

### 9.1 实验供资与正式运行补资

实验可用充足但有限的大额初始余额，并通过正常账本交易补款；保留金额上限、真实扣款、累计核销及资源检查，不使用无限数值、清空占用或免验费用。报告同时给出初始资金、外部补款、实际净消耗和最低余量，另测受限资金下的周转，避免充分供资掩盖核销或补资瓶颈。

正式运行由用户预付 FUEL 或商户提前授权代付，实际手续费和服务收入承担运营成本；CAL 备付来自组织资本、真实回款及追加资金。正常转手不重复占本金覆盖，已垫付但未收回的净支出不能因责任履行而消失。

采用低水位补款：从资金方明确授权的真实账户补到目标余额，按“各资产净消耗速率 × 到账并恢复授权可用的时间＋突发余量”配置缓冲。可用余额扣除已承诺保护用途，观察共同可签成员的实际额度；在途补款仅用于避免重复申请，最终到账及相应授权/核销应用前不得使用。补款保留唯一请求身份和明确金额，重试沿用原身份；同一入款只能选择新增授权或补回原净支出，不同时记入两类。

补款解决资金周转，收费能否覆盖计算、带宽、存储及资本和损失成本另行验证。账户充值只转移已有 FUEL，不能补回全网销毁量；正式部署须按目标服务周期确定储备、供应和销毁参数，当前有限发行与正额销毁不构成无限期运行保证。补款不足时限制新增业务，已成立的支付继续使用原预留履行。

## 10. 组织互通和散户付款示例

甲组织已合法签发一张给乙组织用户 B 的 100 CAL TXCer，输出 SpendOrg=乙。假设它关联甲原先已经成立、尚未落实的担保根 R，甲 CAL 覆盖为 900，原批准成员上限 600，因该根占用后可用 500。本例说明已有义务如何履行，不表示每个最终 UTXO 都必须重新购买担保。

1. B 向丙组织用户 C 支付 70，给自己找零 30。乙用缓存的甲配置验证父凭证，执行自己的一轮持久认证，产生 C/丙的 70 和 B/乙的 30。
2. C 可以立即通过丙组织向散户 D 支付 70，输出写 D/COMMITTEE。D 只看到待确认付款，等最终 UTXO 后使用。
3. 后台按 R→B 的付款→C 的付款顺序落实资金与输入消费。若 R 按原条款由甲备付履行，甲支付 100 一次；乙和丙不接管这项根责任，也不为同一 100 再占本金覆盖。
4. D 最终取得 70 CAL UTXO，B 保有 30 CAL；原凭证与公共输出不重复记余额。D 下一次直接向委员会付款，不产生 TXCer。
5. 甲实际垫付时根计数为 `(Paid,Discharged,Returned,Remaining)=(100,0,0,0)`，原成员权限仍为 500；原交易资金真实回补 100 后成为 `(100,0,100,0)`，原权限恢复 600。原资金先完成结算时则由真实资金支撑，甲不垫付，对应责任永久解除。

各笔 FUEL 按自身实际服务支付；没有 CAL 跨组织转换损失，也没有因为组织变化多收一次“转移担保费”。同一 B 输入同时付给 C 和另一人时，两个候选都由乙处理，不能各找一个组织分别签成。

如果初始就是已最终且消费条件已指定甲的 UTXO，正常直接沿真实资金结算；不需要制造一个尚未到账的来源来跑本例的备付分支。

## 11. 故障处理保持在慢路径

| 情况 | 明确动作 |
|---|---|
| 网关或收集器失联 | 钱包或其他持证节点重传；成员有完整证书时直接返回，否则重发自己的原票，不保证局部票一定可拼齐 |
| 存储提交结果不确定 | 暂停该身份新增签票，核对同库提交点和原事实，不盲退预算 |
| 重复或乱序核销 | 按原事实、资产、账户/政策、版本及累计差额应用 |
| 分票、恶意弃单或隐藏证书 | 保留已签锁、原票、正文和残余占用，补证后推进；无超时改票或退款 |
| 完整持证者全部离线 | 尚未完成可靠保管时允许停滞，等待持证者或保存父证书的后继成员补交；余额不足限制新准入 |
| 委员会或安装暂时停顿 | 使用原预订继续传播、结算与核销；高水位限制新增，不撤销已交付权利 |
| 原输入尚未公共落实 | 仅按原合法条款落实来源或原组织备付一次，缺证不等于可调用备付 |
| 状态损坏、回滚、成员更换或授权退役 | 首版停止受影响身份新增签署并保留材料；恢复/退役释放接口返回 UNSUPPORTED |

本版不沿用“只保全已收集完整 QC，再作废其余候选”的旧重整规则。付款证书可能只在钱包或其他组织，冻结报告中没有它，不能证明它不存在。停止签署不等于释放预算；没有新的安全保全证明前，所有已签输入锁与残余占用继续保留，旧身份不能清库后重新获得额度。

须区分“完整证书隐藏”和“始终没有完整证书”：前者可由持证者恢复重传，后者可能没有可补交的 QC，本版允许其锁及额度长期占用。资源有界不等于必然周转。主体未决配额、字节/速率上限限制局部准备与隐藏证书的累积。先验证用户授权再占其主体配额，不能按任意自报商户身份消耗容量；按公钥或 IP 限流也不单独构成抗批量身份保证。有效证书优先补传播，持续分票可能使受影响组织额度耗尽并停签，这是本版明确的可用性限制，不以“复杂恢复延期”宣称已经解决。以后若需要可撤销候选或在线退役，须单独给出兼容隐藏 SpendQC 的协议和反例测试。

### 11.1 正常重启与状态回滚

正常同库重启使用数据库和共识引擎自身持久保障，从已提交事实继续原身份重传；不重新获得授权。旧备份、损坏数据库或缺失签署尾部不能作为同身份继续签署的依据；无法确认完整性时停签，本版不自动修复后放行。

三个原子边界为：PREPARE 的正文/父证据/效果、输入锁、完整额度、签署意图及 outbox；INSTALL 的完整 SpendQC、输入终态、输出与传播待办；核销/Worker 调配的残余、AppliedCredit、代际和份额记录。公共完成或子消费先到时，迟到安装不得覆盖新状态。安装 ACK 在提交后返回，其丢失只导致同事实重试，不触发再次签票或返额。

### 11.2 服务状态与用户体验

| 状态 | 继续提供的服务 | 限制 |
|---|---|---|
| 至少三名合格组织成员，依赖和共同额度齐备 | 正常签发与续花 | 固定时延取决于部署与负载 |
| 一名组织成员失联，另外三名诚实且状态齐备 | 三票路径继续推进 | 若另有一名恶意拒签，已超出一故障活性条件 |
| 组织不足三名可服务成员 | 查询、证据补齐；健康委员会在完整证书和依赖可取时结算已有 READY | 停止该组织的新付款认证，不降为两票 |
| 委员会暂时停顿 | 在原资金、工作、字节和依赖限额内续签 | 任一硬上限到达后停新，已有证书保持有效 |
| 代付或工作额度不足 | 推进证据齐备的既有承诺，补资、核销和查询 | 不能在不确定付款上悄悄替换费用条款或另付一笔 |
| 状态损坏、回滚或超阈值故障 | 停止受影响身份新增签署、保留材料并取证 | 不承诺在状态不可得时立即切换消费处理方或无限离线续花 |

网关切换可自动进行；消费权威切换不可如此处理。钱包显示付款证据和阶段，不把某个节点拒绝或 UNKNOWN 当成全局终局失败。

## 12. 性能路线：先消除热点，再考虑复杂协议

首版优先做七项优化：

1. **组织内部验证复用。** 按 §6.1 直接读取本成员已完整验证的父输出，减少重复验签与取证；跨组织凭证也可在首次验证后复用。
2. **钱包并行输入池。** 高频付款方预拆分若干独立 UTXO，避免每笔都花上一笔找零；同一钱包可以并行付款。合并碎片放在低负载时执行。
3. **本地分片与私有预算。** 按输入键隔离真实冲突，跨分片多输入仍由同一成员数据库原子提交。无新增本金义务的转手 `c_CAL=0` 时直接跳过 CAL 配额写入与锁，保留 FUEL 和工作额度检查；初版不做 Worker 跨机器两阶段提交。
4. **认证与提交流水。** 解析、验签、提交与回执并行处理不同交易。比较简单独立签名与聚合方案后再选，不把 BLS/DKG 作为启动依赖。
5. **持久缓存与批量传输。** 缓存按正文、配置和规则绑定；公共证明共享认证头，重复证据只发送缺失部分。
6. **有界依赖批结算。** 后台从已最终边界补齐缺失祖先，一次提交多笔，但每笔保留身份、结果与收费。块内同键写合并减少存储成本。
7. **以周转为目标的后台调度。** 根资金落实、可完成的回款和核销优先获得服务，同时设置年龄公平性，避免小额或暂时不能释放资金的业务饥饿。

READY 延迟使用钱包真实保存时间：

$$
L_{ready}=L_{ingress}+P_{(q)}+C_{QC}+L_{delivery+wallet}.
$$

`P_(q)` 是第 q 份匹配、有效、持久批准响应的耗时，含通信、排队、校验、锁等待、同步写和签名；`C_QC` 含收集器验票、组证及自身可靠保存。钱包保存完整证书和待办计入交付终点。INSTALL 不再是前台必等阶段，其 CPU、网络、写盘及保管完成延迟单独计量；不能据少一轮等待推断后台工作减半或 TPS 翻倍。p99 从逐笔样本统计，不把分段 p99 直接相加。

持续容量同时受组织、委员会、证明服务、网络与存储约束：

$$
\lambda\bar w_C<\mu_C,\qquad
\lambda\bar b<\mu_{network},\qquad
r_{sign}^a-r_{credit}^a\le\eta r_{grant}^a.
$$

最后一式是长期平均预算规划条件，不代替逐笔上限。近似所需在途权限为“新增风险金额速率 × 资金落实/核销延迟＋净支出残余＋突发和未决缓冲”。新方案的本金风险速率按新担保根计量，不能按所有后继支付面额重复计算；FUEL 则随每笔服务持续净支出。

同一权利连续转手的串行依赖无法靠增加 Worker 消除。多组织可以扩展前台接入与验证，但共享委员会仍有总容量边界。首版不承诺具体 TPS 数字，先通过测量找瓶颈。

容量规划按不同业务类型与实际资源分别计算。对 CPU、磁盘、网络、证明服务等任一资源 `r`，应满足 `Σ_k λ_k × cost(k,r) + retry(r) + maintenance(r) < capacity(r)`，并保留尾延迟余量。根资金落实、快转、散户直付及维护不能一律当成成本相同的“一笔”。向四成员广播、只取三票通常仍消耗四份处理资源；“最快三票”降低等待，不自动减少总工作。

稳定负载下，某阶段所需工作额度约为“到达率 × 每笔工作量 × 该阶段完成至额度实际恢复的时间”，再加突发缓冲。委员会停顿时，可续签的时间还受剩余工作额度、费用权限和依赖深度共同限制；不能只按 CAL 余额估算。积压量用来控制新增准入，最老未决年龄用来发现已经停滞的业务，两者都要观察。

钱包选择输入时，优先满足本次服务组织对应的输入消费路由、足够金额和较少输入；不按原发行组织分组，并在费用接近时偏向已结算、依赖较浅的输出。高频付款提前拆成独立输入池；不要为追求一次合并而把许多未落实根连接到同一小额付款。该选择是钱包优化，不改变合法支付规则。

用户 nonce 只服务于稳定业务身份，不设置串行所有独立 UTXO 的全钱包递增计数器或共享 SponsorNonce。按 OutputID 亲和调度可作为测后优化，目标是减少缓存迁移；同时测量它是否使某 Worker 私有额度更容易耗尽，保留普通调度作对照。

### 12.1 物理存储也是持续容量约束

WorkCredit 管尚未完成的承诺；公共历史、未花 UTXO、输入消费与核销防重记录仍会增长。按输出数和规范字节计费、设置单笔上限，并不等于磁盘自动扩容。组织和委员会分别统计实际使用量、归档积压与永久索引增长。

空间预留覆盖本地局部准备、全组织可能形成的有效证书（含本成员未准备但需要 INSTALL 的交易）、既有承诺剩余写入、WAL、压实临时空间和恢复副本。查询快照限制数量及寿命，避免长期钉住本应回收的数据。达到高水位要在剩余预留被耗尽前限制新准入；已交付证据不能因磁盘紧张丢弃，INSTALL-only 成员也须完成自己的存储交接。

首版不新增存储租金、UTXO 租约或归档共识；持续容量的适用条件包含可持续存储供给。实验报告每笔写入量、归档速度和实际磁盘增长，长期扩容与备份按这一测量规划。

暂不引入：共识内核重写、前台全局排序、每笔第三轮费用共识、逐后继可交易责任份额、递归零知识证明、仅提交净额而省略审计、未经测量的并行资金执行器。

### 12.2 轻量历史分段与归档

首版采用“活动库＋只追加分段文件”。活动库保留当前 UTXO、未完成交易/锁/责任、资金与授权、输入消费及来源/动作防重、累计核销检查点；已终结且无未完成业务需要直接读取的不可变正文与证据，按目标文件大小滚动封存，并记录高度范围、内容校验值及查询位置。不按日期直接删除安全记录，不为每段生成全量状态快照。

归档顺序为：有界复制并结束读事务 → 文件可靠落盘并校验 → 同库事务保存定位并移除冗余正文。原规范字节、编码版本、历史验签配置和最终事实证明所需材料须继续可取；归档只改变物理位置，不改变公共逻辑事实和承诺。组织释放 B 仍满足第 6 节的公共交接及本地替代条件，写出一个文件不能自行产生核销信用。

封存文件可以迁至独立归档磁盘，确认目标可靠、可校验且查询路径已切换后再移除本地副本。同盘归档不释放总磁盘容量；必要证据不能仅凭保留时长到期而删除。当前 UTXO 和紧凑防重索引仍可能增长，需计入容量与费用。本方案减轻活动库负担，不承诺总存储恒定；具体文件交接及 bbolt 空闲页处理见工程规范 §8.4。

## 13. 问题、取舍与候选贡献

原文并非已经证明存在资金漏洞。更准确的判断是：若干关键规则只表达了成立条件，尚未形成能直接执行的统一状态机。

| 缺口或代价 | 本文处理 | 所付成本 |
|---|---|---|
| 转手零覆盖与子先垫付之间缺少统一边界 | 根整体一次落实，后继只消费同一价值 | 小额后继可能触发较大根的全额垫付 |
| 组织签发、输入裁决与原担保责任混用 | CertifierOrg、SpendOrg、GuarantorOrg 分离，快慢路径统一 OutputID | 收款描述固定下一次消费处理方 |
| 责任解除缺少明确业务触发 | 真实来源落实到受限资金，或实际垫付终结未来责任；后者不释放净支出占用 | 需要根状态与回款身份 |
| 双资产分别够用但共同签署者不足 | 向量联合调度与本地原子准入 | 配额碎片化仍需调配 |
| 登记快、后台未完成义务仍累积 | 未完成工作额度与分类完成收据 | 固定资源状态与准入限制 |
| 后继链变长导致材料增长 | 紧凑父引用、公共边界、后台拓扑补齐 | 冷恢复成本与依赖上限 |
| 后继不断转手拖住原交易服务尾款 | 收益按本笔服务边界结束 | 根签发和普通转手需不同价格类别 |
| 原组织整窗规则与新版核销并存 | 统一采用长期授权及逐项核销 | 原历史规则需按版本隔离 |

三条资金路线的选择是：每笔独立覆盖易理解但重复占用资金；逐份额责任谱系更灵活但拆分合并与证明复杂；**一次根担保＋已有权利守恒转手＋整体根落实**在首版更适合实现和验证。它保留根担保签发能力，又让常规重复支付不反复增加本金风险。

候选贡献集中为两个可检验的组合：

- **风险与流通频率解耦。** 把新增本金覆盖绑定导入根，把多代续花绑定唯一消费 DAG，再以一次资金落实消除后继独立垫付分支。应验证相同支付语义下的覆盖峰值、根落实代价、证明大小与尾延迟。
- **与履约进度一致的持续准入。** 本金残余、费用净支出、未完成工作各有不同释放条件，但共用认证和公共完成事实。应验证它能否在持续负载下维持有界积压，并降低重复授权和恢复成本。

有界计数器、预存快速支付和代付已有公开基础。[R1][R2][R4] 上述组合仍需文献查重和同等安全条件下的对照；设计上的新组合不是已经证明的原创结论。

## 14. 原型与验收

依次实现：确定性资金参考执行器；四成员组织的一轮取证与后台安装；四成员委员会和公共证明；FUEL 代付与工作额度；最后加入 Worker 动态调配、依赖批结算和故障注入。先让顺序参考模型定义正确结果，再优化热点。

| 验证项 | 必须覆盖的情况 |
|---|---|
| 组织互通与散户 | 不同发行者输入合并、固定原责任、散户直付/收款、相同 OutputID 快慢双花拒绝 |
| 内部验证复用 | 同/跨组织冷/热缓存、仅局部 INSTALL、缓存命中后已消费、开关前后结果一致 |
| 根资金唯一落实 | 原输入先结算、备付先履行、垫付尚未回补、重复根提交、迟到回款；用户不重复取得本金 |
| 支付唯一消费 | 组织认证与裸签直付冲突、多输入分票、跨版本迟到 QC、重放旧签名 |
| 多代与合并 | A→B→C、拆分后多分支、多个根合并、父子反序到达、缺失祖先后补证 |
| 两资产与工作额度 | 联合签署者不足、原成员差额恢复、未签成员、重复收据、仅登记未结算 |
| 费用与收益 | 代付耗尽、赞助撤销、尾款条件、重复动作、退款与补回区分、旧报价补资 |
| 持久化 | 批准、钱包保存、后台安装、核销各提交前后中断与同库重启；不以旧快照恢复冒充正常重启 |
| 乱序与压缩 | 子已消费后父安装迟到、核销先于本地观察、同 TxID 多 Worker 重传、历史压缩后重放 |
| 委员会确定性 | 预检缓存有无、批与逐笔、不同接入顺序，均得到相同规范命令序列的结果 |
| 隐藏证书与控制边界 | 分票后证书只在离线钱包、后继携父补交、公共完成早于安装；旧版作废/退役入口不能启用 |
| 可用性与滥用 | 完整证书隐藏与始终无 QC 的不同停滞、商户身份冒用、失败缓存污染、共享祖先唤醒风暴、补证流量挤占 |
| 容量与政策隔离 | 商户累计上限不随补款重置、归档滞后、长快照、临时压实空间、未准备成员的安装容量 |
| 持续运行 | 稳态工作量及证明/核销队列不持续增长、过载后恢复、多周期真实补款防重、归档前后旧凭证验真/查询/防重一致 |

性能基线至少包含：全量委员会确认后才可花费；相同 SpendQC 一轮交付与额外等待 q 安装 ACK 的隔离对照；共享额度计数器与 Worker 私有额度；逐笔提交与依赖批结算；仅金额背压与金额＋工作背压。比较根担保时保持实际担保范围相同，不把取消额外服务产生的节省误称为性能提升。

负载包含：同组织/跨组织冷热缓存、散户直付、独立 UTXO、同钱包多输入、单条长链、多发行组织根合并、金额倾斜、单向费用流出、故障成员和委员会降速。扫描 LAN 与跨地域网络、Worker 数、同步存储、块大小、根大小和依赖深度。

至少持续运行到覆盖多次 CAL 核销与 FUEL 真实补回，再观察稳定区间。报告唯一业务 READY/SETTLED TPS、p50/p95/p99 READY 延迟、最终结算与额度恢复延迟、最老未决年龄、队列斜率、每笔字节/验签/落盘、资本峰值与故障恢复时间。队列持续正增长的短期突发吞吐不能列作持续 TPS。

负载发生器按预定到达速率逐级加压，同时记录请求数、准入数、拒绝数、超时数、最终成功数及客户端自身队列。不能只给已准入成功样本的漂亮延迟，或用“发一笔等一笔”的低并发实验代替满载测量。另测单条支付链延迟，其串行性是不同的业务约束。

分别报告四成员正常与一个成员不可用的稳定容量；给出硬件、地域、网络条件、交易字节和同步持久化设置。按组织和交易类型统计尾延迟与最老年龄，检查加权公平是否实际生效。恢复时间从故障发生计到证据补齐、积压消退且额度重新可用，不能只计进程重启或共识恢复出块。

解释性能结果时，至少提供重复验签数、祖先访问放大率、同步提交等待、每类配额阻塞时间，以及 FUEL 补款前后共同可签集合的变化。这样才能区分计算、资金、授权政策与物理存储各自造成的停顿。

首版验收条件是：模型与参考执行器不违反守恒和唯一性；故障恢复保持已认证付款；目标负载下队列、未完成工作及资金占用达到稳定；所有性能比较使用同样的可靠交付终点。具体部署容量由实验选定，不从已有论文数字外推。

部署前生成一份明确的参数配置，配置分三类：

| 类别 | 必须固定的内容 | 改动方式 |
|---|---|---|
| 协议规则 | 网络、成员与阈值，金额与编码，输入输出/单命令/依赖上限，工作与费用计量，输入类型及消费权威规则 | 新规则版本和受控启用，旧承诺继续可执行 |
| 容量配置 | 各组织 E/B 总额与服务份额，成员安装预留，主体未决上限，维护与归档容量 | 总量检查与低频控制；缩减已授额度须经屏障、保全与排空 |
| 运行调优 | Worker 数、私有额度补充水位、缓存、对冲阈值、批大小、高低水位 | 基于测量调整，不改变签名事实、收费和核销权限 |

首版固定四成员、三票、一轮前台持久批准与后台持久 INSTALL；其余容量参数按目标硬件及故障负载测得。配置校验必须拒绝无法装入区块的原子命令、组织配额总量超过部署承载的组合，以及无法保留足够 INSTALL／恢复空间的设置。这些配置检查是开机条件，不能在交易已经 READY 后再补做。
