审查对象：`feat/authorized-repair-batching@3bb9ceb8838839d3ded9b4e44a08648d577f4d94`，相对 `re@0f7be69`。本轮只审查、复现和记录，未修改生产代码，也未合并分支。

**结论：经济执行与物化分层的实现基本符合设计；但修复取证存在一个可复现的单故障阻塞问题，构造端经济预执行也没有落实。建议先完成这两项小范围修正，再将本分支作为已完成版本合入 re。** 现有正常网络回归仍有效，但不能据此宣称异常修复路径已满足一故障进度保证。

## 1. 已复现问题

### R1 · 高优先级：第四个异常响应能否决已有的三个有效响应

位置：`internal/redaction/batch.go:183–206`，`cmd/committee/repair_runtime.go:234–260`；相关继承问题在 `crypto/chameleon/chameleon.go:139–145`。

实际触发链：

1. 三名诚实委员对同一个合法修复批提供完整有效分片份额。
2. 第四名委员返回 HTTP 200、JSON `[]`。HTTP 收集器将解码成功的空行计入返回集合。
3. `CompleteBatchParts` 对全部行逐一检查长度，任何一行长度不匹配就直接拒绝整批；没有先保留能够组成有效门限的响应。
4. 因而三个有效响应也无法完成合成。调度降级为单项批后仍调用同一函数，不能解决这个故障。

另一条复现是将第一名委员的响应重复作为第四行：`Combine` 在尝试四选三之前，因为重复 Index 拒绝整个集合。当前收集器没有把响应的份额编号绑定到发出请求的固定委员位置，也没有暴露并核对 Contribution 的编号。这部分问题继承自既有份额处理，本次批路径继续受影响。

复用真实 40+60 CAL、门限 RSA、已存在后继付款的 fixture，通过 Go overlay 注入第四行，观察到：

| 输入 | 实际结果 | 应有行为 |
| --- | --- | --- |
| 三个正常响应 | 成功 | 成功 |
| 三个正常响应＋一个空行 | `invalid authorization` | 忽略不合格响应，使用三个有效委员 |
| 三个正常响应＋重放第一行 | `invalid chameleon commitment or contribution` | 不让第四个异常响应破坏已有合法门限 |

**影响是可用性，不是已经证明发生盗款或重复赔付。** 拒绝仍然保守地保住了账务，但一个拜占庭委员可以持续阻断自动赔付取证；这与系统希望提供的四委员、一故障修复能力不一致。单纯增加重试、延长租期或缩小批量没有作用。

最小修正方向：收集时保留响应来源，过滤空行、错误长度、错误编号与不合格结构；按照固定委员身份处理重复项，不能让先到的冒名项占掉诚实份额。组合层有界枚举最多四行中的三行候选，坏形状、重复身份或密码验证失败只淘汰相关候选；一个候选对全部目标分片都合成验证成功后才接受。可保留底层 Combine 对传入三份候选的严格检查，无需放宽密码学接受条件。输入份额、旧单项分片和新批分片三条路径应统一覆盖，无需新增密码学协议或改变门限。

相关效率问题是当前收集器等待四个 HTTP 请求全部结束，即使已有可合成的三个有效响应，也可能等到第四个请求的两秒超时。可在同一个修正中做到“获得可验证的有效门限后返回”，但不能把任意三个 HTTP 200 当成有效门限。

### R2 · 中优先级：设计中的构造前经济预执行缺失

位置：`cmd/committee/repair_batch_runtime.go:243–312`、`internal/redaction/batch.go:66–105`；对应设计 §2.3。

设计明确要求在临时 Overlay 上依次模拟共享备付、费用与义务关闭，剔除当前已知无法支付的项目。实际构造路径仅做 `InputTarget → 输入适配 → BuildBatch → 分片份额 → CompleteBatchParts`。`EvaluateDirectCompensation` 只出现在最终公共 `ExecuteBatch` 中。

复现：将两个缺口 40+60 CAL 的备付余额设为 99 CAL，`BuildBatch` 仍成功，委员 `BatchPartShares` 也能产生份额。已有原子失败测试确认，这样的批在公共执行时才被拒绝且不产生部分扣款。99 CAL 是本轮人为设置的边界状态，不能据此声称正常合法流程会自然造成欠备付，或已经否定系统的资金覆盖推导。

**影响是无效取证、无效公共提交及可行项目的额外等待。** 批中一个资金不足的项目可以让其他本可执行的项目一同失败。已有有限租期、转单项与重试能缓解后续进度，因此不能据此声称永久死锁；但它们没有替代设计承诺的构造前筛选。

最小修正方向：构造端按最终规范顺序，在同一临时 Overlay 中模拟赔付，成功项累计模拟变化，失败项不泄漏变化并保留待办；再只对选定项取证。公共执行仍完整重查，因为预检之后资金、父来源或 Base 可能变化。不要将预检结果变成新的永久授权或真实提前扣款。

提供分片份额的服务也应在昂贵适配前，对收到的固定批进行同样的整批经济试算；任一项失败就拒绝该请求，不能自行删项后返回另一正文的份额。否则外部请求仍能绕过构造者筛选。试算后的“已关闭”状态只用于累计经济检查，不能替代 InputTarget 所需的真实未关闭资格快照。

## 2. 已核对的核心边界

| 设计要求 | 代码核对与现有证据 |
| --- | --- |
| 批内逐项赔付，但原子提交 | `ExecuteBatch` 用自己的 Overlay 顺序执行共享账户与费用；任一项失败返回空 Transition。已有中途余额不足测试通过。 |
| 完整批命令被共识身份绑定 | `BatchID` 使用全部规范编码；修复批不套用普通付款忽略可变 Funding 的稳定身份路径。修改 proof 字节改变命令身份。 |
| 修复只改被授权的来源槽 | 从 Canonical 原文重建，仅设置确定的 ReserveFunding、DebitIdentity 和 Opening；同交易多输入累计修改，未指定字段保持。 |
| 相同义务不能重复赔付 | 批精确重投先查成功 Task；换批与旧单项入口共享 DirectObligation 终态。双入口交错测试通过。 |
| 完整 BlockID 保持 | 执行与安装均检查块 Hash 与 PartSetHeader，而非仅比较块头哈希。 |
| 逻辑授权先于物理安装 | PrepareMaterialization 复制已提交材料；runtime 释放应用视图后 Install，不持块修订锁回调应用存储。 |
| 直达不会跳过其他块任务 | 处理 A1 时可安装 A2，但全局游标只逐个推进；A1/B1/A2 测试实际两次安装，B 不遗漏。 |
| 旧快照不回退新版本 | 统一安装入口核对目标材料与版本；旧已授权版本遇更高已安装版本时不回退。依赖本地版本只由该入口维护。 |
| 安装不再次发钱 | 安装器只写块分片、版本与原始备份，不调用赔付规则；原始命令序列重放的各高度 AppHash 测试通过。 |
| 跟块不会把修复批当普通付款 | 成员按认证 RepairEffects 更新实际占用；钱包处理真实费用输出，网关显式跳过修复批。重复块与 32 项结果跟块测试通过。 |
| 调度状态有界 | 16 个待确认高度、256 项缓存与失败提示、有限租期。缓存命中仍检查当前资格和承诺。 |

本轮在这些已检查路径中未复现重复扣款、后继授权被改动或物化重放产生第二次经济效果。该结论是代码审查与有限测试结论，不是完整实现的机械化安全证明。


上述测试均通过。新增 R1 故障断言失败；R2 的特征测试确认缺少预执行。复现脚本见 [review-reproduce.py](../experiments/authorized-repair-2026-09-29/review-reproduce.py)，从仓库根目录执行即可；使用 Go overlay，不改现有源码，也不会把预期失败断言混入普通 CI。脚本针对所审查版本，未来修复后应改成正式回归。

尚缺的验证应与已证实缺陷区分：

- 三好一坏应答的 HTTP 收集到自动修复全链路测试，含空行、错误编号、错误数值和慢第四节点。本轮对真实密码合成入口完成了故障复现，未启动恶意 HTTP 节点网络。
- 同块跨多个真实分片的合法合批与直达；目前成本 fixture 的改动落在一个分片。
- 协议上限 32 项的完整取证、经济执行、物化闭环。已有 32 项测试覆盖的是认证结果跟块，不能等同完整闭环。
- 持续混合正常付款与修复的同配置性能对照。此前先修复再发送 1,000 笔正常交易，证明兼容贯通，不能单独证明异常负载下尾延迟不受影响。

本轮未重新运行 Mac 吞吐实验；没有新增 TPS 或正常付款延迟结论。

## 4. 建议收敛顺序

1. 先修 R1 的坏响应隔离与身份处理，保留两个已复现失败场景为正式回归。
2. 补 R2 的构造端共享 Overlay 预执行；测一项无法赔付时另一可行项仍能进入候选，且公共执行仍原子重查。
3. 补一个跨分片闭环与一次三好一坏自动修复回归，再合并功能分支。

无需重新设计 TXCer、添加正常支付轮次、降低门限或扩展数据库恢复。第三项机制的主体可以保留；需要修正的是实现中的异常响应处理和未落实的预执行步骤。

## 5. 侧边栏独立复核

已向指定的 [GPT 对话](https://chatgpt.com/c/6aa8b2d7-b6f8-83ec-8e23-ea9f3b634e90)提供源码路径、版本与上述实际复现结果。GPT 返回的判断与本报告一致：R1 是“三份诚实贡献可得却无法选出有效门限”的活性缺陷，R2 是设计与实现差距及无效工作放大；这些证据没有显示账务原子性或至多一次赔付失效。

采纳其两项补充：有效子集选择应覆盖输入、旧单项分片和新批分片；经济预检应同时覆盖构造者筛选及份额服务对固定批的整体检查。明确保留“三个可解码响应不等于三个有效份额”和“99 CAL 人工状态不证明正常资金覆盖破坏”两条边界。GPT 的意见用于交叉审查；本报告的复现测试由本地实际执行，不能用对话认可替代测试或证明。
