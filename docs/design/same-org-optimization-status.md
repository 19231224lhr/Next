# 同组织转账优化：后续工作的固定入口

截至 2026-10-12，开发分支：`fix/partial-approval-reclamation`。本文件总结实现状态，后续开发、实验和论文引用先读这里，再读原始报告。

## 已实现

- 网关将完整证书直接投递给收款钱包；持久队列负责离线重试和幂等投递。慢收款人不会阻塞其他收款人的整批消息。
- 独立、显式启用的组内资金池：先公开锁入资金，三名成员认证组内持有人变更，退出时公开生成普通输出。当前为不可拆分单元、固定组织，不包含池内 FUEL 收费；不是直接删掉普通付款的担保预留。
- 池内正常路径不再预先发四个恢复查询；精确复用成员已持久验证的完整父凭证。
- 成员保存完整凭证与收款钱包保存收据并行。两名不同成员确认且钱包保存完成后，诚实钱包才允许续付/退出；重启重新确认。剩余慢 RPC 会取消。
- 可选收款端 Collector：收款端直接收集三名成员签票，保留完整付款材料与公开提交队列。已接入 gateway 开关及持久钱包；收款/续付预约有接口，尚无钱包 UI 或自动路由发现。

## 已有证据，后续不要混用口径

| 结论 | 对照和范围 |
|---|---|
| 池内单笔 p50 7.6076 → 6.7334 ms，降低 11.49%；p95 降低 9.00% | 本轮旧池实现 vs 最终池实现，5 轮各 200 笔，取各轮统计量的中位数；同步 Bolt、真实成员 HTTP、本机实验 |
| 主要速度收益来自并行保存 | 仅减少查询/验签的 p50 为 7.5764 ms，提升有限；同一最终实现串行保存为 7.7368 ms |
| 收款端收票本地基本无稳定提速 | 11.9759 → 11.9600 ms；不能宣传普遍提速 |
| 收款端收票可避开原交付环节等待 | 仅在网关→收款端额外注入 20 ms 时，34.4194 → 11.3522 ms；约 67% 是受控拓扑结果，不是同组专属或真实 WAN 成绩 |
| 队列阻塞已消除 | 一钱包卡住，另 7 条约 3.95 ms 完成；旧版 1 秒截止时只完成 2 条，属于故障场景回归 |
| 资金池复用保障资金 | 前轮 100 CAL 连续组内转手 100 次，托管仍为 100 CAL；普通未结算证书链各成员本地预留计数为 10,000 CAL，不能把四个计数相加当全局资金 |

上述毫秒结果不包含真实验证者网络的公开确认延迟，不证明池比普通 Direct 更快。之前 12.8788 ms 等旧测量属于不同实验轮次，不能混入本轮百分比。池内资金利用率改善与通用通信路径优化分别归因。
