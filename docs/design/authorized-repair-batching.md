# 完整共识身份保持的授权历史修复：合并修复设计

> 2026-09-29 · 核心实现与回归已完成，位于 `feat/authorized-repair-batching`（从 `re@0f7be69` 分出）。[验证报告](../experiments/authorized-repair-2026-09-29/README.md)区分局部成本与 Mac 网络回归；既有 E1–E8 数据仍对应原版本。本文补充[现行系统模型](system.md)的授权修复机制。

## 1. 目标与选择

每项到期直接义务仍独立核验、实际扣款并至多关闭一次；将多个修复涉及的历史正文构造、分片适配和中间物理写入合并，保持既有授权、完整共识身份和后继引用。正常 TXCer 取证与续花不增加协议往返。

采用两项配合的机制：**有界同块修复批**与**已提交版本直达物化**。输入级适配复用作为局部优化。仅做缓存无法减少所有重复正文构造；先扣款、以后再生成合法修订证明则改变当前原子性，留作其他研究，不纳入本版。

不增加角色、共识选主、修复代币、钱包修复查询或祖先证据链。批量目标是集中异常时的后台效率，不预设正常无异常 TPS 必然提高。

## 2. 合并修复协议

### 2.1 三层状态

| 层 | 保存内容 | 允许的变化 |
| --- | --- | --- |
| 公共经济状态 | 直接义务、备付账户、费用、逐义务修复记录 | 按共识顺序执行；成功修复至多扣款一次 |
| 已提交逻辑表示 | 历史高度、修订号、确切正文及分片材料 | 一项成功批产生一个修订版本，与经济变化同时提交 |
| 本地物理表示 | 实际块分片、已安装版本、原始块备份 | 可延迟安装或直接安装已授权新版本；不执行经济效果 |

Canonical 从已提交逻辑状态取得正文，不从节点碰巧写到哪个物理版本推断授权。修复命令记录在新区块中；旧块 Header/AppHash 不被改成新的执行状态。原始公共命令序列保留用于重放。

### 2.2 命令与身份

新增带独立编码标识的 `RepairBatch`。以下是语义字段，具体编码沿用项目规范：

```text
RepairBatch {
  Network, Height, Base, Previous, Next
  Items[] { Output, TransactionIndex, InputIndex, NewOpening }
  Parts[]
}
```

`Height` 指目标历史块；`Base` 是其当前逻辑修订号，`Previous/Next` 是修改前后正文摘要。Items 按交易序号、输入序号、OutputID 规范排序；重复义务或重复输入槽均拒绝。禁止空批、版本溢出及目标高度不早于当前执行高度。

新来源不是提交者自由指定：仅允许将指定 OriginalFunding 改为 `ReserveFunding + ReserveDebitIdentity(Network, Output)`，Opening 必须通过当前输入承诺验证。金额、组织、证书事实和费用从已提交义务及对应付款读取，不信任命令自行声明。批内同一交易多个输入在同一个副本中累计替换；未指定字段必须保持，交易编码长度、块身份及分片承诺检查继续保留。

防重分两级：批身份使用带域分离的完整规范命令摘要，识别精确重投；每项继续使用 `RepairIdentity(Network, Output)`，限制经济效果。精确成功批重投返回未新增效果；换签名材料、换批或换顺序不能绕过已关闭义务。不能将“旧义务已完成”当成允许任意新批整体成功的依据。

BatchID 不编码在自身哈希输入中。RepairBatch 的全部规范命令字节，包括输入和分片证明，都必须进入公共共识认证；不得套用普通可修订付款中忽略可变 Funding 的身份计算。先查精确成功批，再检查 Base，使早已成功的原命令在后续修订之后仍可返回幂等结果。逐项既有修复记录可增加所属 BatchID，仅用于定位，不另建一套经济防重状态。

现有单项 RepairInput 入口保留。其编码与历史记录不重解释；新旧命令共享逐义务终态和扣款防重规则。新任务采用独立编码/键空间，并由兼容读取器统一取得逻辑修订材料，不能把现有单项 Task 直接反序列化成批 Task。

### 2.3 构造与取证

构造者从已有到期队列公平分页选取就绪义务，按目标历史高度分组。调度默认最多 8 项一批，初版协议上限 32 项，并同时受现有命令字节限制约束；这是实验起点，不是最优参数结论。协议上限固定为所有节点一致的规则，本地调度可选择更小批次。

界限同时覆盖请求、Items/Parts 解码长度和执行结果、FeeOutputs 的编码大小；越界整批拒绝，不能截断结果或在部分写入后报错。沿用现有对象界限，并为新批对象显式校验，不能只在 HTTP 接收层限长。

不等待凑批，只有一项就立即处理。逐项预检剔除已关闭或不再可修复的记录；共享账户和费用在一个临时 Overlay 上依次预执行，避免构造已知无法支付的批。余额不足的义务保持待办并有限退避，不阻挡其他组织的可行修复。最终公共执行仍必须重检。

多次失败的候选拆成单项重新检查后再参与调度，避免一个不合格项目长期拖住其他项；拆批要重新生成对应的完整候选及分片证明。租期届满不撤销仍在网络中的旧命令，旧新候选并存时由公共 Base 与义务终态排除重复效果。

取证分为两层：

1. 每个输入取得 OriginalFunding 到确定 ReserveFunding 的有效适配结果。
2. 在同一 Canonical 基础上组合所有输入，生成唯一候选正文；仅对变化分片取得最终正文对应的门限适配。

不组合各自基于旧正文生成的整块证明。输入适配缓存只保存通过验证的密码结果，以网络、固定交易核心、输入序号、KeyID、旧新来源、原承诺及旧 Opening 的完整元组为键，限制容量，淘汰只影响性能。缓存不保存永久赔付资格；每次仍检查当前输入及义务。

已有合法修订的非目标槽必须保留，只要求本批目标槽仍为 OriginalFunding；不能对整笔交易重新要求所有 Funding 都是原始来源。

同一节点对同一历史高度至多构造一个在途候选，减少自己制造的 Base 冲突。这只是本地调度，不是分布式锁。保留现有有限错开备用提交，不增加选主。收到 HTTP 接收成功不代表上链；原始命令字节在重试中保持不变，只有看到已验证公共成功结果才确认完成。公共 Base 或义务发生变化时，旧候选失效，过滤后重建并重新取得块级材料。

在途状态必须有有限租期和请求超时，失败不能无限占住高度；超时先检查已提交状态，仍合法则补投，已失效则重建。接收成功不延长租期，公共明确拒绝立即释放在途项；租期届满后重新参与公平调度，不永久持有 worker。内存状态丢失可从公共待办重新开始。所有任务与缓存有界，不为每项义务启动永久 goroutine。空闲停块时沿用现有公共时间推进规则，委员会以确定的公共执行时间判断到期，本地时钟不授权扣款。

### 2.4 原子执行

```text
检查精确批重投
校验编码、界限、规范顺序和唯一性
读取同一状态中的 Canonical、Base 和当前义务
构造确切候选正文，校验输入 Opening、Next、完整 BlockID
创建独立 Overlay
按 Items 顺序：重检 Open/到期/责任，执行既有逐项赔付与费用规则
写入逐义务修复索引、一个 Revision、一个 Task 和队列项
统一提交 Overlay 和确定执行结果
```

任何一项失败，整批无经济或逻辑修订效果。不能跳过失效项目，却继续使用原批候选正文与 Parts。遇到父来源先到、同块其他修复先提交等情况，返回确定失败，由构造者重建。

多个项目可能共用备付账户或同一付款的费用托管。第 i 项必须看到前面项目的修改，不能分别从旧余额计算后覆盖。使用既有实际 RepairCost 与结费规则，不增加独立批费用，不因合批取消必要费用，也不把已赔付本金恢复成未损失资金。

经济扣款、义务关闭、合法新正文与物化任务必须在同一个应用状态事务内成立。实际历史文件写入在其后；文件安装失败不重复扣款，只保留重试任务。

### 2.5 跟块与结果

当前成员 `applyRepair` 从单项命令的付款正文取得证书事实与金额。紧凑批命令没有这份正文，因此必须补齐公共结果接口，不能只新增执行器。

设计采用版本化 `RepairBatchResult`：记录 Applied、BatchID、与 Items 对齐的逐项有效赔付摘要，以及顶层规范排序的 FeeOutputs。逐项摘要包含 OutputID、原发行证书 SpendFactID、ConsumerFact、ConsumerTx、Input、金额和 DebitID；全部由委员会从实际执行状态导出，处于现有已验证公共执行结果的认证范围内，不是委员会额外逐笔通知。退款仍绑定原付费交易和既有输出索引，只处理一次，不按批身份重新创建退款币。

成员验证结果中的 BatchID、项目数量与身份和命令一致，再按每项结果推进自己曾签署的责任进度及本地等待项，复用 `finishLocal/resolveLocal` 的现有净损失和费用语义。不能对未占用权限的成员凭空返额度。Applied=false 的精确重投不再产生 RepairEffects 或费用输出。跟块游标与本地修改继续原子提交，确保重复读块不重复计算。

钱包识别批结果中的真实费用输出，同时跳过将 RepairBatch 误解析为普通付款；修订历史表示不能再次给收款人增加原本金。执行结果必须为整批完整有效后才可见；失败批不泄漏已模拟前缀的事件。

预检、执行、结果编码、公共结果认证、成员/钱包跟块、重放器和测试工具共同升级。本版用于一致升级后的实验网络，不设计混合旧新二进制在线滚动升级。

## 3. 安装与一致性

### 3.1 已提交版本直达

新增 `InstallCommittedRevision` 语义接口，不直接放宽现有 ReviseBlock 的 Base 比较。上层从同一已认证应用 ReadView 复制目标高度、修订号 r、正文、对应 Task 身份、提交高度及分片材料，释放 ReadView；下层随后取得块修订锁，重新检查本地版本并安装。不持物理修订锁回调应用 Store，不把释放后的视图引用交给异步安装器。

| 本地物理版本 p | 行为 |
| --- | --- |
| p < r | 校验正文、承诺与原完整 BlockID 后安装 r |
| p = r | 正文及所需分片材料精确一致则幂等；不一致为冲突 |
| p > r | 基于本地版本只经验证安装入口推进的不变量，旧任务视为已覆盖，不回退 |

第一次物化保留真正的原始块；新分片与本地版本元数据同一存储批提交。应用授权先提交、物化后执行，不增加跨数据库事务。读快照后逻辑版本又前进，不使旧的已授权版本自动非法；允许完成已选版本，随后追赶，避免追逐最新版本而永远不安装。

上述覆盖判断依赖统一安装入口与本地版本元数据的原子维护，不接受外部未经验证的版本标记。其他工作器刚安装了更新的合法版本时，不应仅因当前请求持旧快照而判其非法。存储损坏或绕过入口的任意文件篡改不在这条并发覆盖规则的前提内。

处理全局队列 `[A1, B1, A2]` 时，可在处理 A1 时安装当前已提交 A2，但只推进已处理的连续队列前缀；随后仍处理 B1，再将 A2 认定为已覆盖。不能跳游标漏掉其他块。版本“最新”只相对于节点已验证的公共高度，不相信远端自报的新版本。

直达只省去中间物化写入，所有赔付命令、账务事件和原始重放材料仍保留。本版不裁剪历史，也不承诺缩减所有 Revision/Task 的逻辑存储量。

### 3.2 分析命题

证明沿用现有信任、签名、门限承诺及 BFT 假设，不因批处理扩大故障容忍范围。

1. **逐义务至多一次偿付。** 批重投、换批及新旧命令交错不能再次扣同一项责任。
2. **受限补丁组合。** 不相交输入槽只改变获授权的 Funding；同一交易多槽组合保留其他字段及固定授权。
3. **批边界账务等价。** 相同初始状态、时间和项目顺序，且无父到达等外部事件插入时，成功批的经济投影等于合法逐项赔付。不是声称 AppHash、Revision 数或原始库字节相同。
4. **完整共识身份保持。** 新正文继续满足原 BlockID.Hash 和 PartSetHeader，既有共识认证不因物化重新收集。
5. **物化时序独立。** 同一公共命令序列下，合法安装时序不改变经济投影；不得遗漏跨块任务或回退表示。
6. **后继保持。** 修复不要求后继用户重签，不再次执行已成立后继的本金效果；正常审计重放不受禁止。

原子拒绝便于安全分析，但不保证任意竞争下无等待。进度仍依赖充分资金、材料可得、足够签署者、公平调度及公共执行持续推进。单节点同高度在途限制不消除不同节点之间的竞争。

论证顺序固定为：先证明单项经济转移与受限来源补丁，再对批内项目数归纳，最后加入物化步骤。令 E_i 为既有第 i 项赔付转移、π 为账户/义务/费用的经济投影，则成功批要求 `π(Batch(S)) = π(E_k(...E_2(E_1(S))...))`。失败批在边界处保持 S 不变。物化只改变独立物理状态 M，因此在同一公共命令序列下插入合法安装步骤不改变 π；这一结论依赖业务读取 Canonical 而非 M。该式不适用于不同公共时间、不同项目顺序或中间插入父来源到达的比较。

## 4. 验证与论文定位

### 4.1 实现与验收顺序

| 步骤 | 范围 | 完成条件 |
| --- | --- | --- |
| A | 提取现有逻辑修订读取接口；直达物化及输入适配复用 | 不改经济命令即可证明物化与复用边界 |
| B | Batch codec、组合正文、逐项 Overlay、结果及全部跟块入口 | 批执行与逐项经济结果一致，重复与失败路径无额外效果 |
| C | 接入有界批调度、备用补投及小型成本对照 | 实际减少重复工作，单项不等凑批，无跨块饥饿 |

关键功能轨迹：40+60 两个缺失来源合成 C，C 再产生后继 G；对比逐项、合批及延迟后直达。覆盖同交易多输入、同块不同交易、共享账户和费用托管、父先到、中途余额不足、重复批和换批、Base 竞争、A1/B1/A2 队列及节点不同物化顺序。核对 CAL、FUEL、义务、成员净占用、费用输出、固定授权、OutputID、完整 BlockID 和原始序列重放。

小型成本实验比较 k=1/2/4/8，分别布置同分片、同块不同分片和不同块缺口，记录输入适配次数、分片适配次数、重建/拒绝次数、提交字节、写入字节、修复排空及正常快付 P95/P99。使用相同义务和到达序列；逐项基线与新机制保留同样经济检查及存储模式。不同块与 k=1 是负对照，不只选择有利负载。

收益条件是实际工作减少且正确性轨迹通过。缺口很零散或资格变化频繁时，合批可能没有收益；保留单项路径，不强行扩大批量。参数与观察结果一并报告，不将模拟集中赔付解释为真实故障发生率。

### 4.2 论文定位

建议贡献标题仍为 **完整共识身份保持的授权历史修复机制**，内部深化为“逐义务授权下的可合并来源修复”。[RedactChain §VI-B](https://www.comsys.rwth-aachen.de/fileadmin/papers/2022/2022-matzutt-redactchain.pdf)已讨论同块编辑冲突与重做，[CDEdit 作者稿](https://arxiv.org/html/2205.07054)已研究编辑权限及多次编辑成本；不主张首次批量编辑、缓存或跳过中间写入。

本设计的研究对象是：**在每项担保义务仍独立实际偿付的条件下，将确定的来源补丁组合成保持完整 BFT 身份的授权修订，并允许节点以不同物化时序完成安装，而不改变账务或既有后继付款。** 安全命题和实现收益共同支撑这一贡献，不能用方案名称代替论证。

本轮与侧边栏 GPT 的详细评审后，定稿保留以上机制，并补齐了四个契约：跨单项/批入口防重、本地在途候选退出、应用快照与物理锁顺序、逐项认证结果。不纳入 RepairDecision、槽级公共版本或新的协调共识。


## 5. 已实现接口与本轮范围

- `protocol/repair_batch.go`：`RepairBatch`、全字节 `BatchID`、逐项 `RepairEffect` 和独立 `RepairBatchResult`。协议至多 32 项；顶层费用输出不经过旧单付款结果的总数量限制。
- `internal/redaction/batch.go`：同一逻辑正文累计补丁、独立门限分片验证、逐项 Overlay 赔付、一次逻辑修订。批任务键 114、逐义务索引键 115；原有义务键及赔付规则不变。
- `internal/redaction/repair.go` 与 Comet `store/redaction.go`：复制已提交授权快照，释放应用视图后安装绝对版本；顺序 `ReviseBlock` 保留。版本材料缺失时拒绝安装，不凭本地高版本自创授权。
